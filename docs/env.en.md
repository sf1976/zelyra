# Zelyra: `.env` and configuration

This is the central reference for environment-dependent settings and optional
project switches. Update it whenever a Zelyra setting is added or changed.

## Core rule

The simple path requires no extra configuration.

- `zelyra.toml` contains durable project decisions.
- `.env` contains local, environment-specific values and secrets.
- The process environment can override values for one invocation.
- `.env` must never be committed.

For the supported optional feature switches, precedence is:

```text
process environment → .env → zelyra.toml → safe defaults
```

Secrets are never printed by `zelyra config`.

## Feature switches

Feature switches are optional. Without `[features]`, the currently supported
surfaces remain enabled so existing projects keep working unchanged.

```toml
[features]
web = true
api = true
crud = true
auth = true
audit = true
```

| Switch | `.env` / process variable | Default | Meaning |
|---|---|---:|---|
| `web` | `ZELYRA_FEATURE_WEB` | `true` | pages, forms, and web resources |
| `api` | `ZELYRA_FEATURE_API` | `true` | `api` declarations and API surface |
| `crud` | `ZELYRA_FEATURE_CRUD` | `true` | `crud` declarations and generated CRUD surface |
| `auth` | `ZELYRA_FEATURE_AUTH` | `true` | `auth` declarations and authentication surface |
| `audit` | `ZELYRA_FEATURE_AUDIT` | `true` | audit configuration within authentication |

Example local profile:

```dotenv
ZELYRA_FEATURE_API=false
ZELYRA_FEATURE_CRUD=false
```

If source uses a disabled surface, the compiler reports `E-FEATURE-001`.
Feature switches can never disable type checking, SQL checking, capabilities,
contracts, CSRF protection, or other security rules.

Inspect effective configuration without displaying secrets:

```bash
zelyra config main.zyl
zelyra config main.zyl --format=json
```

The JSON output contains only switches, their source, and the statement that
secrets are not displayed.

## Generated MariaDB/Docker projects

`zelyra new --mariadb`, `zelyra init --mariadb`, and MariaDB templates create
`.env.example` and immediately create a protected local `.env` with randomly
generated passwords. `zelyra setup` remains available as an idempotent recovery
command for existing MariaDB projects.

The generated `.env` activates only the values required by Compose and local
database commands. The selected MariaDB host port stays active so
`ZELYRA_DATABASE_MAIN_URL` and Compose use the same port. Web port overrides, feature switches, authentication, and other
options are described extensively as commented lines. `.env.example` has the
same structure, but its `change-me` placeholders and active secret fields are
only a template.

| Variable | Generated default | Use |
|---|---:|---|
| `ZELYRA_WEB_PORT` | `3000` | internal web-server port in the container |
| `ZELYRA_HOST_PORT` | `3000` | web port published on the local host |
| `ZELYRA_DB_HOST_PORT` | `3306` | MariaDB port published on the local host |
| `ZELYRA_DATABASE_MAIN_URL` | project-specific | preferred connection for the `database main` declaration; may contain a secret |
| `DATABASE_URL` | project-specific | backwards-compatible connection fallback; may contain a secret |
| `MARIADB_DATABASE` | `zelyra_app` | Compose database name |
| `MARIADB_USER` | `zelyra` | Compose application user |
| `MARIADB_PASSWORD` | generated by `zelyra new`/`init` or `setup` | Compose application password |
| `MARIADB_ROOT_PASSWORD` | generated by `zelyra new`/`init` or `setup` | MariaDB root password |

## UI language and learning level

| Variable | Values | New MariaDB `.env` default | `serve` fallback | Security / effect |
|---|---|---:|---:|---|
| `ZELYRA_LANGUAGE` | `de`, `en` | `de` | `en` | Not a secret; selects the UI locale |
| `ZELYRA_LEVEL` | `learn`, `work` | `learn` | `work` | Not a secret or permission; `learn` shows the learning guide and `work` hides it |

For `zelyra serve`, precedence is the process environment, then the project's
`.env`, then the serve fallback. The server automatically reads only these two UI settings from
`.env`; other values such as `DATABASE_URL` must still be explicitly exported
or injected by Compose. Values must be exactly `de`/`en` and `learn`/`work`.
Invalid values produce a configuration error instead of being silently ignored.

Affected commands and runtime surfaces: `zelyra serve`, the MariaDB project
scaffolds `new`/`init`, and the generated Compose web service. Regression tests
cover process-environment → `.env` → fallback precedence in the CLI, accepted
values and catalog references in `web/src/i18n.rs`, and generated defaults and
Compose forwarding in `cli/tests/machine_interfaces.rs`. Project catalogs are
also checked for UTF-8, valid JSON, size limits, and symbolic links; a CLI
integration test verifies marker resolution and safe error output.

New MariaDB projects activate `ZELYRA_LANGUAGE=de` and
`ZELYRA_LEVEL=learn`; edit `.env` to change them. The Compose template passes
both variables to the web service. Zelyra's shipped locale catalogs are
`web/locales/de.json` and `web/locales/en.json`. They contain Zelyra-provided
UI copy, including CRUD, form, authentication, error, and learning-guide text.
Example views refer to entries using `data-zelyra-i18n="app.home_title"`;
configurable Zelyra text can use `@i18n:app.home_title`. Missing German entries
fall back to English. A key missing from both catalogs renders as
`[missing translation]` to expose the incomplete catalog entry.

`zelyra new` and `zelyra init` also create optional project catalogs at
`locales/de.json` and `locales/en.json`; the generated Dockerfile copies this
directory into the runtime image. Add project UI keys or override text
referenced by a view using `data-zelyra-i18n="custom.key"` or by a Zelyra text
setting using `@i18n:custom.key`. The same catalogs add or override every
catalog-backed generated label in the shell, CRUD, forms, tableviews, login,
authentication administration, validation, and learning guide. Generated
field identifiers use `identifier.<field>` keys; parameterized copy can use
`{field}` and `{max}`. German lookup order is project German → project English
→ built-in German → its English fallback. These files are optional UTF-8 JSON
objects containing nonempty strings, limited to 256 KiB each. `zelyra serve`
rejects invalid catalogs, symbolic links, and other file types with
`E-I18N-001`. Catalog text is HTML-escaped when inserted. It is presentation
content, not authorization or business-rule configuration; never put
credentials or other secrets in a catalog.

Catalogs do not translate business records or arbitrary HTML text from a
project. Machine API/JSON contracts and compiler diagnostics remain language
neutral or in their defined technical language; the UI locale does not change
them.

## Application email in 0.9.5

The Zelyra email API uses the same SMTP variables as password recovery. Set
`[capabilities].email = true` as well, and add the exact SMTP host to
`[network].allowed_hosts`. The 0.9.5 mail outbox supports MariaDB and must be
created explicitly with `zelyra outbox setup main.zyl`.

| Variable | Default | Use and security classification |
|---|---:|---|
| `ZELYRA_SMTP_HOST` | none | Required SMTP host for delivery. |
| `ZELYRA_SMTP_PORT` | `465` / `587` / `25` | Port for `implicit_tls` / `starttls` / `local_plaintext`; plaintext is limited to loopback without authentication. |
| `ZELYRA_SMTP_SECURITY` | `implicit_tls` | `implicit_tls`, `starttls`, or `local_plaintext`; TLS failure never falls back to plaintext. |
| `ZELYRA_SMTP_FROM` | none | Required sender address. |
| `ZELYRA_SMTP_USERNAME` | none | Optional SMTP user; must be set together with the password. Secret. |
| `ZELYRA_SMTP_PASSWORD` | none | SMTP password. Secret; never print or commit it. |
| `ZELYRA_SMTP_CA_CERT` | none | Optional PEM root certificate, relative to the project or absolute; regular non-symlink file up to 128 KiB. Public trust material; hostname checks remain enabled. |

Set up the table and explicitly run a delivery worker:

```sh
zelyra outbox setup main.zyl
zelyra outbox run main.zyl --handler zelyra.mail.send=deliver_mail --once
```

`mail_queue` writes the message to the outbox inside a database transaction.
The worker later sends it over SMTP. Delivery is at least once and may produce
duplicates. Configuration and a complete example are in
[`mail.en.md`](mail.en.md).

## Password recovery

An auth declaration with `reset_tokens: password_resets` must also set
`reset_rate_limits: password_reset_limits`. The reset table needs `user_id`, a
unique `token_hash`, `expires_at`, `consumed_at`,
`delivery_payload: String(2048)`, nullable `delivery_retry_at: Timestamp`, and
a foreign key to `users.id`; an auth audit table is also required. The separate
rate-limit table needs `bucket_key: String(64) primary`,
`window_started: Timestamp required`, `request_count: Int required`, `blocked_until: Timestamp?`,
and an index on `window_started`. See the complete
[`examples/password_reset.zyl`](../examples/password_reset.zyl) project.

Limits are keyed by TCP peer IP and shared by instances using the same MariaDB
and identical quota settings and delivery key. Database errors reject reset attempts.
The operator log records the sanitized `E-AUTH-043` diagnostic; public responses
remain generic. The table stores no IP
address: `bucket_key` is an HMAC fingerprint made with the delivery key.
The table admits at most 4,096 entries and rejects new clients when full. A
MariaDB advisory lock coordinates capacity and counters across instances,
waiting for at most one second. Each subsequent request removes at most 100
expired entries whose window started more than 48 hours ago. No automatic
cleanup runs without further requests. Forwarded-IP headers are ignored, so
clients behind one proxy share its limit. This protects
the application's reset endpoints; it is not a network-level defense against
distributed denial-of-service attacks. Password recovery currently requires
MariaDB.

`reset_rate_limits` has no default or environment override; the auth
declaration is authoritative. Its table holds security state. `check` and
`serve` validate its schema, while `db setup` creates declared tables. Existing
reset projects must add the auth option and table and apply a reviewed additive
schema plan. Diagnostics `E-AUTH-039` through `E-AUTH-042` identify missing,
incompatible, or orphaned configuration. Parser, schema, module-permission,
restart tests, and `tests/password-reset-rate-limit-e2e.sh` cover this contract.
Password login without recovery does not require this table.

| Variable | Default | Use and security classification |
|---|---:|---|
| `ZELYRA_PUBLIC_BASE_URL` | none | Public HTTPS origin for email links; HTTP is allowed only for loopback. Not a secret. |
| `ZELYRA_SMTP_HOST` | none | SMTP relay hostname; required when `reset_tokens` is enabled. |
| `ZELYRA_SMTP_PORT` | `465` / `587` / `25` | Port for `implicit_tls` / `starttls` / `local_plaintext`; the last mode permits plaintext only on loopback without authentication. |
| `ZELYRA_SMTP_SECURITY` | `implicit_tls` | `implicit_tls`, `starttls`, or `local_plaintext`; TLS failure never falls back to plaintext. |
| `ZELYRA_SMTP_FROM` | none | Sender address for reset email. |
| `ZELYRA_SMTP_USERNAME` | none | Optional SMTP user; must be set together with the password. Secret. |
| `ZELYRA_SMTP_PASSWORD` | none | SMTP password. Secret; never print or commit it. |
| `ZELYRA_RESET_DELIVERY_KEY` | none | Stable 32-byte key as 64 hexadecimal characters for outbox encryption and HMAC fingerprints. It must match on all instances. Secret. |

For `zelyra serve`, process environment takes precedence over the project
`.env`. If the auth declaration includes `reset_tokens`, `serve` will not start
without complete SMTP configuration and the delivery key. Generate a key with
`python3 -c 'import secrets; print(secrets.token_hex(32))'` and keep it in the
secret store used by every app instance. `ZELYRA_PUBLIC_BASE_URL` must be an HTTPS origin or a loopback HTTP origin
without a path, query, or fragment. Reset
links contain 256 bits of randomness, expire after 15 minutes, and are moved
from the URL into an HttpOnly cookie after exchange. Only the token hash is
stored in the database; the email address and reset link are stored only in the
encrypted outbox payload. A successful password change consumes the token and
revokes the account's persistent and in-process sessions.

Delivery uses a database-backed outbox encrypted with
`ZELYRA_RESET_DELIVERY_KEY`; only the token hash and encrypted mail payload are
stored. A background worker retries pending messages after temporary SMTP
failures and process restarts, with a 30-second retry delay after a failed
attempt. Delivery is at least once: a crash after SMTP
accepts a message but before the database acknowledges it can produce a
duplicate email. Keep the key stable and backed up; losing it makes pending
messages unreadable. The HTTP request does not wait for SMTP responses. The E2E
deliberately delays the SMTP response and verifies that the generic response
returns before delivery finishes. Affected commands are `zelyra serve` and the
generated MariaDB Compose web service; tests cover key parsing/encryption and
restart recovery in `tests/password-reset-e2e.sh`.

This feature is experimental. SMTP availability, public TLS termination,
rate-limit persistence across restarts, and independent security review remain
operational or release gates. `tests/password-reset-e2e.sh` uses a local
loopback SMTP sink and MariaDB; it sends no external email.

## Web server host allowlist

| Variable | Values | New MariaDB `.env` default / fallback | Precedence | Security classification and effect | Affected commands and tests |
|---|---|---|---|---|---|
| `ZELYRA_ALLOWED_HOSTS` | Comma-separated ASCII hostnames or IP addresses (IDNs in punycode); no scheme, port, wildcard, or empty item | `localhost,127.0.0.1,[::1]` | Process environment → project `.env` → loopback fallback | Not a secret, but a security-sensitive allowlist against forged `Host` headers and DNS rebinding. Add only hosts actually used. | `zelyra serve`, MariaDB scaffolds `new`/`init`, generated Compose; CLI, web, and scaffold regression tests |

Every HTTP request containing `Host` must match an entry. Matching is
case-insensitive; a request port is parsed separately and is not compared to
the allowlist. Wildcards, URLs, ports, and invalid hostnames are rejected as
configuration values. An empty or invalid list prevents server startup with
`E-ENV-001`. Internationalized domain names must be entered as ASCII punycode.
If the app is reachable through a reverse proxy or on a LAN under
a custom hostname, configure that hostname explicitly. The proxy must preserve
the public `Host`, overwrite `X-Forwarded-Proto`, and prevent direct access to
the app port. This setting only extends the host allowlist; it does not disable
CSRF or origin checks.

Each accepted HTTP connection has a fixed
30-second deadline for reading the complete request and writing the response.
A timeout closes the connection; there is no configurable retry. During
request dispatch, MariaDB and the bounded PostgreSQL SQL runtime use the
smaller of their configured pool/statement timeout and the remaining request
deadline. The database cancels a statement that reaches that limit;
transactional batches roll back after an error. The synchronous handler then
unwinds. Disconnecting the client does not interrupt the handler. CPU-bound
or other blocking application code is not interrupted; a late response is
discarded, and that handler can occupy a worker until it returns. External TLS
proxies should also set their own deadlines and connection limits.

## Integrated UI stylesheet

`ZELYRA_UI_STYLESHEET` selects the locally served stylesheet for Zelyra UI.
The default is `zelyra`; `tabler` selects the locally bundled Tabler Core CSS;
a project-relative path such as `assets/tabler.css` is also accepted. Paths
must end in `.css`, contain UTF-8 text, and must not use symlinks, `.`/`..`
segments, or files larger than 512 KiB.

| Variable | Default | Precedence | Security classification and effect | Affected commands and checks |
|---|---|---|---|---|
| `ZELYRA_UI_STYLESHEET` | `zelyra` | Process environment → project `.env` → `zelyra` | Not a secret; selects the public CSS file (`zelyra`, `tabler`, or a safe relative `.css` path). | `zelyra serve`, generated MariaDB Compose projects; CLI and Web checks for selection, path safety, MIME type, and caching. |

The selection **replaces** the integrated Zelyra UI stylesheet; the two CSS
frameworks are not loaded together. `tabler` uses the locally bundled MIT-
licensed Tabler Core CSS. It does not load Tabler JavaScript or make CDN
requests. A project `zelyra.theme.css` remains separate and is included after
the selected stylesheet. Custom CSS can make external requests with `@import`
or `url(...)`; review those references yourself.

Reserved asset routes are `/__zelyra/ui/1.0.6/zelyra-ui.css`,
`/__zelyra/ui/1.0.6/zelyra-ui.js`, and `/__zelyra/ui/project.css`. Built-in,
versioned assets are embedded in the Zelyra binary, work offline, and receive
long-lived caching. Selected project CSS is served with `no-cache`. Zelyra
includes UI assets only on pages with Zelyra UI markup.

## Project-local theme

`zelyra new` and `zelyra init` create an optional `zelyra.theme.css`.
`zelyra serve` loads this regular UTF-8 file from the project directory and
includes it after the selected stylesheet. Symbolic links and files larger
than 128 KiB are rejected. The theme changes presentation, not data access,
CSRF checks, authentication, or authorization.

When creating a project color scheme, update related tokens together:

Change the primary color and `--z-color-on-primary` together, and verify text
contrast. Dark themes use their own `--z-color-on-*` pairs. The
[Zelyra UI handbook](ui.en.md) covers density, content width, and component
adjustments. The theme file is public browser content, not a secret store; do
not put credentials or tokens in it.

The former `/* zelyra:tabler */` marker no longer selects a stylesheet. Set
`ZELYRA_UI_STYLESHEET=tabler` to use the supplied Tabler CSS. The `.env` value
is passed to generated Compose web services; restart a running application to
apply changes.

`ZELYRA_REF` in the generated Dockerfile is a Docker `ARG` containing a
published tag, branch, or commit, not a `.env` variable loaded by Zelyra. The
build fetches the reference and checks it out detached. Set it explicitly
during the Docker build with `--build-arg ZELYRA_REF=...` if needed.

Ports can be changed independently:

```dotenv
ZELYRA_WEB_PORT=3000
ZELYRA_HOST_PORT=18080
ZELYRA_DB_HOST_PORT=3308
```

`zelyra new`, `zelyra init`, and `zelyra setup` select free published host
ports when they create a new `.env` and a default is occupied. `setup` accepts
`--host-port` and `--db-host-port` for strict selections. If Docker Compose
still reports a database or web port conflict, `zelyra setup` selects a free
next port in the existing local `.env`, updates matching local MariaDB URLs,
and retries within a bounded number of attempts. Other `.env` values and
database volumes are preserved. A process-wide `ZELYRA_HOST_PORT` or
`ZELYRA_DB_HOST_PORT` takes precedence; Zelyra does not change that explicit
override and reports that it must be changed or unset.

Then run:

```bash
docker compose --env-file .env -f docker-compose.mariadb.yml up -d --build
```

In the current 1.0.4 release, a declaration
`database <name> { ... }` prefers `ZELYRA_DATABASE_<NAME>_URL`; the name is
uppercased and non-alphanumeric characters become `_`. For `database main`,
the key is `ZELYRA_DATABASE_MAIN_URL`. If that key is not set, `DATABASE_URL`
remains the backwards-compatible fallback. When both are set, the named key
wins. A present but empty named variable counts as set and does not fall back.

Normal `run`, `serve`, `db`, `auth`, and `audit` commands read these values
from the process environment. The CLI does not generally auto-load `.env` for
this purpose; Compose injects them, or they must be exported before invocation.
`zelyra doctor --env-file <file>` checks that file in this order: the named key,
then `DATABASE_URL`. Restart Zelyra servers after changing their process
environment. Without `--env-file`, `doctor` automatically checks the `.env`
beside the selected source file when it exists. A process-environment value
takes precedence over a value in that file. Doctor output includes only the
selected variable name and file path, never the connection value. This automatic
file selection applies only to `doctor`; `run` and `serve` do not generally load
database URLs from `.env`. Named variables are available starting with Zelyra
1.0.4.

## MariaDB timeouts, connection pool, and TLS

These settings are available in the current 1.0.4 release. They are read only from the process
environment. Zelyra does not load a `.env` file for these settings and has no
matching `zelyra.toml` option. A Docker Compose service can receive them from
Compose's `.env`; a running server must be restarted to inherit changed process
values.

| Variable | Default | Allowed | Precedence / source | Secret | Affected paths and tests |
|---|---:|---:|---|---|---|
| `ZELYRA_DB_CONNECT_TIMEOUT_SECS` | `10` seconds | integer `1`–`300` | process environment; otherwise default | no | MariaDB and PostgreSQL pool connections; PostgreSQL applies to the bounded 0.6.0 runtime API |
| `ZELYRA_DB_QUERY_TIMEOUT_SECS` | `30` seconds | integer `1`–`3600` | process environment; otherwise default | no | MariaDB and PostgreSQL runtime statements; not `db apply`/DDL; PostgreSQL applies to the bounded 0.6.0 runtime API |
| `ZELYRA_DB_POOL_MAX_SIZE` | `8` connections | integer `1`–`64` | process environment; otherwise default | no | Hard maximum MariaDB and PostgreSQL pool size per Zelyra process |
| `ZELYRA_DB_POOL_WAIT_TIMEOUT_SECS` | `10` seconds | integer `1`–`300` | process environment; otherwise default | no | Maximum wait for an available MariaDB or PostgreSQL pooled connection |
| `ZELYRA_DB_TLS_MODE` | `auto` | `auto`, `disabled`, or `required` | process environment; otherwise `auto` | no, but security-critical | TLS policy for runtime pools and MariaDB CLI; restart to change |
| `ZELYRA_DB_TLS_CA_CERT_FILE` | unset | absolute path to readable PEM/DER CA file; PostgreSQL runtime API expects PEM | process environment; optional; invalid with `disabled` | no; certificate is public, trust anchor is security-critical | Additional trusted CA for runtime pools and MariaDB CLI |

Invalid values produce a secret-free configuration diagnostic; the supplied
value is not echoed. In `auto` mode, Zelyra requires TLS for non-local hosts and
verifies both the certificate chain and hostname; `localhost`, names under
`.localhost`, and loopback IP addresses remain plaintext for local development.
For the PostgreSQL runtime pool, rustls verifies the certificate chain and host
name using the Mozilla Web PKI roots plus the optional PEM CA. `required` enforces verified TLS even locally. `disabled` explicitly turns TLS
off and is intended only for isolated local networks; TLS failures never fall
back to an insecure connection. Without a custom CA, the Rustls driver uses its
bundled public roots. A PostgreSQL CA file must be absolute, readable, and PEM
encoded; the MariaDB client supports PEM/DER. For schema inspection and DDL, the MariaDB client gets
the same TLS policy through `--ssl` and `--ssl-verify-server-cert`, plus
`--ssl-ca` when configured. With Docker, mount a private CA into the container
and make it readable at the configured path. The full MariaDB project template
explicitly selects `disabled` for its own isolated Compose network. An exported
Docker module connects to an external database and therefore defaults to
`auto`; set its `.env` to `disabled` only for a deliberately isolated local
database network.

The MariaDB client also receives `--skip-reconnect`, so a lost connection
cannot silently reconnect or replay a statement. MariaDB runtime SQL and the
bounded PostgreSQL API use process-wide bounded pools. Connections are
checked on checkout; after statement errors they are discarded, and a rollback
is attempted inside a transaction. There are no automatic retries. A process
can use only one database URL and one pool configuration; changes require a
restart. Schema inspection and DDL are not routed through this pool and still
use the MariaDB client process. MariaDB enforces the statement limit
server-side. It does not bound large-result transfer or the full
response/process lifecycle. DDL remains excluded because an aborted schema
command may leave partial state. The positive TLS handshake and rejection of an
untrusted CA are tested automatically in the MariaDB compatibility matrix;
Windows TLS has not been tested separately.

## Related non-secret `zelyra.toml` settings

Not every project option belongs in `.env`. Current supported configuration
sections include `[capabilities]`, `[filesystem]`, `[network]`, `[process]`,
`[runtime]`, `[web]`, and `[features]`. They are explicit policy, not a way to bypass
security: capabilities, allowlists, SQL checks, CSRF, and destructive database
approval cannot be disabled through `.env`.

Example runtime configuration:

```toml
[runtime]
max_steps = 100000
max_stack_depth = 100
```

`[runtime].max_steps` is optional and must be a positive integer representable
on the platform. If unset, AST evaluation through `zelyra run` and regular web
handlers has no evaluation-step limit; MIR and bytecode CLI runs use their
documented 100,000-step default. An explicit `zelyra run --max-steps <n>` takes
precedence over the project value. The project limit applies to `zelyra run`,
web handlers, and scheduler commands launched by the integrated service through
`zelyra run`. It does not limit external process runtime and does not replace
network, database, or process timeouts. It is not secret; `.env` and process
variables do not override it.

The existing `[runtime].max_stack_depth` is separate and limits function-call
depth to 1 through 500 (default 20).

Function-level SQL can use the narrower declarations `uses Database(read)` for
`SELECT` and `uses Database(write)` for `INSERT`, `UPDATE`, or `DELETE`. Grant
them with `database_read = true` and `database_write = true` under
`[capabilities]`. The legacy `uses Database` and `database = true` remain
backward-compatible broad grants. SQL statements the checker cannot classify
require the broad capability; these source grants do not create or restrict
MariaDB users. Framework-managed CRUD, forms, authentication, and page data
still require the broad database grant.

`console = false` is the default project grant for interactive terminal input.
Programs that call `read_console(prompt)` must also declare `uses Console` on
the enclosing function. Set the grant to `true` only for CLI programs; it does
not change web forms or browser routes. When a project has no `[capabilities]`
section, there is no additional project allowlist, but the `uses Console`
function declaration is still required. Process environment variables and
`.env` cannot grant this capability. Terminal input is echoed and must not be
used for passwords or other secrets. Affected checks and commands are
`zelyra check`, `zelyra build`, and `zelyra run`; compiler and CLI integration
tests cover typing, capabilities, prompt output, line endings, and EOF. This
setting is not a secret.

## Maintenance rule for new settings

Every new environment variable or project switch must be added here before its
commit. The entry must include:

1. name and spelling;
2. storage (`.env`, process environment, or `zelyra.toml`);
3. default;
4. precedence;
5. purpose and affected CLI/runtime commands;
6. secret classification;
7. security impact and tests.

A setting is not fully documented if it appears only in compiler code or a
template.

## DATABASE_URL: fixed decimal precision

With a configured database and a granted Database capability, `serve` and an
interpreter's first SQL operation verify declared Decimal/Money/UInt precision
using read-only metadata. Metadata access is required; a legacy or incompatible
schema is not silently used or migrated. There is no bypass switch. Existing
URL precedence and secret rules still apply. See [rules and tests](decimals.en.md).

## DATABASE_URL: date and time

Native runtime connections use UTC; existing PostgreSQL URL startup options are
preserved with UTC appended. MariaDB/MySQL DATETIME contains no timezone, so
external writers must use the same UTC convention. Before `serve` or the first
interpreter SQL operation, read-only metadata verifies declared Date, Time and
Timestamp storage. Missing columns, wrong kinds and incompatible time precision
produce source-located errors; metadata access is required. Migrations retain
explicit review. There is no new switch. See [date rules](dates.en.md).
## Local package settings (experimental)

`zelyra.settings.toml` stores non-secret package values under
`[package_settings."<package-path>"]`; manifest defaults apply to omitted optional
fields. Secret fields may only reference process environment names matching
`UPPERCASE_NAME`. The CLI reads those values solely for
`zelyra module settings check`; there is no fallback file and no automatic
`.env` resolution for this mechanism. An existing process value is the only
source; secret defaults are forbidden. Output contains only availability
status, never variable names or values. The file is checked for symlinks, types,
and a 1 MiB size limit; it is neither part of the package lockfile nor a runtime
setting yet. Package and CLI integration tests cover the behavior.

## Internal Linux service identity

`ZELYRA_SYSTEMD_SERVICE_ID` is set only in a systemd user unit generated by
`zelyra service install` or `zelyra service change`. Its value is derived
from the canonical project path; it is neither a secret nor an authorization
credential. The unit sets it after the optional project `.env`, so that file
cannot override the internal identity. Setting it manually does not activate
the scheduler: Zelyra also verifies that the systemd unit for this exact
project is active. Without the marker, or outside that service, `serve` does
not execute schedules. Affected commands are `zelyra service install|change`
and `zelyra serve`; the Linux scheduler integration test verifies this gate.
