# Zelyra: `.env` and configuration

This is the central reference for environment-dependent settings and optional
project switches. Update it whenever a Zelyra setting is added or changed.

## Core rule

The simple path requires no extra configuration.

- `zelyra.toml` contains durable project decisions.
- `.env` contains local, environment-specific values and secrets.
- The process environment can override values for one invocation.
- `.env` must never be committed.

For the supported optional feature switches, precedence is:

```text
process environment → .env → zelyra.toml → safe defaults
```

Secrets are never printed by `zelyra config`.

## Feature switches

Feature switches are optional. Without `[features]`, the currently supported
surfaces remain enabled so existing projects keep working unchanged.

```toml
[features]
web = true
api = true
crud = true
auth = true
audit = true
```

| Switch | `.env` / process variable | Default | Meaning |
|---|---|---:|---|
| `web` | `ZELYRA_FEATURE_WEB` | `true` | pages, forms, and web resources |
| `api` | `ZELYRA_FEATURE_API` | `true` | `api` declarations and API surface |
| `crud` | `ZELYRA_FEATURE_CRUD` | `true` | `crud` declarations and generated CRUD surface |
| `auth` | `ZELYRA_FEATURE_AUTH` | `true` | `auth` declarations and authentication surface |
| `audit` | `ZELYRA_FEATURE_AUDIT` | `true` | audit configuration within authentication |

Example local profile:

```dotenv
ZELYRA_FEATURE_API=false
ZELYRA_FEATURE_CRUD=false
```

If source uses a disabled surface, the compiler reports `E-FEATURE-001`.
Feature switches can never disable type checking, SQL checking, capabilities,
contracts, CSRF protection, or other security rules.

Inspect effective configuration without displaying secrets:

```bash
zelyra config main.zyl
zelyra config main.zyl --format=json
```

The JSON output contains only switches, their source, and the statement that
secrets are not displayed.

## Generated MariaDB/Docker projects

`zelyra new --mariadb`, `zelyra init --mariadb`, and MariaDB templates create
`.env.example` and immediately create a protected local `.env` with randomly
generated passwords. `zelyra setup` remains available as an idempotent recovery
command for existing MariaDB projects.

The generated `.env` activates only the values required by Compose and local
database commands. The selected MariaDB host port stays active so
`DATABASE_URL` and Compose use the same port. Web port overrides, feature switches, authentication, and other
options are described extensively as commented lines. `.env.example` has the
same structure, but its `change-me` placeholders and active secret fields are
only a template.

| Variable | Generated default | Use |
|---|---:|---|
| `ZELYRA_WEB_PORT` | `3000` | internal web-server port in the container |
| `ZELYRA_HOST_PORT` | `3000` | web port published on the local host |
| `ZELYRA_DB_HOST_PORT` | `3306` | MariaDB port published on the local host |
| `DATABASE_URL` | project-specific | database connection for CLI/runtime; may contain a secret |
| `MARIADB_DATABASE` | `zelyra_app` | Compose database name |
| `MARIADB_USER` | `zelyra` | Compose application user |
| `MARIADB_PASSWORD` | generated by `zelyra new`/`init` or `setup` | Compose application password |
| `MARIADB_ROOT_PASSWORD` | generated by `zelyra new`/`init` or `setup` | MariaDB root password |

`ZELYRA_REF` in the generated Dockerfile is a Docker `ARG` containing a
published tag, not a `.env` variable loaded by Zelyra. Set it explicitly during
the Docker build with `--build-arg ZELYRA_REF=...` if needed.

Ports can be changed independently:

```dotenv
ZELYRA_WEB_PORT=3000
ZELYRA_HOST_PORT=18080
ZELYRA_DB_HOST_PORT=3308
```

`zelyra new`, `zelyra init`, and `zelyra setup` select free published host
ports when they create a new `.env` and a default is occupied. `setup` accepts
`--host-port` and `--db-host-port` for strict selections. It never changes an
existing `.env`; edit that file explicitly when changing a running project.

Then run:

```bash
docker compose --env-file .env -f docker-compose.mariadb.yml up -d --build
```

Normal `run`, `serve`, `db`, `auth`, and `audit` commands read `DATABASE_URL`
from the process environment. The CLI does not generally auto-load `.env` for
this purpose; Compose injects it, or it must be exported before invocation.
`zelyra doctor --env-file <file>` specifically reads `DATABASE_URL` from that
file for its read-only check.

## Runtime and authentication

| Variable | Use | Security |
|---|---|---|
| `ZELYRA_AUTH_TOKEN` | optional local Bearer token for protected requests | secret; never commit |
| `ZELYRA_AUTH_PERMISSIONS` | comma-separated local permission allowlist | do not log unnecessarily |
| `ZELYRA_MODE` | example value for `env("ZELYRA_MODE")` with `Environment` capability | application-specific |

Applications may use `env(...)` only when the corresponding capability is
granted. `DATABASE_URL` and auth secrets do not belong in source, JSON
diagnostics, context output, or logs.

Variables beginning with `GENERATED_*`, `*_E2E_*`, and `ZELYRA_BIN` are not a
public application API. They exist for reproducible CI and local integration
tests and must never contain production credentials.

Test variables are not application configuration. Use them only in local test
environments and never store real values in examples.

## Related non-secret `zelyra.toml` settings

Not every project option belongs in `.env`. Current supported configuration
sections include `[capabilities]`, `[filesystem]`, `[network]`, `[process]`,
`[web]`, and `[features]`. They are explicit policy, not a way to bypass
security: capabilities, allowlists, SQL checks, CSRF, and destructive database
approval cannot be disabled through `.env`.

## Maintenance rule for new settings

Every new environment variable or project switch must be added here before its
commit. The entry must include:

1. name and spelling;
2. storage (`.env`, process environment, or `zelyra.toml`);
3. default;
4. precedence;
5. purpose and affected CLI/runtime commands;
6. secret classification;
7. security impact and tests.

A setting is not fully documented if it appears only in compiler code or a
template.
