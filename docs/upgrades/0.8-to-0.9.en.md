# Upgrade from Zelyra 0.8.0 to 0.9.0

Version 0.9.0 remains experimental. Do not enable optional local MFA in a
production application: independent security review is reserved for the 1.0.0
production release.

## Standard upgrade

1. Back up project source, configuration, `.env`, and the database together.
2. Stop the running Zelyra process and install the 0.9.0 artifact from its
   release page. Verify its published SHA-256 checksum.
3. Check the project before starting it:

   ~~~bash
   zelyra check src/main.zyl
   zelyra db inspect src/main.zyl
   zelyra db plan src/main.zyl
   ~~~

4. Review every schema difference. A normal 0.8 project needs no database
   change just to upgrade the Zelyra binary. Apply only changes you explicitly
   want and have reviewed with `zelyra db apply`.
5. Start the process and check `/health/live` and the documented application
   workflows. Keep the backup until verification is complete.

## Optional MFA preview feature

MFA requires MariaDB, persistent sessions with `mfa_verified`, factor,
recovery-code, and audit tables, plus a separately protected 32-byte key.
First read the [database matrix](../database-support.en.md) and
[threat model](../release-readiness/0.9.0-mfa-threat-model.en.md).

1. Add the MFA declarations and tables from the
   [technical reference](../handbook/en/technical-reference.md).
2. Check `zelyra check`, `db plan`, and every generated SQL step. Apply the
   extension first to a disposable database and test login, recovery, and the
   documented operator procedure.
3. Generate the key with `openssl rand -hex 32`, store it in an operator-managed
   secret store, and set `ZELYRA_MFA_ENCRYPTION_KEY` only for the server
   process. Never commit the key or back it up with the database.
4. Enable MFA only after the operator has understood and tested key and
   recovery procedures. Losing the key makes stored TOTP factors unreadable.

## Roll back to 0.8.0

Stop the 0.9 process first and back up the database and source again. For a
complete rollback, restore that matching backup. Without a database restore,
remove MFA declarations from source because 0.8.0 does not recognize them.
New MFA tables can remain unused; do not drop them automatically, and do not
remove sessions or audit data without a documented operator decision.

For a standard upgrade without MFA, the database is unchanged. Roll back by
restoring the 0.8.0 artifact and the backed-up project source.
