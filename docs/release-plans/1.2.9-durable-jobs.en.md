# Zelyra 1.2.9 — durable scheduler jobs

## Outcome

Scheduled commands declared in a Zelyra project are queued durably only while
the installed Linux service for that project is active. The scheduler never
installs host cron entries. Operators can inspect attempts, leases, retry
times, terminal failures, and requeue exhausted work through Zelyra's existing
outbox tooling.

## Architecture decision

Reuse the existing MariaDB transactional outbox as the durable job store
instead of adding a second queue with a separate lease and retry model. Each
scheduled occurrence has a deterministic event ID derived from the canonical
project identity, schedule name, and UTC minute. A unique event ID makes
repeated ticks and service restarts idempotent. A worker rechecks the current
compiled schedule before executing a queued occurrence. The handler runs as a
child `zelyra run ... --entry ...` process without shell interpolation.

Delivery is at least once. A crash after a handler performs an external side
effect but before acknowledgement can cause a retry; exactly-once side effects
are not promised. Handlers must remain idempotent or use their own business
transaction/outbox boundary. The outbox's bounded retries and lease recovery
remain authoritative.

## Acceptance criteria

- [x] `setup` creates or upgrades the outbox once for any project with native
  schedules, using the configured MariaDB connection and no secret copying.
- [x] The active project service enqueues due occurrences transactionally and
  deduplicates the same project/schedule/minute across concurrent ticks and
  restarts.
- [x] Only the active installed project service starts schedule workers;
  manual `serve`, `schedule trigger`, and cron exports cannot dispatch them.
- [x] Workers use serialized bounded concurrency, the configured wall-clock timeout,
  renewable leases, bounded retries, and a dead-letter state.
- [x] A queued occurrence is revalidated against the current project before
  dispatch; a removed or invalid declaration is acknowledged as cancelled and
  is never executed from stale stored handler text.
- [x] `zelyra schedule jobs <main.zyl>` exposes bounded, payload-free status
  pages in text and versioned JSON; `zelyra outbox requeue` is the explicit
  operator action for exhausted occurrences.
- [x] Positive and negative tests cover deduplication, competing workers,
  expired leases, retry/dead-letter/requeue, source removal, offline/manual
  service gating, and no real mail delivery.
- [x] German/English help, command handbook, changelog, and release notes
  describe the implementation. No new environment settings were introduced.

## Security and operational boundaries

The outbox stores only a schedule identity and due timestamp, not secrets or
handler source. The worker recompiles the project and resolves the current
handler. The service must have the same explicit database, filesystem,
network, and email grants as ordinary command execution. Requeue does not
immediately execute a job. Database setup is additive and repeat-safe; it
does not create host cron entries or alter application tables.
