# Zelyra 1.2.25 — native database console and query commands

## Goal

Give project developers a safe CLI path to inspect and query their configured
MariaDB/MySQL or PostgreSQL database without copying connection passwords into
shell arguments.

## Scope

- `zelyra db console [file.zyl]` resolves the project's declared database URL,
  starts the matching installed host client, inherits the terminal streams,
  passes credentials through the client-specific environment variable, and
  returns the client's exit status.
- `zelyra db query <file.zyl> <SQL>` accepts one SQL statement and renders
  table, JSON, or RFC 4180 CSV output.
- Queries use database-enforced read-only transactions by default. Explicit
  `--allow-mutation` runs the statement in a transaction and commits only after
  successful completion.
- `--tenant` binds an explicit `:tenant_id` placeholder. It does not infer or
  enforce row-level tenant predicates.
- `--limit` bounds returned rows. Documentation must not claim that it bounds
  server-side query work.

## Security and compatibility constraints

- Never place a password in process arguments or diagnostics.
- Reject multiple statements in one invocation.
- Never describe arbitrary SQL as tenant-safe.
- Retain existing database driver pools and parameter binding.
- Report missing host client binaries with stable `E-CLI-DB-001` diagnostics.
- Keep MariaDB/MySQL and PostgreSQL behavior covered. SQLite client support is
  deferred unless the existing URL/storage conventions can be supported
  without inventing a second connection-resolution path.

## Verification

- Unit tests for credential URL parsing, statement boundaries, CSV escaping,
  JSON scalar types, and read-only statement handling.
- CLI integration tests for `SELECT 1`, table/JSON/CSV output, explicit
  mutation opt-in, pipe-through console behavior, and absence of passwords in
  process argument vectors.
- Run workspace check, tests, formatter, Clippy, release metadata validation,
  and release artifact smoke test before publication.

## Follow-on work

The language REPL is planned separately for 1.2.26. It requires persistent
runtime bindings and a transaction lifetime that spans input lines; it must
not simulate sandbox rollback by issuing a rollback after auto-committed SQL.
