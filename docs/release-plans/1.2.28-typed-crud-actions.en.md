# Zelyra 1.2.28 — typed CRUD domain actions

## Goal

Allow a CRUD action to execute checked Zelyra statements against the selected
record while preserving the CRUD route's authentication, permission, tenant,
CSRF, and transaction guarantees. This is a small typed action language inside
the existing CRUD action declaration, not a general workflow engine.

## Repository baseline

- `FormAction` already stores CRUD action statements, metadata, and declared
  permissions. `parser/src/lib.rs::form_action` currently accepts statements
  directly in `action name { ... }`.
- `forms` checks duplicate action/field names and the CLI validates action SQL
  against the declared database schema.
- `web/src/lib.rs::execute_form_action_with_children` currently rejects every
  action statement except SQL expressions, then executes SQL in a protected
  decision transaction. Edit records are locked and tenant/recipient access is
  revalidated before writes.
- The AST runtime can execute a checked function with a shared MariaDB
  interactive transaction. Other runtime host operations and the existing
  database transaction abstraction must be audited before being used inside
  CRUD requests.

## Initial architecture decisions

1. Preserve existing `action name { SQL ... }` behavior. Add an explicit
   `execute { ... }` body and optional `guard when <expr> { error: "..." }`
   to the existing action syntax; do not add another action/component system.
2. Resolve `row` from the persisted target record under the existing row lock.
   Resolve `session.user_id` and `session.tenant_id` from authenticated,
   verified request context only. No request fields may populate those values.
3. Type-check action bodies and guards using the ordinary compiler type and
   capability rules with an explicit action context. Reject unsupported
   effects, unknown fields, unbounded/raw SQL interpolation, and invalid
   return types at compile time with stable diagnostics and source spans.
4. Evaluate the guard while holding the row lock, then execute the body and
   audit/outbox writes within the same transaction. Any runtime or SQL failure
   must roll back the whole action. Preserve existing permission checks before
   execution and tenant revalidation inside the transaction.
5. Reuse existing safe SQL parameter binding, `hash_sha256`, `now()`,
   `render_pdf`, and `mail_queue` only where their current APIs and transaction
   semantics allow it. Do not create `crypto::` aliases or interpolate SQL.

## Work stages and evidence

1. Complete the baseline audit across AST, parser, compiler validation,
   runtime transaction providers, web route construction, and action HTTP
   handling. Record backend-specific transaction constraints.
2. Extend AST/parser/formatter/compiler checking for action execution bodies,
   guards, row/session types, supported effects, and negative cases.
3. Add an execution bridge that runs the checked action with a locked record
   and verified session in the existing request transaction. Keep old SQL-only
   declarations compatible.
4. Add MariaDB end-to-end tests for permissions, tenant isolation, guard
   concurrency, successful row-plus-audit update, and full rollback when a
   later statement fails. Add PostgreSQL coverage if the shared transaction
   API can provide equivalent semantics; otherwise reject unsupported backend
   use explicitly and track it as an open criterion.
5. Update both handbooks, both roadmaps, release notes, and runnable examples
   only for behavior proven by compiler and runtime tests.

## Acceptance criteria

- Existing SQL-only CRUD actions still compile and run.
- Action code is type-checked in a scope containing only the persisted `row`
  and trusted `session` fields plus ordinary declared functions.
- An action permission is checked on GET and POST; tenant-scoped writes
  revalidate tenant access inside the transaction.
- A guard executes against the current locked row and fails with its declared
  message without performing writes.
- Multiple SQL statements and supported typed calls commit together or roll
  back together.
- Tests prove a successful lock action updates the invoice and writes one
  audit event, while an induced later failure leaves both unchanged.
- Documentation distinguishes statically proven behavior from backend or
  effect limitations.

## Not in this milestone

File uploads, arbitrary dynamic SQL, general-purpose workflows, unbounded
action callbacks, and implicit capabilities. Those remain separate roadmap
items.
