# Zelyra 1.2.28 — typed CRUD domain actions

## Goal

Allow a CRUD action to execute checked Zelyra statements against the selected
record while preserving the CRUD route's authentication, permission, tenant,
CSRF, and transaction guarantees. This is a small typed action language inside
the existing CRUD action declaration, not a general workflow engine.

## Repository baseline

- `FormAction` already stores CRUD action statements, metadata, and declared
  permissions. `parser/src/lib.rs::form_action` currently accepts statements
  directly in `action name { ... }`.
- `forms` checks duplicate action/field names and the CLI validates action SQL
  against the declared database schema.
- `web/src/lib.rs::execute_form_action_with_children` currently rejects every
  action statement except SQL expressions, then executes SQL in a protected
  decision transaction. Edit records are locked and tenant/recipient access is
  revalidated before writes.
- The AST runtime can execute a checked function with a shared MariaDB
  interactive transaction. Other runtime host operations and the existing
  database transaction abstraction must be audited before being used inside
  CRUD requests.

## Initial architecture decisions

1. Preserve existing `action name { SQL ... }` behavior. Add an explicit
   `execute { ... }` body and optional `guard when <expr> { error: "..." }`
   to the existing action syntax; do not add another action/component system.
2. Resolve `row` from the persisted target record under the existing row lock.
   Resolve `session.user_id` and `session.tenant_id` from authenticated,
   verified request context only. No request fields may populate those values.
3. Type-check action bodies and guards using the ordinary compiler type and
   capability rules with an explicit action context. Reject unsupported
   effects, unknown fields, unbounded/raw SQL interpolation, and invalid
   return types at compile time with stable diagnostics and source spans.
4. Evaluate the guard while holding the row lock, then execute the body and
   audit/outbox writes within the same transaction. Any runtime or SQL failure
   must roll back the whole action. Preserve existing permission checks before
   execution and tenant revalidation inside the transaction.
5. Reuse existing safe SQL parameter binding, `hash_sha256`, `now()`,
   `render_pdf`, and `mail_queue` only where their current APIs and transaction
   semantics allow it. Do not create `crypto::` aliases or interpolate SQL.

## Work stages and evidence

1. Complete the baseline audit across AST, parser, compiler validation,
   runtime transaction providers, web route construction, and action HTTP
   handling. Record backend-specific transaction constraints.
2. Extend AST/parser/formatter/compiler checking for action execution bodies,
   guards, row/session types, supported effects, and negative cases.
3. Add an execution bridge that runs the checked action with a locked record
   and verified session in the existing request transaction. Keep old SQL-only
   declarations compatible.
4. Add MariaDB end-to-end tests for permissions, tenant isolation, guard
   concurrency, successful row-plus-audit update, and full rollback when a
   later statement fails. Add PostgreSQL coverage if the shared transaction
   API can provide equivalent semantics; otherwise reject unsupported backend
   use explicitly and track it as an open criterion.
5. Update both handbooks, both roadmaps, release notes, and runnable examples
   only for behavior proven by compiler and runtime tests.

### Stage 1 audit findings (2026-10-20)

- `FormAction` retains legacy `statements` and now has separate optional
  `execute_body` and action-guard AST nodes. The parser accepts `execute {}`
  and `guard when ... { error: "..." }`, rejects duplicates and mixing with
  legacy direct statements, and tests that source structure. The CLI now
  checks execute bodies and guards in synthetic scopes built from the target
  table columns and explicitly available session fields. Transaction-bound
  web execution is still disabled.
- `web/src/lib.rs::execute_form_action_with_children` validates legacy action
  bodies as SQL-only, then runs those statements inside
  `zelyra_database::with_decision_transaction`. That transaction already
  revalidates tenant access and locks/rechecks the selected record before the
  action's SQL. This is the compatibility path to retain.
- `DecisionTransaction<'a>` is a short-lived borrowed executor inside a
  closure. Runtime `HostServices` has no transaction-aware database method;
  the existing `ReplSession` transaction is MariaDB-only and cannot safely be
  passed into PostgreSQL's borrowed transaction. Calling the AST runtime from
  the current web closure would therefore use another connection and would
  break atomicity. The action implementation must first provide an owned or
  otherwise safely scoped shared query interface for both backends, or reject
  unsupported backend/effect combinations explicitly. No raw pointer or
  second-connection workaround is acceptable.
- `DecisionTransaction::execute` rejects transaction control and implicit
  commit DDL, and marks the transaction failed after the first rejected or
  failed statement. This remains an important invariant for typed actions.
- `CrudActionRoute` carries the action's existing metadata and a `FormRoute`;
  route creation and permission checks are separate from the SQL execution
  helper. The new semantics must preserve those authorization and POST/CSRF
  layers rather than bypassing them.
- The AST runtime now has a bounded execution entry point that routes every
  SQL expression through a borrowed caller-provided transaction query bridge.
  It rejects nested `transaction` blocks and `parallel` blocks while that
  bridge is active, so those paths cannot escape to another connection. This
  foundation is covered by callback-routing and fail-closed tests; the web
  action handler does not use it yet.
- Module linking, action SQL inventory, formatter parsing, and impact analysis
  now traverse the new AST nodes. The web runtime also rejects them explicitly
  instead of dropping them or executing legacy statements.

This audit changes the implementation order: establish the transaction-aware
runtime/database boundary before enabling arbitrary Zelyra statements in an
action. The AST bridge and compiler action scopes are in place; web integration
and end-to-end transaction evidence were open at the initial inventory; the
chronological implementation update below records the subsequent work.

## Progress: compiler-checked action scope

- `FormAction` now stores explicit action capabilities. `uses` accepts known
  capability names, including `Database(read)` and `Database(write)`; normal
  capability analysis and project-grant checks remain authoritative.
- The CLI adds private synthetic records and functions for checking. `row`
  contains exactly the target CRUD table columns. `session` exposes optional
  nominal `tenant_id` and `user_id` values; scoped tables use their declared
  tenant type for `tenant_id`. Execute bodies are checked as `Unit`, guards as
  `Bool`, using the normal Zelyra type checker. Guards receive no capabilities.
- CLI regression coverage checks valid `row`/`session` access and rejects an
  unknown row field. The parser test covers explicit capability syntax.
- At this recorded compiler-only stage, web routes still rejected typed actions until
  row loading and guard evaluation use the same locked request transaction via
  the borrowed query bridge. MariaDB end-to-end atomicity and audit/outbox
  rollback remain open.
- Verified at the 2026-10-20 compiler-only stage: parser test, targeted CLI
  compiler test, 7 runtime REPL tests, 2 CLI pipe tests, CLI/Web `cargo check`,
  rustfmt, and `git diff --check` passed. No database E2E had run yet.

## Implementation update: MariaDB request transaction

- AST exposes one deterministic lowering map for action wrapper names and the
  private row/session record types. Compiler validation and WebApp runtime use
  the same lowering path, preventing wrapper-name drift.
- The Web action handler loads the target row with `FOR UPDATE`, applies the
  existing tenant membership/ownership and recipient checks in the request
  transaction, converts stored columns to typed runtime values, and evaluates
  the guard before the execute body. The body uses the runtime's borrowed
  transaction query bridge; failed queries poison and roll back the enclosing
  decision transaction. Framework audit insertion stays in that transaction.
- The route builder passes project capability grants and runtime policy into
  the web runtime. A granted `Database(read)` or `Database(write)` counts as a
  database grant for serving the application; runtime checks still enforce
  the exact action effect. MariaDB timestamps are converted from its
  space-separated microsecond representation to Zelyra UTC milliseconds.
- A `transaction { ... }` inside a typed action is a logical batch on the
  already-open request transaction. SQL and `mail_queue` use the same borrowed
  executor; no inner commit or second connection is possible. PDF bytes must
  come directly from the existing bounded `render_pdf` path.
- `examples/typed_crud_actions/main.zyl` compiles and runs. The MariaDB HTTP
  E2E test proves row update/hash/time plus audit insert, guard rejection on a
  repeated action, and rollback after an update and audit insert followed by a
  runtime failure. It also verifies one pending outbox message with a real PDF
  attachment and no immediate send. It passed against an isolated MariaDB 11.4
  container on 2026-10-20.
- `tests/mariadb-tenant-crud-e2e.sh` also executes a typed action with
  authenticated `session.user_id` and selected `session.tenant_id`, rejects a
  row from a different selected tenant, and denies a direct action POST to a
  CRUD viewer who lacks the action permission. This HTTP E2E passed against an
  isolated MariaDB 11.4 container.
- CLI regression coverage confirms `uses Database(write)` is rejected when
  the project configuration explicitly denies `database_write`, and that a
  `Database(read)` declaration cannot authorize an UPDATE. The web database
  gate separately accepts only an explicit read or write grant.
- PostgreSQL uses the existing decision transaction adapter. The new
  `tests/postgres-typed-crud-actions-e2e.sh` creates and drops its own local
  test database, then verifies successful row/hash/timestamp and audit updates
  plus rollback after a runtime failure. Both database E2Es also race two
  lock requests and assert one success, one guarded conflict, and one audit
  row. They do not invoke the separately authorized SMTP worker or verify
  PostgreSQL outbox attachments.

## Acceptance criteria

- Existing SQL-only CRUD actions still compile and run.
- Action code is type-checked in a scope containing only the persisted `row`
  and trusted `session` fields plus ordinary declared functions.
- An action permission is checked on GET and POST; tenant-scoped writes
  revalidate tenant access inside the transaction.
- A guard executes against the current locked row and fails with its declared
  message without performing writes.
- Multiple SQL statements and supported typed calls commit together or roll
  back together.
- Tests prove a successful lock action updates the invoice and writes one
  audit event, while an induced later failure leaves both unchanged.
- Documentation distinguishes statically proven behavior from backend or
  effect limitations.

## PostgreSQL verification update (2026-10-20)

The PostgreSQL HTTP E2E ran successfully against an isolated PostgreSQL 16.15
container, including simultaneous guarded action requests. The script restricts its base connection to a local `zelyra_ci` or
`zelyra_test` database, creates a uniquely named database for the run, and
drops it during cleanup. CI now runs this test. It covers successful typed
action writes, guard concurrency, and rollback; the broader
permission/capability matrix remains open.

## Not in this milestone

File uploads, arbitrary dynamic SQL, general-purpose workflows, unbounded
action callbacks, and implicit capabilities. Those remain separate roadmap
items.
