# Zelyra 1.0.0 first productive release plan

**Status:** planned; not a stable release promise. `v1.0.0` is the first major
productive release and the mandatory target for all deferred independent
human acceptance tests. It follows the 0.9.9 feature freeze.

## Release gates

- [ ] Freeze the 1.0.0 product scope, support matrix, compatibility promises,
  and documentation before preparing the final candidate.
- [ ] Verify real-server support for MariaDB, MySQL, and PostgreSQL in separate
  version matrices. Cover project setup, schema operations, typed SQL,
  transactions, and the generated web/CRUD workflows included in the frozen
  scope. Do not treat a URL alias or shared SQL syntax as server support.
- [ ] Deliver and verify end-to-end foreign-key support on MariaDB, MySQL, and
  PostgreSQL: declared references receive compiler validation; schema setup and
  reviewed migrations create and inspect real database constraints; Studio
  displays relationships; generated CRUD can choose and display related records
  and saves valid references. Adding constraints to existing data checks for
  orphan rows before changing the schema. Failed or unsupported changes preserve
  data and fail closed. Restrictive deletion is the default; any declared
  cascade or set-null policy must be checked against nullable/type rules and
  tested for every backend on which it is supported.
- [ ] Secure and integrate tenant-filtered generated CRUD for MariaDB, MySQL,
  and PostgreSQL. Resolve the tenant from an active membership of the
  authenticated user and enforce it server-side together with the resource
  permission on every read and mutation: list, detail, create, edit, update,
  delete, and restore. Client-submitted tenant keys must never assign records to
  another tenant. With foreign keys, referenced records must also belong to the
  active tenant. Reject custom SQL actions on tenant-owned data unless they can
  be proven tenant-aware. Per-database integration evidence must cover tenant
  separation, permissions, missing/revoked memberships, forged selection, and
  every read and mutation path. The current experimental MariaDB implementation
  for one table without relations does not satisfy this gate by itself.
- [ ] Complete the Laravel Migrator compatibility matrix and verify its
  read-only behavior, source locations, secret/PII exclusion, relationship
  evidence, ambiguity reporting, safe output separation, generated-file
  provenance, and compiler-valid scaffold output. Reports must separate
  generated structure from verified behavior transfer and flag business-rule,
  authorization, tenant, transaction, money, file, payment, and integration
  behavior that needs review. The Migrator must not claim functional or security
  parity from syntactic matches.
- [ ] Confirm the local developer studio and invoice tutorial work without
  mandatory cloud services, telemetry, or external AI providers.
- [ ] Pass technical, security, dependency, artifact, checksum, SBOM, and
  provenance checks on the exact candidate revision.
- [ ] Publish an immutable 1.0.0 release candidate and conduct the independent
  human study using its exact assets and shipped documentation.
- [ ] Fix every human-study blocker, verify a corrected immutable candidate,
  and repeat the affected study tasks.
- [ ] Complete the bilingual human acceptance record with the exact candidate
  tag and commit, participant/task evidence, redacted observations, blockers,
  and the project owner's explicit decision.
- [ ] Publish stable `v1.0.0` only after every technical gate and the human
  acceptance decision pass.

Human acceptance is specific to the recorded tasks and participants. It does
not establish general usability, production readiness, security certification,
or correctness for arbitrary programs.
