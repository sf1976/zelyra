# Zelyra 1.0.0 roadmap: contract stabilization and human acceptance

**Status:** planned on the stacked `release/1.0.0` branch. This milestone
starts only after the 0.5.0 human gate and the 0.6.0–0.9.0 technical release
gates are complete. It introduces no new platform feature.

## Decision

Use 1.0.0 to stabilize and accurately describe the language, compiler, CLI,
database, and web-runtime contracts that have passed the preceding milestones.
The release is ready only when those contracts are documented in English and
German, the release artifacts are reproducible and independently checked, and
an independent human accepts the exact published candidate.

## Contract inventory

Before the first candidate, publish a reviewed compatibility inventory for:

- Language syntax and semantics, module visibility/imports, and the supported
  static-verification boundary.
- CLI commands, stable diagnostic codes, exit behavior, project setup, and
  supported installation targets.
- MariaDB runtime behavior and the bounded PostgreSQL schema/parameterized
  runtime subset. Do not imply complete PostgreSQL parity or universal SQL.
- HTTP, sessions, local MFA, authorization, tenant-scoped generated CRUD, and
  transactional outbox behavior, with explicit exclusions for each boundary.
- Schema changes and upgrade steps from the last accepted stable version.

An inventory entry must cite its documentation and verification evidence.
Experimental or incomplete behavior remains labeled as such; a green workflow
does not establish broader compatibility than its jobs cover.

## Release gates

- The 0.5.0 candidate has passed its independent human acceptance and the
  acceptance record names the exact immutable candidate commit.
- The 0.6.0–0.9.0 branches are reviewed, their documented gates have evidence,
  and the full intended stack is present on the 1.0.0 candidate branch.
- Exact-head CI, dependency policy, fuzzing, compatibility jobs, and release
  artifact verification pass for every supported target. Record the target
  list explicitly; do not infer support from one successful build.
- Linux and Windows release archives, checksums, SPDX SBOMs, and provenance are
  tied to the same immutable candidate commit. Repeatability is verified by
  rebuilding before publication.
- Both language handbooks, CLI references, migration guidance, threat models,
  and release notes match the candidate behavior.
- Security reviews for tenant isolation, outbox delivery, and local MFA are
  complete, with findings resolved or explicitly accepted by the project owner.
- An immutable `v1.0.0-rc.N` is published. The independent acceptance study
  uses those exact assets on a clean machine and records installation, project
  creation, database setup, application run, and a representative authenticated
  workflow. The record includes platform, candidate commit, date, redacted
  observations, blockers, and an explicit decision.
- Any release-blocking change creates a new candidate and repeats artifact
  verification and human acceptance. Stable `v1.0.0` is published only after a
  passing record for that candidate.

## Exclusions

1.0.0 does not imply WebAuthn/passkeys, OAuth2/OIDC, full PostgreSQL parity,
MySQL or SQL Server support, universal SQL, general-purpose queues, complete
visual theme editing, arbitrary client hydration, compiler self-hosting, a
native backend, cloud or AI dependencies, telemetry, certification, or a
public performance guarantee.
