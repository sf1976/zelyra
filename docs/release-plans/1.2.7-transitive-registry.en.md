# Zelyra 1.2.7 — Trusted transitive packages

## Work log

Status: implementation complete; release gates still pending.

## User outcome

A signed package may declare exact versions of separately published Zelyra
packages. `zelyra package add` and an explicit update plan resolve the complete
dependency graph deterministically, verify each package signature against
explicitly configured publisher trust, install the complete closure together,
and record provenance and digest for every artifact in the lockfile. After
installation, check, run, and bundle must work offline.

## Architecture decision

Dependencies stay explicit and exact-versioned. Registry dependencies are
limited to a validated credential-free registry URL, package name, and exact
SemVer requirement. There is no implicit `latest`, build scripts, or
capability grant. Validate every package identity, alias, version, provenance
record, and signature before changing the project manifest. Conflicts, cycles,
ambiguous aliases, version mismatches, or untrusted keys fail closed.

The source syntax for a registry dependency inside a signed package is:

```toml
[dependencies.text]
registry = "https://packages.example.test/index.json"
name = "text"
version = "=1.4.2"
```

`registry`, `name`, and a normalized exact `version` are the only accepted
fields for this dependency kind. Root applications continue to receive local
cache paths for direct dependencies so existing import resolution stays
offline. Registry provenance for every resolved artifact is stored in a
versioned `[package_provenance."name@version"]` table in the root manifest and
the lockfile; legacy direct-alias `[package_sources.<alias>]` entries remain
readable. Package source files and signed manifests are never rewritten to
inject registry metadata. An old lockfile without provenance remains usable
for its existing graph; converting a graph with registry dependencies requires
an explicit `zelyra package lock --update` after reviewing the complete diff.

The resolver caps the closure at 128 artifacts, 256 MiB compressed payload,
and five minutes, rejects package cycles and duplicate aliases within a
manifest, and records every exact dependency edge. Every publisher key must
already be trusted in the project trust file. A root-package update resolves
its full new closure before changing the manifest. The recovery journal is
created before downloads and durably extended before each new staging path. The
installer stages all cache paths, switches the manifest and lock through the
1.2.6 journal, then compiler-checks the complete tentative project before
committing. On a partial filesystem failure, rollback removes only newly
created paths and preserves the journal if recovery is incomplete.

## Stages and acceptance

1. [x] Finish the manifest, resolver, trust, and lockfile inventory.
2. [x] Specify the registry dependency fields and a provenance-aware lockfile
   version in both languages; older lockfiles need an explicit safe update.
3. [x] Implement a bounded recursive resolver with download/time/graph limits and
   conflict, cycle, and trust checks.
4. [x] Verify every artifact before mutation, stage each package under its cache
   root, then switch the manifest and lock through the recovery journal and
   compiler-check the complete tentative project before committing the journal.
5. [x] Test offline check, run, update, remove, and Docker bundle with at least
   three package levels; reject publisher changes and tampering.
6. Run workspace gates, GitHub CI, handbook validation, changelog, and release
   artifact checks; record evidence here.

The three-level registry integration now signs and resolves `first -> second ->
third`, checks offline execution and lock verification, creates and checks an
offline bundle, and updates the whole closure through an update plan. A negative
integration test verifies cycle rejection leaves the project manifest and
cache unchanged. Signing stays offline: for a manifest with registry edges,
the complete compiler validation is performed by installation after each
artifact's signature and publisher trust are checked.

## Limits

This release must not claim a general package registry, native plugins,
automatic capability grants, arbitrary resolver versions, or conflict-free
SemVer upgrades. Package conflicts must be reported explicitly.
