# Zelyra UI 1.0.6 – Work Log

## Objective

Integrate a locally delivered, versioned UI framework with compiler-checked
components and semantic variants. This work log covers implementation and
verification; publishing a release or deploying an external system is
explicitly out of scope.

## Baseline (`01e5884`)

- Named views, slots, typed components with declared props, dynamic type
  checking, CRUD layouts, and compiler-checked query controls already exist.
- The default application shell is rendered in `web/src/ui.rs`. Its styles are
  in `web/assets/zelyra.css` and are currently embedded as an inline style.
- `assets/vendor/tabler/tabler.min.css` is embedded by `cli/src/main.rs` and is
  prepended to project stylesheets that contain `/* zelyra:tabler */`. The
  invoice tutorial uses this path.
- `zelyra.theme.css` is read as a bounded regular project file; symlinks are
  rejected and its size is limited to 128 KiB.
- The invoice tutorial already has a print view, SMTP/outbox features are
  present, and Studio already creates grouped bar/line charts and local
  presentations that can be printed to PDF in the browser. These are
  integration points. There is no standardized Zelyra UI chart for running
  applications and no code property inspector that reports documented
  framework defaults at the cursor.
- The current online Handbook contains older claims: it calls 1.0.4 stable and
  names Tabler 1.6.1 in the invoice tutorial even though the repository has
  advanced the 1.0.5 reference application and its local Tabler path. Treat
  that site as orientation, not the implementation authority; reconcile the
  repository Handbook sources against code.
- The Handbook has older statements that conflict with the current Views and
  component implementation. Affected statements must be reconciled against
  the compiler, runtime, and tests at completion.

## Work packages and acceptance points

1. **Inventory and contract** – inspect grammar, AST, component checking,
   Forms/CRUD, asset routes, CSP, release/Docker packaging, Studio, and the
   tutorial. Produce concrete public syntax and document its limits.
2. **Framework foundation** – provide design tokens, scoped Cascade Layers,
   base/layout/component styles, and small progressive JavaScript as local,
   versioned assets. Unrelated pages remain unchanged; core navigation and
   forms work without JavaScript. Provide a shared page layout with header,
   content, and footer slots for authored and generated pages.
3. **Typed components and variants** – add unambiguous Zelyra UI resolution,
   finite checked properties/variants, source positions, and stable
   diagnostics. Success, warning, and danger examples receive positive and
   negative checks.
4. **Forms, CRUD, and data views** – connect existing centralized rendering to
   the same component styles while preserving input values, errors, CSRF,
   escaping, permissions, search, filters, sorting, and pagination.
5. **Applications and Studio** – migrate the invoice tutorial, component
   gallery, project templates, and suitable Studio areas. Studio shows relevant
   component and form metadata at the cursor, marks framework defaults, and
   explains their explicit overrides. Avoid unnecessary schema changes.
6. **Business media** – provide print-ready components and browser-based PDF
   output; ship compiler-checked bar, line, and donut charts. `EmailLink` opens
   a locally prefilled draft. The generic `mail_queue`/outbox pipeline remains
   available to deliberately authorized server routes, but is not directly
   connected to `EmailLink` and does not support PDF attachments. Sending a
   finished invoice with an attachment remains open.
7. **Evidence and documentation** – check packaged assets, themes,
   browser/responsive/keyboard/accessibility behavior, Handbook, and both
   roadmaps. Any browser or environment check that cannot run is reported as
   open.

The integrated stylesheet is selected with `ZELYRA_UI_STYLESHEET`: `zelyra`
(default), `tabler` (the locally bundled Tabler selection), or a project-relative
`.css` path. The selected stylesheet replaces the built-in framework sheet;
`zelyra.theme.css` remains an optional project override. Remote URLs, path
traversal, symlinks, and oversized CSS files are rejected. Document this
environment variable in both environment references, including its default,
precedence, security classification, affected commands, and tests.

## Binding decisions

- No CDN, runtime telemetry, external font request, or additional frontend
  build for application users.
- Replacement CSS is loaded from a bounded project-local path;
  `ZELYRA_UI_STYLESHEET` precedence is process environment, then `.env`, then
  the default. `zelyra.theme.css` is still loaded last.
- Public classes use the `z-` prefix, variables use `--z-`, and CSS uses
  Cascade Layers scoped to the framework.
- Appearance (for example `appearance: warning`) stays separate from actual
  validation state (for example `aria-invalid`).
- Generic buttons do not submit forms; links remain links. Native HTML provides
  baseline interaction behavior.
- Reuse existing Studio charts/presentations and the tutorial print view. PDF
  initially uses the browser's native print/PDF feature; add a custom PDF
  renderer only if existing technical prerequisites can support it reliably
  without disproportionate dependencies.
- Email sending uses Zelyra's existing explicit SMTP/outbox boundary. Charts
  remain local, keyboard/screen-reader usable, and include a text or table
  equivalent.
- Studio metadata reflects actual compiler/renderer defaults and overrides; it
  must not invent defaults.
- New standard projects and the reference application do not depend on the
  full Tabler framework. Any migration aid is explicitly bounded.
- No 1.0.6 release will be created and no external system will be deployed.
