# Zelyra 1.2.30 — typisierte Schema-Fremdschlüssel für Mandantenschlüssel

Status: im aktiven 1.2.30-Branch implementiert und geprüft. Dieses fokussierte
Schema-Referenzpaket schließt nicht allein den umfassenderen 1.2.30-Meilenstein
für Laravel-Abläufe ab. Ziel ist, relationale Quellspalten wie
`tenant_id` zugleich als nominal typisierte Zelyra-IDs und als echte
Datenbank-Fremdschlüssel abzubilden. Es werden keine Laravel-Dateien oder
Datenbankdaten in das Zelyra-Projekt kopiert.

## Ziel und begrenzter Quellschnitt

Der aktuelle Laravel-Importer schreibt einen mit `tenants.id` verbundenen
`tenant_id`-Fremdschlüssel als Relation `tenant: Tenant`. Dadurch wird die
physische Fremdschlüsselspalte bewahrt, aber der Zelyra-Compiler kann sie nicht
als Mandantenschlüssel `scoped by tenant_id: TenantId` prüfen. Das erschwert
eine sichere native Form-/CRUD-Übernahme.

Die Sprachsyntax soll eine skalare, nominale ID-Spalte explizit an ein
Referenzziel binden können:

```zelyra
type TenantId = Id

table customer_groups scoped by tenant_id: TenantId {
    id: Id primary auto
    tenant_id: TenantId required references tenants on_delete cascade
    name: String(100) required
}
```

`references` erhält den tatsächlichen Datenbank-Fremdschlüssel, während
`TenantId` und `scoped by` die Mandantenidentität für Typprüfung und Runtime
festhalten. Die Referenzziel- und Löschregeln müssen in DDL-Plan,
Schema-Inspektion und allen unterstützten Backends deterministisch bleiben.

## Anforderungen

- `references <table>` wird nur für ID-kompatible skalare Spaltentypen
  akzeptiert; relationale Record-Typen behalten ihr bestehendes Verhalten.
- Referenzen müssen auf eine deklarierte Tabelle und deren Primärschlüssel
  auflösbar sein. Ungültige Ziele erhalten stabile Compilerdiagnostik.
- Die referenzierte Tabelle bestimmt nicht implizit den Zelyra-Spaltentyp.
  Eine nominale Alias-ID bleibt erhalten.
- `on_delete` bleibt explizit; inkompatible Kombinationen mit Nullability und
  Tenant-Constraints werden abgewiesen.
- MariaDB-, PostgreSQL- und SQLite-DDL sowie Schema-Inspektion und Migration
  stimmen mit dem tatsächlichen Zelyra-Fremdschlüssel überein.
- Der Laravel-Importer erzeugt `scoped by tenant_id: TenantId` und
  `tenant_id: TenantId required references tenants ...` nur, wenn die statische
  Migration genau diesen Fremdschlüssel belegt. Andere Relationen bleiben
  unverändert oder sichtbar manuell.
- Wiederholte Generierung gegen `/opt/siedelmann-laravel/app` bleibt
  schreibgeschützt und deterministisch. Der Generator führt kein PHP aus,
  liest keine `.env` und verbindet sich nicht mit der Quelldatenbank.

## Abnahmetests

- Positive/negative Parser- und Typechecker-Tests für gültige ID-Referenzen,
  unbekannte Tabellen, fehlende Primärschlüssel, inkompatible Typen,
  Nullability und Löschaktionen.
- DDL-Plan-Tests für MariaDB, PostgreSQL und SQLite einschließlich des
  nominalen `TenantId`-Feldnamens und der echten `tenant_id -> tenants.id`
  Constraint.
- Integrationstest mit zwei Mandanten: gültige eigene Referenz wird
  akzeptiert; ungültiges Ziel wird von der Datenbank abgewiesen; bestehende
  scoped relationale Fremdschlüssel bleiben zusammengesetzt.
- Laravel-Importer-Test prüft den erzeugten Kunden-/Gruppen-Schemateil gegen
  Compiler, DDL-Plan und die tatsächlichen statischen Migrationen. Es liest
  keine Anwendungszeilen und verändert `/opt/siedelmann-laravel/app` nicht.

## Für diesen Branch dokumentierte Prüfungen

- Parser-, Typechecker-, Linker- und DDL-Unit-Tests liefen erfolgreich. Die
  DDL-Erzeugung ist für MariaDB, PostgreSQL und SQLite abgedeckt.
- `tests/mariadb-tenant-relations-e2e.sh` enthält nun zusätzlich zur
  Record-Relation eine skalare nominale Relation
  `CustomerGroupId? references customer_groups`. Unter MariaDB 11.8 werden
  gleichmandantige Referenzen akzeptiert und mandantenfremde für beide Formen
  abgewiesen; auch die mandantenbezogene Eindeutigkeit wird geprüft.
- Die Prüfungen des tatsächlichen Importers gegen
  `/opt/siedelmann-laravel/app` stehen im laufenden Fortschrittsprotokoll. Sie
  sind statisch, lesen weder `.env`, öffnen die Quelldatenbank, führen PHP aus
  noch ändern das Quellprojekt.

Laravels `SET NULL` auf einer zusammengesetzten Tenant-Relation wird bewusst
als Verhaltensabweichung ausgewiesen: Das Leeren beider FK-Spalten würde auch
den erforderlichen Mandantenschlüssel löschen. Prüfpflichtige Kandidaten
verwenden `RESTRICT`; eine verhaltensgleiche Workflow-Migration bleibt offen.

## Abgrenzung

Dieses Paket importiert noch keinen vollständigen Kunden- oder Rechnungsablauf.
Eine korrekte Schemaabbildung ist Voraussetzung für den folgenden
route-/controller-/view-zu-Modul-Schnitt. Das erzeugte Schema bleibt ein zu
prüfender Kandidat; es wird nicht automatisch auf eine Datenbank angewendet.
