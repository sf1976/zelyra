# Zelyra 0.9.0 roadmap: local multi-factor authentication

**Status:** implementation is present on exact head
`5a37bfcf43deb754b2f029ba3b3ed34a431bcb50`; all eight CI jobs passed in [CI
#556](https://github.com/sf1976/zelyra/actions/runs/38041496904), and Linux /
Windows package validation passed in [release run
#268](https://github.com/sf1976/zelyra/actions/runs/38041496914). MFA-specific
integration coverage, security review, operator recovery rehearsal, and
release acceptance remain open.
This release is intentionally limited to optional, account-local MFA for the
existing password authentication flow.

## Decision

Implement time-based one-time passwords (TOTP) and one-time recovery codes for
local accounts. Keep password authentication usable for projects that do not
enable MFA. Do not add an external identity provider or require a network
service.

WebAuthn/passkeys and OAuth2/OIDC are deferred beyond 0.9.0. They need separate
protocol and browser integration reviews, provider configuration, key
management, and deployment guidance. This keeps the first MFA release
independently operable and reviewable. Reassess these options after 1.0.0
acceptance.

## Scope

- Allow an authenticated account to enroll a TOTP authenticator after recent
  password confirmation; activate it only after a valid confirmation code.
- Require a valid TOTP code or one unused recovery code after password
  verification. A password-only intermediate session must not authorize
  application routes, API access, or session management.
- Generate high-entropy recovery codes, display them once, store only
  password-hashed code verifiers, and consume each code atomically once.
- Protect enrollment, removal, and recovery-code replacement with recent
  password confirmation, CSRF and same-origin checks, and explicit audit
  events. Revoke existing sessions after MFA settings change.
- Encrypt TOTP secrets at rest using a documented operator-managed key. Fail
  closed when MFA is enabled but the key is absent or invalid. Never log the
  secret, provisioning URI, OTP, or recovery codes.
- Persist replay prevention and bounded failed-attempt throttling so concurrent
  requests cannot accept the same time step or bypass the limit.
- Keep MFA opt-in per project and provide an explicit recovery procedure for
  administrators that does not expose stored secrets.

## Implementation status

The branch now contains the parser/runtime configuration, encrypted TOTP
enrollment, password-plus-MFA login challenge, replay checks, persistent
attempt throttling, one-time recovery codes, account disable, and recovery-code
replacement. A locked offline compile check passes for `zelyra-web` and
`zelyra-cli`. Integration coverage, a drill of the documented operator recovery
procedure, and independent security review are still required; this is not an
RC or a claim of production readiness.

## Explicit exclusions

No WebAuthn/passkeys, OAuth2/OIDC, external identity providers, social login,
mandatory MFA, cloud dependency, remote secret store, telemetry, or phone-home
behavior. No claim of general identity-provider interoperability.

## Release gates

- Positive and negative integration coverage for enrollment, challenge,
  recovery, session restrictions, CSRF, same-origin checks, replay races,
  throttling, key loss, and secret-redacted diagnostics.
- Verify migration behavior for existing users and projects with MFA disabled.
- Complete independent security review of TOTP storage, session transitions,
  recovery codes, throttling, auditing, and administrator recovery.
- Update both language handbooks and the threat model with tested behavior and
  limitations; run the release readiness check before an RC.

## Relationship to 1.0.0

0.9.0 is an optional security capability, not a prerequisite for logging in.
The 1.0.0 release should stabilize the documented language/runtime contract,
resolve release-blocking defects, publish reproducible candidate artifacts,
and receive independent human acceptance. It must not imply WebAuthn/OIDC
support or security certification.
