# Zelyra 1.2.30 — typed schema references for tenant keys

Status: implemented and verified in the active 1.2.30 branch; this focused
schema-reference package does not by itself complete the broader 1.2.30
Laravel workflow milestone. The goal is to represent relational
source columns such as `tenant_id` both as nominally typed Zelyra IDs and as
real database foreign keys. Laravel files and database rows are not copied
into the Zelyra project.

## Goal and bounded source slice

The current Laravel importer emits a `tenant_id` foreign key to `tenants.id`
as the relation `tenant: Tenant`. This preserves the physical foreign key,
but prevents the Zelyra compiler from checking it as the tenant key
`scoped by tenant_id: TenantId`. That makes safe native Forms/CRUD migration
harder.

The language syntax should let a scalar nominal ID column explicitly name its
referenced table:

```zelyra
type TenantId = Id

table customer_groups scoped by tenant_id: TenantId {
    id: Id primary auto
    tenant_id: TenantId required references tenants on_delete cascade
    name: String(100) required
}
```

`references` preserves the actual database foreign key, while `TenantId` and
`scoped by` retain tenant identity for type checking and runtime policy. The
reference target and delete behavior must remain deterministic in DDL plans,
schema inspection, and every supported backend.

## Requirements

- `references <table>` is accepted only for ID-compatible scalar column
  types; existing relation-record types keep their current behavior.
- References resolve to a declared table and its primary key. Invalid targets
  receive stable compiler diagnostics.
- The referenced table does not implicitly choose the Zelyra column type. A
  nominal ID alias remains intact.
- `on_delete` stays explicit; invalid combinations with nullability or tenant
  constraints are rejected.
- MariaDB, PostgreSQL, and SQLite DDL, schema inspection, and migration agree
  on the actual Zelyra foreign key.
- The Laravel importer emits `scoped by tenant_id: TenantId` and
  `tenant_id: TenantId required references tenants ...` only when the static
  migration proves that exact foreign key. Other relations remain unchanged
  or explicitly manual.
- Repeated generation against `/opt/siedelmann-laravel/app` is deterministic
  and read-only. The generator does not execute PHP, read `.env`, or connect
  to the source database.

## Acceptance tests

- Positive and negative parser/typechecker tests for valid ID references,
  unknown tables, missing primary keys, incompatible types, nullability, and
  delete actions.
- DDL-plan tests for MariaDB, PostgreSQL, and SQLite, including preservation
  of the nominal `TenantId` column and the real `tenant_id -> tenants.id`
  constraint.
- Integration test with two tenants: a valid own reference succeeds, an
  invalid target is rejected by the database, and existing scoped relational
  foreign keys remain composite.
- Laravel importer test checks generated customer/group schema against the
  compiler, DDL plan, and static migration evidence. It reads no application
  rows and does not modify `/opt/siedelmann-laravel/app`.

## Verification recorded for this branch

- Parser, type-checker, linker, and DDL unit tests passed. DDL generation is
  covered for MariaDB, PostgreSQL, and SQLite.
- `tests/mariadb-tenant-relations-e2e.sh` now includes a scalar nominal
  `CustomerGroupId? references customer_groups` relation in addition to the
  existing record-typed relation. Against disposable MariaDB 11.8 it accepts
  same-tenant references and rejects cross-tenant references for both forms;
  tenant-local uniqueness checks also pass.
- The actual importer checks against `/opt/siedelmann-laravel/app` are recorded
  in the active progress log. They are static and do not inspect `.env`, open
  the source database, run PHP, or modify the source project.

Laravel `SET NULL` on a composite tenant relation is intentionally reported as
a behavioral difference: clearing both FK columns would erase the required
tenant key. Generated review candidates use `RESTRICT`; a behavior-equivalent
workflow migration remains open.

## Scope boundary

This package does not yet import a complete customer or invoice workflow.
Correct schema mapping is a prerequisite for the next
route/controller/view-to-module slice. Generated schema remains a reviewed
candidate and is never automatically applied to a database.
