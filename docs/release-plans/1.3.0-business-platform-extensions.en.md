# Business-platform extensions through Zelyra 1.3.0

This document turns the local architecture blueprint `/root/5erweiterungen.md` into verifiable
goals that fit Zelyra's actual language and runtime architecture. The blueprint
is a requirements proposal, not evidence that these features exist. Laravel
website migration remains independent, desirable, and deferred.

## Guardrails

- Do not claim tenant leaks are “physically impossible,” full Laravel parity,
  or improved performance without matching tests and measurements.
- Every database and host operation remains subject to static capability
  checks, runtime grants, policies, SQL validation, contracts, and source-mapped
  diagnostics. Raw `sql<T>` must not bypass tenant boundaries.
- New syntax must have consistent semantics across parser, AST/HIR, type
  checking, interpreter, MIR verifier/interpreter, and bytecode verifier/VM.
  A backend that cannot safely support it must reject it instead of silently
  running different semantics.
- The AST interpreter is the reference, not an exception to backend acceptance:
  every language syntax or AST semantic added for these extensions also needs
  a checked MIR and bytecode mapping with source locations, verifier rules,
  serialization where relevant, differential tests, or an explicit
  fail-closed diagnostic in a backend that does not support it yet.
- Network, file, scheduler, queue, and plugin access stays explicit, offline
  capable, resource-bounded, and denied by default. Destructive work requires
  visible approval.

## Work order and acceptance

### A. Request and form pipeline

1. Inventory existing web handlers, forms, auth, CSRF, and error paths as the
   semantic reference.
2. Integrate typed Request/Response contracts and explicit middleware/handler
   binding into the existing Zelyra grammar; do not introduce a parallel router
   language alongside existing routes.
3. Validation failures must preserve field paths and safe permitted inputs and
   render correct redirect/response status through the same renderer.
   Passwords, tokens, and other sensitive fields are never replayed as old
   input.
4. CSRF, authentication, authorization, and rate limits must apply server-side
   before the handler. AST, MIR, and bytecode share checked semantics or reject
   unsupported paths.

**Acceptance:** positive/negative parser and type checks; HTTP integration tests
for success, invalid input, CSRF, missing permissions, and sensitive values;
browser checks for error rendering. Existing Page/CRUD applications remain
compatible.

### B. Typed relational query expressions

1. Design a small schema-bound query HIR with projection, `where`, stable
   ordering, and pagination.
2. Resolve tables, columns, nullability, and output records from the checked
   schema; generate SQL with bound parameters. Do not pass unvalidated runtime
   strings as column names.
3. Add joins only after safe key/cardinality modeling. Automated N+1 avoidance
   or query-planner claims require separate evidence and are not promised yet.
4. State dialect boundaries; MariaDB remains the primary verification path.
   Unsupported backends reject unrepresentable queries.

**Acceptance:** schema-change/refactoring tests, injection negatives, nullability
and type diagnostics, SQL parameter checks, and real MariaDB integration. AST,
MIR, and bytecode agree or fail closed for unsupported query paths. This also
applies to AST and type-system extensions needed for query, request, and tenant
syntax; an AST-only implementation does not count as complete.

### C. Compiler-enforced tenant boundaries

1. Define tenant identity and context as nominal values that cannot be freely
   constructed. A `TenantId = Id` alias or arbitrary request value is not proof
   of authorization.
2. Bind `scoped by` to table metadata and query HIR. Every read/write query
   needs a verified active tenant context; the compiler generates or verifies
   the tenant predicate.
3. Initially reject raw SQL touching scoped tables until a source-mapped SQL
   parser can prove its tenant constraint. Do not use heuristic string scans
   or silent scope injection.
4. Runtime, MIR, and bytecode recheck the tenant context and scope before the
   database host call. Bind tenant IDs; never interpolate them into SQL.
   Background jobs carry explicit tenant context.

**Acceptance:** negative cases for missing, wrong, expired, or backend-mutated
contexts; read/write/join/raw-SQL cases; database tests with two tenants proving
cross-tenant reads and writes are denied. Do not claim a general guarantee over
arbitrary application code.

### D. Durable jobs and scheduler

1. Keep `command` and `schedule` as declarative, statically checked metadata.
   Existing host export remains available for simple deployments.
2. Define a separate versioned job contract for typed payloads, schema versions,
   idempotency keys, attempts, timeouts, retry limits, backoff, and dead-letter
   state.
3. Enqueue jobs in the same validated transaction as business changes. Workers
   claim jobs with leases/locks, bounded batches, and controlled concurrency;
   crashes, lease expiry, duplicates, and retries have deterministic behavior.
4. An integrated `serve` scheduler needs leader/lease protection,
   timezone/DST rules, restart semantics, and auditable run history. It must be
   disableable and must not start workers without explicit configuration.
   Multiple servers must not run the same occurrence without coordination.
5. Mail remains a separate effect. Tests use fake transports; no real mail is
   sent during development or CI.

**Acceptance:** MariaDB integration tests for atomic enqueue/business
transactions, lease contention, process crashes, retry, dead letters,
idempotency, and duplicate scheduler runs. Document operations limits and
provide CLI/Studio status visibility.

### E. Wasm and sidecar extension bridge

1. Stabilize the pure package path, lockfile, checksums, compatibility rules,
   and effect ceilings before dynamic extensions.
2. Evaluate Wasm as an optional, local/offline runtime extension for pure or
   tightly bounded computation. Specify ABI/component contract, memory/fuel/time
   limits, deterministic error mapping, capability imports, and versioning.
   Wasm sandboxing alone is not a security proof.
3. Sidecars are separate, explicitly started processes. Define local IPC/RPC
   transport, peer authentication, protocol version, size/time limits,
   cancellation, errors, and audit. Only approved structured values cross the
   boundary; there is no implicit SQL or credential access.
4. No stable Rust ABI, automatic registry execution, automatic downloads, or
   blanket publisher trust. The first reference integration is a local mock
   driver, with no live bank connection or external credentials.

**Acceptance:** adversarial tests for invalid/incompatible modules, limits,
capability denial, protocol errors, and process crashes; reproducible offline
builds. Do not claim provider banking interoperability without separate real
certification/sandbox tests.

## Stage gates

- **1.2.0:** Semantics/HIR designs for query, request, and tenant context; safe
  query and request foundations; queue/scheduler operating model;
  HostServices/package compatibility contract. No production-readiness claim.
- **1.3.0:** Tested end-to-end vertical slices across AST, MIR, and bytecode (or
  precise fail-closed backend boundaries) for queries, tenancy, requests, and
  durable jobs/schedules. For Wasm/sidecar, at least one versioned,
  sandbox/policy-checked reference slice or a substantiated architectural
  blocker. Pass security and compatibility gates before calling each feature
  complete.

## Additional enterprise work packages through 1.3.0

This section places the six packages in `/root/weitereerweiterungen.md` within
the existing architecture. It supplements the previous five extensions; it
does not replace them. Performance and compliance statements in the source
brief are targets to investigate, not guaranteed properties.

### F. Formal state machines

- **1.1.5:** Compare existing enum, contract, CRUD, outbox, and schema
  semantics against a state-machine design. Specify state identity, legal
  transitions, actor authorization, `requires`, `ensures`, and outbox triggers.
- **1.2.0:** Design parser/HIR representation and stable diagnostics. Managed
  state fields must be distinguishable from ordinary record/SQL writes; an
  incomplete static scan must never classify direct writes as safe.
- **1.3.0:** Deliver a constrained executable transition path: reject illegal
  edges, validate actor authorization and pre/postconditions, and enqueue
  outbox events transactionally. AST, MIR, and bytecode must check identical
  transitions or reject the feature explicitly.

**Acceptance:** positive and negative graph/type/permission/contract tests;
attempted direct writes through assignment, CRUD, SQL, and transactions;
atomic database/outbox integration; concurrent transitions; and AST/MIR/
bytecode differential tests. Helpers such as `transition_to_approved` are
available only when resolved to a checked state machine.

### G. Auditable and bitemporal data

- **1.1.5:** Record audit requirements and database dialect limits; distinguish
  system time from business-valid time.
- **1.2.0:** Review a history/migration design covering retention, actor
  identity, action type, and atomic recording. Existing tables are never
  silently altered; `db plan` must expose every generated change.
- **1.3.0:** Implement a narrow audit vertical slice for supported MariaDB
  paths only. UPDATE/DELETE must be historized in the same transaction or
  safely rejected. `as_of` depends on Query HIR and must define timestamp,
  timezone, and system-versus-valid-time semantics. Technical history alone
  does not establish legal GoBD compliance.

**Acceptance:** UPDATE, DELETE, rollback, crash, concurrency, retention, and
authorization tests; schema plan/apply/drift checks; verification that every
supported write path records history and unsupported paths fail closed.
History tables cannot be bypassed through `sql<T>` or another backend path.

### H. Server-driven reactive UI (LiveUI)

- **1.1.5:** Distinguish the need from existing server-rendered UI, Studio
  event channels, and local asset delivery. Do not introduce a second,
  incompatible WebSocket/SSE protocol without shared security review.
- **1.2.0:** Specify state model, event schema, Origin/session authentication,
  CSRF, reconnect, backpressure, cancellation, and version invalidation.
  Prototype the offline embedded vanilla-JS client; measure the under-15-KB
  goal instead of assuming it.
- **1.3.0:** If the host-server architecture and security model support it,
  implement a bounded reference flow with explicit component handlers,
  session isolation, and minimal typed patches. Do not claim general template
  diffing or sub-millisecond latency without representative load measurements.

**Acceptance:** real browser and keyboard checks, concurrent sessions,
cross-Origin requests, expired sessions, forged events, slow clients,
reconnect, queue/payload limits, and resource use. Project code must not gain
access to privileged Studio APIs or another session's state.

### I. Zero-sum ledger

- **1.1.5:** Document decimal arithmetic, rounding rules, currencies, account
  identity, transaction boundaries, and valid posting models.
- **1.2.0:** Define a typed Ledger HIR contract. Statically known amounts may
  be checked at compile time; dynamic amounts require a runtime invariant
  before commit.
- **1.3.0:** Implement a constrained `Decimal` posting path that is exactly
  balanced before database commit and rolls back the entire transaction on
  imbalance. No floating point or implicit rounding.

**Acceptance:** test signs, precision, boundaries, rounding, multiple
currencies, overflow, missing accounts, intentional imbalance, rollback, and
concurrent postings. AST, MIR, and bytecode must produce the same exact
amounts and commit/rollback state.

### J. Bundled single-binary deployment

- **1.1.5:** Inventory release binaries, assets, `serve`, scheduler, outbox,
  Docker bundles, and cross-compilation targets.
- **1.2.0:** Design `zelyra build --bundle`: supported platforms, embedded
  files, configuration/secrets, database drivers, health/metrics endpoints,
  and reproducible archives. Do not promise static Linux linking without
  toolchain and runtime evidence.
- **1.3.0:** If existing build/server architecture permits, deliver a
  platform-specific prototype with embedded local assets and a health check.
  Automatic migration remains off by default; `--auto-migrate` requires
  explicit opt-in, validated plan, policy checks, and documented failure
  behavior before binding the application port. `/metrics` must not expose
  secrets or personal data.

**Acceptance:** archive/hash/content checks, offline startup, missing and
invalid configuration, migration failure, occupied port, health checks,
reviewed migration preview, and a smoke test for every actually supported
platform. Cross-compilation is not a platform runtime test.

### K. Deterministic architecture export for people and AI agents

- **1.1.5:** Inventory AST/HIR, route, schema, contract, capability, and
  package indexes; define stable JSON field names and source references.
- **1.2.0:** Implement `zelyra reflect --format=json` as a deterministic,
  versioned export of resolved symbols, tables, routes, request/response
  types, validations, and contracts. Do not export secrets or environment
  values; mark unresolved semantics as unknown.
- **1.3.0:** Add Markdown and OpenAPI only for semantically supported
  elements; mark missing state/job/query information as incomplete. The export
  is a derived project view, not an “immutable single source of truth” or a
  substitute for compiler checks.

**Acceptance:** deterministic repeated output, schema versioning,
Unicode/path tests, secret redaction, incomplete/unresolved projects, API
compatibility, and comparison against compiler resolution. Export format
changes require documented versioning.

## Release placement

These six work packages are not equal in size and will not be forced into one
release as if all were complete:

| Version | Commitment |
| --- | --- |
| **1.1.5** | Architecture/semantic contracts, dependency analysis, and clear scope boundaries; continue existing implementation only where verifiable foundation work is possible. |
| **1.2.0** | Parser/HIR/runtime contracts and safe foundations; first deterministic JSON `reflect` export; LiveUI and bundle prototypes only after security review. |
| **1.3.0** | Bounded, tested vertical slices for state machines, audit, ledger, LiveUI, and bundling, plus versioned `reflect` formats; AST/MIR/bytecode parity or an explicit fail-closed boundary. Gates that do not pass remain open and move beyond 1.3.0. |

No general GoBD certification, arbitrary static Linux binary, maximum LiveUI
performance, complete workflow coverage, or trustworthy AI “truth” is claimed
without separate technical and operational evidence.
