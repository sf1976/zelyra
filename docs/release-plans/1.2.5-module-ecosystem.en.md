# Zelyra package ecosystem — 1.2.5 to 1.3.0

Status: active implementation plan. Existing local source modules and offline
path packages remain the compatibility baseline. This document separates
implemented behavior from the work required for a trustworthy distributable
ecosystem.

## Architecture decisions

- Packages contain Zelyra source, typed manifest metadata, and documentation;
  they do not run build scripts or install native code.
- Package resolution and compilation remain local and deterministic after an
  explicit fetch. Runtime use does not require a registry connection.
- Remote package bytes are never accepted based only on an index response or
  transport checksum. A trusted signature must bind the package identity,
  version, compiler-compatibility requirement, and canonical source digest.
- A project owner explicitly configures trusted publishers. Trust setup never
  grants application capabilities.
- The initial registry format should be static-file hostable, replaceable, and
  usable on a private server. No mandatory account, telemetry, or central
  service is introduced.
- No native Rust ABI is a package extension point. WASI/component or local
  sidecar integrations stay in the later 1.2.8/1.3.0 plan and must use
  versioned, capability-checked host interfaces.

## Milestones and acceptance

### 1.2.5 — signed source packages and explicit trust

- Define a bounded, deterministic source-package artifact format and stable
  canonical signature payload.
- Add secure publisher-key creation, package signing, signature verification,
  and a project trust store with explicit add/list/remove commands.
- Add a static registry index format, package discovery, exact-version fetch,
  and safe extraction to a project-local content-addressed package store.
- Bind registry, package identity, exact version, source digest, signer, and
  compatibility requirement in the lockfile. Preserve offline checks and
  execution after installation.
- Update dependencies only through explicit version selection and a reviewed
  lock diff; reject stale, unsigned, incompatible, oversized, malformed, or
  path-escaping artifacts before changing the project.
- Update several installed aliases from one explicit plan: fetch and verify
  all exact releases first, then apply the manifest, lock, and package-cache
  changes together. Detected failures must roll back; process interruption and
  recovery remain separate work. Never select a "latest" version implicitly.
- Add tests for forged/tampered artifacts, untrusted keys, version mismatch,
  archive traversal, interrupted writes, offline rebuild, and missing runtime
  capabilities.

### 1.2.6 — transitive registry packages and recovery

- Resolve separately published transitive dependencies with exact versions,
  independently verified signatures, explicit trust, and per-package
  provenance.
- Integrate multi-level install, lock, offline build, update, removal, and
  bundle operations; reject conflicts and ambiguous aliases before changes.
- Protect transactions against process interruption with a durable recovery
  journal and add failure and recovery tests.

### 1.2.7 — application settings and integration packages

- Provide compiler-checked module settings forms on ordinary application pages
  with revision checks, secret redaction, and no implicit capability grants.
- Establish a bounded, documented HostServices foundation for reusable data
  exchange and ship CSV import/export as installed example packages with safe
  size limits and integration tests.
- Add providers such as ODBC or Excel only after reproducible tests cover
  availability, licensing, platform support, and security behavior.

### 1.2.8 — ecosystem backend and deployment parity

- Execute supported module calls, settings, effects, package locks,
  HostServices, and runtime limits consistently in AST, MIR, and Bytecode, or
  fail closed with stable unsupported diagnostics in every backend.
- Prove recovery, reproducible builds, offline use, package compatibility,
  supply-chain checks, and standalone bundle deployments with integration
  tests.
- Report deployment readiness only after an executed runtime deployment
  check, not from static analysis alone.
- Do not claim a stable plugin ABI, universal driver support, or complete
  deployment without separate conformance evidence.

### 1.3.0 — Bytecode as a verified default

- Keep AST as the reference until all language, SQL, effects, capabilities,
  contracts, resource limits, and host operations required by the 1.3.0
  roadmap have Bytecode evidence.
- Make Bytecode the default only after differential, security, integration, and
  performance checks pass; otherwise AST remains the default.

## Current evidence and limits

The development branch now implements Ed25519 key generation, source-package signing and verification, explicit publisher trust, deterministic static index generation, untrusted metadata search with `package search`, and exact-version `package add`. Installation requires a trusted publisher, HTTPS (loopback HTTP for integration testing), same-origin artifact URLs, bounded responses, signature and digest checks, a compiler-checked source package, and a rollback-protected manifest/lock update. Registry, publisher, key, and artifact digest provenance are recorded in the lock. The CLI package-signature integration suite exercises key non-overwrite, trust rejection/acceptance, tampering, deterministic index output, a two-request loopback download, offline lock verification, and project compilation.

The integration fixture also signs and installs a package-local dependency closure (a nested package manifest plus its source), verifies all three package graph entries lock and compile offline, and creates/checks a deployment bundle after relocating the hidden cache path to portable `packages/<name>/<version>` paths while retaining provenance. Single-alias updates use manifest/lock rollback. `zelyra package update --plan <file.toml>` now supports up to 128 explicitly pinned aliases. All exact registry entries and artifacts are checked before commit; publisher and signing key stay fixed per alias, and total download and runtime are bounded. One transaction stages cache versions, writes the manifest/lock, and compiles the full project. The integration fixture checks two aliases, duplicate aliases, revoked publisher trust, a corrupted digest, a compiler failure caused by the new package API, unchanged manifest/lock/cache on rollback, and a successful update with offline lock validation. `package cache clean` previews unused versions by default and removes only cache roots not referenced by a current lock after symlink checks; its integration case verifies dry-run and apply behavior. Still open: separately published transitive dependencies, ordinary application-page settings forms, integration packages, and broader backend/deployment parity. Studio settings remain local editor configuration. A process interruption is not a cross-file transaction; a stale lock blocks use and must be regenerated after reviewing the manifest. This work does not complete 1.2.5 or the package ecosystem.

An actual Compose runtime smoke exposed that library-only closures could
generate a broken `serve` bundle. `module bundle --docker` now refuses closures
without a web entry before writing; the business application example contains
a real page and bundles its full application entry for Docker. The bundle pinned
to pushed commit `bfc177655edae4e175014bff1aa0baedcc63b192` was built and started
with Compose on 2026-10-17; `GET /` returned the rendered page. The test
container and its Compose network were removed afterward.

Every milestone must update this status with exact tests and known gaps. A
design, format draft, or signed artifact without tested install/verification
behavior does not complete the registry milestone.

## Implemented: coordinated package updates

`zelyra package update --plan <file.toml>` accepts 1 to 128 entries with
unique aliases, registry indexes, package names, and normalized exact SemVer
versions. Unknown fields, duplicate aliases, and duplicate package identity /
version pairs are rejected. Indexes and artifacts are limited to 256 MiB total
download and five minutes; the plan allows at most 16,384 source files. All
signatures, index digests, exact identities, existing publishers/keys, and
local trust grants are checked before active dependencies switch. Existing
cache versions are reused only when their source checksum matches. Detected
download, lock, or compiler errors roll back the manifest, lockfile, and newly
installed cache versions; old versions remain. Abrupt process termination is
not recovered by a persistent journal: an inconsistent lock blocks project
use and can be repaired with `zelyra package lock --update` after reviewing
the manifest. The focused integration test verifies successful updates and
rollback. The original single-alias update command remains compatible.
