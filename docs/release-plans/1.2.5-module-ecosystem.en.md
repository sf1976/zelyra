# Zelyra package ecosystem — 1.2.5 to 1.3.0

Status: active implementation plan. Existing local source modules and offline
path packages remain the compatibility baseline. This document separates
implemented behavior from the work required for a trustworthy distributable
ecosystem.

## Architecture decisions

- Packages contain Zelyra source, typed manifest metadata, and documentation;
  they do not run build scripts or install native code.
- Package resolution and compilation remain local and deterministic after an
  explicit fetch. Runtime use does not require a registry connection.
- Remote package bytes are never accepted based only on an index response or
  transport checksum. A trusted signature must bind the package identity,
  version, compiler-compatibility requirement, and canonical source digest.
- A project owner explicitly configures trusted publishers. Trust setup never
  grants application capabilities.
- The initial registry format should be static-file hostable, replaceable, and
  usable on a private server. No mandatory account, telemetry, or central
  service is introduced.
- No native Rust ABI is a package extension point. WASI/component or local
  sidecar integrations stay in the later 1.2.8/1.3.0 plan and must use
  versioned, capability-checked host interfaces.

## Milestones and acceptance

### 1.2.5 — signed source packages and explicit trust

- Define a bounded, deterministic source-package artifact format and stable
  canonical signature payload.
- Add secure publisher-key creation, package signing, signature verification,
  and a project trust store with explicit add/list/remove commands.
- Add a static registry index format, package discovery, exact-version fetch,
  and safe extraction to a project-local content-addressed package store.
- Bind registry, package identity, exact version, source digest, signer, and
  compatibility requirement in the lockfile. Preserve offline checks and
  execution after installation.
- Update dependencies only through explicit version selection and a reviewed
  lock diff; reject stale, unsigned, incompatible, oversized, malformed, or
  path-escaping artifacts before changing the project.
- Add tests for forged/tampered artifacts, untrusted keys, version mismatch,
  archive traversal, interrupted writes, offline rebuild, and missing runtime
  capabilities.

### 1.2.8 — reusable integrations and configuration

- Provide a compiler-checked module settings form on ordinary application
  pages, with revision checks, secret redaction, and no implicit capability
  grants.
- Add bounded reusable data-exchange packages and a reference database adapter
  behind the shared HostServices contract. Begin with mocks and isolated
  integration fixtures; document provider limitations.
- Make standalone bundle readiness depend on an executed deployment check, not
  only on source closure or static analysis.

### 1.3.0 — backend and release parity

- Keep AST as reference until module calls, settings, effects, package locks,
  HostServices, and runtime limits behave identically in every supported
  backend or fail closed with a stable unsupported diagnostic.
- Prove reproducible builds, offline operation, upgrade recovery, package
  compatibility, supply-chain verification, and supported deployment targets.
- Do not claim a stable plugin ABI, universal driver support, or complete
  deployment before separate conformance evidence exists.

## Current evidence and limits

The development branch now implements Ed25519 key generation, source-package signing and verification, explicit publisher trust, deterministic static index generation, and exact-version `package add`. Installation requires a trusted publisher, HTTPS (loopback HTTP for integration testing), same-origin artifact URLs, bounded responses, signature and digest checks, a compiler-checked source package, and a rollback-protected manifest/lock update. Registry, publisher, key, and artifact digest provenance are recorded in the lock. The CLI package-signature integration suite exercises key non-overwrite, trust rejection/acceptance, tampering, deterministic index output, a two-request loopback download, offline lock verification, and project compilation.

The integration fixture also signs and installs a package-local dependency closure (a nested package manifest plus its source), verifies all three package graph entries lock and compile offline, and creates/checks a deployment bundle after relocating the hidden cache path to portable `packages/<name>/<version>` paths while retaining provenance. Exact single-alias updates and removal use manifest/lock rollback. `package cache clean` previews unused versions by default and removes only cache roots not referenced by a current lock after symlink checks; its integration case verifies dry-run and apply behavior. Still open: fetching independently published transitive dependencies, coordinated multi-package upgrade planning, ordinary application-page settings forms, integration packages, and broader backend/deployment parity. Studio settings remain local editor configuration. The subfeature does not complete 1.2.5 or the package ecosystem.

Every milestone must update this status with exact tests and known gaps. A
design, format draft, or signed artifact without tested install/verification
behavior does not complete the registry milestone.
