# Zelyra 1.2.29 — bounded secure file uploads

Status: active design and implementation package. No `File` form field or
upload API is currently promised by this plan until every release gate below
passes.

## Evidence and user outcome

A read-only static analysis of the current `/opt/siedelmann-laravel/app`
source tree on 2026-10-20 completed with 2,186 findings, 2,738 graph nodes,
1,829 edges (1,828 resolved), and 538 route nodes. It did not execute PHP, read
`.env`, connect to the database, or modify the source. Static source inspection
found upload-related controller flows for invoices, contracts, settings,
postal letters, and inbound mail. The current importer does not generate these
flows. This is evidence of an important migration gap, not evidence that the
workflows have been ported.

The HTTP server now reads a bounded byte request path and passes valid
`multipart/form-data` bodies through the standalone decoder in
`web/src/multipart.rs`. Existing text requests still become the same public
`Request { body: String, ... }` values. Routes without declared file fields
receive HTTP 415 for multipart; malformed
multipart receives HTTP 400. Unsupported `Transfer-Encoding` is rejected
instead of treating chunked bytes as an empty request. The 1 MiB limit remains
for ordinary routes. A matching POST multipart route with declared `File`
fields gets a compiler-derived body ceiling, and a process-wide 256 MiB
in-flight body budget bounds aggregate buffering. Matching POST forms with
declared `File` fields proceed through route authorization and CSRF before the
server validates or stages the bytes.

The parser and Forms checker now accept the staged declaration shape
`field document: File { max_size: "10MB" allowed_types: ["application/pdf"] }`
for standalone forms and table-backed forms whose same-named column is
`FileRef`. They check byte-size units, a 1-byte to 100-MiB declared range, and
the current MIME allowlist (PDF, PNG, JPEG). `File` is rejected in table
columns, records, and form action parameters. Rendering uses a multipart file
control and does not echo filenames into HTML. Each file field requires a
persistence action whose SQL uses that field's named parameter. Server-side
content detection ignores the submitted MIME header and checks the declared
type and size; the browser `accept` attribute is not a security validation.

The first storage primitive now exists in `web/src/file_storage.rs`. On Unix
it stages signature-checked PDF/PNG/JPEG bytes under
`tenants/<numeric-tenant>/<random-uuid>` and publishes the opaque blob with a
private sidecar manifest containing detected media type, byte length, and
SHA-256. The blob and manifest use separate no-replace filesystem links; a
partial publication failure removes either final entry. Verified reads reopen
the manifest and check the blob's size, checksum, and detected type. Tenant-
scoped removal validates both entry types before mutation, then removes the
manifest before the blob so an invalid manifest cannot cause a partial deletion.
Dropping unpublished staging removes both staged files. Tests cover content spoofing, size limits, tampered
manifests, hash mismatch, tenant separation, symlinked paths, partial
publication cleanup, and staging cleanup. Matching POST form routes that
declare `File` fields now use this storage path. After route authorization and
CSRF checks, file bytes are signature-checked against the declared type and
size, then staged; only server-issued UUID references reach validation and SQL
parameters. Successful form actions publish staged files before SQL execution;
validation failures discard staging and failed actions remove published files.
Unscoped projects use project-local storage tenant id `0`; scoped forms require
the authenticated tenant id.
Declared table-backed upload fields now receive a generated download route at
`<crud-path>/{id}/files/{field}`. The route requires an authenticated session
and the CRUD read permission, then selects the reference only from the matching
record under the CRUD tenant, recipient, and active-record conditions. It
serves verified bytes as a private attachment with `nosniff`; unknown fields,
records, missing references, and storage errors return a non-descriptive 404.
The CRUD detail view links to declared uploaded-file fields without exposing
the opaque reference. The MariaDB E2E covers a successful download, headers,
reference redaction, unauthenticated access, and recipient isolation.
This is not crash-atomic across filesystem and database commit: a crash between
publication and SQL commit can leave an orphan. Replacement/deletion and
backup/restore are not implemented.
On non-Unix platforms storage creation
currently fails closed because private ACL handling is not implemented. The
PDF check is a signature check, not PDF sanitization or malware scanning.

`FileRef` is now a checked database scalar for linking future upload forms to
stored blobs: MariaDB maps it to `CHAR(36)`, PostgreSQL to `UUID`, and SQLite
to `TEXT`; it does not create a relation. A checked table-backed `File` field
must match a same-named `FileRef` column, including through a type alias.
Automatic CRUD refuses to render `FileRef` as text, and JSON API input does not
accept the opaque reference. `zelyra files cleanup` now previews old,
unreferenced blobs and abandoned staging pairs by default. It requires a
configured database so references can be checked, scans at most 100,000
generated storage entries and 100,000 database reference rows, and refuses
symlinked or inconsistent paths. An isolated MariaDB E2E confirms that preview
lists only an old orphan, preserves a database-referenced upload, and explicit
apply removes only the orphan pair. The
default age is 30 days; `--min-age-days` accepts 1 through 3650. Deletion
requires both `--apply` and `--maintenance-window`. Upload-enabled Zelyra
servers hold a shared advisory lock for their lifetime; cleanup must obtain a
non-blocking exclusive lock before it rechecks database references and removes
files. A server started during maintenance fails closed. This coordinates
Zelyra processes on the same local host and local filesystem, not unrelated
programs or arbitrary network filesystems. Upload submission
works for matching declared form fields, but replacement/deletion and complete
backup/restore and release acceptance remain open.

On an edit form, an existing authorized `FileRef` now satisfies a required file
field when no new file is selected. The HTML file input remains blank, while a
request-supplied reference is ignored. A disposable MariaDB test covers the
edit GET, signed snapshot, POST without a file, unrelated field update, and
verified read of the original bytes afterward. A later SQL failure still
removes only the newly staged replacement.

User outcome: a developer can declare a bounded file field, accept only
validated content, store it privately with tenant ownership, and provide a
protected download link without allowing the client to choose a filesystem
path. Failed database writes do not leave a reachable file; crashes can leave
only unreferenced files that a safe, explicit cleanup operation can identify.

## Architecture decisions to validate during implementation

- Parse HTTP bodies as bounded bytes. Keep text decoding at the existing
  URL-encoded/JSON boundaries. Reject malformed multipart boundaries, duplicate
  field names where the field is not declared multi-valued, oversized headers,
  excessive part counts, excessive filenames, and any request whose total size
  exceeds the server hard limit.
- Resolve per-route upload limits before accepting a large body. Keep a hard
  global ceiling, bounded concurrent workers, and a separate per-file and
  aggregate-per-request limit. The current server authenticates after reading
  the request body, so route recognition from the bounded header must not by
  itself authorize an unbounded allocation. Reserve from a process-wide
  in-flight body-byte budget before reading; reject requests that exceed the
  route limit or cannot reserve capacity. Keep the ordinary 1 MiB limit for
  routes without declared uploads. Do not buffer unlimited bodies or trust
  `Content-Length` alone.
- Use a finite compiler-checked content-type allowlist and server-side content
  validation. The submitted filename and client-provided MIME type are display
  metadata only. Reject path separators, control characters, invalid UTF-8
  names, executable formats, and unimplemented archive/container formats.
  Initial supported formats must be selected from tested business needs; no
  claim of malware scanning or safe active-document sanitization is allowed.
- Generate cryptographically random opaque file identities. The client never
  selects the storage path or tenant directory. Keep blobs outside `public/`
  and serve them only through an authenticated, authorized resource route.
  Verify that the record, tenant, file identity, and requested permission all
  match on every download.
- Stage to a private temporary file under the same storage filesystem, enforce
  permissions, use create-new/no-follow semantics, hash while writing, fsync,
  then atomically move to a generated final path. Never derive a path from a
  filename, tenant string, or request value.
- Coordinate file publication with the existing database transaction. A
  database failure removes the just-published blob; old-file deletion happens
  only after the replacement transaction commits. A crash may leave an orphan,
  so cleanup must be preview-first, bounded, age-gated, symlink-safe, and
  limited to generated names not referenced by Zelyra metadata. It must never
  recursively erase user-selected directories.
- Backups must include private blobs and matching metadata consistently, or
  report the missing storage component. Restore checksums before making files
  available. Document retention and explicit deletion behavior.
- Hold a process-lifetime shared local advisory lock in upload-enabled `serve`
  processes. Destructive cleanup must take a non-blocking exclusive lock before
  its final reference scan. Servers fail to start while maintenance holds the
  lock. Do not claim coordination with external programs or network filesystems.
- The stored application value must be an opaque file reference, not raw bytes
  or an absolute host path. Decide and test the compiler mapping to the physical
  database type before adding parser syntax. Existing records and string
  fields remain backward compatible.

## Implementation stages

1. Inventory request routing, `Request` body users, form field type checking,
   database transaction boundaries, auth/tenant policy, file serving, backup,
   and path/symlink helpers. Record the exact existing APIs reused.
2. Add a standalone multipart decoder with fuzz/regression tests and a bounded
   byte request representation. Preserve all existing URL-encoded and JSON
   behavior. Reject valid multipart explicitly until the target route declares
   upload support; malformed/over-limit parts fail as bad requests.
3. Add checked `File` field metadata (maximum bytes, allowed detected types,
   optional/multiple semantics) with precise source spans. Reject File fields
   in unsupported schema/API/CRUD contexts instead of silently treating them
   as strings. Do not add an untyped raw-HTML escape.
4. Add private managed storage with opaque references, tenant separation,
   hash verification, transaction-aware staging/cleanup, and preview-only
   orphan inspection/removal.
5. [x] Add permission- and tenant-checked downloads through one documented
   generated route. A guessed file ID cannot bypass record authorization.
6. Integrate multipart fields with generated Forms/CRUD, validation error
   handling, edit preservation, CSRF, and field-specific authorization. File
   inputs must never replay a prior file value. Existing non-upload forms
   remain unchanged.
7. Exercise one target workflow (invoice document or banking CSV) only after
   it has been generated as native Zelyra source, compiler-checked, and run
   against an isolated Zelyra database. The Laravel project remains read-only;
   never send real mail or call payment providers.
8. Document backup/restore, operations, allowed types, size limits, storage
   layout, access policy, cleanup, and unsupported cases in both languages.

## Required tests and release gates

- Multipart parser tests for binary/NUL/invalid UTF-8 payloads, CRLF framing,
  quoted boundaries, duplicate fields, filename attacks, part/header/request
  limits, truncation, and malformed boundaries. Add a bounded fuzz target.
- Positive and negative compiler tests for `File` fields, size bounds, finite
  MIME variants, multi-file semantics, nullability, and invalid contexts.
- End-to-end create/edit tests: valid upload, wrong content, spoofed MIME,
  oversized file and request, traversal filename, unauthenticated request,
  wrong tenant, missing permission, invalid CSRF, invalid ordinary field,
  successful retry, replace existing file, delete record, and rollback after
  a later SQL/audit failure.
- Prove the protected download route checks the owning record, selected tenant,
  and permission, returns safe content headers, and does not reveal absolute
  storage paths. Test symlink replacement and concurrent cleanup attempts.
- Prove a failed database transaction leaves no reachable new reference and
  that cleanup removes only old, unreferenced, Zelyra-generated blobs.
- `tests/mariadb-upload-cleanup-e2e.sh` verifies preview, reference
  preservation, and explicit apply against a disposable MariaDB database.
- Backup/restore test preserves file bytes and metadata or explicitly reports
  an incomplete backup. No test sends real email.
- Run full workspace, browser, MariaDB, PostgreSQL, release artifact, security,
  and documentation gates. Do not claim PostgreSQL upload support unless the
  complete HTTP/storage lifecycle passes there.

## Scope limits

The first release may support a deliberately small set of formats and one file
per field. SVG, ZIP, DOCX/XLSX, arbitrary archive extraction, virus scanning,
remote object stores, public uploads, and multi-file collections remain
unsupported unless their own validation and security tests are completed.
The Laravel importer must classify unsupported upload workflows as manual;
analysis findings do not count as imported behavior.
