# Zelyra 0.9.8 release plan: production-readiness rehearsal

**Status:** planned. This is the stabilization rehearsal before the 0.9.9
feature freeze. It is not human acceptance or production approval.

## Goals

- Advance Studio toward a professional IDE with a complete light appearance
  across the editor, project tree, properties, dialogs, database view, and
  project map. Theme selection must remain consistent across Studio pages, be
  accessible, and persist the user's choice. Keep diagnostics and contextual
  language help available while editing, and prevent large projects from
  making the interface confusing or horizontally clipped.
- Extend the notification center with personal read receipts, recipient-level
  authorization, and bounded retention. Enable safe templates, bounded
  attachments, and optional SMTP delivery only after source, size, escaping,
  and recipient checks. A recipient's records must not be visible or mutable
  by another user through lists, counts, or manipulated IDs.
  Declare ownership in Zelyra with `recipient: user_id` on the CRUD resource.
  Assign the signed-in user automatically on create and scope lists, counts,
  details, and mutations on the server. Add a generated CSRF-protected “mark as
  read” action for unread items; include its read receipt in the same database
  transaction's authentication audit log when one is configured.
- Exercise clean installation, upgrade, rollback, migration, backup, and restore
  on the supported operating systems and the exact promised MariaDB, MySQL,
  and PostgreSQL server matrix.
- Close documentation, dependency/license review, security finding, resource
  bound, secret-redaction, and release artifact gaps. Every remaining finding
  must have an owner and a documented disposition; release blockers stay open.
- Validate the complete 1.0 workflow: create a project, edit it in Studio,
  inspect the database, build relational CRUD, send test mail through a local
  SMTP sink, and use the notification center.
- Measure startup, common CRUD paths, and bounded resource use on reproducible
  fixtures. Publish methods and results without unsupported performance claims.
- Validate bilingual handbook examples, offline documentation, SBOMs,
  attestations, checksums, and the immutable candidate publication process.
- Complete the staged Laravel Migrator scope from 0.9.3–0.9.7. Validate its
  supported Laravel/package matrix, static source evidence and locations,
  route-to-data graph, business/security uncertainty reporting, and separate
  compiler-valid scaffold output. Confirm source files and databases remain
  untouched, reports and output paths cannot overlap the input, and secrets,
  personal records, and production data never appear in artifacts.
  Run generated applications through real CRUD flows on each supported backend,
  including tenant, relation, authorization, transaction, and money fixtures.
  Close Zelyra language/compiler/runtime gaps that block accepted mappings;
  otherwise keep the individual mapping explicitly manual or unsupported.

## Exit criteria

- [ ] The light IDE appearance covers every Studio area, stays consistent
  across navigation and dialogs, supports keyboard operation, and meets checked
  contrast requirements. The selected appearance survives reloads; editor
  diagnostics and help work in both light and dark modes.
- [ ] All rehearsals pass from clean environments with reproducible evidence.
- [ ] Every database workflow promised for 1.0 has an exact server-version
  result and a documented limitation list.
- [ ] Security, dependency, privacy, migration, recovery, and authorization
  findings have verified dispositions; no release blocker remains.
- [ ] The Studio, invoice tutorial, SMTP mail, and notification-center workflows
  work together without mandatory cloud services, external AI, or telemetry.
- [ ] Notification integration runs cover at least two users in one tenant and
  two tenants. Personal read receipts, recipient filters, direct IDs, archive,
  expiry, retries, and optional delivery are negatively tested for other users
  and tenants; `recipient: user_id` must not be exposed as a form field, filter,
  or search field, or be overridden by submitted values. Other CRUDs, forms,
  table views, and SQL routes must not query the protected table directly;
  the only permitted foreign key is the recipient key to the authentication
  user table, and unsafe relation views are rejected. Templates and attachments
  pass size, escaping, source, MIME, and secret-redaction checks.
- [ ] Laravel analysis fixtures cover tenant boundaries, foreign-key relations,
  transactions, decimal money, authorization, files, jobs, and integrations.
  Unsupported and ambiguous behavior is reported for manual work; generated
  scaffolding is clearly separated from verified behavior transfer.
- [ ] Every mapping labeled directly supported has a runnable generated-project
  integration result on its documented backend matrix. Zelyra gaps blocking an
  accepted mapping are fixed or that mapping is explicitly removed from the
  supported set with its reason and evidence.
- [ ] All bilingual documentation and generated handbook exports match shipped
  behavior and their examples pass validation.
- [ ] The 0.9.9 feature freeze scope and evidence checklist are reviewed and
  ready. Independent human acceptance remains reserved for the exact 1.0.0
  candidate.
