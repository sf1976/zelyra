# Project layout and architecture rules through Zelyra 1.3.0

This plan turns `/root/struktur.md` into dependency-ordered work. Its directory
tree and syntax are a target design, not a description of current behavior.
Do not describe these features as implemented until parser, CLI, and
integration tests establish them.

## Design decisions

- The layout is an explicit, versioned profile. Projects without it initially
  retain their current behavior.
- `routes/` holds HTTP entry points, `domain/` business flows, `schema/`
  declarative database definitions, and `assets/` static files. `plugins/`
  becomes standard only if a concrete, secured loading format exists.
- Vertical slices organize reusable modules; they must not create a second,
  incompatible import system beside `pkg:`.
- `use schema::...` and `use domain::...` become syntax only after parser and
  deterministic module index support them. Ambiguity, cycles, relative paths,
  and name conflicts need clear diagnostics.
- Architecture rules inspect resolved symbols, AST/HIR, and file paths. Regex
  is not enough to certify compliance.
- `migrate-layout --check` is read-only first. A write mode needs a preview,
  conflict checks, atomic per-file replacement, a journal, and recovery.

## Stages and dependencies

### 1.1.5 — Inventory and contract

1. Inventory `zelyra.toml`, package manifests, import resolution,
   multi-file projects, `zelyra new`, build/bundle paths, and existing
   route/schema/CRUD declarations.
2. Compare namespace and directory roles with grammar and module architecture;
   document mismatches against the target design.
3. Specify an opt-in profile and backward-compatibility boundary.
   `strict_architecture` applies only when the profile is explicitly enabled
   and valid.

**Gate:** reproducible inventory, configuration schema, and positive/negative
test specification; no changed defaults for legacy projects.

### 1.2.0 — Profile and module foundation

1. Define TOML schema and stable diagnostics for unknown/invalid values; do not
   silently accept unknown keys as validated configuration.
2. Load the profile only when opted in. Schema, domain, route, and asset roots
   stay inside the project; symlinks and nonexistent targets obey the same
   workspace boundaries as other CLI operations.
3. Extend existing package/import resolution with explicit namespaces only if
   the grammar and architecture support them cleanly. Test ambiguity, cycles,
   case sensitivity, and source positions.
4. Make `zelyra new` generate a small, actually checkable project, with no
   stubs or unsupported `router` syntax.

**Gate:** legacy projects remain unchanged; the new profile passes checks;
import failures are deterministic and source-mapped.

### 1.3.0 — Architecture checking and migration

1. **ARCH-001:** Detect route-handler SQL writes when AST/HIR resolves them
   unambiguously. Report dynamic/unresolved cases as unknown, never safe.
2. **ARCH-002:** Check resolved Request/Response/Session/Cookie references in
   domain modules, including import aliases and parameters.
3. **ARCH-003:** Check status-field changes against declared state machines.
   Use `E-STATE-001` only if its documented semantics fit; otherwise specify a
   stable architecture code.
4. `zelyra migrate-layout --check` emits sorted findings with file, source
   span, rule, reason, and candidate destination. Mark a suggestion as
   automatically movable only if it is safe and unambiguous.
5. Generate a starter project only with supported syntax. Bundle assets only
   when build, release packaging, and offline smoke tests prove their presence.

**Gate:** positive/negative tests per rule, legacy compatibility,
symlink/path-traversal boundaries, deterministic `--check` output, and a
generated-project integration test. No multi-file write mode without a
separate rollback/recovery gate.

## Open items

Router, middleware, cron-job, and worker grammar is not settled by the proposal
alone; align it with existing route/command/scheduler declarations. `assets/`
bundling needs platform smoke tests. `plugins/wasm` and sidecars are not
standard features without sandbox, ABI, and trust models. Backend or
compatibility gates that fail move beyond 1.3.0.
