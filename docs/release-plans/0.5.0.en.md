# Zelyra 0.5.0 Release Roadmap

**Status:** planning proposal; no release promise or date · **Verified
upstream baseline (2026-10-03):** stable `v0.3.0`; `v0.4.0` has not been
released.

This roadmap describes a direction for 0.5.0, not delivered functionality.
The published 0.3.0 release and the 0.4.0 plan precede it. Work may
be designed and prototyped early, but no item below is considered accepted
until its release baseline, implementation, tests, docs, and evidence are
reviewed together. A prerelease is not a substitute for those gates.

## Goal

Let people build one coherent business application while Zelyra resolves and
checks its modules automatically. On request, a developer should be able to
select a complete application area and export it as an independently runnable
Docker deployment, without manually copying views, handlers, models, or hidden
shared code.

For example, invoicing, inventory, and asset accounting may be separate
application modules. They may reuse a dedicated, configurable database module,
but must not depend on one another unless that dependency is explicit. When a
module is extracted, Zelyra must include its verified code and runtime
dependencies, or clearly declare a remote service contract. MariaDB remains an
external service by default; a shared connection does not imply safe shared
schema ownership.

## Preconditions

- [x] Final `v0.3.0` is published with its source commit, Linux/Windows
  artifacts, checksums, known limitations, and release evidence. The explicit
  human-study deferral (not a test result) is in the [verification
  record](../release-readiness/0.3.0-final-release-verification-2026-10-03.md).
- [ ] Complete or explicitly rescope the 0.4.0 acceptance gates and publish
  the accepted 0.4.0 baseline. Do not relabel unfinished 0.4.0 work as 0.5.0.
- [ ] Select a reference business application, disposable MariaDB fixture,
  restore procedure, and clean target environment. The complete path must run
  locally without a hosted service or external AI provider.
- [ ] Decide compatibility policy for language syntax, project manifests,
  CLI JSON, generated artifacts, and database plans before changing formats.
- [ ] Maintain a bilingual risk register; map every public promise to a
  repeatable test, artifact, or clearly stated limitation.

**Exit criterion:** a clean machine can reproduce the baseline and acceptance
suite, and each 0.5.0 claim has positive and negative criteria plus a fallback.

## Principles

1. **One authoring project, automatic wiring.** Authors describe domain
   modules; the compiler resolves their dependency graph and checks interfaces.
   Routine wiring must not require hand-maintained container files or copied
   source.
2. **Deployment is an explicit selection.** The normal application remains
   easy to run as a whole. Exporting a module or view is an optional operation
   that includes its complete, verified dependency closure.
3. **Database access is a reusable module.** Business modules use a dedicated
   database interface with explicit configuration and schema ownership. The
   design must distinguish a shared library/module from a separately operated
   database service.
4. **No hidden trust.** Extraction cannot grant capabilities, permissions,
   routes, data access, or schema changes that were not checked in the source
   project.
5. **Local and inspectable by default.** Builds need no cloud account, network
   lookup, telemetry, or AI service. Docker contents and external dependencies
   must be inspectable; secrets never enter an image.

**Experimental precursor in the unreleased 0.4 branch:**
`zelyra module plan <entry> <module>` follows explicit imports and references
recognized by the current static impact graph in a read-only, deterministic
way. This includes known page-to-view/component, page-SQL-to-table,
table-relation, and database-configuration edges; unresolved references are
reported. Dynamic or unmodeled dependencies, runtime, assets, external service
contracts, complete configuration, Docker builds, and independent startup are
not covered. It explicitly sets `complete_deployment` to `false` and satisfies
no 0.5.0 acceptance criterion.

## Milestone 0 — Establish the accepted baseline (P0)

- [ ] Record final 0.3.0 and accepted 0.4.0 commits, artifacts, checksums,
  targets, and residual risks.
- [ ] Freeze a multi-file business application, module graph, MariaDB fixture,
  and interrupted-update/restore scenario as the 0.5 acceptance suite.
- [ ] Specify compatibility and deprecation rules for source, project
  configuration, CLI JSON, generated output, and schema plans.
- [ ] Produce a secret-free project compatibility report listing only
  capabilities verified by the compiler.

**Acceptance:** a clean checkout reproduces the baseline; unsupported project
formats and version changes fail with actionable diagnostics.

## Milestone 1 — Automatic module and database boundaries (P0)

- [ ] Stabilize the supported multi-file module model, visibility, namespaces,
  cycle rules, and diagnostics before promising source compatibility.
- [ ] Design and implement automatic dependency resolution from the application
  entry point through checked public contracts. Record deterministic graph
  output and reject undeclared, ambiguous, cyclic, or out-of-project edges.
- [ ] Define the dedicated database module interface: connection settings are
  independently configurable for each deployable application unit; credentials
  are injected at runtime and never embedded in source or generated images.
- [ ] Define schema ownership and read/write contracts. Invoicing, inventory,
  and asset-accounting modules may share data through the database module but
  cannot silently claim or migrate one another's tables.
- [ ] Carry types, SQL parameter/result checks, capabilities, authorization,
  contracts, and audit obligations across module boundaries.
- [ ] Add positive and negative tests for reusable database access, missing or
  conflicting configuration, unauthorized calls, capability escalation,
  incompatible contracts, and schema ownership conflicts.

**Acceptance:** a multi-module project checks and runs reproducibly. Every
dependency and database boundary is visible in machine-readable project
context; invalid boundaries fail before execution.

## Milestone 2 — Independently deployable application slices (P0)

- [ ] Define deployable units from compiler-resolved module and resource
  dependencies; do not equate a view or source file alone with an application.
- [ ] Include exactly the selected unit's source, transitive modules, views,
  routes, assets, runtime adapters, and generated metadata. Reject incomplete
  or unresolved closures.
- [ ] Keep external services (normally MariaDB, and optionally mail or other
  APIs) as explicit, versioned contracts. Document ports, persistent data,
  required runtime settings, and operational boundaries.
- [ ] Generate a reproducible Docker build and inspectable manifest for a
  selected unit. Never copy secrets into image layers or build logs.
- [ ] Provide a machine-readable export plan before writing files; applying an
  export must not overwrite unrelated user files and must identify every
  output path.
- [ ] Split the reference application into at least two independently runnable
  units. Build and start them on a clean target without the original project.
- [ ] Test versioned service contracts, database schema compatibility,
  authorization, failure behavior, and upgrades between the extracted units.

**Acceptance:** repeated exports are deterministic; each unit builds and starts
independently with no source-project dependency. Missing resources, capabilities,
configuration, or contracts prevent a successful export.

## Milestone 3 — Safe database operations and recovery (P0)

- [ ] Provide bounded connection pools and explicit connection/query timeouts
  for the supported MariaDB runtime. Cancellation must leave a known state.
- [ ] Add versioned schema plans with preconditions, operator approval,
  idempotent re-planning, drift detection, and safe handling of partial
  failures. Never silently remove unmanaged objects.
- [ ] Generate rollback SQL only for proven reversible changes. Otherwise
  identify the change as non-reversible and give tested backup/restore steps.
- [ ] Retry only operations explicitly known to be safe; do not blindly retry
  writes or transactions.
- [ ] Rehearse backup and restore on disposable databases, including an
  interrupted update and repeat execution.
- [ ] Keep SQLite and PostgreSQL claims separate unless their runtime paths
  have equivalent implementation and integration evidence.

**Acceptance:** an operator can inspect, approve, interrupt, re-plan, and
recover a disposable database change using documented commands. Unknown state
is never reported as success.

## Milestone 4 — Reference business application (P0)

- [ ] Deliver a multi-file inventory/order reference app with relations,
  transactions, search/filtering, forms, CRUD, roles, and audit.
- [ ] Make browser and API requests use the same business validation,
  authorization, and transaction rules.
- [ ] Detect concurrent edits or expose an explicit conflict; do not silently
  overwrite a newer record.
- [ ] Standardize localizable field and cross-field validation errors without
  exposing database internals or secrets.
- [ ] Document a fresh local setup, database initialization, module operation,
  Docker extraction, update, backup, and recovery.
- [ ] Run a recorded acceptance session with a person who does not develop
  Zelyra and resolve observed blockers.

**Acceptance:** positive and negative CRUD, authorization, invalid-input,
concurrent-edit, schema-update, independent deployment, and recovery scenarios
are repeatable on a clean environment.

## Milestone 5 — Accounts, APIs, and external effects (P1)

- [ ] If not already accepted in 0.4.0, add expiring, single-use, hash-only
  password reset tokens and generic responses that prevent account enumeration.
- [ ] Support individual session revocation, safe key rotation, and clearly
  documented expiry behavior.
- [ ] Add bounded, configurable rate limits for login, reset, and write APIs;
  state the storage and multi-instance limitations.
- [ ] Add API versions and correlation identifiers that contain no user data
  or secrets, plus explicit deprecation behavior.
- [ ] Add email and jobs only behind explicit, checked effects and runtime
  grants. Specify payload limits, idempotency, retries, cancellation, and
  dead-letter handling before claiming delivery guarantees.
- [ ] Keep transports replaceable and locally testable; no external mail or AI
  provider is required for development.

**Acceptance:** negative replay, enumeration, CSRF, revocation, quota,
capability, cancellation, and duplicate-delivery cases are covered.

## Milestone 6 — Tooling, security, and distribution (P1)

- [ ] Provide local editor diagnostics and navigation tied to the compiler
  version; do not require a hosted language service.
- [ ] Fuzz or property-test parser, module resolver, SQL binder, HTML renderer,
  and HTTP parser with bounded, recorded runs.
- [ ] Review dependencies and produce SBOM and provenance for release artifacts;
  document exactly what those attestations do and do not prove.
- [ ] Verify installers, checksums, archive safety, update, and rollback paths
  for each published platform.
- [ ] Automate keyboard, focus, label, and language checks for generated web
  interfaces before claiming accessibility coverage.
- [ ] Add a platform to the support matrix only after native build and smoke
  evidence exists for it.

## 0.5.0 release gates

- [ ] Final 0.3.0 and accepted 0.4.0 baselines are published and residual risks
  are classified.
- [ ] Every P0 item is complete or explicitly removed from 0.5.0 scope before
  starting a release candidate.
- [ ] At least two application units from the reference project build and run
  independently in Docker on a clean target.
- [ ] Database ownership, external service contracts, compatibility, backup,
  restore, and update behavior have end-to-end evidence.
- [ ] MariaDB compatibility matches the executed version matrix; SQLite and
  PostgreSQL runtime parity is not implied.
- [ ] German/English documentation, security review, dependency review, and
  residual-risk register agree with the shipped behavior.
- [ ] Human acceptance and release artifact, checksum, update, and rollback
  checks pass against the exact candidate commit.
- [ ] Publish `v0.5.0` only after all mandatory gates pass. Otherwise retain a
  clearly labeled prerelease or defer the release.

## Deferred unless separately accepted

Full PostgreSQL/MySQL runtime parity, multi-tenancy, OIDC/WebAuthn, a visual
drag-and-drop designer, compiler self-hosting, general formal proof, and
performance guarantees are not implied by this roadmap. Every new inclusion
requires separate scope, risk, implementation, and acceptance decisions.
