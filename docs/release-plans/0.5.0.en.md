# Zelyra 0.5.0 Release Roadmap

**Status:** active technical preparation on `release/0.5.0-human-acceptance-prep`; no release promise or date · **Verified
upstream baseline (2026-10-10):** stable `v0.4.0` at
`507c29e95084a59029d6b436bd69d9132c3a8937`.

This roadmap records 0.5.0 scope, not delivered functionality. The published
0.4.0 release precedes it. Its technical gates passed; the independent human
onboarding study was explicitly deferred to mandatory 0.5.0 acceptance. Work may
be designed and prototyped early, but no item below is considered accepted
until its release baseline, implementation, tests, docs, and evidence are
reviewed together. A prerelease is not a substitute for those gates.

## Goal

Let people build one coherent business application while Zelyra resolves and
checks its modules automatically. On request, a developer should be able to
select a complete application area and export it as an independently runnable
Docker deployment, without manually copying views, handlers, models, or hidden
shared code.

For example, invoicing, inventory, and asset accounting may be separate
application modules. They may reuse a dedicated, configurable database module,
but must not depend on one another unless that dependency is explicit. When a
module is extracted, Zelyra must include its verified code and runtime
dependencies, or clearly declare a remote service contract. MariaDB remains an
external service by default; a shared connection does not imply safe shared
schema ownership.

## Principles

1. **One authoring project, automatic wiring.** Authors describe domain
   modules; the compiler resolves their dependency graph and checks interfaces.
   Routine wiring must not require hand-maintained container files or copied
   source.
2. **Deployment is an explicit selection.** The normal application remains
   easy to run as a whole. Exporting a module or view is an optional operation
   that includes its complete, verified dependency closure.
3. **Database access is a reusable module.** Business modules use a dedicated
   database interface with explicit configuration and schema ownership. The
   design must distinguish a shared library/module from a separately operated
   database service.
4. **No hidden trust.** Extraction cannot grant capabilities, permissions,
   routes, data access, or schema changes that were not checked in the source
   project.
5. **Local and inspectable by default.** Builds need no cloud account, network
   lookup, telemetry, or AI service. Docker contents and external dependencies
   must be inspectable; secrets never enter an image.

**Experimental capabilities included in the published 0.4.0 baseline:**
`zelyra module plan <entry> <module-or-resource-id>` follows explicit imports
and references recognized by the current static impact graph in a read-only,
deterministic way. This includes known page-to-view/component, page-SQL and
form/CRUD-action SQL-to-table, API-handler-to-function, type references from
API fields, function signatures and bodies (including explicit local types,
record literals, and SQL result types), records, and aliases (including aliases
referenced by table columns and typed resource fields), protected-resource-to-authentication,
authentication-to-table, table-relation,
and database-configuration edges; unresolved references are reported.
The selection may be a source module or a supported page/API/CRUD/form/tableview
resource ID. Resource selection starts at its owning source module and still
includes every declaration in that file; it does not yet extract a resource-only
application or define a deployable unit. `modules[].declarations` lists the
recognized declarations per source file in stable order so that co-located
declarations are visible before a future export. `declaration_closure` also
separates statically reachable declarations from additional declarations in
included files; `configuration_edges` reports database configuration
separately. `database.configurations` lists the backend, logical database name,
source file, and `DATABASE_URL` for declarations in the closure. The runtime
still supports only one project-wide connection; a named, independently
configurable database interface is not implemented. The graph is explicitly
incomplete. Dynamic or unmodeled dependencies,
runtime, assets, external service contracts, complete configuration, Docker
builds, and independent startup are not covered. It explicitly sets
`complete_deployment` to `false` and satisfies no 0.5.0 acceptance criterion.
The branch also has `zelyra module bundle` with an experimental
`--docker --compiler-ref <40-character-commit>` option. It generates a
Dockerfile, a Compose app, `.env.example`, and a build that fetches the
compiler from an exactly pinned public commit. Each exported Compose app gets
its own `DATABASE_URL`; MariaDB remains external. The bundle manifest marks
the scope as `per_exported_compose_project` in
`docker.database_connection_scope`. An integration test checks that bundles
for two CRUD modules each contain separate database configuration and only
their selected module source. The Docker end-to-end test starts both CRUD
packages separately and reads one row from each from its own, separately
provisioned schema (`zelyra_invoice` and `zelyra_inventory`). Each app receives
the matching `DATABASE_URL` and a distinct MariaDB user with read-only access
to its table. Both schemas still live on the same MariaDB server in this test.
The images include `mariadb-client` as the current runtime adapter; MariaDB
remains a separate service. This remains one
connection per application unit; multiple named connections in one process
and a runtime-checked database interface are not implemented. This is bounded
runtime evidence for separate app configurations and these two CRUD modules,
not a split of the complete
business application or proof of complete extraction: the manifest keeps
`source_closure_complete` and
`complete_deployment` false because unmodeled runtime and asset dependencies
may remain. A separately named, deployable database interface inside a
composed application is also not implemented yet. Multiple database
definitions are rejected with `E-DB-001` before a bundle writes files. This is
a development precursor, not a delivered 0.5.0 capability or acceptance
result.

**Pinned Docker rehearsal:** on 2026-10-10,
`tests/generated-project-docker-e2e.sh` passed on a fresh generated project
using preparation source `c978008`.
The application runtime and both exported-image compilers were pinned to the
published 0.4.0 commit `507c29e95084a59029d6b436bd69d9132c3a8937`. The test
started the generated application twice through `setup --all`, exercised the
customer/order workflow including stale-edit `409` and invalid-relation `422`
responses, then exported invoice and inventory as separate Docker apps and
passed writable CRUD and negative permission checks. This is bounded evidence
for these fixtures; it does not prove arbitrary closure completeness,
schema-update recovery, authorization, or full P0 reference-app acceptance.

**Additional experimental progress:** `zelyra module bundle --dry-run` now
validates a candidate package in a temporary staging directory and emits a
deterministic JSON list of every planned relative file and destination path.
The requested destination remains absent, secrets are excluded, and the
temporary package is removed. Locale JSON files are sorted before being
recorded in the bundle manifest, and an integration test builds the same
locale-bearing package twice and compares every output file byte for byte.
Both completeness flags remain false. This advances the inspect-before-write
and reproducibility requirements but does not prove that the selected
dependency closure is complete or make export an accepted 0.5.0 capability.

**0.5.0 preparation progress:** `zelyra module plan` now emits a deterministic
inventory of explicitly declared function capabilities in the included source
modules. It identifies `FileSystem`, `Network`, `Process`, and `Environment`
capabilities as deployment blockers when their file scope, service contract,
process dependencies, or variable names are not declared, and reports
unresolved static references separately. `deployment_readiness.ready` remains
false. This inventory is intentionally not a complete effect proof: implicit
resource effects and complete service contracts still need modeling. For auth
modules with password-reset tables, the plan now records the public base URL,
SMTP variables, encrypted-outbox key, secret variable names, and at-least-once
delivery semantics, 30-second retry delay, and possible duplicate delivery
under contract version 1. Generated Docker `.env.example` files include these
configuration placeholders with the existing `implicit_tls`/465 default and
key generation guidance; no credentials are copied. The bundle manifest now
carries the same runtime effects, external contracts, and readiness blockers
as the plan, so undeclared effects remain visible after export. A focused
regression test and all 47 module-import integration tests pass.
For selected non-entry modules, bundle creation also synthesizes the entry
file's required empty `fn main()`; a regression test checks the generated
source package with `zelyra check` while preserving runtime blockers in its
manifest.

**Additional experimental progress:** generated MariaDB projects in the
published 0.4.0 baseline place the database declaration in the importable
`src/database.zyl` module, explicitly imported by `main.zyl`. This gives new
projects a dedicated source boundary, but not a multi-connection database
interface within a process: the runtime still supports exactly one
project-wide database connection.

**Additional experimental increment:** The name of a single database
declaration now selects its preferred runtime variable:
`database main { ... }` uses `ZELYRA_DATABASE_MAIN_URL`. CLI execution, web
serving, database, doctor, auth-role, and audit commands, plus Docker bundles,
use this variable; `DATABASE_URL` remains a backwards-compatible fallback.
`.env` files use the same precedence with `doctor --env-file` and the setup
assistant. The project still accepts only one database declaration and one
connection per process. This name mapping does not implement multiple
simultaneous connections, table ownership, schema permissions, or a
runtime-checked module interface. The bundle manifest and Docker end-to-end
test check the explicit variable; invoice and inventory still run as separate
application processes.

**Additional experimental increment:** views and components in the published
0.4.0 baseline accept `pub`. Cross-module page/CRUD layout references and
recognized component tags in page, view, component, and CRUD slot HTML require
both a public declaration and an explicit direct or transitive import path.
Private UI references report `E-MOD-007`; missing import edges report `E-MOD-020`.
Integration tests cover exported and private UI declarations, missing edges,
context export metadata, and rendering. Component discovery scans known tag
names in HTML strings; this is not a full HTML AST or a complete namespace
system. It advances the visibility slice of milestone 1 but does not complete
its module-contract, database-ownership, or deployment requirements.

**Additional experimental progress:**
`tests/mariadb-backup-restore-e2e.sh` rehearses a dump and restore using a
read-only source account, a separate disposable target database, a restore
account scoped to that target, and backup-file mode `0600`. It also checks
that a failure before publication does not leave a final-looking backup name.
The smoke test passed locally against MariaDB 10.11.19, 11.4.13, 11.8.9, and
12.3.3. The final tagged CI run passed this test. Separately, on 2026-10-10,
`bash tests/schema-safety-e2e.sh` passed against SQLite and a fresh disposable
MariaDB 11.4 container. It killed Zelyra between DDL steps and while DDL waited
on a metadata lock, verified interrupted history, then recovered by applying a
fresh plan and checking for no remaining changes. It also required explicit
approval for reverse DDL and verified unrelated rows remained. This bounded
test does not cover a MariaDB server failure after DDL commit but before the
journal update, concurrent application writes, or production backup/recovery
guarantees. On 2026-10-10 at source `5680c8e`, both
`bash tests/schema-safety-e2e.sh` and `bash tests/mariadb-backup-restore-e2e.sh`
passed again against fresh disposable MariaDB 11 databases; the first also
passed SQLite. They remain separate rehearsals: interrupted-update recovery
has not yet been followed by backup/restore in one clean-target run. These
acceptance cases remain open.

**Multi-file reference slice:** `examples/customer_orders_modules/` separates
the customer, order, reporting, UI, and database modules. Orders refer to the
customer record through an explicit module import; reporting has explicit
read-only table grants. An integration test checks the application and verifies
that the reporting plan includes the customer, order, and database modules with
no unresolved references. The Docker rehearsal also creates and updates a
customer, checks stale-edit rejection, creates an order for that customer,
rejects an unknown customer ID, and renders the report. Authorization, schema
update, export of this specific slice, and restore are not yet joined in one
repeatable workflow.

## Milestone 1 — Automatic module and database boundaries (P0)

- [ ] Stabilize the supported multi-file module model, visibility, namespaces,
  cycle rules, and diagnostics before promising source compatibility.
- [ ] Design and implement automatic dependency resolution from the application
  entry point through checked public contracts. Record deterministic graph
  output and reject undeclared, ambiguous, cyclic, or out-of-project edges.
- [ ] Define the dedicated database module interface: connection settings are
  independently configurable for each deployable application unit; credentials
  are injected at runtime and never embedded in source or generated images.
- [ ] Define schema ownership and read/write contracts. Invoicing, inventory,
  and asset-accounting modules may share data through the database module but
  cannot silently claim or migrate one another's tables.
- [ ] Carry types, SQL parameter/result checks, capabilities, authorization,
  contracts, and audit obligations across module boundaries.
- [🧪] Add positive and negative tests for reusable database access, missing or
  conflicting configuration, unauthorized calls, capability escalation,
  incompatible contracts, and schema ownership conflicts. Positive and
  negative tests now cover the explicit import-closure requirement for
  recognized cross-module table use and explicit table-level `read`, `write`,
  and `read_write` grants for recognized SQL and generated CRUD access.
  Capability escalation, complete contract compatibility, and schema-change
  permissions remain open.

**Experimental intermediate step on the 0.4 development branch:** the module
plan now reports observed SQL read/write modes and table owners inferred from
declaration source files. The compiler also rejects recognized cross-module
table references unless the table-owner module is reachable through the
consumer's declared imports (`E-MOD-019`), including tables declared in the
entry module. Shared schema declarations therefore need their own importable
module. Tables in the published 0.4.0 baseline can also declare
`access { read: [...], write: [...], read_write: [...] }`; recognized access
without a matching module-path grant fails with `E-MOD-021`. CRUD, form,
authentication, and unknown SQL access require `read_write`. This is a
compiler contract, not a MariaDB permission. Analysis remains conservative and
incomplete; `schema_ownership.enforced` remains `false`, and schema-change
permissions are not enforced. This does not meet the milestone's complete
schema-ownership or read/write-contract acceptance criteria.

**Further experimental runtime step:** the internal MariaDB pool cache can
now retain up to eight distinct connection URLs and reuse a pool per URL. It
stores only SHA-256 URL fingerprints as cache keys; changing timeout or TLS
settings for the same URL is rejected while the process is running. Tests cover
profile isolation, reuse, and the bound. This does not enable multiple database
declarations: `zelyra` still rejects more than one declaration in a project
graph, and the interpreter still receives only one selected project URL.
Language-level connection selection, query routing, and an integration test
using multiple databases simultaneously are still missing. This cache step does
not satisfy the database-interface criterion.

**Experimental module contract:** `zelyra check` now requires SQL functions
and database-backed resources to have a direct or transitive import path to the
database provider (`E-MOD-022`). An import declared only by the entry module is
not inherited sideways; the provider declaration must move into an importable
module such as `src/database.zyl`. Positive tests cover direct/transitive
imports, and negative tests cover an entry-only import. This binds the source
graph but does not configure a runtime connection or prove independent module
deployments.

`zelyra context --format=json` now reports the boundary explicitly: provider
module, database-consuming modules, direct/transitive import resolution, and
the runtime variable name and `DATABASE_URL` fallback. Credentials are
excluded; runtime remains one connection per process. This makes the database boundary machine-readable but
does not implement multi-connection routing or complete schema ownership.

**Acceptance:** a multi-module project checks and runs reproducibly. Every
dependency and database boundary is visible in machine-readable project
context; invalid boundaries fail before execution.

## Milestone 2 — Independently deployable application slices (P0)

- [ ] Define deployable units from compiler-resolved module and resource
  dependencies; do not equate a view or source file alone with an application.
- [ ] Include exactly the selected unit's source, transitive modules, views,
  routes, assets, runtime adapters, and generated metadata. Reject incomplete
  or unresolved closures.
- [ ] Keep external services (normally MariaDB, and optionally mail or other
  APIs) as explicit, versioned contracts. Document ports, persistent data,
  required runtime settings, and operational boundaries.
- [ ] Generate a reproducible Docker build and inspectable manifest for a
  selected unit. Never copy secrets into image layers or build logs.
- [🧪] Provide a machine-readable export plan before writing files; applying an
  export must not overwrite unrelated user files and must identify every
  output path. `module bundle --dry-run` now previews a sorted file inventory
  without creating the requested destination; completeness and deployment
  remain explicitly unproven.
- [ ] Split the reference application into at least two independently runnable
  units. Build and start them on a clean target without the original project.
- [ ] Test versioned service contracts, database schema compatibility,
  authorization, failure behavior, and upgrades between the extracted units.

**Further experimental analysis step:** `module plan` now includes function
calls inside form and CRUD actions in the resource and declaration graphs. An
integration test selects a form calling an imported helper and a CRUD calling a
second helper, and checks both edges and their owning source module. It also
tracks named type aliases referenced by table columns and includes the alias
declaration when planning the schema module, covered by a multi-module
regression test. Typed fields on forms, form actions, and CRUD actions now
produce the same type edges; an integration test checks the form and CRUD
resource plans. Function-body annotations, record constructors, and SQL result
types also contribute type edges. MariaDB SQL result mapping accepts
module-qualified record names by removing the module qualifier before
matching its backing table. Focused tests cover this resolver and a composed
project using imported types in local annotations, record literals, and SQL
result types. Unmodeled dependencies, assets, runtime adapters, and
configuration remain open. `complete_deployment` remains `false`, and the 0.5
acceptance criteria are not met.

**Acceptance:** repeated exports are deterministic; each unit builds and starts
independently with no source-project dependency. Missing resources, capabilities,
configuration, or contracts prevent a successful export.

## Milestone 3 — Safe database operations and recovery (P0)

- [ ] Provide bounded connection pools and explicit connection/query timeouts
  for the supported MariaDB runtime. Cancellation must leave a known state.
- [ ] Add versioned schema plans with preconditions, operator approval,
  idempotent re-planning, drift detection, and safe handling of partial
  failures. Never silently remove unmanaged objects.
- [ ] Generate rollback SQL only for proven reversible changes. Otherwise
  identify the change as non-reversible and give tested backup/restore steps.
- [ ] Retry only operations explicitly known to be safe; do not blindly retry
  writes or transactions.
- [ ] Rehearse backup and restore on disposable databases, including an
  interrupted update and repeat execution.
- [ ] Keep SQLite and PostgreSQL claims separate unless their runtime paths
  have equivalent implementation and integration evidence.

**Acceptance:** an operator can inspect, approve, interrupt, re-plan, and
recover a disposable database change using documented commands. Unknown state
is never reported as success.

## Milestone 4 — Reference business application (P0)

- [ ] Deliver a multi-file inventory/order reference app with relations,
  transactions, search/filtering, forms, CRUD, roles, and audit.
- [ ] Make browser and API requests use the same business validation,
  authorization, and transaction rules.
- [🧪] Detect concurrent edits or expose an explicit conflict; do not silently
  overwrite a newer record.
- [ ] Standardize localizable field and cross-field validation errors without
  exposing database internals or secrets.
- [ ] Document a fresh local setup, database initialization, module operation,
  Docker extraction, update, backup, and recovery.
- [ ] Run a recorded acceptance session with a person who does not develop
  Zelyra and resolve observed blockers.

**Experimental concurrent-edit guard:** edit forms whose name ends in `Edit`
carry an HMAC snapshot bound to the form's CSRF key. Submission locks the
database row and compares the snapshot before executing form and audit SQL in
the same transaction. Stale submissions return `409 Conflict`. Unit tests
cover signature binding and missing/modified snapshots; the Docker rehearsal
passed on 2026-10-10 at commit `c978008`. It makes two submissions from one
snapshot and verifies that the second is rejected without changing the newer
value, for the generated app, customer workflow, and both exported CRUD
fixtures. This remains scoped to the form path and is not yet accepted as an
application-wide concurrency contract.

**Separate authorization rehearsal:** on 2026-10-10,
`tests/generated-project-machine-auth-e2e.sh` passed at preparation source
`afc844a` against a fresh disposable MariaDB. It checked anonymous denial,
login, allowed search and CRUD, viewer denial for create/edit, and authorized
edit/delete. This does not join authorization to the customer/order workflow;
that combined reference-app gate remains open.

**Acceptance:** positive and negative CRUD, authorization, invalid-input,
concurrent-edit, schema-update, independent deployment, and recovery scenarios
are repeatable on a clean environment.

## Milestone 5 — Accounts, APIs, and external effects (P1)

- [ ] If not already accepted in 0.4.0, add expiring, single-use, hash-only
  password reset tokens and generic responses that prevent account enumeration.
- [ ] Support individual session revocation, safe key rotation, and clearly
  documented expiry behavior.
- [ ] Add bounded, configurable rate limits for login, reset, and write APIs;
  state the storage and multi-instance limitations.
- [ ] Add API versions and correlation identifiers that contain no user data
  or secrets, plus explicit deprecation behavior.
- [ ] Add email and jobs only behind explicit, checked effects and runtime
  grants. Specify payload limits, idempotency, retries, cancellation, and
  dead-letter handling before claiming delivery guarantees.
- [ ] Keep transports replaceable and locally testable; no external mail or AI
  provider is required for development.

**Acceptance:** negative replay, enumeration, CSRF, revocation, quota,
capability, cancellation, and duplicate-delivery cases are covered.

## Carried human acceptance gate

The independent human acceptance deferred from 0.4.0 is mandatory for 0.5.0. The deferral record is not acceptance evidence. Before the final 0.5.0 release, a non-developer participant must complete the onboarding protocol against the exact published candidate; record the commit, date, redacted observations, blockers, and explicit owner decision. Do not defer this gate again without a new, explicit project-owner scope decision and a replacement release target.

## 0.5.0 release gates

- [ ] Final 0.3.0 and accepted 0.4.0 baselines are published and residual risks
  are classified.
- [ ] Every P0 item is complete or explicitly removed from 0.5.0 scope before
  starting a release candidate.
- [ ] At least two application units from the reference project build and run
  independently in Docker on a clean target.
- [ ] Database ownership, external service contracts, compatibility, backup,
  restore, and update behavior have end-to-end evidence.
- [ ] MariaDB compatibility matches the executed version matrix; SQLite and
  PostgreSQL runtime parity is not implied.
- [ ] German/English documentation, security review, dependency review, and
  residual-risk register agree with the shipped behavior.
- [ ] Independent human acceptance by a non-developer. Complete the 0.5.0
  onboarding study against the exact published candidate and record the
  commit, date, redacted observations, blockers, and owner decision in the
  [acceptance record](../release-readiness/0.5.0-human-acceptance.en.md).
- [ ] Release artifacts, checksums, update, and rollback verification pass
  against the exact candidate. Publish a prerelease candidate before the human
  study; do not publish stable `v0.5.0` until the acceptance record is complete.
- [ ] Publish `v0.5.0` only after all mandatory gates pass. Otherwise retain a
  clearly labeled prerelease or defer the release.

## Deferred unless separately accepted

Full PostgreSQL/MySQL runtime parity, multi-tenancy, OIDC/WebAuthn, a visual
drag-and-drop designer, compiler self-hosting, general formal proof, and
performance guarantees are not implied by this roadmap. Every new inclusion
requires separate scope, risk, implementation, and acceptance decisions.
