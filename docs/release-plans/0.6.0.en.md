# Zelyra 0.6.0 Release Roadmap

**Status:** implementation in progress on `release/0.6.0`; no release promise.
**Prerequisite:** 0.5.0 is published and has passed independent human
acceptance. This branch plans the next step; it does not declare 0.5.0
published or accepted.

## Goal

Add a bounded PostgreSQL runtime for selected, documented Zelyra database
workflows. PostgreSQL schema inspection and changes already exist; runtime
schema inspection and changes already exist. The new direct SQL API is native
and pooled; schema inspection and other web/database paths still start `psql`
as an external process. 0.6.0 will test a direct `sql<T>` CRUD workflow end to
end without claiming complete PostgreSQL parity. Generated web/CRUD paths are
explicitly deferred.

## Scope and acceptance criteria

The first implementation step adds a pooled PostgreSQL API to the database
crate. The synchronous Zelyra runtime routes direct SQL queries and transaction
batches to it based on the URL. The API uses Rustls, named parameters, bounded
scalar result values, transactions, and existing database limits. Generated
web/CRUD paths do not use it yet. It has been tested against PostgreSQL 16
locally, including TLS with a private test CA and hostname verification; the CI
run is still pending. Results are returned as strings; supported types are
bool, int2/int4/int8, float4/float8, text, varchar, bpchar, and name. Other
PostgreSQL result types fail with a diagnostic. 0.5.0 remains a prerequisite
for merging and release.

- [x] Define data sources, pool/timeout limits, and TLS rules. Credentials
  remain in runtime configuration; TLS trust and hostname checks have passed a
  local PostgreSQL 16 test. Request cancellation remains open.
- [x] Integrate a native PostgreSQL connection into the synchronous runtime:
  direct SQL queries and transaction batches use the native pool; other
  application and web paths still start external `psql` processes.
- [x] Implement parameterized queries, scalar results, and explicit
  transactions for a bounded subset; direct `sql<T>` CRUD and rollback pass a
  local PostgreSQL 16 test. Dialect limits and additional result types remain
  open.
- [~] Bounded pools, connection limits, and statement timeouts are implemented;
  local PostgreSQL 16 tests pass. The new CI integration step is configured
  but has not run. A size-one pool now verifies bounded exhaustion wait and
  recovery; HTTP request cancellation remains to verify.
- [ ] Run the PostgreSQL 16 CI integration and extend the compatibility matrix
  with exact workflows and known limits. Do not claim a version or SQL feature
  as supported without a test.
- [ ] Pass MariaDB regression, Linux/Windows builds, SBOM, and dependency
  review. Changes to published CLI/project formats need migration tests.

## Explicitly out of scope

Complete PostgreSQL runtime parity is larger than one release. MySQL Server,
SQL Server, and a universal SQL dialect are not included. Zelyra will document
shared typed SQL capabilities and backend-specific limits instead. SQLite
remains a separate, bounded backend path.

Multi-tenancy, tenant context and tenant-aware authorization, a general
job/queue platform, a transactional outbox for arbitrary effects, MFA/WebAuthn,
OAuth2/OIDC, a full visual editor, arbitrary client hydration,
compiler self-hosting, general formal verification, and a native backend are
outside 0.6.0.

Cloud accounts, external AI services, telemetry, and unsupported performance
claims remain excluded. External network access must be explicit, reviewable,
and optional.

## Later version path

- **0.7.0 — Tenant context:** only after a dedicated threat model. First test a
  server-derived tenant context and fail-closed authorization in a bounded
  database path; never trust an unverified tenant ID from a form or request.
- **0.8.0 — Durable tasks:** a bounded local worker/queue interface and
  transactional outbox with retry, idempotency, cancellation, retention, and
  crash-recovery contracts. Do not promise a general distributed job platform.
- **0.9.0 — Strong authentication and federation:** WebAuthn/MFA and optional
  OAuth2/OIDC only after protocol, key, recovery, and account-linking review;
  development and local operation remain possible without an external identity
  provider.
- **1.0.0 — Stabilization:** frozen language, CLI, project, and runtime
  contracts; completed compatibility and security evidence; migration guidance;
  and independent human acceptance of a release-ready candidate. This does not
  replace the 0.5.0 human acceptance.

This sequence is prioritized planning, not a guarantee. Reassess evidence,
risks, and scope after each release candidate.
