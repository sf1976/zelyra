# Zelyra 0.6.0 Release Roadmap

**Status:** feature implementation merged; 0.6.0 version candidate prepared. Candidate CI and immutable release artifact verification are pending.
**Prerequisite:** stable 0.5.0 is published. Independent human acceptance is
deferred to 1.0.0 by project-owner decision and is not a 0.6.0 prerequisite.
Stable 0.5.0 is published; this does not claim human acceptance, which remains
deferred to 1.0.0.

## Goal

Add a bounded PostgreSQL runtime for selected, documented Zelyra database
workflows. PostgreSQL schema inspection and changes already exist. The new
direct SQL API is native
and pooled; schema inspection and other web/database paths still start `psql`
as an external process. 0.6.0 will test a direct `sql<T>` CRUD workflow end to
end without claiming complete PostgreSQL parity. Generated web/CRUD paths are
explicitly deferred.

## Scope and acceptance criteria

The first implementation step adds a pooled PostgreSQL API to the database
crate. The synchronous Zelyra runtime routes direct SQL queries and transaction
batches to it based on the URL. The API uses Rustls, named parameters, bounded
scalar result values, transactions, and existing database limits. Generated
web/CRUD paths do not use it yet. It has been tested against PostgreSQL 16
locally, including TLS with a private test CA and hostname verification. CI
run [#505](https://github.com/sf1976/zelyra/actions/runs/38025176314) passed
all eight jobs on commit `b88456e`; its test job passed both PostgreSQL schema
safety and parameterized runtime integration. After synchronizing the latest
0.5.0 preparation, CI
[#518](https://github.com/sf1976/zelyra/actions/runs/38030557744) passed all
eight jobs on merge head `715ecc2`, including PostgreSQL schema safety.
Focused parameterized transaction and runtime-dispatch tests also pass locally
against PostgreSQL 16 on that exact merge head. Results are returned as
strings; supported types are
bool, int2/int4/int8, float4/float8, text, varchar, bpchar, and name. Other
PostgreSQL result types fail with a diagnostic. 0.5.0 remains a prerequisite
for merging and release.

## Explicitly out of scope

Complete PostgreSQL runtime parity is larger than one release. MySQL Server,
SQL Server, and a universal SQL dialect are not included. Zelyra will document
shared typed SQL capabilities and backend-specific limits instead. SQLite
remains a separate, bounded backend path.

Multi-tenancy, tenant context and tenant-aware authorization, a general
job/queue platform, a transactional outbox for arbitrary effects, MFA/WebAuthn,
OAuth2/OIDC, a full visual editor, arbitrary client hydration,
compiler self-hosting, general formal verification, and a native backend are
outside 0.6.0.

Cloud accounts, external AI services, telemetry, and unsupported performance
claims remain excluded. External network access must be explicit, reviewable,
and optional.

## Later version path

- **0.7.0 — MySQL runtime, tenant context, and developer-studio preview:**
  implement a real MySQL server backend and test it separately from MariaDB;
  `mysql://` counts as MySQL support only after that evidence exists. Also,
  after a dedicated threat model, test a server-derived tenant context and
  fail-closed authorization in a bounded database path; never trust an
  unverified tenant ID from a form or request. Plan a local,
  read-only-by-default studio combining diagnostics, module and route views,
  and app preview. Add `zelyra --tutorial invoice` as a guided local path
  through customers, items, dashboard, and invoice entry.
- **0.8.0 — Durable tasks:** a bounded local worker/queue interface and
  transactional outbox with retry, idempotency, cancellation, retention, and
  crash-recovery contracts. The studio may add controlled editing: project-root
  bounded, explicit saves followed by formatting and compiler checks. Text
  changes should have a readable replacement form: name the pattern and
  replacement, give capture groups names, and preview affected locations before
  applying. Keep regular expressions as the pattern language while avoiding
  opaque Perl one-liners, ambiguous backreferences, and silent overwrites. Do
  not promise a general distributed job platform.
- **0.9.0 — Backend coverage, strong authentication, and federation:** verify
  core MariaDB, MySQL, and PostgreSQL workflows end to end in one compatibility
  matrix, including schema operations, parameterized SQL, transactions, and
  supported generated web/CRUD paths. Add WebAuthn/MFA and optional OAuth2/OIDC
  only after protocol, key, recovery, and account-linking review; local
  development remains possible without an external identity provider. The
  studio and tutorial require no cloud, telemetry, or external AI; permission,
  filesystem, and loopback security boundaries must be complete before 1.0.
- **0.99.0 — Feature freeze and final technical readiness:** no new product
  features. Language, CLI, project, and runtime contracts, compatibility
  real-server compatibility matrices for MariaDB, MySQL, and PostgreSQL,
  security review, migrations, studio, and tutorial are documented
  and technically verified. This prepares the 1.0.0 candidate; only independent
  human acceptance tests remain as the release gate.
- **1.0.0 — first productive version:** publish stable only after independent
  human acceptance of the immutable 1.0.0 release candidate, all technical gates,
  and confirmed core support for MariaDB, MySQL, and PostgreSQL. Each server has
  its own tested version matrix; do not claim unsupported parity. Blocking study
  findings require a new candidate and a repeated acceptance check.

This sequence is prioritized planning, not a guarantee. Reassess evidence,
risks, and scope after each release candidate.
