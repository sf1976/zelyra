# Zelyra 0.4.0 Release Plan

**Status:** working proposal, not a release promise · **Verified upstream
state (2026-10-03):** stable release `v0.3.0`; no `v0.4.0` release yet. The
independent human onboarding acceptance explicitly deferred from 0.3.0 is
mandatory before the final 0.4.0 release.
**Goal:** make Zelyra suitable for larger local business applications without
weakening its explicit effects, data-safety, or AI-independent design.

This plan is the written starting point for 0.4.0. It does not claim that any
item below is implemented. Every checked item must have implementation,
positive and negative tests, diagnostics, documentation in both languages,
and a working example where applicable.

## Preconditions and guiding decisions

- [x] Final `v0.3.0` is published. Its tag, commit, Linux/Windows artifacts,
  checksums, and limits are in the [verification
  record](../release-readiness/0.3.0-final-release-verification-2026-10-03.md).
  The 0.3.0 human onboarding acceptance was explicitly deferred and is
  mandatory before 0.4.0.
- [x] Keep the product local-first and AI-provider-independent. No cloud
  account, external model, telemetry, or hosted control plane is a 0.4.0
  prerequisite.
- [x] Create a 0.4.0 risk and acceptance register before implementation:
  `docs/release-readiness/0.4.0-risk-register.en.md` and
  `docs/release-readiness/0.4.0-risikoregister.de.md`.
- [ ] Assign every release claim to a test, a reproducible artifact, or an
  explicit limitation. A green unit test is not evidence for a broader claim.

## Scope decision

0.4.0 should concentrate on three user-visible problems:

1. **Projects must scale beyond one source file.** Modules, imports, visibility,
   deterministic builds, and actionable diagnostics are the language priority.
2. **Applications must survive normal operational pressure.** Connection
   lifecycle, timeouts, health checks, safe schema evolution, and rollback
   guidance are the runtime/data priority.
3. **Business applications need a safer account and API lifecycle.** Password
   recovery, session/device control, request correlation, and bounded API use
   are the security/integration priority.

AI-native effect declarations and supply-chain evidence are cross-cutting
acceptance requirements. They are not permission to add an external AI
service.

## Milestone 1 — Modules and deterministic multi-file projects (P0)

The [Docker module acceptance](../module-docker-acceptance.en.md) describes the
combined application and separate invoice/inventory exports, with negative
tests for missing configuration, unrelated routes and database permissions.
This bounded read test does not replace full writable CRUD acceptance.

The current development branch contains an experimental first slice: imported
files may contain functions, type aliases, records, tables, tableviews, named
views, typed components, and one
project-wide database connection definition through explicit aliases; cycle,
path escape, private function/type, type, capability, and
contract checks are exercised.
The machine-readable context now exposes the reachable graph in deterministic
order. Database configuration is composed project-wide rather than accessed
through its alias, and only one connection is supported. Imported tables join
the shared physical schema and retain global SQL names. Imported tableviews,
named views, and typed components are composed under global names; MariaDB-backed
tableviews can be served by the application, while SQLite-backed tableview
execution is not implemented. Resource-name collisions are rejected. This does
not close the milestone. Context spans for imported declarations identify their
project-relative source file. `modules[].exports` also lists the currently
supported public functions, types, and records per source file; this is not a
complete export or deployment manifest. Verification diagnostics are not yet
consistently attributed per module. `zelyra module plan <entry> <module-or-resource-id>`
emits a read-only, deterministic preview that follows explicit imports and
references recognized by the current static impact graph. It includes known
page-to-view/component, page and form/CRUD-action SQL-to-table,
API-handler-to-function, protected-resource-to-authentication,
authentication-to-table, declaration type references from APIs, function
signatures, records, and type aliases, table-relation, and database-configuration edges;
unresolved references are reported. SQL-to-table references additionally
carry a conservative `access` value (`read`, `write`, `read_write`, or
`unknown`); complex joined `UPDATE`/`DELETE` forms are marked `unknown`.
`schema_ownership` reports the table declaration's source file as an inferred
owner but sets `enforced` to `false`. This metadata supports dependency
inspection only; it does not enforce authorization or schema ownership.
`modules[].declarations` lists recognized
declarations in each included source file, making co-located declarations
visible. `declaration_closure` separates declarations reachable through the
known static impact graph from additional declarations in included files;
`configuration_edges` also reports database configuration.
`database.configurations` reports the backend, logical database name, source
file, and `DATABASE_URL` for declarations in the closure. The runtime still
supports only one project-wide connection; this is not a named, independently
configurable database interface. This analysis is incomplete and is not an
export plan. Dynamic or
unmodeled dependencies, assets, runtime configuration, external contracts, and
Docker packaging remain outside the preview. `complete_deployment` is
explicitly `false`, and no files are written.
`impact` analyzes the linked graph with
file-attributed spans. Database commands build schemas from the linked graph;
schema-building diagnostics now retain imported source paths and spans, covered
by a CLI regression test; some template and verification diagnostics still
lack module attribution. `fmt` and `edit` remain file-local. Imported views
and components now support `pub`; cross-module
page/CRUD layout references and known component tags in page, view, component,
and CRUD slot HTML require a public declaration and an explicit import path
(`E-MOD-007` / `E-MOD-020`). Component-reference discovery is limited to known
tags in the current HTML source and is not a general HTML/component namespace
system. Some template diagnostics still lack precise module source attribution.
Imported pages join the application route set, and overlapping
route patterns are rejected. Forms, CRUD declarations, API routes, and
authentication configuration also compose from imported files. API handler
references and declared types resolve in their owning module, and auth tables
are validated against the composed schema.
Broader namespace/visibility rules, source-aware
verification,
integration with formatter/edit/database tools, and full multi-file acceptance
fixtures remain open. The published 0.3.0 binary has no module support. The
generated MariaDB Docker project now copies the conventional `src/` directory
into its runtime image, allowing imported project source files there to load
in the container. This is whole-project Docker support only: it does not
extract a module or provide independent database configuration.
The unreleased project generator now places the MariaDB declaration in
`src/database.zyl` and adds an explicit import from `main.zyl`. This establishes
a source-module boundary only; the runtime still exposes one project-wide
`DATABASE_URL`, and 0.3.0 templates are unchanged.
The branch also has `zelyra module bundle <entry> <module-or-resource>
--output <dir>` and the experimental `--docker --compiler-ref <40-character
commit>` option. The latter generates a Dockerfile, Compose configuration, and
secret-free `.env.example`; it builds the compiler from the exact pinned public
source commit. `--dry-run` emits a machine-readable sorted output-path plan and
does not publish the candidate bundle. The Compose application receives its
own `DATABASE_URL`, while MariaDB remains an external service. A Docker
end-to-end test builds the
exported app and requests an imported route in a separate container. The
compiler also emits `E-MOD-019` when a recognized cross-module table reference
has no import path to its owner module, including tables declared in the entry
module. Shared schema declarations must live in a separately importable module.
Tables in the unreleased branch also declare explicit `access` lists for
`read`, `write`, and `read_write`; recognized accesses without a matching grant
report `E-MOD-021`. CRUD, forms, authentication, and unknown SQL accesses
require `read_write`. These are compiler checks, not MariaDB grants.
Unrecognized SQL forms and schema-change permissions remain unchecked.
Database-consuming modules must also directly or transitively import the
provider (`E-MOD-022`); an entry-only import is not inherited by child modules.
A `database` declaration in the entry file must therefore move to an
importable module. This is a checked source dependency, not a runtime
connection interface.
The manifest still keeps `source_closure_complete` and
`complete_deployment` false:
the static dependency analysis does not yet prove every runtime and asset
dependency. This is neither a complete module export nor a 0.5.0 acceptance
result. Multiple database definitions in the checked project graph fail with
`E-DB-001` before the bundle writes files; only one project-wide connection is
currently supported.

- [x] Document the experimental import grammar, aliases, current visibility
  scope, and project-file boundaries in the
  [language specification](../specification.md) and [handbook](../handbook/en/handbook.md).
  `pub` applies to supported functions, types, records, views, and components.
- [x] Implement and test project-relative imports, explicit cycle detection,
  duplicate-definition diagnostics, private/public visibility for currently
  supported symbols, and source spans. CLI and project-loader tests cover
  these cases. `db create` also reports schema-building errors at their
  imported source file and span; template and verification diagnostics still
  need more complete source attribution.
- [x] Implement and test a deterministic dependency graph with stable order,
  missing-module diagnostics, project-root boundaries, and no network access
  during module loading.
- [x] Generate an experimental Docker source-package prototype with a pinned
  compiler commit, external database configuration, and a separate-container
  smoke test; keep the incomplete graph analysis visible in its manifest.
- [x] Preserve capability and contract checks across supported module
  boundaries; CLI and runtime tests confirm imported functions cannot bypass
  project grants or preconditions.
- [x] Compose imported named views and typed components into the linked project;
  prove `serve` renders an imported layout/component and rejects duplicate
  component names with the correct source-file diagnostic. Public/private UI
  visibility, CRUD layout/slot references, and missing UI import edges are
  covered by CLI tests.
- [x] Add a multi-file application example and tests for module cycles,
  visibility failures, and missing imports. The CLI integration suite checks
  and runs the example; loader tests cover cycles, visibility, and missing
  modules.
- [x] Check graph handling for `check`, `context`, `impact`, `fmt`, `edit`,
  and database commands and document the boundary: graph-wide behavior where
  implemented; `fmt` and `edit` remain file-local. CLI/integration tests cover
  the documented cases. This does not close the module milestone.

**Acceptance:** repeated checks and builds produce identical diagnostics and
artifacts; valid imports run; invalid cycles, paths, visibility, and duplicate
names fail before execution; no source outside the project root is read.

## Milestone 2 — Reliable data and runtime lifecycle (P0)

- [x] Add bounded, secret-free MariaDB connection and statement timeout
  settings in the development branch: 10 seconds to connect by default
  (allowed 1–300) and 30 seconds per statement (allowed 1–3600). Disable client
  reconnect so connection loss cannot trigger a silent retry. The runtime still
  starts one client process per database operation; this is not a connection
  pool. Do not apply statement timeout to schema DDL while partial state is not
  safely recoverable. Unit tests and the full MariaDB CI matrix (10.11.19,
  11.4.13, 11.8.9, and 12.3.3) verified the configuration and cancellation of
  a slow runtime statement on 2026-10-03. This does not implement pooling or
  retries.
- [x] Set pool-size and wait bounds (default 8 and 10 seconds; hard maxima 64
  and 300 seconds). Total-response deadlines, health-check categories, and
  retry rules remain separate open work until TLS and cancellation states are
  handled safely.
- [x] Implement bounded pooling in the MariaDB runtime SQL path: default
  maximum 8 (allowed 1–64), default pool wait 10 seconds (allowed 1–300),
  checkout ping, no automatic retry, and discard a connection after statement
  errors; attempt rollback before discarding when in a transaction. Verified
  locally against isolated MariaDB 11.4, including reuse, hard pool limit,
  timeout cancellation, and connection replacement. Schema inspection/DDL
  still uses the CLI and is outside this pool.
- [x] Add configurable verified MariaDB TLS for the runtime pool and every CLI
  query and DDL connection:
  `auto` verifies remote hosts, `required` forces TLS, and `disabled` is an
  explicit local-development opt-out. Support a custom CA file and fail closed
  on invalid certificates or hostnames. The positive handshake, schema inspect,
  migration apply, and wrong-CA rejection passed locally on MariaDB 11.4 and in
  PR CI run
  [37161345832](https://github.com/sf1976/zelyra/actions/runs/37161345832)
  across all four MariaDB matrix versions. Standalone module Docker bundles
  default to `auto`; the full local Compose template explicitly disables TLS
  only on its isolated app/database network. Windows TLS is not yet separately
  verified.
- [🧪] Define response deadlines, health-check categories, and retry rules
  without reusing connections in uncertain transaction states. The new
  [HTTP operations guide](../http-operations.en.md) defines TCP listener
  liveness, application-owned readiness, the absolute 30-second exchange
  deadline, and bounded retries only for safe/idempotent requests. Zelyra does
  not automatically retry; handlers remain synchronous and uncancellable.
  A reserved, database-free `GET`/`HEAD /__zelyra/health/live` endpoint now
  confirms request dispatch; shadowing routes fail validation. Application
  readiness remains application-owned. The generated `mariadb-business`
  project now provides a bounded, read-only `GET /health/ready` query; its E2E
  checks both a reachable and unavailable database without leaking connection
  details. Other templates define readiness for their own dependencies.
  The HTTP server handles up
  to 64 connections concurrently and drops excess connections; socket tests
  cover slow/fast concurrency and the worker cap. This item remains partial.
- [x] Extend `zelyra doctor --json` with stable configuration, project, connectivity,
  authentication, timeout, schema, and tooling categories. Database client
  failures are mapped to actionable messages without returning raw backend
  diagnostics or credentials. Unit tests cover category mapping and secret
  redaction; the unreachable-database integration test verifies the
  connectivity category.
- [ ] Design versioned, reversible migration plans with preflight checks,
  rollback guidance, drift reporting, and an explicit operator approval step.
  Unsupported or ambiguous changes must remain fail-closed. Partial progress:
  `zelyra db plan --format=json` now emits a versioned plan with schema
  fingerprints, stable ID, drift, preflights, and an approval flag. It does not
  claim or generate inverse SQL; `rollback.generated` is `false`. `db apply`
  can accept that plan ID and refuses a stale plan before preflights or SQL;
  a SQLite CLI integration test verifies stale rejection without applying SQL
  and successful application with a freshly reviewed ID. Omitting the ID
  remains supported. MariaDB `db apply` now stores plan fingerprints and
  per-step checkpoints in `_zelyra_schema_history`; `db history` reports
  applied, failed, active, and interrupted plans. A database-scoped advisory
  lock prevents concurrent Zelyra migrations, and schema inspection hides the
  reserved journal table. A MariaDB 11.4 E2E test kills the process between
  DDL steps, verifies the interrupted checkpoint and lock release, then applies
  a freshly reviewed plan to finish the schema. SQLite and PostgreSQL history,
  safe reverse plans, and crash behavior inside a DDL statement remain open.
  `db apply` now executes
  PostgreSQL and SQLite plans transactionally; regression and PostgreSQL
  integration tests verify failed DDL rolls back earlier steps and a repaired
  plan can be retried. Before any plan SQL, read-only checks now reject
  duplicate values for new unique indexes and orphan values for new foreign
  keys, alongside required-column and nullability checks. They do not prevent
  concurrent-write races. MariaDB DDL can still partially apply; recovery from
  a process kill between statements is verified, but ambiguity from a kill
  during a DDL statement remains open.
- [x] Run the full database-crate suite, including pool and timeout tests,
  against MariaDB 10.11.19, 11.4.13, 11.8.9, and 12.3.3; [PR CI run
  37156746403](https://github.com/sf1976/zelyra/actions/runs/37156746403)
  succeeded.
- [x] Verify the TLS handshake, CLI connection, wrong-CA rejection, and
  secret-free TLS diagnostic against MariaDB 10.11.19, 11.4.13, 11.8.9, and
  12.3.3 with `tests/mariadb-tls-e2e.sh`; all four versioned images passed
  locally and in [PR CI run
  37161345832](https://github.com/sf1976/zelyra/actions/runs/37161345832).
  The generated Docker-project E2E also passes with standalone bundles explicitly opting out
  only for their isolated local test network.
- [ ] Add further populated-table, interruption-during-DDL, idempotency-aware
  retry, drift, and backup/restore rehearsal tests. Transactional failure and
  corrected retry are verified separately for SQLite and PostgreSQL; MariaDB
  interruption between DDL steps and recovery with a fresh plan are verified.
  A second MariaDB E2E now holds a table metadata lock, waits until the server
  reports the submitted `ALTER TABLE` blocked on that lock, kills the Zelyra
  process group, verifies the journal says `interrupted` and the new column is
  absent, then applies a newly reviewed plan successfully. This covers process
  loss while a DDL request is waiting; a server/process crash during actual DDL
  execution and the resulting statement-level ambiguity remain open.
- [x] Document backup/restore responsibilities and the boundary between a
  Zelyra migration plan and an operator-owned database backup in
  [English](../database-operations.en.md) and
  [German](../database-operations.de.md). A related smoke test passed locally
  against MariaDB 10.11.19, 11.4.13, 11.8.9, and 12.3.3; CI is rerunning the
  updated test, and interrupted schema updates remain open.

**Acceptance:** a disposable database can be upgraded, intentionally
interrupted, inspected, and restored using documented commands; repeated
planning is deterministic; failures leave no silent partial-success claim.

## Milestone 3 — Account and API lifecycle (P0)

- [🧪] MariaDB development builds implement password recovery with a single-use
  15-minute token (hash only at rest), generic response, audit, CSRF,
  loopback/HTTPS SMTP configuration, bounded asynchronous delivery, and
  session revocation. Parser/schema tests and a MariaDB/SMTP-sink E2E with an
  intentionally delayed SMTP response cover schema, response timing and
  enumeration, URL exchange, replay, expiry, cross-origin requests, password
  change, and two simultaneous submissions of one reset token; exactly one
  succeeds and only its password authenticates. Reset limits are process-local
  and keyed by IP. Within one process, token replacement and FIFO mail enqueue
  are serialized within one process. MariaDB advisory locks now coordinate
  issuance and delivery across instances, and the mail worker skips tokens
  that are no longer current. A two-instance MariaDB/SMTP-sink E2E delays the
  first relay while a second instance issues a token, then confirms the later
  email matches the stored token. The reset E2E now also drives SMTP connection
  refusal and verifies identical generic responses for known and unknown
  accounts plus redacted logs. Frozen-clock expiry equality, durable delivery
  recovery, operational/threat review,
  and independent security review remain acceptance gates. This item is not
  complete.
- [🧪] Add explicit session/device listing and revocation, bounded session
  lifetime, and safe behavior when the last administrator or current session
  is revoked.
  Administrative persistent-session listing and individual revocation are
  implemented. `/account/sessions` also lists and revokes only the signed-in
  user's persistent or in-memory sessions; revoking the current session clears
  its cookie and returns to login. Account/role data remains intact. In-memory
  sessions expire after 24 hours too. HTTP tests cover
  revocation/replay, invalid IDs, mismatched ownership, CSRF, cross-origin,
  missing permissions, audit, re-login and persistent expiry. The MariaDB
  protected-app E2E also verifies self-service ownership, revocation of another
  session and clearing the current cookie. Device metadata remain open.
- [🧪] Login and reset rate limits are configurable and run in local process
  memory (`login_rate_limit`, `login_block_seconds`, `reset_rate_limit`,
  `reset_block_seconds`). The table holds at most 4,096 keys and rejects new
  keys when full. Unit and reset end-to-end tests cover limits; persistent or
  distributed quotas and load/abuse review remain open.
- [🧪] API request-correlation IDs, version/deprecation metadata, and bounded
  quotas per TCP peer IP are implemented and tested without changing typed
  validation or capability boundaries. Validated request IDs,
  response/OpenAPI version and deprecation metadata, and process-local quotas
  are covered by unit and integration tests. The
  client-bucket count is bounded and reverse-proxy headers are not trusted.
  Tests cover valid, invalid, and missing incoming correlation IDs, response
  header deduplication, quota exhaustion, bounded client state, and window
  expiry. Additional quota/metadata compatibility tests and persistent or
  distributed limiting remain open, so this item is not complete.
- [🧪] Negative tests cover reset-token replay, enumeration, CSRF, cross-origin
  requests, session revocation, API quota exhaustion, and correlation context.
  The MariaDB E2E sets `expires_at = NOW()` and confirms that a current-time
  token is rejected; a frozen-clock equality test remains open. SMTP connection
  failure is covered by an E2E that checks indistinguishable responses and
  generic secret-free logs. Durable delivery recovery remains open.
- [🧪] The threat boundary is documented in both languages: TLS termination, proxy trust, mail
  delivery, key storage, and operational rate-limit persistence remain
  deployment responsibilities unless explicitly implemented.

**Acceptance:** a generated business application can safely reset a test
  account, revoke a session, correlate an API request, and reject abuse cases;
  no secret or account-existence signal is revealed by error paths.

## Milestone 5 — Quality, supply chain, and accessibility (P1)

Partial progress: the release workflow generates a deterministic SPDX-2.3
SBOM for Linux and Windows from the resolved Cargo dependency graph and checks
the SHA-256 of each binary. License fields Cargo does not express as SPDX are
reported as `NOASSERTION` with the original value. Tag builds are configured
to attest each Linux and Windows release archive and its SBOM with GitHub Artifact
Attestations. Consumers can verify a published archive with the GitHub CLI;
see the [artifact verification guide](../release-readiness/artifact-verification.en.md).
The workflow change still needs a published-candidate rehearsal. Dependency/
license auditing and complete native artifact verification remain open. CI now
runs pinned `cargo-deny` 0.20.2 across Linux and Windows dependency graphs to
check RustSec advisories, allowed SPDX licenses, duplicate versions, wildcard
requirements, and registry/git sources. The policy records a hash-verified ISC
clarification for `webpki` and a reasoned exception for the transitive
unmaintained `rustls-pemfile` compatibility crate. Duplicate `base64` and
`getrandom` versions remain visible as warnings. This automated check does not
replace a human review of dependency purpose, license obligations, or the
remaining warnings; see the [cargo-deny policy](../../deny.toml) and the
[RustSec advisory](https://rustsec.org/advisories/RUSTSEC-2025-0134).

- [🧪] Add bounded fuzzing or property-based regression coverage for the
  lexer/parser, SQL binder, template renderer, and HTTP request parser. A
  deterministic mutation corpus now exercises all four paths in normal CI:
  1,024 grammar-seed mutations plus 1,024 randomized byte-sequence cases per
  path from a bounded grammar/special-byte alphabet, capped at 256 bytes and
  12 edits. Lexer output, SQL binder outcomes, HTTP
  parse results, and template output are checked for determinism; panics fail
  the tests. This is not coverage-guided fuzzing and has no minimized crash
  corpus; those remain open.
- [ ] Add dependency/license auditing, an SBOM, provenance metadata, and
  documented verification for every native release artifact.
- [ ] Add security regressions for secret redaction, unwanted network access,
  CSRF/origin/host boundaries, archive traversal, and installer replacement.
- [ ] Add deterministic view snapshots and automated accessibility checks for
  generated navigation, forms, tables, errors, focus order, and language
  selection.
- [ ] Keep Linux/Windows native artifacts and source-install fallbacks honest;
  unsupported targets must remain visible in the release notes.

- [ ] All P0 items are implemented, reviewed, and backed by positive and
  negative tests.
- [ ] The multi-file example, generated business application, and a migration
  recovery scenario pass on a clean supported environment.
- [ ] MariaDB compatibility claims match the tested matrix; unsupported
  PostgreSQL/MySQL behavior is not implied.
- [ ] Security review, threat model, dependency audit, and residual risks are
  updated in both languages. The [working review](../security-review-0.4.0.en.md)

  implied unless one exists.
- [ ] CLI JSON, diagnostics, project files, migration plans, and release
  artifacts have compatibility notes and deterministic tests.
- [ ] Run a real human acceptance test with a person who does not develop
  Zelyra. Use the updated 0.4.0 onboarding protocol, record redacted
  observations and blockers, and complete the test before the final 0.4.0
  release. A technical rehearsal cannot replace it.
- [ ] Release artifacts, checksums, SBOM/provenance, upgrade/rollback smoke,
  and supported-platform claims are verified from the published candidate.
- [ ] Publish `v0.4.0` only after every mandatory gate passes. Otherwise keep
  the candidate or reduce scope explicitly.

## Explicitly not automatic in 0.4.0

The following remain deferred unless a later scope decision adds capacity and
acceptance tests:

- full PostgreSQL runtime parity, MySQL/SQL Server support, or universal SQL;
- multi-tenancy and tenant-aware authorization;
- a complete background-job/queue platform and transactional outbox;
- MFA/WebAuthn, OAuth2/OIDC, and external identity-provider integration;
- a visual drag-and-drop editor, full theme editor, or arbitrary client
  hydration;
- general formal verification, compiler self-hosting, or a native backend;
- mandatory cloud services, external AI providers, telemetry, or a public
  performance guarantee.

## Working method

Work in vertical slices. For every completed slice, update both plan
languages, the relevant handbook/API docs, tests, and evidence; run the
narrowest meaningful checks plus the full CI path; then create one focused
commit and push it before starting the next slice. Never mark a checkbox from
intent or from a test with a narrower scope than the claim.
