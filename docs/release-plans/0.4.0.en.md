# Zelyra 0.4.0 Release Plan

**Status:** working proposal, not a release promise · **Starting point:** the
published experimental Zelyra 0.3.0 release
**Goal:** make Zelyra suitable for larger local business applications without
weakening its explicit effects, data-safety, or AI-independent design.

This plan is the written starting point for 0.4.0. It does not claim that any
item below is implemented. Every checked item must have implementation,
positive and negative tests, diagnostics, documentation in both languages,
and a working example where applicable.

## Preconditions and guiding decisions

- [ ] Close and publish 0.3.0 first. Record the completed human onboarding
  result, re-run the final release checks, and link the final release evidence
  before treating 0.3.0 as the baseline.
- [x] Keep the product local-first and AI-provider-independent. No cloud
  account, external model, telemetry, or hosted control plane is a 0.4.0
  prerequisite.
- [x] Create a 0.4.0 risk and acceptance register before implementation:
  `docs/release-readiness/0.4.0-risk-register.en.md` and `.de.md`.
- [ ] Assign every release claim to a test, a reproducible artifact, or an
  explicit limitation. A green unit test is not evidence for a broader claim.

## Scope decision

0.4.0 should concentrate on three user-visible problems:

1. **Projects must scale beyond one source file.** Modules, imports, visibility,
   deterministic builds, and actionable diagnostics are the language priority.
2. **Applications must survive normal operational pressure.** Connection
   lifecycle, timeouts, health checks, safe schema evolution, and rollback
   guidance are the runtime/data priority.
3. **Business applications need a safer account and API lifecycle.** Password
   recovery, session/device control, request correlation, and bounded API use
   are the security/integration priority.

AI-native effect declarations and supply-chain evidence are cross-cutting
acceptance requirements. They are not permission to add an external AI
service.

## Milestone 0 — Baseline and scope

- [ ] Publish the final 0.3.0 release and record its exact commit, artifacts,
  checksums, supported targets, and known limitations.
- [ ] Copy the 0.3.0 residual risks into the 0.4.0 register and classify each
  as fixed, carried forward, or explicitly deferred.
- [ ] Add a minimal 0.4.0 example application that will be exercised at every
  acceptance milestone. It must use more than one source file once modules
  are available and must run without a hosted service.
- [ ] Define compatibility rules for project files, generated output, CLI
  JSON, and database plans before changing their formats.

**Exit criterion:** the baseline, scope, compatibility rules, and evidence
owners are written down in English and German.

## Milestone 1 — Modules and deterministic multi-file projects (P0)

- [ ] Specify modules, imports, visibility, namespaces, and the project file
  syntax in the language specification and both handbooks.
- [ ] Implement project-relative imports with explicit cycle detection,
  duplicate-definition diagnostics, private/public visibility, and stable
  source spans across files.
- [ ] Build a deterministic dependency graph with stable ordering, actionable
  missing-module errors, and no network access during compilation.
- [ ] Preserve capability and contract checking across module boundaries;
  importing a function must not weaken its declared effects or obligations.
- [ ] Add a three-file application example, a module-cycle failure fixture, a
  visibility failure fixture, and a missing-import fixture.
- [ ] Verify that `check`, `fmt`, `context`, `impact`, and `edit` handle the
  project graph consistently, or document commands that intentionally remain
  source-file local.

**Acceptance:** repeated checks and builds produce identical diagnostics and
artifacts; valid imports run; invalid cycles, paths, visibility, and duplicate
names fail before execution; no source outside the project root is read.

## Milestone 2 — Reliable data and runtime lifecycle (P0)

- [ ] Define explicit connection timeout, query timeout, pool-size, retry, and
  health-check configuration with safe defaults and secret-free diagnostics.
- [ ] Implement bounded connection pooling and cancellation behavior for the
  supported MariaDB runtime path. A timeout must not leave a transaction or
  connection silently reusable in an unknown state.
- [ ] Add an inspectable `doctor`/machine-readable health result that
  distinguishes configuration, connectivity, authentication, timeout, and
  schema failures without exposing credentials.
- [ ] Design versioned, reversible migration plans with preflight checks,
  rollback guidance, drift reporting, and an explicit operator approval step.
  Unsupported or ambiguous changes must remain fail-closed.
- [ ] Add populated-table, interrupted-operation, retry, timeout, drift, and
  rollback rehearsal tests against the documented MariaDB matrix. Keep SQLite
  and PostgreSQL claims separate unless their runtime behavior is actually
  implemented and tested.
- [ ] Document backup/restore responsibilities and the boundary between a
  Zelyra migration plan and an operator-owned database backup.

**Acceptance:** a disposable database can be upgraded, intentionally
interrupted, inspected, and restored using documented commands; repeated
planning is deterministic; failures leave no silent partial-success claim.

## Milestone 3 — Account and API lifecycle (P0)

- [ ] Implement password-reset flows using single-use, expiring, hashed reset
  tokens, generic user-facing responses, audit events, and no token leakage in
  logs or URLs after exchange.
- [ ] Add explicit session/device listing and revocation, bounded session
  lifetime, and safe behavior when the last administrator or current session
  is revoked.
- [ ] Add configurable login and reset rate limits with deterministic local
  behavior, clear diagnostics, and tests that do not require a third-party
  service.
- [ ] Add API request-correlation IDs, version/deprecation metadata, and
  bounded request quotas or rate limits without changing the existing typed
  validation and capability boundaries.
- [ ] Add negative tests for token replay, expiration, enumeration, CSRF,
  cross-origin requests, revoked sessions, quota exhaustion, and missing
  correlation context.
- [ ] Document the threat boundary: TLS termination, proxy trust, mail
  delivery, key storage, and operational rate-limit persistence remain
  deployment responsibilities unless explicitly implemented.

**Acceptance:** a generated business application can safely reset a test
  account, revoke a session, correlate an API request, and reject abuse cases;
  no secret or account-existence signal is revealed by error paths.

## Milestone 4 — AI-native effects and machine interfaces (P1)

- [ ] Specify granular effects such as `Database(read)`, `Database(write)`,
  `Email`, and `Jobs` with explicit project grants and diagnostics.
- [ ] Ensure effects propagate through calls, modules, generated handlers, and
  custom actions; missing grants fail statically and at runtime where needed.
- [ ] Extend `impact` with module, migration, email, job, test, and live-schema
  reference categories only when the edges are verified rather than guessed.
- [ ] Extend semantic edit previews to show affected files, effects, tests,
  and schema references, with stale-source fingerprints and atomic apply.
- [ ] Add machine-readable examples and a small reproducible authoring
  benchmark. Do not publish comparative AI claims until controlled human and
  AI runs have been recorded.

**Acceptance:** an automated author can obtain context and proposed edits, but
  cannot silently gain a new effect, escape the project root, or bypass
  compiler/test approval.

## Milestone 5 — Quality, supply chain, and accessibility (P1)

- [ ] Add fuzzing or property-based regression coverage for the lexer/parser,
  SQL binder, template renderer, and HTTP request parser with bounded CI jobs.
- [ ] Add dependency/license auditing, an SBOM, provenance metadata, and
  documented verification for every native release artifact.
- [ ] Add security regressions for secret redaction, unwanted network access,
  CSRF/origin/host boundaries, archive traversal, and installer replacement.
- [ ] Add deterministic view snapshots and automated accessibility checks for
  generated navigation, forms, tables, errors, focus order, and language
  selection.
- [ ] Keep Linux/Windows native artifacts and source-install fallbacks honest;
  unsupported targets must remain visible in the release notes.

## Release gates

- [ ] All P0 items are implemented, reviewed, and backed by positive and
  negative tests.
- [ ] The multi-file example, generated business application, and a migration
  recovery scenario pass on a clean supported environment.
- [ ] MariaDB compatibility claims match the tested matrix; unsupported
  PostgreSQL/MySQL behavior is not implied.
- [ ] Security review, threat model, dependency audit, and residual risks are
  updated in both languages. No external audit is implied unless one exists.
- [ ] CLI JSON, diagnostics, project files, migration plans, and release
  artifacts have compatibility notes and deterministic tests.
- [ ] A real human acceptance test follows the published onboarding protocol
  for the new workflows; a technical rehearsal cannot replace it.
- [ ] Release artifacts, checksums, SBOM/provenance, upgrade/rollback smoke,
  and supported-platform claims are verified from the published candidate.
- [ ] Publish `v0.4.0` only after every mandatory gate passes. Otherwise keep
  the candidate or reduce scope explicitly.

## Explicitly not automatic in 0.4.0

The following remain deferred unless a later scope decision adds capacity and
acceptance tests:

- full PostgreSQL runtime parity, MySQL/SQL Server support, or universal SQL;
- multi-tenancy and tenant-aware authorization;
- a complete background-job/queue platform and transactional outbox;
- MFA/WebAuthn, OAuth2/OIDC, and external identity-provider integration;
- a visual drag-and-drop editor, full theme editor, or arbitrary client
  hydration;
- general formal verification, compiler self-hosting, or a native backend;
- mandatory cloud services, external AI providers, telemetry, or a public
  performance guarantee.

## Working method

Work in vertical slices. For every completed slice, update both plan
languages, the relevant handbook/API docs, tests, and evidence; run the
narrowest meaningful checks plus the full CI path; then create one focused
commit and push it before starting the next slice. Never mark a checkbox from
intent or from a test with a narrower scope than the claim.
