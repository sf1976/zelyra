# Zelyra 0.8.0: visuelle Datenbankkarte und geführtes CRUD

**Status:** in Entwicklung. Dieses Release ergänzt das lokale Studio um sichere,
compilergeprüfte Datenbank- und Quelltextabläufe. Es ist kein Produktivrelease.

## Ergebnis für Entwickler

Entwickler können eine konfigurierte Projektdatenbank öffnen, Tabellen und
Beziehungen überblicken, eine Tabelle auswählen, ein erzeugtes CRUD-Modul
prüfen und die Quelltextänderung nach erfolgreicher Compilerprüfung anwenden.
Datenbankinhalte bleiben in diesem Release schreibgeschützt.

## Umfang

- Eine schreibgeschützte, anklickbare Beziehungskarte zeigt Tabellen und
  Fremdschlüsselpfeile. Der Detailbereich zeigt Spalten, Schlüssel,
  Beziehungen und Abweichungen zwischen deklariertem und live vorhandenem
  Schema. Bekannte Quellmodule werden den Deklarationen zugeordnet.
- Entwickler wählen Tabelle und Felder aus, sehen den erzeugten Zelyra-Quelltext,
  lassen ihn vom Compiler prüfen, kontrollieren den Diff und übernehmen die
  Änderung ausdrücklich.
- Der visuelle Ablauf verändert weder Datenbankschema noch Datensätze. Er
  erzeugt keine stillen Änderungen und überschreibt keine seit der Vorschau
  geänderte Datei.
- Die begrenzte lokale MariaDB-Outbox aus dem gestapelten 0.8-Branch aufnehmen:
  typisiertes Enqueue innerhalb einer Geschäftstransaktion, ausdrücklich
  gestarteter Worker für einzelne Ereignisse, begrenzte Wiederholungen sowie
  Einsicht und Wiederherstellung durch Betreiber. Zustellung erfolgt mindestens
  einmal; Handler müssen idempotent sein. Dies ist keine allgemeine Queue.
- Das Korpus für Linie 0.1 wird für Lexer, Parser, Typprüfung und Formatter
  erweitert. Jede Grammatikfamilie erhält gültige und ungültige Fixtures;
  Formatter-Idempotenz wird geprüft.
- Der Entwurf für lesbare Regex-Textbearbeitung wird geprüft und als
  zweisprachige Designspezifikation übernommen. Ein ausführbarer CLI-Befehl ist
  kein 0.8-Versprechen; der geplante Umsetzungsmeilenstein ist 0.9.0.
- Der Ablauf bleibt lokal und überträgt keinen Quelltext an externe Dienste.
  Datenbank-Introspektion wird je Backend getrennt dokumentiert.

## Release-Gates

- [ ] Schemas mit fehlenden, zusätzlichen, umbenannten, nullable und verknüpften
  Spalten sowie unbekannten Merkmalen prüfen; Unsicherheit muss sichtbar bleiben.
- [x] Belegen, dass erzeugter Quelltext dieselben Compilerprüfungen wie manuell
  geschriebener Code besteht. Der lokale Compiler-Fixturetest prüft außerdem,
  dass die Vorschau die Quelldatei nicht ändert.
- [x] Veraltete Dateiversionen vor Vorschau und Schreiben zurückweisen.
- [ ] Abbruch, fehlerhafte Metadaten und schreibgeschützte Introspektion für
  jedes unterstützte Backend in der Datenbankmatrix testen.
- [ ] Atomarität von Outbox und Geschäftsdaten bei Commit/Rollback, Lease-Sicherheit
  paralleler Worker, begrenzte Wiederholungen, Absturzwiederherstellung,
  Payload-Grenzen und redigierte Betreiber-Ausgaben für unterstützte MariaDB-
  Versionen nachweisen. Transaktions- und Lease-Grenzen unabhängig prüfen.
- [x] Das aktuelle Sprachkorpus aus gültigen, ungültigen und Laufzeit-Fixtures
  auf der Entwicklungsrevision ausführen; Grammatik, Musterabgleich und
  Option-Typisierung wurden ergänzt. Auf dem exakten Release-Kandidaten erneut
  ausführen.
- [ ] Zweisprachiges Editorhandbuch, Datenbankmatrix und Beispiele aktualisieren.

Das Release verspricht weder eine vollständige IDE noch einen uneingeschränkten
Datenbankdesigner, Parität außerhalb der geprüften Matrix, Exactly-once-
Zustellung oder verteilte Queue-Unterstützung.
