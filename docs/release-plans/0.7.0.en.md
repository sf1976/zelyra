# Zelyra 0.7.0 roadmap: bounded tenant-aware CRUD

**Status:** experimental implementation in progress. This is a scoped roadmap,
not a statement that multi-tenancy is complete or safe for arbitrary queries.

## Current verification

The local MariaDB 11.4.13 E2E covers two tenants, missing and forged
selection, permission denial, a permissioned user with no membership, list and
detail isolation, create/edit/delete/restore, cross-tenant guessed IDs and
mutation attempts, submitted tenant keys, selector propagation through
generated navigation, membership-query failure, and a concurrent revocation
during delete. The full workspace suite, Clippy, handbook snippets, and release
metadata checks pass on the same working tree. Migration/backfill/rollback
review, exact-head CI, and an independent security review remain release gates.

## Goal

Let an authenticated user use one generated CRUD route family against a table
owned by one explicitly selected tenant. The first implementation targets the
MariaDB runtime. Existing projects remain unchanged unless they opt into tenant
membership and declare a tenant column.

## Accepted first slice

- Declare a dedicated membership table on a database-backed `auth` definition
  and declare `tenant: tenant_id` on a generated CRUD table.
- Resolve the principal only from a validated database session. Resolve the
  active membership on every request. Treat `X-Zelyra-Tenant` and `?tenant_id=`
  only as selectors, validate them against membership, reject ambiguous or
  conflicting selection, and preserve URL selection across generated CRUD
  links, forms, and redirects.
- Scope generated list and detail reads to tenant-owned rows. Hide the tenant
  key from generated output and form fields. Supply it from verified server
  context on create and constrain updates, deletes, and restores in the
  generated SQL path. Lock active membership and the target record inside a
  mutation transaction. Send tenant responses with `private, no-store`.
- Require database integration evidence with two tenants, including forged
  selectors, guessed foreign record IDs, untrusted submitted tenant keys, and
  membership revocation.

## Explicit exclusions

This slice does not provide full multi-tenancy, a visual tenant switcher,
tenant-aware migrations or data backfill, PostgreSQL tenant support, composite
same-tenant foreign-key guarantees, tenant-safe custom actions, raw SQL,
TableViews, reports, custom API handlers, exports, aggregates, caches, or
arbitrary modules. Relations and custom CRUD actions on tenant-scoped tables
are rejected until a separately reviewed implementation can enforce
same-tenant ownership.

No tenant state is stored globally or in pooled connections. No cloud service,
external identity provider, telemetry, or phone-home behavior is required.

## Release gates

- Complete positive and negative MariaDB integration tests for list, detail,
  create, edit, delete, restore, permission checks, no membership, ambiguous
  membership, revoked membership, forged selection, and transaction failure.
- Verify all tenant-owned response paths are non-cacheable and that generated
  links and redirects retain the selected tenant.
- Complete independent security review of request dispatch, generated SQL,
  membership revocation behavior, error/log output, and route coverage.
- Update this plan and the bilingual threat model with the exact commit and
  results before calling the feature ready.
