# 1.2.8 typed query and request/form work log

## Scope and baseline

This milestone extends the existing SQL AST/HIR/MIR path. It does not add a
second query syntax, claim safe tenant-scoped raw SQL, or mark request/form
semantics complete. The current source-level `sql<T> { ... }` remains the input
and remains subject to the compiler's schema, parameter, capability, and
tenant-scope checks.

## Implemented slice: typed SQL HIR through MIR

- HIR keeps the project's table declarations and represents each SQL node with
  an operation, deterministic table-access list, and ordered parameters.
- Each bound parameter carries its resolved local and the type inferred by the
  successful compiler check when available. `lower_with_expression_types`
  accepts types only for the same checked source revision; plain `lower` keeps
  its compatibility behavior and leaves inferred local types absent.
- MIR carries the query plan. Its verifier rescans the SQL source and rejects
  stale operation, table, or parameter bindings as `E-MIR-VERIFY-004`.
- The bytecode compiler only accepts verified MIR, and the bytecode VM
  revalidates SQL against its checked schema and actual parameter types before
  database host calls. Query-plan metadata is an analysis aid, not an
  authorization grant.
- `zelyra check` rejects form-action redirect targets that are not same-site
  absolute paths, use protocol-relative URLs, contain backslashes, or contain
  control characters (`E-FORM-007`). Normal local paths and query strings are
  accepted. This prevents external redirect and response-header injection
  through this literal form-action property.

## Evidence

- HIR tests cover table access ordering, parameter identity/type, and inferred
  binding types.
- MIR tests cover propagation of typed query metadata and rejection of a
  mutated plan. The targeted HIR/MIR test run passed on 2026-10-18.
- CLI integration coverage accepts a local redirect and rejects external,
  protocol-relative, backslash, and CR/LF targets, and checks that the
  diagnostic appears in structured JSON output.
- `cargo check --workspace --locked`, `cargo clippy --workspace --locked -- -D
  warnings`, `cargo fmt --all -- --check`, and `cargo test --workspace --locked`
  passed on this worktree. Two pre-existing tests were ignored because the
  disposable `DATABASE_URL` and MariaDB password-reset E2E fixture were not
  configured.
- Full backend, tenant-context, request/form, and redirect/response parity are
  still open. They must be delivered or fail closed before the 1.2.8 milestone
  is called complete.

## Security boundaries and remaining release work

- Existing authenticated generated CRUD binds tenant scope from the server's
  authenticated request context. Raw SQL against tenant-scoped tables remains
  rejected across AST, MIR, and bytecode; this milestone adds no user-authored
  scoped SQL syntax. Never accept a caller-supplied tenant identifier as proof
  of authorization.
- API error/output coupling, typed page and form inputs, server-side form
  validation, CSRF, permissions, escaping, and safe-value/secret handling are
  existing checked behavior. The redirect boundary added here is covered by a
  positive and negative CLI integration test.
- HTTP `serve` continues to use the AST interpreter. MIR and bytecode do not
  claim web-runtime parity; final backend parity remains a 1.3.0 gate. The
  supported raw SQL subset remains schema-checked at each backend's existing
  compiler/runtime boundary.
- Remaining release work is to complete the 1.2.8 version bump, full gates,
  release artifacts, and publication, and then verify the published assets.
