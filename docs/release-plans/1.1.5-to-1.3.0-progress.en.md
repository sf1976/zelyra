# Delivery status: Zelyra 1.1.5 through 1.3.0

Status: active modules/packages and interpreter roadmap. Zelyra 1.1.5 is
published; additional package/backend evidence originally assigned to that
topic remains open and is tracked as follow-up work. 1.3.0 is not complete.
This file records current scope and remaining evidence.

## 1.1.5 — modules, packages, and safe metadata

- Local `pkg:` dependencies, deterministic locking, public exports,
  type/cycle/capability checks, and offline resolution are implemented.
- Imported commands and schedules are namespace-qualified; local settings have
  typed schemas. Studio can edit local values with revision checks and redacts
  secrets.
- HostServices abstracts supported clock, environment, random, process,
  filesystem, database, console, HTTP, and mail operations. This does not prove
  full backend parity or a stable plugin ABI.
- `zelyra reflect <entry> --format=json` deterministically exports checked
  modules, symbols, tables, routes, APIs, forms, and contract source locations.
  Schema version 1 is implemented; live database schema and Markdown/OpenAPI
  formats remain open.
- Open: broad package/VM effect parity, package trust/signatures, safe web
  configuration for all modules, and a fully evidenced multi-backend module
  deployment.

## 1.3.0 — AST reference, MIR, and bytecode

- AST remains the reference backend and default. MIR and versioned bytecode are
  opt-in experimental subsets with verification, step/stack limits, HostServices,
  and differential tests.
- Supported slices include typed control flow, records, collections, tuples,
  enums/match, closures, and selected host/SQL/outbox operations. Unsupported
  operations must fail closed.
- Goal: make verified Bytecode the default for `run`, `serve`, and tasks only
  after full supported-language, effect, capability, contract, resource, host,
  and diagnostic parity is proven. AST remains the reference and differential
  backend. Until those gates pass, AST remains the default and unsupported
  Bytecode operations fail closed. This is a portable Bytecode goal, not native
  machine-code generation.
- Open: full parity; broader differential, fuzz, and security coverage;
  reproducible performance measurements; and the backend-default release gate.

## 1.2.0, 1.2.5, and 1.2.8 — operations through integration

The authoritative release allocation for commands, schedules/jobs, typed
request/forms, scoped query foundations, the `public/` directory, Apache/Nginx
proxy deployment, and fixed-port OS services is in
[`ROADMAP.md`](../ROADMAP.md). In particular, service installation must fail
when the requested port is occupied; changing a port is explicit and must
restore the previous service configuration if restart fails.

### Linux systemd service slice — implemented on the current work branch, unreleased

- `zelyra service install --port <port>` writes a per-project systemd user unit
  for the canonical current directory. It references an existing project
  `.env` without copying values, uses an explicit loopback port, checks the
  project first, and rolls back the unit if systemd start/readiness fails.
- `change --port`, `status`, `restart`, and `remove` are implemented. Port
  change stops the old process, rejects an occupied target, atomically replaces
  the unit, reloads systemd, and verifies the listener. Failed startup restores
  the prior unit and attempts to restart the prior service. Manually edited
  units are not overwritten by port changes.
- Ports are never automatically selected. Service state is managed with
  `systemctl --user`; enabling user lingering for startup before login remains
  a deliberate administrator action. Apache/Nginx can proxy to the loopback
  listener but do not execute Zelyra code.
- Focused tests cover argument validation, port conflicts, path escaping and
  newline rejection, generated-unit verification with `systemd-analyze`, and
  simulated occupied-port and failed-restart rollback paths. A live systemd
  user bus is unavailable in this environment (`systemctl --user` reports no
  `DBUS_SESSION_BUS_ADDRESS`/`XDG_RUNTIME_DIR`), so install/change/restart/remove
  have not been run against a real user manager. Do not call the service slice
  production-verified yet.
- Remaining 1.2.5 work is substantial: tenant context and safe query HIR,
  typed request/form lifecycle and safe old input, durable transactional jobs
  and lease workers, cross-backend security parity, and full release gates.
  The resident scheduler now runs inside the active `serve` service; distributed
  leases and persistent retries remain open.
- Audit of the five reported compiler gaps against code and workspace tests:
  payload enums, typed string interpolation, generic structs/records, and
  opt-in mutable arrays are already implemented; the full workspace test run
  confirms their existing positive and negative checks. The Bytecode VM remains
  a tested, limited subset, and changing its default remains open until parity
  is demonstrated. The roadmap now reflects this evidence.
- Schedule automation acceptance added: checked schedule declarations must
  drive idempotent outbox setup and the resident scheduler. The scheduler in
  `serve` reloads project source at each minute boundary and runs only current,
  valid declarations. Setup does not install cron rows and removes old
  Zelyra-managed `.zelyra/schedules.cron` files; foreign crontabs are never
  modified.
- CLI help and tutorial docs now state that manually started `serve` does not
  run schedules, cron export is only a preview, and the legacy trigger does not
  execute jobs. The resident scheduler runs only inside the installed, active
  Linux systemd service.
- Scheduler handlers now also have a configurable wall-clock limit:
  `[runtime].scheduler_job_timeout_seconds` applies to the resident service,
  defaults to 300 seconds, and accepts 1 through 86,400. On expiry the scheduler
  terminates the child process and logs the failure; Studio displays the
  effective value in its runtime budget dialog. A real child-process test
  verifies termination, while parser checks cover bounds and duplicate values.
  This is still not a durable job system: failed jobs are not retried
  automatically, and external effects that occurred before timeout cannot be
  rolled back.
- `zelyra schedule status main.zyl [--json]` reports declared schedules,
  service installation/activity, and the resulting scheduler state. It checks
  the project, is read-only, and does not start a service. A CLI integration
  test isolates the systemd configuration directory and confirms that declared
  schedules are inactive without an installed service. The JSON interface is
  versioned.
- Studio Run supports interactive `read_console` input through protected local
  API routes: prompt output appears live, one line is sent to the same process,
  EOF closes stdin, and cancel stops the process. Input is limited to 4,096
  bytes; the existing 15-second run limit still applies. A Rust test covers a
  line and EOF. A Chromium browser E2E runs the same console flow through
  `zelyra run` and Studio and compares actual output. This remains part of the
  unreleased 1.2.5 work branch.
- `examples/algorithms/` adds five runnable console exercises: insertion sort,
  linear search, an array-backed stack, bounded recursive factorial, and
  dynamic-programming Fibonacci. `zelyra check` and `zelyra run` passed; CLI
  integration verifies expected output and edge cases. The project allows
  20,000 steps; sorting/search are capped at 100 values, factorial at 12, and
  Fibonacci at index 45. The example makes no large-data performance claim.

### Public directory and reverse proxy — partial

- `zelyra new` now creates `public/` as an Apache or Nginx document root. The
  German and English deployment guides show direct serving of existing files
  and proxy fallback for Zelyra routes.
- `zelyra serve` now serves files up to 32 MiB with binary-safe responses,
  MIME types, GET/HEAD, cache hints, and security headers. Declared routes have
  precedence. Dotfiles are denied except beneath `.well-known/`; traversal,
  encoded path separators, and symlinks outside canonical `public/` are denied.
- All 148 web tests passed, including real HTTP binary transfer, HEAD length, route
  precedence, dotfile/traversal protection, and external symlink rejection.
  The Apache/Nginx examples have not been tested against installed web servers.

### Form sensitivity — focused slice implemented

- Form `widget` values are compiler-checked; `password` renders a native
  password input. Password fields and fields named with `password`, `token`,
  `secret`, or `hash` are not replayed in form values. Unknown widgets produce
  `E-FORM-006`.
- Positive/negative compiler and rendering tests pass. A 422 POST integration
  test confirms safe values are retained and escaped, invalid fields are
  marked, and secrets are redacted. The complete request/middleware/redirect
  pipeline and a general typed sensitivity contract remain open.

### Project evaluation step budget — implemented, unreleased

- `[runtime].max_steps` sets an optional positive step budget for `zelyra run`,
  executed API handlers, and scheduled handlers launched by the resident
  service through `zelyra run`. The CLI `--max-steps` option overrides the
  project value. Without either value, AST evaluation is unbounded, while MIR
  and Bytecode use their CLI defaults.
- Studio displays the configured project value or reports that it is unset.
  The option is documented in `docs/env.*` and the Studio guide.
- Tests cover valid/invalid settings, CLI precedence, AST/MIR/Bytecode, API
  handlers, and the Studio property in Chromium.
