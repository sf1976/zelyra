# Delivery status: Zelyra 1.1.5 through 1.3.0

Status: active modules/packages and interpreter roadmap; neither 1.1.5 nor
1.3.0 is complete. The published stable release is 1.1.2. This file records
current scope and remaining evidence.

## Removed from the project

At the owner's request, the Laravel migration tool was removed from the active
repository on 2026-10-17. Previous source, guides, tests, and analysis reports
are preserved in the external archive
a private archive outside the repository. No Laravel
importer or exporter is part of the current release gates.

## 1.1.5 — modules, packages, and safe metadata

- Local `pkg:` dependencies, deterministic locking, public exports,
  type/cycle/capability checks, and offline resolution are implemented.
- Imported commands and schedules are namespace-qualified; local settings have
  typed schemas. Studio can edit local values with revision checks and redacts
  secrets.
- HostServices abstracts supported clock, environment, random, process,
  filesystem, database, console, HTTP, and mail operations. This does not prove
  full backend parity or a stable plugin ABI.
- `zelyra reflect <entry> --format=json` deterministically exports checked
  modules, symbols, tables, routes, APIs, forms, and contract source locations.
  Schema version 1 is implemented; live database schema and Markdown/OpenAPI
  formats remain open.
- Open: broad package/VM effect parity, package trust/signatures, safe web
  configuration for all modules, and a fully evidenced multi-backend module
  deployment.

## 1.3.0 — AST reference, MIR, and bytecode

- AST remains the reference backend and default. MIR and versioned bytecode are
  opt-in experimental subsets with verification, step/stack limits, HostServices,
  and differential tests.
- Supported slices include typed control flow, records, collections, tuples,
  enums/match, closures, and selected host/SQL/outbox operations. Unsupported
  operations must fail closed.
- Goal: make verified Bytecode the default for `run`, `serve`, and tasks only
  after full supported-language, effect, capability, contract, resource, host,
  and diagnostic parity is proven. AST remains the reference and differential
  backend. Until those gates pass, AST remains the default and unsupported
  Bytecode operations fail closed. This is a portable Bytecode goal, not native
  machine-code generation.
- Open: full parity; broader differential, fuzz, and security coverage;
  reproducible performance measurements; and the backend-default release gate.

## 1.2.0, 1.2.5, and 1.2.8 — operations through integration

The authoritative release allocation for commands, schedules/jobs, typed
request/forms, scoped query foundations, the `public/` directory, Apache/Nginx
proxy deployment, and fixed-port OS services is in
[`ROADMAP.md`](../ROADMAP.md). In particular, service installation must fail
when the requested port is occupied; changing a port is explicit and must
restore the previous service configuration if restart fails.

### Linux systemd service slice — implemented on the current work branch, unreleased

- `zelyra service install --port <port>` writes a per-project systemd user unit
  for the canonical current directory. It references an existing project
  `.env` without copying values, uses an explicit loopback port, checks the
  project first, and rolls back the unit if systemd start/readiness fails.
- `change --port`, `status`, `restart`, and `remove` are implemented. Port
  change stops the old process, rejects an occupied target, atomically replaces
  the unit, reloads systemd, and verifies the listener. Failed startup restores
  the prior unit and attempts to restart the prior service. Manually edited
  units are not overwritten by port changes.
- Ports are never automatically selected. Service state is managed with
  `systemctl --user`; enabling user lingering for startup before login remains
  a deliberate administrator action. Apache/Nginx can proxy to the loopback
  listener but do not execute Zelyra code.
- Focused tests cover argument validation, port conflicts, path escaping and
  newline rejection, generated-unit verification with `systemd-analyze`, and
  simulated occupied-port and failed-restart rollback paths. A live systemd
  user bus is unavailable in this environment (`systemctl --user` reports no
  `DBUS_SESSION_BUS_ADDRESS`/`XDG_RUNTIME_DIR`), so install/change/restart/remove
  have not been run against a real user manager. Do not call the service slice
  production-verified yet.
- Remaining 1.2.5 work is substantial: tenant context and safe query HIR,
  typed request/form lifecycle and safe old input, durable transactional jobs,
  lease workers, coordinated scheduling, cross-backend security parity, and
  full release gates.
- Schedule automation acceptance added: checked schedule declarations must
  drive idempotent outbox setup and a project-managed cron export, while the
  coordinated `serve` scheduler actually runs those declarations. Cron export
  is not activation, and user crontabs must not be modified implicitly. This
  remains the complete acceptance target. The setup slice now creates
  `.zelyra/schedules.cron` during schema setup or `serve` startup and
  idempotently ensures MariaDB outbox storage for scheduled handlers declaring
  `Email`. Host activation and coordinated schedule execution in `serve` are
  still open.

### Verification of the current worktree

- `cargo fmt --all -- --check`, `cargo check --workspace --locked`,
  `cargo test --workspace --locked`, and
  `cargo clippy --workspace --locked -- -D warnings` passed. Workspace tests
  reported one ignored MariaDB password-reset end-to-end fixture; it was not
  counted as executed. `git diff --check` passed.
- Service tests include generated-unit validation with `systemd-analyze` when
  available and simulated lifecycle/rollback paths. A live user-systemd manager
  is still unavailable in this environment, so OS lifecycle behavior remains
  unverified. Full release artifact gates have not been run for this worktree.
- The automatic schedule-setup slice runs after explicit schema setup or when
  `serve` starts: schedules in the checked linked project produce a managed
  `.zelyra/schedules.cron` export, changed declarations refresh only that
  managed file, and removing all declarations removes that managed export.
  Scheduled `Email` handlers ensure MariaDB outbox storage through idempotent
  DDL. `schedule trigger` now requires the project's installed and active
  systemd user service plus the authenticated `serve` probe. The service unit
  supplies a project identity marker; manually starting `serve` does not
  publish a scheduler probe. A Linux integration test exercises a trigger with
  a simulated active unit and verifies skipping after server shutdown. The
  focused schedule-export, trigger, and web-probe tests passed. Full workspace
  tests and Clippy have not yet been rerun after these newest service gates.
  Cron remains an external, manually activated preview; a scheduler integrated
  directly into `serve` is the preferred next implementation step.

## Last checks for this work slice

- 493 CLI unit tests and 107 machine-interface integration tests passed before
  the Laravel tool was removed.
- The `reflect` export ran on the invoice tutorial; focused integration tests
  cover determinism, relative paths, omitted UI text, and fail-closed behavior
  on syntax errors.
- After removing the Laravel tool, targeted CLI tests and release checks must
  run again; earlier test counts do not apply to that state.
- A bounded pure `csv_import` package was added to `examples/business_modules`.
  It uses the existing 16 MiB-limited CSV decoder, requires a header with
  non-empty column names, and rejects data rows with a different field count; it does not write to a
  database. `zelyra package lock --check` and `zelyra check main.zyl` passed.
  The CLI integration tests
  `reusable_csv_export_package_runs_with_matching_backend_output` and
  `reusable_csv_import_package_checks_rows_on_all_execution_backends` passed
  on this worktree; both exercise AST, MIR, and Bytecode, including malformed
  row shape and an empty header column for the import example. This does not complete ODBC, Excel/PDF
  exchange, database mapping, or general backend parity.
- Package manifests now accept an optional `zelyra` SemVer requirement. The
  package graph rejects malformed or incompatible requirements before lock
  generation or use; `zelyra module list` exposes the requirement in both
  output formats. The manifest checksum makes compatibility changes invalidate
  the lock. The business-modules example declares the supported 1.1 line. The
  package unit test covers compatible, incompatible, malformed, and stale-lock
  cases; an integration test verifies that an incompatible package cannot
  produce a lockfile. The bundle integration also confirms that a selected
  package keeps its compatibility range and that its lock and compiler check
  still pass. All 70 `module_imports` integration tests passed after this
  change. This narrows compiler-version drift but does not establish a
  publisher-signature or remote package trust model.

- `zelyra module init <directory> --name <package-name> [--version <semver>]`
  now creates a checkable offline package scaffold. Its manifest declares the
  current CLI minor compatibility range and no effects; the source contains a
  typed public starter function. Creation refuses existing targets and
  duplicate options. The integration test locks, checks, and runs the generated
  package, then verifies the rejection cases. The focused test and all 70
  `module_imports` integration tests passed; `cargo check -p zelyra-cli --locked`,
  `cargo fmt --all -- --check`, and `git diff --check` passed.
- Final 1.1.5 Studio verification: `npm ci --prefix editor` completed with zero
  reported vulnerabilities; editor metadata/language tests passed (55 UI
  components and 98 compiler-reserved words); the rebuilt standalone editor
  bundle is 567,017 bytes (553.7 KiB), below the 600 KiB hard limit. The full
  browser suite passed in Chromium, including responsive overflow and axe checks
  at 360, 768, 1280, and 1920 CSS pixels, 200% zoom-equivalent layout, PDF,
  semantic rename, Canvas, capabilities, runtime tools, and module settings.
  The new two-row toolbar keeps the project-check action visible; selecting a
  file closes the mobile overlay after the viewport enters the narrow layout.
  The reviewed Studio screenshot baseline records this intentional layout fix.
  First usable editor was measured at 1,078 ms and the analysis response at
  53 ms in the semantic rename browser scenario; these are scenario timings, not
  server startup benchmarks.
- The 1.1.5 release build and packaged Linux archive smoke passed, including
  SHA-256 checks, installation dry-run, CLI version output, and HTTP retrieval
