# Zelyra 0.3.0 Release Plan

**Status:** Working plan, not a release promise · **Starting point:** published experimental Zelyra 0.2.0
**Goal:** a clear next step toward an approachable, distinctive, extensible platform for database-backed applications

This is the separate working document for 0.3.0. It complements, but does not
replace, the [maintained roadmap](../ROADMAP.md). The roadmap records long-term
goals; this plan proposes priorities for the next release. Open items are not
claims that the work is already implemented. Scope and status will be reviewed
as milestones are completed.

## Guiding decision

0.3.0 should advance Zelyra not by maximizing the number of new language
constructs, but by delivering a coherent and convincing path from a first
project to a professionally customizable web application:

1. **Easy to start:** installation, project creation, database startup, and
   troubleshooting must be understandable and reproducible for new users.
2. **Distinctive views:** Zelyra's web design should be recognizable and
   professional. Developers need documented extension points that do not
   require editing compiler files or generated output.
3. **Evidence of correctness:** MariaDB-backed core workflows, safe schema
   changes, and generated CRUD pages must be backed by real tests.

The release remains experimental unless its maturity, platform coverage, and
security evidence justify a different classification. Neither a release tag
nor passing tests demonstrate general production readiness or mathematical
freedom from defects.

## Proposed milestones

### 0 — Establish scope and baseline

- [ ] Collect known defects, open release risks, and feedback from 0.2.0; rank
  them by severity.
- [ ] Define a concrete acceptance condition and reproducible test path for
  each included scope item.
- [ ] Separate release blockers, 0.3.0 goals, and roadmap items explicitly
  deferred.
- [ ] Set no dates or public performance claims until effort and dependencies
  have been reviewed.

**Exit criterion:** an agreed scope in which every release claim points to a
test, verifiable artifact, or explicitly stated limitation.

### 1 — Simple and safe first run

- [ ] Document and exercise a complete clean installation on a supported Linux
  system: install, `zelyra new`, check, database setup, and application start.
- [ ] Make missing Docker/Compose, Docker permissions, occupied ports, invalid
  configuration, and unreachable MariaDB produce clear, actionable guidance.
- [ ] Review whether suggested permission changes are properly explained. In
  particular, Docker-group membership grants extensive, effectively
  root-equivalent privileges and must not be presented as a harmless default.
- [ ] Ensure `.env` remains protected by default, credentials never appear in
  success or error output, and existing `.env` files are never silently
  overwritten.
- [ ] Test port selection and actual host/container port mappings on first and
  repeated setup.
- [ ] Verify German/English and `ZELYRA_LEVEL=learn|work` across generated
  onboarding pages.
- [ ] Run at least one documented onboarding test with a person who does not
  develop Zelyra; record observations and blockers.

**Exit criterion:** a new user can follow the documented path without hidden
prior knowledge; failures lead to safe, specific next steps. Tested platforms
and limitations are stated accurately.

### 2 — Distinctive, extensible views and templates

- [ ] Document the existing views, components, slots, CRUD layouts, language
  catalogs, and `zelyra.theme.css` as one coherent public customization model.
- [ ] Define a stable project-local extension point for the default design.
  Customizations should survive updates and must not require editing generated
  files or the Zelyra compiler.
- [ ] Give the standard template a consistent, responsive visual system across
  CRUD list, detail, create/edit, delete, login, form, tableview, navigation,
  and error states.
- [ ] Deliberately complete design tokens and define which areas are customized
  through CSS versus Zelyra views/components.
- [ ] Provide a complete customization example: use the default view, change
  colors/typography, adapt a layout, and give one resource a custom view.
- [ ] Verify that customizations cannot bypass HTML escaping, CSRF,
  authorization, form validation, or safe database access.
- [ ] Add tests for rendering order, fallback slots, language selection, and
  preserved security boundaries.
- [ ] Do not make a drag-and-drop editor a prerequisite for 0.3.0.

**Exit criterion:** the default design is coherent and recognizable; a project
can customize it through documented, tested extension points without losing
security controls. Do not describe the delivered scope as a complete theme
editor.

### 3 — Harden the MariaDB core path and schema safety

- [x] MariaDB `db create` and `db setup` emit the documented InnoDB/
  utf8mb4 baseline DDL, with regression coverage that keeps SQLite and
  PostgreSQL output backend-specific.
- [ ] Test `zelyra db create|setup|bootstrap|inspect|plan|apply` against the
  documented MariaDB scope on an isolated test database.
- [ ] Keep schema changes fail-closed: destructive or unsupported changes must
  not run silently; risk, preview, and required approval must be clear.
- [ ] Cover fresh install, repeated setup, existing schemas, connection errors,
  and port conflicts.
- [ ] Update MariaDB compatibility tests for the versions declared for 0.3.0
  and document their limits.
- [ ] Preserve SQLite regression tests. Do not claim PostgreSQL runtime parity
  or broad database portability unless the relevant scope and tests exist.
- [ ] If appropriate, rerun the machine-management application as a complete
  acceptance application, from a fresh generated project through search,
  filtering, forms, and permission cases.

**Exit criterion:** documented database commands and important CRUD workflows
pass isolated positive and negative integration tests; risky or unsupported
schema changes remain protected.

### 4 — Prove one real business workflow end to end

- [~] Fully exercise at least one representative MariaDB application generated
  from a fresh project, including schema, relations, search/filters, form
  validation, permissions, and views. A checked customer/order application
  with a custom shell, CRUD pages, and an aggregate tableview is now included;
  its MariaDB path is wired into the reusable tableview E2E test. Clean CI
  execution remains the release evidence.
- [ ] As a recommended extension test, build a small customer/order application
  with a relational query, aggregation, and custom view. Make it a release gate
  only if it fits the agreed scope without displacing security and stability
  work.
- [ ] Isolate setup and test data; tests must not alter user or production data.
- [ ] Ensure the example, documentation, and integration test use the same
  actually supported Zelyra code path.

**Exit criterion:** at least one complete application workflow is
automatically reproducible. A second application may be a target, but must not
be advertised as a delivered release capability without evidence.

### 5 — Keep compiler and AI interfaces dependable

- [ ] Review existing machine-readable diagnostics, `context`, `impact`, and
  formatting for deterministic output, stable schema versions, and portable
  relative paths.
- [ ] Add repeatability and secret-redaction tests where coverage is missing.
- [ ] Preserve human-readable diagnostics, stable error codes, and precise
  source spans; do not hide compiler failures by weakening checks.
- [ ] Accurately distinguish implemented, experimental, and planned AI-related
  features in the handbook and CLI reference.
- [ ] Do not require an external AI integration; source code must not be sent
  to external providers without an explicit, separately reviewed decision.
- [ ] Do not automatically make richer semantic edits, complete impact
  analysis, granular effects, or a benchmark 0.3.0 blockers; if included, give
  each its own acceptance criteria.

**Exit criterion:** documented machine interfaces are tested and
vendor-neutral; no AI output substitutes for compiler and test evidence.

### 6 — Release quality and publication

- [ ] Update bilingual release notes, changelog, installation, and upgrade
  instructions.
- [ ] Check version numbers, package metadata, `zelyra --version`, tags, and
  artifacts for consistency.
- [ ] Before release, run at least `cargo fmt --check`,
  `cargo check --workspace`,
  `cargo clippy --workspace --all-targets -- -D warnings`,
  `cargo test --workspace`, and relevant MariaDB/web end-to-end tests.
- [ ] Build release binaries and archives for the targets actually supported;
  verify SHA-256 checksums. Claim reproducibility only for toolchains and
  targets where it has been demonstrated again.
- [ ] Smoke-test installation and update paths for the published artifacts.
- [ ] Clearly list known issues, experimental status, and unsupported
  platforms/database capabilities.
- [ ] Publish 0.3.0 only when all mandatory gates pass; otherwise adjust scope
  or defer publication.

## Not automatically in 0.3.0

These remain long-term or optional goals unless explicitly added to scope with
capacity and tests:

- a complete visual theme/drag-and-drop editor;
- formal proof of general correctness or complete verification;
- full PostgreSQL, MySQL, or SQL Server runtime parity;
- AI-provider integration or a cloud requirement;
- a self-hosting compiler;
- every roadmap item, including jobs, multi-tenancy, additional package
  platforms, or every view capability.

## Release gate (must be completed before publication)

- [ ] All included P0 issues are fixed or explicitly deferred with a visible
  rationale.
- [ ] Formatting, workspace check, Clippy, and tests pass.
- [ ] Isolated MariaDB integration and generated-application acceptance pass.
- [ ] Database, web, authentication, and secret boundaries have been reviewed.
- [ ] German/English documentation and example commands are verified against
  the release build.
- [ ] Installation artifacts, checksums, and update path are verified.
- [ ] Known limitations and release maturity are published honestly.
- [ ] The roadmap and both handbooks reflect what was actually delivered.

## Working through this plan

Work through milestones individually and in a sensible order. After each
completed step, run tests and update both roadmaps and, where needed, both
handbooks. Commit completed subfeatures in focused changes; push no later than
before a longer pause. This document is the worklist, not a release tag or
advance approval for risky database changes.
