# Zelyra 0.3.0 Release Plan

**Status:** Working plan, not a release promise · **Starting point:** published experimental Zelyra 0.2.0
**Goal:** a clear next step toward an approachable, distinctive, extensible platform for database-backed applications

This is the separate working document for 0.3.0. It complements, but does not
replace, the [maintained roadmap](../ROADMAP.md). The roadmap records long-term
goals; this plan proposes priorities for the next release. Open items are not
claims that the work is already implemented. Scope and status will be reviewed
as milestones are completed.

## Guiding decision

0.3.0 should advance Zelyra not by maximizing the number of new language
constructs, but by delivering a coherent and convincing path from a first
project to a professionally customizable web application:

1. **Easy to start:** installation, project creation, database startup, and
   troubleshooting must be understandable and reproducible for new users.
2. **Distinctive views:** Zelyra's web design should be recognizable and
   professional. Developers need documented extension points that do not
   require editing compiler files or generated output.
3. **Evidence of correctness:** MariaDB-backed core workflows, safe schema
   changes, and generated CRUD pages must be backed by real tests.

The release remains experimental unless its maturity, platform coverage, and
security evidence justify a different classification. Neither a release tag
nor passing tests demonstrate general production readiness or mathematical
freedom from defects.

## Proposed milestones

### 0 — Establish scope and baseline

- [x] Collect known defects, open release risks, and feedback from 0.2.0; rank
  them by severity. `docs/release-readiness/0.3.0-risk-register.en.md` records
  the automated-test baseline, the absence of documented external feedback,
  residual risks, and the missing candidate-artifact evidence.
- [x] Define a concrete acceptance condition and reproducible test path for
  each included scope item. The risk register maps compiler, database, web,
  authentication, packaging, installation, and documentation claims to their
  exact checks.
- [x] Separate release blockers, 0.3.0 goals, and roadmap items explicitly
  deferred. The risk register and bilingual release notes provide the three
  categories and keep P0/P1/P2 decisions visible.
- [x] Set no dates or public performance claims until effort and dependencies
  have been reviewed. The register makes no schedule or performance promise.

**Exit criterion:** an agreed scope in which every release claim points to a
test, verifiable artifact, or explicitly stated limitation.

### 1 — Simple and safe first run

- [x] Document and exercise a complete clean installation on a supported Linux
  system: install, `zelyra new`, check, database setup, and application start.
  The isolated `tests/installer-e2e.sh` exercises a real source install, repeat
  install, version check, and safe uninstall. The complete installed-CLI path
  is covered by `tests/clean-onboarding-e2e.sh`, and passed on the fresh Ubuntu
  runner in [CI run 35573616419](https://github.com/sf1976/zelyra/actions/runs/35573616419).
- [x] Make missing Docker/Compose, Docker permissions, occupied ports, invalid
  configuration, and unreachable MariaDB produce clear, actionable guidance.
  `doctor`, Compose failure handling, port validation, and the machine-interface
  test for an unavailable database cover these cases without echoing secrets.
- [x] Review whether suggested permission changes are properly explained. The
  setup guide and onboarding guide explicitly state that Docker-group
  membership grants extensive, effectively root-equivalent privileges; they
  recommend checking `docker ps` and using the distribution's documented setup
  rather than presenting group membership as a harmless default.
- [x] Ensure `.env` remains protected by default, credentials never appear in
  success or error output, and existing `.env` files are never silently
  overwritten. The generated Docker E2E verifies owner-only permissions,
  secret-free output, unchanged credentials, and repeated setup.
- [x] Test port selection and actual host/container port mappings on first and
  repeated setup. The generated Docker E2E checks the effective URL and
  published mappings on both runs.
- [x] Verify German/English and `ZELYRA_LEVEL=learn|work` across generated
  onboarding pages. The MariaDB CRUD E2E renders all four combinations.
- [ ] Run at least one documented onboarding test with a person who does not
  develop Zelyra; record observations and blockers.

**Exit criterion:** a new user can follow the documented path without hidden
prior knowledge; failures lead to safe, specific next steps. Tested platforms
and limitations are stated accurately.

### 2 — Distinctive, extensible views and templates

- [x] Document the existing views, components, slots, CRUD layouts, language
  catalogs, and `zelyra.theme.css` as one coherent public customization model.
  The getting-started guide and both handbook languages point to the checked
  theme customization example.
- [x] Define a stable project-local extension point for the default design.
  Customizations should survive updates and must not require editing generated
  files or the Zelyra compiler. `zelyra.theme.css` and project-local views are
  copied into generated Docker projects and loaded beside the source file.
- [x] Give the standard template a consistent, responsive visual system across
  CRUD list, detail, create/edit, delete, login, form, tableview, navigation,
  and error states. The built-in stylesheet uses shared tokens for table/card
  lists, detail and form cards, confirmation/loading/error states, actions, and
  navigation; web tests cover all state families and responsive breakpoints.
- [x] Deliberately complete design tokens and define which areas are customized
  through CSS versus Zelyra views/components. `env.en.md` documents the full
  token contract and generated `zelyra.theme.css` includes every token as a
  safe template; structure, content, and security logic remain in views and
  generated components.
- [x] Provide a complete customization example: use the default view, change
  colors/typography, adapt a layout, and give one resource a custom view.
  `examples/theme_customization/` covers the custom `Customer` resource and
  the default-shell `Ticket` resource; its source and rendered route pass CI.
- [x] Verify that customizations cannot bypass HTML escaping, CSRF,
  authorization, form validation, or safe database access. Web tests cover
  escaping loaded values in custom CRUD layouts plus CSRF, validation, and
  authorization in custom form layouts; compiler and runtime tests keep
  database access typed and parameterized.
- [x] Add tests for rendering order, fallback slots, language selection, and
  preserved security boundaries. Theme and web tests cover default/project CSS
  order, existing slot fallbacks, and locale catalogs; a regression test
  ensures a custom form layout cannot bypass CSRF, validation, or authorization.
- [x] Do not make a drag-and-drop editor a prerequisite for 0.3.0. The draft
  release notes list it as an explicit non-goal.

**Exit criterion:** the default design is coherent and recognizable; a project
can customize it through documented, tested extension points without losing
security controls. Do not describe the delivered scope as a complete theme
editor.

### 3 — Harden the MariaDB core path and schema safety

- [x] MariaDB `db create` and `db setup` emit the documented InnoDB/
  utf8mb4 baseline DDL, with regression coverage that keeps SQLite and
  PostgreSQL output backend-specific.
- [x] Test `zelyra db create|setup|bootstrap|inspect|plan|apply` against the
  documented MariaDB scope on an isolated test database. The MariaDB CRUD E2E
  path now renders DDL, repeats bootstrap, inspects, plans, and applies an
  idempotent schema before exercising the web workflow.
- [x] Keep schema changes fail-closed: destructive or unsupported changes must
  not run silently; risk, preview, and required approval must be clear. The
  SQLite and MariaDB schema-safety suites verify refusal, review levels,
  read-only preflights, data preservation, and explicit approval paths.
- [x] Cover fresh install, repeated setup, existing schemas, connection errors,
  and port conflicts. The generated-project and MariaDB CRUD E2E paths cover
  fresh and repeated setup; schema-safety covers populated existing schemas;
  the CRUD path checks `E-DB-002` plus credential redaction; and CLI machine
  interface tests cover automatic free-port selection and explicit conflicts.
- [x] Update MariaDB compatibility tests for the versions declared for 0.3.0
  and document their limits. CI run [35571692858](https://github.com/sf1976/zelyra/actions/runs/35571692858)
  passed the core integrations on MariaDB 10.11.19, 11.4.13, 11.8.9, and
  12.3.3; the compatibility document records the non-claims.
- [x] Preserve SQLite regression tests. The SQLite schema E2E and schema-safety
  suite remain in CI; PostgreSQL coverage remains schema-safety-only and is not
  presented as runtime parity.
- [x] Rerun the machine-management application as a complete acceptance
  application, from a fresh generated project through search, filtering, forms,
  and permission cases. `examples/machine_management_auth.zyl` and
  `tests/generated-project-machine-auth-e2e.sh` cover anonymous denial, viewer
  access, create/edit denial, authorized CRUD forms, search, and deletion; the
  complete evidence is green in [CI run
  35583000462](https://github.com/sf1976/zelyra/actions/runs/35583000462).

**Exit criterion:** documented database commands and important CRUD workflows
pass isolated positive and negative integration tests; risky or unsupported
schema changes remain protected.

### 4 — Prove one real business workflow end to end

- [x] Fully exercise at least one representative MariaDB application generated
  from a fresh project, including schema, relations, search/filters, form
  validation, permissions, and views. A checked customer/order application
  with a custom shell, CRUD pages, and an aggregate tableview is now included;
  its MariaDB path is wired into the reusable tableview E2E test. The complete
  CI run for the generated business application and customer/order acceptance
  path passed on 2026-09-21.
- [x] As a recommended extension test, build a small customer/order application
  with a relational query, aggregation, and custom view. The checked example
  uses the same MariaDB tableview E2E path as the baseline example; release
  gating still depends on the primary application's clean CI evidence.
- [x] Isolate setup and test data; tests must not alter user or production data.
  The tableview examples use dedicated CI databases, and the acceptance
  fixture removes its generated rows during cleanup.
- [x] Ensure the example, documentation, and integration test use the same
  actually supported Zelyra code path. The customer/order documentation points
  to `examples/customer_orders.zyl`, and CI executes that exact file.

**Exit criterion:** at least one complete application workflow is
automatically reproducible. A second application may be a target, but must not
be advertised as a delivered release capability without evidence.

### 5 — Keep compiler and AI interfaces dependable

- [~] Review existing machine-readable diagnostics, `context`, `impact`, and
  formatting for deterministic output, stable schema versions, and portable
  relative paths. Project files now use project-relative paths in JSON
  diagnostics and impact entries; non-project paths retain their useful input
  path.
- [x] Add repeatability and secret-redaction tests where coverage is missing.
  Machine-interface tests repeat JSON output and verify that configuration and
  failed database diagnostics do not expose credentials.
- [x] Preserve human-readable diagnostics, stable error codes, and precise
  source spans; do not hide compiler failures by weakening checks. CLI tests
  cover lexer/parser/database errors with stable codes and source locations.
- [x] Accurately distinguish implemented, experimental, and planned AI-related
  features in the handbook and CLI reference. Both handbook languages list
  `check`, `context`, source-only `impact`, and validated `edit` preview as
  experimental, available interfaces; richer typed gaps, runtime/schema
  impact, and benchmarks remain planned.
- [x] Do not require an external AI integration; source code must not be sent
  to external providers without an explicit, separately reviewed decision.
  The architecture, handbooks, and release-note draft describe only local,
  source-based interfaces.
- [x] Do not automatically make richer semantic edits, complete impact
  analysis, granular effects, or a benchmark 0.3.0 blockers; the release-note
  draft lists them as planned or explicitly out of scope.

**Exit criterion:** documented machine interfaces are tested and
vendor-neutral; no AI output substitutes for compiler and test evidence.

### 6 — Release quality and publication

- [x] Update bilingual draft release notes, changelog, installation, and
  upgrade instructions. `docs/release-notes/0.3.0.en.md` and `.de.md` state
  clearly that the candidate is not yet released; final tag-specific values
  remain a release-time task.
- [x] Check version numbers, package metadata, `zelyra --version`, tags, and
  artifacts for consistency. `scripts/check_release_metadata.py` compares
  workspace/lockfile versions, the matching tag, the changelog, and optionally
  the built CLI version; CI and packaging no longer hard-code a version.
- [x] Before release, run at least `cargo fmt --check`,
  `cargo check --workspace`,
  `cargo clippy --workspace --all-targets -- -D warnings`,
  `cargo test --workspace`, and relevant MariaDB/web end-to-end tests. The
  complete evidence, including the MariaDB matrix, Windows updater, onboarding,
  theme, and release-artifact smoke tests, is green in [CI run
  35579570133](https://github.com/sf1976/zelyra/actions/runs/35579570133).
- [ ] Build release binaries and archives for the targets actually supported;
  verify SHA-256 checksums. Claim reproducibility only for toolchains and
  targets where it has been demonstrated again.
- [ ] Smoke-test installation and update paths for the published artifacts.
  The reusable `tests/published-release-smoke.sh v0.2.0` passed on Linux
  x86_64, covering the published archive download, checksum-verified install,
  repeated install, and `zelyra update --check`. The final 0.3.0 candidate tag
  still needs the same evidence before this checkbox can be closed.
- [x] Clearly list known issues, experimental status, and unsupported
  platforms/database capabilities in both draft release-note files. The final
  publication gate remains open until the candidate evidence is complete.
- [ ] Publish 0.3.0 only when all mandatory gates pass; otherwise adjust scope
  or defer publication.

## Not automatically in 0.3.0

These remain long-term or optional goals unless explicitly added to scope with
capacity and tests:

- a complete visual theme/drag-and-drop editor;
- formal proof of general correctness or complete verification;
- full PostgreSQL, MySQL, or SQL Server runtime parity;
- AI-provider integration or a cloud requirement;
- a self-hosting compiler;
- every roadmap item, including jobs, multi-tenancy, additional package
  platforms, or every view capability.

## Release gate (must be completed before publication)

- [ ] All included P0 issues are fixed or explicitly deferred with a visible
  rationale.
- [x] Formatting, workspace check, Clippy, and tests pass.
- [x] Isolated MariaDB integration and generated-application acceptance pass.
- [x] Database, web, authentication, and secret boundaries have been reviewed.
  `docs/security-review-0.3.0.md` records the accepted experimental boundaries,
  residual risks, and exact CI evidence without claiming an external audit.
- [x] German/English documentation and example commands are verified against
  the current locked, release-compatible build and handbook snippets;
  candidate-tag artifact verification remains a separate open gate.
- [ ] Installation artifacts, checksums, and update path are verified.
- [x] Known limitations and release maturity are published honestly in both
  draft release-note files; final candidate publication remains gated.
- [x] The roadmap and both handbooks reflect what was actually delivered.
  The bilingual roadmaps and master/intro handbooks now identify 0.2.0 as the
  current experimental release and link the proposed 0.3.0 plan; candidate
  artifact and human onboarding gates remain separate and open.

## Working through this plan

Work through milestones individually and in a sensible order. After each
completed step, run tests and update both roadmaps and, where needed, both
handbooks. Commit completed subfeatures in focused changes; push no later than
before a longer pause. This document is the worklist, not a release tag or
advance approval for risky database changes.
