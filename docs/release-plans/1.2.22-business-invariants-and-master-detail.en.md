# 1.2.22 — Business Rules and Master-Detail CRUD

## Assessment of the submitted requirements

The four layers are a target architecture, but they are not four new compiler
gaps. The state on `main` after 1.2.21 is:

| Area | Actual state | Boundary |
| --- | --- | --- |
| Tenant schema | `scoped by`, `unique within tenant`, composite tenant-scoped foreign keys, and required target keys are implemented. MariaDB tests prove that cross-tenant relations are rejected. | The `tenant_id` column must also be declared as shown in the example. The database planner checks schema changes and existing data; this is not general tenant authorization for arbitrary SQL. |
| Invariants | Table rules are type-checked and run before generated CRUD and declarative form writes. APIs can explicitly bind input fields. | API binding is currently limited to POST/PUT/PATCH and unscoped tables. Handler transformations and raw SQL writes are not covered. |
| Lifecycle permissions | 1.2.21 supports type-checked `permits ... when` and `guard ... when` rules for edit/delete. Server mutation paths check stored rows inside the mutation transaction; CRUD detail actions and assigned TableView actions synchronize visibility. | Conditions currently target the existing edit/delete rules. They do not replace permission checks and do not automatically apply to arbitrary hand-written routes. |
| Master-detail | CRUD `has_many`, joint parent/child persistence, and transactional aggregates were missing before this milestone. | This implementation supports one direct child relation per CRUD and at most 50 rows per submission. |

## Scope decisions

1. The first implementation supports one direct child relation per CRUD. It
   must reference a declared foreign-key column in the child model pointing
   to the parent primary key. Ambiguous, cyclic, or untypable relations fail
   during checking.
2. Create and Edit receive a generated accessible line-item grid. Existing
   CRUD routes remain responsible for authorization, CSRF, validation, tenant
   scope, and persistence. Child values come only from declared child fields;
   IDs and tenant keys are never accepted from the form.
3. Parent and child changes are persisted in one database transaction. A
   child validation or write failure rolls back the entire operation. Edit
   loads and changes only children belonging to the authorized parent.
4. Delete behavior comes from the existing relation/schema declaration. CRUD
   does not introduce a second, conflicting cascade configuration.
5. Aggregates are added only when their target column and expression are
   statically typable and computed server-side within the same transaction.
   Free SQL expressions and client-authoritative subtotals are excluded.
6. Existing business rules and record permissions from 1.2.20/1.2.21 remain
   in force. This feature does not silently expand their coverage to
   unprotected API or raw-SQL paths.

## Current implementation status

The parser creates `CrudChildRelationDef` and `CrudAggregateDef` nodes with
source spans. `zelyra check` validates the child model, relation to the CRUD
parent primary key, ordering field, optional consistency of the delete action,
and numeric targets and arithmetic aggregate expressions. The diagnostic code
is `E-CRUD-009`. Create/Edit render bounded server-side line-item rows. Parent
and child writes, invariant checks, edits, and aggregate recomputation run in a
single transaction. Child form values are excluded from parent-form validation
and validated against the child schema; sensitive child fields are omitted.
The MariaDB E2E has proved row add, rollback on invalid child data, create with
two lines and exact aggregate values, edit/recompute, and schema cascade delete.

- Parser/AST: typed `has_many` declaration with precise spans and tests for
  duplicate/invalid relations.
- Semantics: validate parent/child tables, foreign key, sort column,
  permitted form fields, and aggregate types.
- Web: Create/Edit render bounded child rows; successful and failed validation
  retain values and show errors.
- Database: MariaDB E2E proves atomic parent/line-item persistence, rollback,
  aggregates, edit, and the declared cascade. The fixture is unscoped, so this
  E2E does not claim to prove tenant isolation; existing tenant-relation tests
  cover the composite foreign-key constraint separately.
- Documentation and EN/DE roadmaps describe only verified syntax and keep the
  unsupported API/raw-SQL paths explicit.
