# Zelyra 0.8.0 release plan: visual schema map and guided CRUD

**Status:** Implementation is integrated at `e938a44` in the stacked branch.
The latest full CI run
[#38083443317](https://github.com/sf1976/zelyra/actions/runs/38083443317)
and Linux/Windows release builds
[#38083443319](https://github.com/sf1976/zelyra/actions/runs/38083443319) pass.
Functional, outbox, editor, and language-corpus gates plus an independent review
of transaction and lease boundaries remain open. This is not a production release.

## User outcome

A developer can open a configured project database, understand tables and
relationships, select a table, preview a generated CRUD module, and apply that
source change after Zelyra accepts it. Database data remains read-only in this
release.

## Scope

- Show a read-only schema map with table columns, keys, relationships, and
  differences between declared and live schemas. Make the source module for
  each declaration visible when that information is known.
- Let the user choose a table and fields, preview the generated Zelyra source,
  run compiler validation, inspect the source diff, and explicitly apply it.
- Keep schema writes and row mutations out of the visual workflow. Do not
  generate silently or overwrite files changed since the preview.
- Include the bounded local MariaDB transactional outbox already developed on
  the stacked 0.8 branch: an explicit typed enqueue in a business transaction,
  explicit one-event worker calls, bounded retry, and operator inspection and
  recovery. Delivery is at least once; handlers must be idempotent. This is not
  a general queue platform.
- Expand the 0.1 conformance corpus across lexer, parser, type checking, and
  formatting. Require accepted and rejected fixtures and formatter
  idempotence.
- Keep the workflow local, avoid external code services, and document each
  database introspection path separately.

## Release gates

- [ ] Test schemas with missing, extra, renamed, nullable, related, and unsupported
  columns; show uncertainty instead of guessing.
- [ ] Prove generated source passes the same compiler checks as hand-written code.
- [ ] Test stale-preview conflicts, cancellation, malformed database metadata, and
  read-only behavior for every supported introspection backend.
- [ ] Prove outbox/business-row commit and rollback atomicity, lease safety under
  competing workers, bounded retry, crash recovery, payload limits, and
  redacted operator output on supported MariaDB versions. Complete independent
  security review of transaction and lease boundaries.
- [ ] Run the full language corpus and keep its expected behavior reviewable.
- [ ] Update the bilingual editor guide, database compatibility matrix, and
  handbook examples against the exact release candidate.

Do not claim a complete IDE, unrestricted database designer, database parity
beyond the tested matrix, exactly-once delivery, or distributed queue support.
