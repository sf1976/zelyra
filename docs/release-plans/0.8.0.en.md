# Zelyra 0.8.0 release plan: visual studio and bounded event outbox

**Status:** in progress; the local MariaDB outbox has an experimental
implementation, while the visual database map and guided CRUD workflow remain
planned. This is not a production release. The branch depends on completion of
the 0.7 review gates.

## User outcome

A developer can understand a project's database schema, preview and apply a
compiler-checked CRUD source change, and optionally record a business event
atomically with its MariaDB transaction for explicit local processing.

## Studio scope

- Show a read-only schema map with columns, keys, relationships, and differences
  between declared and live schemas. Show source ownership when known.
- Let the user choose a table and fields, preview generated Zelyra source, run
  compiler validation, inspect the diff, and explicitly apply it.
- Keep schema writes and row mutations out of the visual workflow. Do not
  overwrite a file changed since the preview or apply code with compiler errors.
- Keep the editor local; no project source is sent to an external service.

## Bounded MariaDB outbox

- An explicit typed enqueue participates in the same transaction as a business
  update. A rollback commits neither the update nor its event.
- Persist a stable event ID and type, bounded payload, creation time, attempt
  count, next-attempt time, and lease metadata. Use transaction-safe claims so
  concurrent local workers do not share a live lease; a worker can renew only
  its own unexpired lease.
- Dispatch one event per explicit worker call to explicitly registered
  handlers. Acknowledge success, retry failures with bounded backoff, and keep
  exhausted events available for operator inspection and explicit recovery.
- Provide setup, bounded metadata inspection, recovery, and worker commands.
  Inspection omits payload contents. Workers never start automatically with
  the web server.
- Delivery is at least once. Handlers must use the stable event ID for
  idempotency because a process can fail after handler success and before the
  acknowledgement is stored.
- Current implementation is below the full target: language-level handler
  declarations and application-runtime integration are absent; CLI handlers
  cannot renew leases. The eight-claim and retry limits are implementation
  details until the release contract is reviewed.

## Language compatibility

Expand the line `0.1` conformance corpus across lexing, parsing, type checking,
and formatting. Each grammar family needs accepted and rejected fixtures, and
formatter output must be idempotent.

## Release gates

- Test schema introspection with missing, extra, renamed, nullable, related,
  and unsupported columns. Show unknown metadata as unknown rather than
  guessing.
- Prove generated source passes the same compiler checks as hand-written code.
- Test stale-preview conflicts, cancellation, malformed metadata, and read-only
  behavior on every supported introspection backend.
- Prove outbox/business-row atomicity on commit and rollback, lease safety with
  competing workers, bounded retry, crash recovery, payload limits, and
  redacted operator output on supported MariaDB versions.
- Complete an independent security review of outbox transaction/lease
  boundaries and the Studio's local file and apply boundaries.
- Run the full language corpus and update the editor guide, database matrix,
  outbox operations guide, and handbook against the exact candidate.

## Explicit exclusions

This is not a general job or workflow platform. It adds no cron scheduler,
distributed worker service, external broker, arbitrary serialized function
execution, exactly-once guarantee, built-in email/SMS provider, mandatory
network connection, cloud account, telemetry, or phone-home behavior. The
outbox does not imply PostgreSQL support or tenant isolation. Do not claim a
complete IDE, unrestricted database designer, or database parity beyond the
tested matrix.
