# Zelyra 0.8.0 roadmap: local transactional outbox

**Status:** in progress; the database crate now has bounded MariaDB event
envelopes, explicit schema setup, transaction-bound enqueue, renewable atomic
claims, handler registration, explicit one-event dispatch, acknowledgement,
bounded retry, operator-approved recovery, and CLI setup/inspection/recovery/
worker commands. Zelyra-language handler declarations and application runtime
integration are not implemented. The local MariaDB-backed tests were skipped
because no test URL is configured; exact-head CI must exercise them.
Branch
`release/0.8.0` is based on the 0.7 development branch and remains dependent
on the 0.7 review and the earlier 0.5 acceptance gate.

## Goal

Provide a small local durability boundary for application events that must be
recorded atomically with a business transaction. A worker started explicitly
by the operator can deliver pending events to application-defined handlers.
The first backend is MariaDB.

## Proposed first slice

- An explicit, typed outbox write participates in the same MariaDB transaction
  as the business update. A rollback leaves neither the business change nor
  its event committed.
- Persist an event identifier, type, bounded payload, creation time, attempt
  count, next-attempt time, and lease metadata. Claim pending rows with a
  transaction-safe lease so multiple local workers do not process the same
  active lease concurrently; a worker may extend only its own live lease.
- Deliver one event per explicit worker call to application handlers registered
  through the database crate API. Acknowledge success;
  retry failures with bounded backoff and a configured maximum attempt count;
  retain exhausted rows for operator inspection and explicit recovery.
- Provide explicit setup, bounded metadata inspection, exhausted-event
  recovery, and worker CLI commands. Inspection omits payloads. The CLI maps
  public functions with a fixed `(String, String, String) -> Bool` signature to
  event types; the worker runs only when explicitly invoked and never starts
  with the web server.
- Document at-least-once delivery. Handlers must use the stable event ID for
  idempotency because a crash can happen after handler success but before the
  acknowledgement is persisted.

## Explicit exclusions

This is not a general job or workflow platform. No cron scheduler, arbitrary
serialized function execution, external broker, distributed worker service,
exactly-once claim, built-in email/SMS provider, mandatory network connection,
cloud account, telemetry, or phone-home behavior is included. PostgreSQL
outbox support is not implied. Multi-tenant partitioning of outbox events is
deferred until the tenant path has its own release review.

## Verification gates

- Prove event and business-row atomicity on commit and rollback.
- Run competing workers and show one active lease per event, lease expiry
  recovery, bounded retries, and safe operator recovery.
- Inject crashes before delivery, after handler success, and before/after
  acknowledgement; verify documented at-least-once behavior and idempotency.
- Test payload and attempt limits, redacted errors, permission boundaries, and
  MariaDB compatibility on supported versions.
- Complete a security review of transaction boundaries, locking, lease
  expiration, duplicate delivery, and operator commands before calling the
  feature ready.

## Current implementation boundary

The database crate implements the outbox table, transaction-safe primitives,
a Rust API for registering handlers and explicitly dispatching one event, and
CLI setup, bounded metadata inspection, exhausted-event recovery, and worker
execution. Inspection omits event payloads. CLI handler mappings are explicit;
Zelyra source-level declarations and application-runtime integration remain
unimplemented.
It currently uses an eight-claim limit, exponential retry starting at five
seconds and capped at one hour, fixed redacted failure codes, and caller-owned
unique lease tokens. The CLI invokes the dispatcher using explicit mappings
from event types to public Zelyra functions; Zelyra source cannot yet declare
handlers, and the application runtime cannot invoke the dispatcher. Rust API
handlers can renew their still-live lease through the context. CLI handlers
cannot renew leases; a crashed or long-running handler can be delivered again,
so all handlers must remain idempotent because delivery is at least once.
