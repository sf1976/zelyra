# 1.2.21 — CRUD lifecycle guards and row-conditioned permissions

## Goal

Allow edit and delete operations to be additionally checked against typed
properties of the stored record. Existing server-side CRUD authorization, CSRF
checks, and database transactions remain authoritative.

## Implemented so far

- `permits edit "permission" when <Bool expression>` and the corresponding
  `delete` form are parsed.
- `guard edit when <Bool expression> { error: "..." }` and the corresponding
  `delete` form are parsed.
- `permits edit/delete "permission" when condition` requires both a true
  condition and the named permission. A false condition denies the operation;
  multiple declarations are conjunctive.
- Conditions are lowered to private functions over typed table fields and sent
  through the existing type checker and capability analyzer.
- Edit GET checks the current row. Edit POST checks it under `FOR UPDATE` in the
  existing write transaction before executing write queries.
- Delete checks the row under `FOR UPDATE` inside the existing mutation
  transaction before deletion or archival.
- The CRUD detail page hides its edit action when the row condition denies it.
- TableView row actions can opt into the same rules with operation-specific
  slots:

  ```zelyra
  row_actions {
      item: invoice
      crud: Invoice
      edit { html { <a href="/invoices/{invoice.id}/edit">Edit</a> } }
      delete { html { <button type="button">Delete</button> } }
  }
  ```

  The result row must be `Invoice` and expose every table field through
  `columns` or `row_fields`. Legacy generic `html` actions remain unclassified
  for backward compatibility and are not automatically associated with a
  policy.
- Web evaluator tests cover allowed permissions, missing permissions, and
  guards.
- Table-invariant evaluation resolves nominal relation fields such as
  `Department` to their schema table and converts submitted relation IDs to
  integer identity values. Tables without invariants skip invariant evaluation
  instead of requiring unrelated fields from custom action submissions.
- The complete MariaDB CRUD HTTP E2E passes locally, including related-record
  creation, custom actions, edit/delete workflows, and localized views.

## Remaining release gates

- `tests/mariadb-crud-lifecycle-policies-e2e.sh` exercises direct edit and
  delete requests against MariaDB, verifies guarded rows remain unchanged, and
  checks both the detail page and TableView actions.
- The integration test changes the row after the edit form is loaded while
  holding the database row lock. The POST waits, reads the locked state, and is
  denied.
- The test is registered in the MariaDB CI workflow with an isolated database.
  The full external PR CI run passed for the implementation commit; this
  follow-up records that result and the additional regression correction.
- Formatter, parser, CLI compiler checks, workspace tests, Clippy, handbook
  snippet validation, and the MariaDB CRUD HTTP E2E all ran locally and passed.

The local and external functional evidence is complete. The milestone is ready
for release review; no stable release is created by this work log.
