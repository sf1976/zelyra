# Zelyra 1.2.23 — authenticated tenant-scoped API validation

## Goal

Complete the safe API-validation boundary recorded as open after 1.2.21. An API
that validates a tenant-scoped table must derive the tenant identifier from the
authenticated session and active membership lookup. The request body must never
choose the tenant. The same typed table invariants must run before the handler
executes.

## Scope

- Permit `api ... validates table_name` for scoped tables only with required
  authentication and a configured active membership table.
- Omit the scoped tenant key from client-declared API inputs and supply it as a
  separately typed final handler parameter from verified request context.
- Resolve the optional tenant selector through existing session/membership
  logic; reject missing, conflicting, inactive, or unauthorized tenants.
- Include the verified tenant value in table invariant evaluation before the
  API handler runs.
- Preserve HTTP 422 validation errors, CSRF/origin policy, permissions, and
  database transaction ownership in user handlers.

## Not included

- Automatic INSERT/UPDATE generation for APIs; a typed handler still owns its
  write and must use safe database operations.
- Raw SQL validation or enforcement of arbitrary handler behavior.
- Tenant API reads or writes where the handler can bypass scoped query APIs.
- Changing the tenant through request JSON, form data, or path parameters.

## Verification

Add compiler positive/negative tests for handler signature and rejected client
input, unit tests for route context resolution, and a MariaDB HTTP integration
test for a valid tenant, forged tenant field, unauthorized membership, and
cross-field invariant failure. Document this boundary explicitly.
