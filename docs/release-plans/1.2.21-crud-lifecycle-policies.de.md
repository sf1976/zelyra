# 1.2.21 — CRUD-Lifecycle-Guards und datensatzabhängige Rechte

## Ziel

Bearbeiten und Löschen sollen anhand typgeprüfter Eigenschaften des jeweils
gespeicherten Datensatzes zusätzlich geschützt werden. Die vorhandene
serverseitige CRUD-Autorisierung, CSRF-Prüfung und Datenbanktransaktion bleiben
maßgeblich.

## Derzeit umgesetzt

- `permits edit "permission" when <Bool-Ausdruck>` und die entsprechende
  `delete`-Variante werden geparst.
- `guard edit when <Bool-Ausdruck> { error: "..." }` und die entsprechende
  `delete`-Variante werden geparst.
- Ein `permits edit/delete "Recht" when Bedingung` verlangt sowohl eine wahre
  Bedingung als auch das genannte Recht. Ist die Bedingung falsch, wird die
  Operation verweigert; mehrere Deklarationen gelten gemeinsam.
- Bedingungen werden als private Funktionen über die typisierten Tabellenfelder
  an den vorhandenen Typechecker und Capability-Analyzer übergeben.
- Edit-GET prüft die aktuelle Zeile. Edit-POST prüft sie innerhalb der
  bestehenden Schreibtransaktion mit `FOR UPDATE`, bevor Schreibqueries laufen.
- Delete prüft die Zeile innerhalb der bestehenden Mutationstransaktion mit
  `FOR UPDATE`, bevor Löschen oder Archivieren ausgeführt wird.
- Die Edit-Aktion auf der CRUD-Detailseite wird bei einer verweigerten
  Datensatzbedingung ausgeblendet.
- TableView-Zeilenaktionen können operation-spezifisch unter dieselben Regeln
  gestellt werden:

  ```zelyra
  row_actions {
      item: invoice
      crud: Invoice
      edit { html { <a href="/invoices/{invoice.id}/edit">Bearbeiten</a> } }
      delete { html { <button type="button">Löschen</button> } }
  }
  ```

  Der Ergebnisdatensatz muss `Invoice` sein und alle Tabellenfelder in
  `columns` oder `row_fields` bereitstellen. Generische `html`-Aktionen bleiben
  aus Rückwärtskompatibilitätsgründen unklassifiziert und werden nicht
  automatisch einer Policy zugeordnet.
- Der Web-Auswerter hat Tests für erlaubte Rechte, fehlende Rechte und Guards.
- Die Tabelleninvarianten lösen nominale Relationsfelder wie `Department` zur
  passenden Schematabelle auf und wandeln übermittelte Relations-IDs in
  numerische Identitätswerte um. Tabellen ohne Invarianten überspringen die
  Prüfung, statt bei Custom-Aktionen nicht übermittelte Fremdfelder zu verlangen.
- Der vollständige MariaDB-CRUD-HTTP-E2E-Lauf war lokal erfolgreich, einschließlich
  verwandter Datensätze, Custom-Aktionen, Bearbeiten/Löschen und lokalisierten
  Ansichten.

## Noch offene Abnahme

- `tests/mariadb-crud-lifecycle-policies-e2e.sh` prüft mit einer echten
  MariaDB direkte Edit- und Delete-Requests, unveränderte gesperrte Datensätze,
  die Detailseite und TableView-Aktionen.
- Der Integrationstest ändert den Datensatz nach dem Laden des Edit-Formulars
  unter einer gehaltenen Zeilensperre. Der POST wartet, liest danach den
  gesperrten Stand und wird abgewiesen.
- Der Test ist im MariaDB-CI-Workflow mit einer isolierten Testdatenbank
  eingetragen. Der vollständige externe PR-CI-Lauf für den Implementierungs-
  Commit war erfolgreich; diese Dokumentationskorrektur hält das Ergebnis und
  die zusätzliche Regressionkorrektur fest.
- Formatter, Parser, CLI-Compilerprüfung, Workspace-Tests, Clippy,
  Handbuch-Snippetprüfung und MariaDB-CRUD-HTTP-E2E wurden lokal ausgeführt und
  bestanden.

Der lokale und externe Funktionsnachweis ist vollständig. Der Milestone ist
releasebereit.
