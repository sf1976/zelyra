# Zelyra 1.2.6 — Recoverable package transactions

## Work log

Status: implemented and verified. This focused 1.2.6 release makes
package-cache, manifest, and lockfile changes recoverable after process
interruption. Transitive registry dependencies, typed query/request pipelines,
and durable jobs are assigned to later releases in the roadmap.

## Acceptance goal

An interrupted package installation or update must not leave the project
silently inconsistent. Zelyra must detect the transaction, safely restore the
previous manifest/lockfile and affected cache directories, and exclude
concurrent package mutations.

## Stages

1. Inventory `add`, `update --plan`, `remove`, and cache write paths and the
   current lockfile validation.
2. Add a bounded, versioned transaction journal with atomic backups, path
   validation, and a per-project exclusive operation lock.
3. Add `zelyra package recover` with preview as the default and explicit
   `--apply` recovery.
4. Simulate interruption at every commit phase; add symlink/traversal negative
   tests and German/English documentation.
5. Run workspace, release-metadata, package, and CI checks; record results and
   limitations here.

## Rules

- Recovery restores the previous state; it does not publish a new package
  version or execute application code.
- Backups and journals are read only from a real project path; deletion targets
  must remain under `.zelyra/packages/`.
- Corrupt or unknown journals fail with recovery data preserved; they are not
  cleaned heuristically.
- A normal package operation cannot start while a journal is pending.

## Recovery-slice result — 2026-10-18

- `zelyra package recover` previews by default. With `--apply`, it rolls back a
  prepared package transaction or removes the journal for a committed one.
- Registry trust, add/update/remove, cache cleanup, and recovery share a
  per-project package-operation lock. A pending transaction blocks new package
  mutations.
- Interrupted cache cleanup uses quarantine directories. Recovery validates
  package names, normalized SemVer versions, symlinks, and destination
  conflicts; it never overwrites an existing cached version.
- Passed on commit `2e1715f`: full `cargo test --workspace --locked` (one
  MariaDB test requiring a configured disposable database was ignored),
  `cargo clippy --workspace --locked -- -D warnings`,
  `python3 scripts/check_release_metadata.py`, and
  `tests/release-artifact-smoke.sh`. The smoke test built the optimized Linux
  binary, verified archives and SHA-256 sidecars, ran the packaged CLI, and
  requested its local UI assets.
- Passed on PR head `abd2dee` and merged as `fb330e0`: PR #96 workspace and
  release CI passed, including the full test/E2E workflow (17m20s), MariaDB
  10.11, 11.4, 11.8, and 12.3 compatibility, MySQL 8.4, Linux and Windows
  release builds, the bundled editor, dependency audit, and coverage-guided fuzz.
- Limits: The journal enables recovery but is not an atomic transaction across
  multiple files. Corrupt data, symlinks, cache collisions, or I/O failures
  fail closed and preserve remaining recovery data. Interruption while
  cleaning a journal after a committed operation leaves a journal that can be
  safely removed by recovery.

The release metadata and artifact gates are rerun for the versioned release
commit. Transitive registry resolution, typed tenant/request/form pipelines,
and durable transactional jobs remain open and are assigned to later roadmap
releases.
