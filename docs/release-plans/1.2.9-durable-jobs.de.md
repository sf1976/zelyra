# Zelyra 1.2.9 — dauerhafte Scheduler-Jobs

## Ergebnis

Deklarierte Zelyra-Zeitpläne werden nur dann dauerhaft eingereiht, wenn der
installierte Linux-Dienst dieses Projekts aktiv ist. Der Scheduler installiert
keine Cron-Einträge auf dem Host. Über die vorhandenen Outbox-Befehle können
Betreiber Versuche, Leases, Wiederholungszeitpunkte, endgültige Fehler und
erneut freigegebene Jobs einsehen.

## Architekturentscheidung

Die vorhandene transaktionale MariaDB-Outbox wird als dauerhafter Job-Speicher
wiederverwendet. Es entsteht keine zweite Queue mit eigener Lease- und
Retry-Implementierung. Jede geplante Ausführung erhält eine deterministische
Event-ID aus kanonischer Projektidentität, Zeitplanname und UTC-Minute. Die
eindeutige ID verhindert doppelte Einträge über wiederholte Ticks und
Dienstneustarts hinweg. Vor dem Start prüft ein Worker den aktuell kompilierten
Zeitplan erneut. Der Handler läuft als Kindprozess
`zelyra run ... --entry ...`, ohne Shell-Interpolation.
Das Payload enthält nur einen SHA-256-Projektschlüssel, Schedule-Namen,
UTC-Fälligkeitsminute und Definitionsfingerprint. Der Worker ist bewusst
seriell, damit sich Ausführungen desselben Projekts nicht überschneiden.

Die Zustellung erfolgt mindestens einmal. Stürzt der Prozess ab, nachdem ein
Handler eine externe Wirkung ausgelöst, aber bevor er diese bestätigt hat, kann
ein Retry die Wirkung wiederholen. Genau-einmal-Nebenwirkungen werden nicht
versprochen. Handler müssen idempotent bleiben oder ihre Geschäftsänderung mit
einer eigenen Transaktions-/Outbox-Grenze absichern. Begrenzte Retries und
Lease-Recovery der Outbox bleiben maßgeblich.

## Abnahmekriterien

- [x] `setup` erstellt oder aktualisiert die Outbox einmalig für jedes Projekt
  mit nativen Zeitplänen über die konfigurierte MariaDB-Verbindung, ohne
  Geheimnisse zu kopieren.
- [x] Der aktive Projektdienst reiht fällige Ausführungen transaktional ein und
  dedupliziert dieselbe Projekt-/Zeitplan-/Minuten-Kombination über parallele
  Ticks und Neustarts.
- [x] Nur der aktive, installierte Projektdienst startet Scheduler-Worker;
  manuelles `serve`, `schedule trigger` und Cron-Exporte führen sie nicht aus.
- [x] Ein serieller Worker verwendet begrenzte Ausführung, konfiguriertes Zeitlimit,
  erneuerbare Leases, begrenzte Wiederholungen und einen Dead-Letter-Status.
- [x] Vor Ausführung wird der aktuelle Quellstand geprüft. Entfernte oder
  ungültige Deklarationen werden als abgebrochen bestätigt; gespeicherter alter
  Handlertext wird nie ausgeführt.
- [x] `zelyra schedule jobs <main.zyl>` zeigt begrenzte, payloadfreie Status-
  Seiten als Text und versioniertes JSON; erschöpfte Ausführungen werden nur
  durch die bewusste Aktion `zelyra outbox requeue` erneut freigegeben.
- [x] Positive und negative Tests prüfen Deduplizierung, konkurrierende Worker,
  abgelaufene Leases, Retry/Dead-Letter/Requeue, entfernte Quellen, Sperren
  gegen manuelles Ausführen und den Ausschluss echten Mailversands.
- [x] Deutsche/englische Hilfe, Befehlsdokumentation, Changelog und
  Release-Notizen beschreiben die Implementierung; es gibt keine neuen
  Env-Einstellungen.

## Sicherheits- und Betriebsgrenzen

Die Outbox speichert nur Zeitplanidentität und Fälligkeitszeit, keine
Geheimnisse oder Handlerquellen. Der Worker kompiliert das Projekt erneut und
löst den aktuellen Handler auf. Datenbank-, Datei-, Netzwerk- und E-Mail-
Freigaben entsprechen dem normalen Command-Lauf. Requeue führt einen Job nicht
sofort aus. Datenbankeinrichtung ist additiv und wiederholbar; sie installiert
keine Host-Cronjobs und ändert keine Anwendungstabellen.
