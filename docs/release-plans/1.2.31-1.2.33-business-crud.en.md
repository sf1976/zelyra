# Business CRUD completion plan: 1.2.31–1.2.33

This plan tracks five findings from practical invoice and tenant workflows.
Two defects are included in the 1.2.30 candidate: invoice-number collision
lookups and updates include the verified tenant key, and generated
`has_many` legend localization survives HTML escaping. The remaining three
capabilities are assigned to the releases below. This plan is a commitment to
deliver or explicitly block each capability before 1.3.0; it is not evidence
that they are already implemented.

## 1.2.31 — transactional tenant-aware number series

### User outcome

Developers can declare reusable identifiers for customers and business
documents without making each field name a special case. A tenant-scoped
resource receives an independent sequence in its verified tenant context.

### Design constraints

- Prefer a field-level declaration that the existing parser and schema model
  can represent; do not assume `auto_sequence("...")` syntax until parser
  design, type checking, formatting and diagnostics are implemented.
- Treat the counter as persistent database state protected by the same
  transaction/locking guarantees as the record write. Define counter keys by
  sequence name and, when declared, tenant identity.
- Support only documented format tokens (literal text, calendar year, and
  zero-padded positive counter). Reject unknown tokens, invalid widths and
  ambiguous declarations at compile time where possible.
- Keep uniqueness constraints aligned with scoped/unscoped table semantics.
  Handle a uniqueness race through the database constraint and bounded retry,
  never by trusting a prior unlocked lookup.
- Preserve legacy automatic `invoice_number` behavior for existing projects
  until users opt into a declared series.
- Do not promise gapless numbering. Failed transactions can consume a
  reservation depending on backend semantics, and a voided legal document
  must remain auditable rather than being silently reused. Document the
  chosen reservation/void policy and database-specific guarantees.

### 1.2.31 work status (unreleased branch)

The syntax `auto_sequence("KD-{0001}")` and
`auto_sequence("AG-{year}-{0001}")` passes the parser and schema checks. Schema
planning includes the internal `_zelyra_number_sequences` table. Generated
create forms ignore client-submitted numbers and allocate the value in the same
database transaction as the record write. Counters are separated by resource
and tenant; `{year}` additionally separates them by UTC calendar year. Existing
values are checked and skipped. A MariaDB integration test exercises the CRUD
write path, tenant isolation, rollback, pre-existing collisions, forged input,
and concurrent requests. The same test also passes on PostgreSQL 16. The
remaining release gates are still open. This branch is not a published or fully
accepted release.

### Acceptance evidence

- Positive/negative compiler tests for declared series, formats, unknown
  fields, invalid widths and duplicate declarations.
- MariaDB concurrent-request E2E proving no duplicate allocation, independent
  tenant counters, rollback behavior and unique-index enforcement.
- PostgreSQL coverage or a stable unsupported-backend diagnostic; SQLite
  behavior must also be explicit.
- Existing invoice tutorial behavior remains compatible unless its source
  explicitly opts into the new series.
- On MariaDB, apply the generated schema to a disposable database, inspect it
  again, and require a clean second plan with no unsupported drift.
- Bilingual handbook, migration note and runnable customer/quote/invoice
  examples.

## 1.2.32 — typed computed business fields

### User outcome

Line totals and other derived values are calculated consistently and cannot be
forged by submitting a different client value.

### Design constraints

- Define a pure, deterministic expression subset and type-check it against
  declared fields. It must not call effectful functions or arbitrary runtime
  code.
- Build and validate a dependency graph; reject cycles, missing inputs and
  incompatible result types with source-mapped diagnostics.
- Recompute on the server before storage for each supported mutation path.
  Computed fields are not writable request inputs. Ensure table invariants
  inspect the recomputed values, not the submitted values.
- Define Decimal precision, scale, rounding, overflow and NULL propagation
  explicitly. Monetary calculations must use exact Decimal operations.
- Optional inputs remain typed as `Option<T>`; expressions must handle them
  explicitly with the existing `match` syntax. A `None` result is persisted as
  a missing database value for an optional target column.
- A live browser preview is optional until it can reuse or faithfully mirror
  the checked expression semantics. Any preview is advisory; the server value
  remains authoritative.
- State database/backend support. Do not silently create vendor-specific
  generated columns unless equivalent semantics are proven across supported
  engines.

### Acceptance evidence

### 1.2.32 development status (unreleased)

The parser, AST and type checker currently recognize `compute(expr)`, validate
field dependencies, and reject cycles, unknown fields, incompatible result
types and invalid modifier combinations. Generated parent and child CRUD forms
recompute values before validation and persistence; submitted computed values
are ignored. Raw SQL mutation paths that could bypass recomputation are
rejected. Decimal values are rounded to the declared scale (half away from
zero), and overflow is detected. A MariaDB HTTP test verified the persisted
server-calculated value on create. Validated API `POST` and `PUT` routes now
receive computed values as additional typed handler parameters; request
payloads cannot declare computed columns. The SQL checker permits API-handler
inserts and updates only when computed outputs and their dependencies bind
matching parameters. Such handlers cannot be called from ordinary Zelyra
functions or selected as a CLI entry point. A disposable MariaDB 11.8 E2E test
verified create and update, including that forged input is ignored and the
recomputed Decimal value is persisted. The executable example is
`examples/computed_api.zyl`. A MariaDB CRUD HTTP integration test covers
create, edit, rejected validation, unchanged persistence after rejection, and
the recalculated value returned on the error response. API `PATCH`, broader
database coverage and complete release gates remain unverified. Optional
Decimal values and explicit `match`-based `None`/`Some` handling have unit
coverage. This branch is not a completed release.

- Parser/type-check tests for valid dependencies and cycles, unknown fields,
  forbidden effects, bad result types and precision failures.
- Forms, generated CRUD, validated API `POST`/`PUT`, and relevant SQL mutation
  tests prove recalculation and rejection of forged computed values. API
  `PATCH` remains unsupported until it has an equivalent safe mutation path.
- Exact Decimal tests cover quantity × price, tax, rounding, overflow and
  nullable inputs.
- Create/edit/error response behavior and documentation are tested against a
  runnable invoice-line example.
- AST, MIR and Bytecode either share verified semantics or reject unsupported
  paths with a stable diagnostic until the 1.3.0 backend gate passes.

## 1.2.33 — FileRef-aware generated CRUD

### User outcome

Applications can declare bounded attachment metadata once and receive checked
create/edit upload controls and authorized detail downloads from generated
CRUD.

### Design constraints

- Reuse the existing `File` form validation, multipart limits, private
  FileRef storage, integrity checks and authorized download path. The new
  work is schema/CRUD integration, not a second storage system.
- Define a typed attachment column/configuration with explicit maximum bytes
  and MIME allowlist. Validate the actual content against policy; do not trust
  the browser-provided filename or MIME header.
- Derive tenant storage scope from the authenticated tenant context. Direct
  references from request data must never select an arbitrary tenant or blob.
- On edit, omission retains the existing authorized FileRef. Replacement
  publishes the new reference transactionally and cleans the old object only
  after commit and after reference checks. Rollback removes only staged bytes.
- Detail downloads must authorize the current record and tenant on every
  request, avoid exposing storage paths, and set safe content-disposition and
  content-type headers. List views must not render raw FileRef values.
- Preserve permission checks, CSRF, request size limits, and stable
  diagnostics. Existing projects without attachment declarations remain
  unchanged.

### 1.2.33 implementation status (in progress)

The parser stores bounded `attachment { max_size, allowed_types }` metadata on
`FileRef` columns. Form checking rejects non-FileRef targets, missing policies,
unsupported MIME values, invalid size limits, and FileRef CRUD search/filter
fields. The CRUD generator creates native `File` inputs from this metadata, and
CRUD list/detail rendering uses protected download links without displaying
the opaque reference. Existing staged upload, edit-retention/replacement,
failure cleanup, tenant checks, and delete-time reference checks remain the
single storage path. Parser, form validation, generator, list-render, and
metadata-to-download tests pass. A disposable MariaDB/HTTP test through the
CLI-generated CRUD path confirms `.env` database resolution, `GET /new`,
multipart persistence, list links without raw references, and authenticated
downloads. A separate upload-form test confirms edit preservation and
replacement, SQL rollback, and file cleanup. Explicit cross-tenant denial and
browser checks remain open before release. This is not a release yet.

### Acceptance evidence

- Positive/negative schema and form checks for optional/required attachments,
  byte limits, MIME allowlists and incompatible column declarations.
- Disposable MariaDB/HTTP tests cover create upload, edit retention,
  replacement, SQL rollback cleanup, delete/reference cleanup, and cross-
  tenant download denial.
- Tests show that a forged FileRef cannot replace a stored reference and that
  client filenames cannot escape the managed storage root.
- Browser test verifies generated controls and download behavior; the
  no-JavaScript form path remains usable.
- Bilingual docs include a complete contract/invoice attachment example and
  explain backup/restore boundaries.

## Release dependency and completion rule

These features are sequentially versioned to keep parser, runtime, database,
security and generated-CRUD changes reviewable. Each release updates both
roadmaps and includes full project checks, database integration coverage,
documentation validation, and release-artifact smoke checks. 1.3.0 remains
blocked until all three packages are completed or a concrete external blocker
is documented; the Bytecode backend must also meet its independent parity
gate. No function is considered complete merely because its syntax parses.
