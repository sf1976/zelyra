# Zelyra 1.2.24 — multiple transactional CRUD child collections

## Goal

Generalize the existing typed `has_many` CRUD implementation from one direct
child collection to multiple named child collections, while preserving the
current parent and child validation, tenant isolation, row caps, aggregates,
and single transaction boundary.

## Scope

- Allow more than one distinct `has_many` declaration in a CRUD resource.
- Reject duplicate collection names, duplicate child tables, ambiguous foreign
  keys, and child relationships that cannot be safely mapped to the parent.
- Render each collection as a separate labeled section on Create and Edit.
- Keep child inputs namespaced by the declared collection name so they cannot
  collide with parent fields or another collection.
- Validate every submitted collection before any write; preserve field values
  and errors on failure.
- Save the parent and all child rows in one database transaction. On Edit,
  replace only rows owned by the locked parent and collection relationship.
- Recompute declared aggregates per collection and roll back parent, children,
  and aggregates together on any error.
- Keep each existing per-collection row limit and reject ambiguous or oversized
  submissions before database work.

## Security invariants

- Tenant identity comes from authenticated membership context, never from child
  request fields.
- Every child read, update, and delete is constrained by the parent identity;
  tenant-scoped relations additionally use the verified tenant identity.
- Table invariants, CSRF, authorization, safe SQL parameter binding, escaping,
  and allowed-field checks remain active for every collection.
- A failed validation in any collection must cause zero writes. A database
  error in any collection must roll back all preceding writes in the request.

## Required verification

- Compiler positive and negative cases for two collections, duplicate names,
  duplicate tables, incompatible foreign keys, and invalid aggregates.
- HTTP tests for two collection forms, invalid second collection, full rollback,
  successful create, successful edit replacement, preservation of another
  parent's children, tenant isolation, limits, CSRF, and authorization.
- MariaDB E2E using an isolated database. Include at least two child tables and
  an aggregate; demonstrate that a failed second collection leaves no parent
  or child writes, then demonstrate valid create and edit.
- Full repository tests, Clippy, formatting, release metadata, package smoke,
  Handbook checks, and PR/release CI.

## Explicitly excluded

- More than one direct parent level or arbitrary nested collection trees.
- Arbitrary CRUD action statements, file uploads, or schema changes.
- Custom JavaScript submission frameworks or client-side-only validation.
