# Zelyra 1.2.27 — Laravel Website Import Foundation

Status: planned and active. This work resumes the user's Laravel-to-Zelyra
migration goal after the earlier migrator was removed in v1.1.2. That archived
tool is evidence and reference material only; it is not restored wholesale.

## Goal

Move selected website behavior from Laravel into idiomatic, compiler-checked
Zelyra source and reusable local packages. This is a website migration tool,
not Laravel framework compatibility, PHP execution, or a promise to translate
every Laravel application automatically.

The importer must compose with Zelyra's existing module/package graph,
capability system, Forms/CRUD, auth, UI, tasks, settings, database planning,
and deployment tools. It must not introduce a second plugin loader or copy
Laravel's MVC runtime into generated projects.

## Release stages

### 1.2.27 — source-evidenced analysis and selected generation

- Add `zelyra import laravel analyze <source>` and an explicit generation path
  into a new destination. Keep the old `migrate laravel` name retired.
- Build a versioned graph from statically supported route declarations through
  controller actions, services, models, migrations, Blade layouts/views, and
  local assets. Findings include stable IDs, source spans, resolution status,
  and an actionable next step. Dynamic or ambiguous relationships remain
  unresolved.
- Allow an explicitly requested, read-only database-schema inspection using
  Laravel's `.env` connection settings. Read only catalog metadata; do not read
  application rows, execute migrations, or change the source project. Never
  serialize credentials, connection URLs, or secret environment values.
- If a configured MariaDB host is an unresolved Compose service alias, resolve
  it only among running containers whose Compose working-directory label
  matches the nearest Compose project containing the source. Ask Docker only
  for that label, network aliases, and container IPs; never request container
  environment variables. Bound each Docker metadata command to five seconds.
  Detect the database server vendor before selecting its bounded catalog-query
  timeout. Do not disable TLS automatically. For a
  trusted local Compose network without TLS, an operator can explicitly set
  the existing `ZELYRA_DB_TLS_MODE=disabled` for that invocation.
- Require explicit module selection before generation: `--table <name>` for a
  selected schema closure or `--all-supported` for every detected supported
  subset. An omitted selection is an error. Generate only the supported source
  closure into a new or empty destination, then run the Zelyra compiler against
  it. Never overwrite an existing destination.
- Emit `ROUTE_CANDIDATES.json` to trace explicitly selected tables through
  conventional model names to statically resolved controller actions and
  routes. Separate conventionally named resource controllers from other routes
  that merely consume the model. For a resource controller with direct model
  use evidence, also include resolved actions that rely on implicit route model
  binding. This is source navigation evidence only; it must not be labeled as
  generated or imported behavior.
- `generate --table <name>` selects schema-related artifacts and their
  relation closure only. It must not emit project-wide form, auth, Blade view,
  layout, or asset artifacts; those require unfiltered project generation.
- Use project-local modules such as `src/features/`, `src/domain/`, `src/ui/`,
  `src/shared/`, and `src/tasks/`, with explicit Zelyra imports. Reusable
  cross-project functions such as login, CSV, PDF, and mail belong in normal
  versioned Zelyra packages when their contracts fit; do not clone them per
  imported controller.
- A generated selection manifest records source-to-output mapping and
  distinguishes generated, assisted, and manual findings. It must not imply
  that an analyzed or selected route was successfully migrated unless
  generated code compiles and its behavior has an integration test.
- Standalone validation suggestions must not be imported automatically:
  Zelyra form declarations create routes, so a suggestion with no source route,
  handler, authorization, or persistence mapping must not silently become a
  public endpoint. Emit the checked source separately and require explicit
  integration.

### 1.2.28–1.2.29 — language and integration prerequisites

- Continue typed CRUD domain actions at 1.2.28 with transaction, row, auth,
  tenant, permissions, and audit semantics enforced by the existing compiler
  and runtime security model.
- Keep secure file upload work at 1.2.29 behind its complete size, content,

  must not claim upload migration while the destination lacks a secure native
  equivalent.

### 1.2.30 — application-level migration coverage

- Expand the tested route/controller/view-to-module slice against
  `/opt/siedelmann-laravel/app` without modifying the Laravel project.
- Run generated modules against a disposable Zelyra database, test the selected
  workflows over HTTP and in a browser, and compare visible links, forms,
  authorization outcomes, and persisted business results.
- Publish a coverage report that separately counts statically analyzed,
  generated, compiler-checked, behavior-tested, assisted, unresolved, and
  intentionally excluded website elements. Do not claim full-site migration
  unless every declared in-scope behavior passes.

## Safety and correctness boundaries

- Source discovery is bounded by file count, file size, total bytes, depth, and
  safe-path rules. Skip symlinks, `vendor`, build outputs, caches, and secrets.
- Do not run imported PHP, `artisan`, Composer scripts, or application jobs as
  part of analysis or generation. Reading route declarations must not be
  confused with executing Laravel middleware or proving authorization.
- `.env` is a secret input. Use it only when the user explicitly requests live
  schema inspection; redact it from diagnostics and outputs. The database
  inspection uses catalog queries only and must fail closed if it cannot
  establish that guarantee.
- Never copy production records. Generated schema remains a reviewed
  `zelyra db plan`/`apply` workflow against a separately configured destination.
- Translate Blade only for explicitly supported templates and constructs.
  Preserve local links as local, correctly rooted URLs; report unresolved
  dynamic URL generation, layouts, directives, JavaScript behavior, and
  authorization rather than silently dropping them.
- Every generated function and route must pass the current Zelyra compiler and
  its capability, SQL, auth, CSRF, validation, tenant, and escaping checks.

## First acceptance fixture inventory (2026-10-20)

`/opt/siedelmann-laravel/app` is Laravel 13.16.1 on PHP 8.5.0. A read-only
`php artisan route:list --json` inventory returned 538 routes and 821 expanded
HTTP methods; the source tree contains 66 controllers, 67 models, 47 services,
56 migrations, and 208 Blade views. From the running app container, a catalog-
only query confirmed access to schema metadata for 80 tables. No application
rows were queried and no project files or database objects were changed.

The DB host in `.env` is a Compose-internal hostname and does not resolve from
the host shell. The importer now resolves that alias within the matching
Compose project and uses its container IP without reading container
environment variables. A read-only run connected to the database and reported
80 tables and 1,215 columns, with `application_rows_read=false` and
`credentials_recorded=false`. This local database has no TLS, so that run
explicitly set `ZELYRA_DB_TLS_MODE=disabled`; remote database inspection should
retain TLS verification. The previous archived analyzer reported partial
coverage and is not acceptance evidence for the current importer or current
source snapshot.

A full scaffold dry run against this inspected schema emitted 71 Zelyra table
declarations, 34 pure model projections, five enum adapters, 108 standalone
validation candidates, and two pure service helpers. `main.zyl` and the
separate, unimported `src/imported_forms.zyl` both passed `zelyra check`.
Migration projections for 78 tables were compared with live metadata: zero
differences, with two live tables outside the migration scanner's model. This
checks schema evidence only; route handlers, validation persistence, and
Laravel behavior were not thereby migrated.

## Verification gates

- Positive/negative static fixtures for routes, nested groups, middleware,
  controller resolution, models, migrations, Blade layouts/includes, local
  asset links, secrets, symlinks, and ambiguous/dynamic syntax.
- Stable versioned JSON output and source spans; repeated analysis is
  deterministic and leaves source and destination unchanged.
- Selected generation never overwrites files, rejects stale source snapshots,
  and leaves no partial destination on compiler failure.
- Generated modules compile and run representative selected business flows
  across the supported AST/MIR/Bytecode subset or fail closed with an explicit
  unsupported diagnostic.
- The target application's database test is read-only. End-to-end generated
  application tests use a separate disposable Zelyra schema and never send
  real email or external payment requests.
- The v1.3.0 backend-parity and distribution gates remain independent; passing
  importer tests does not prove Bytecode default readiness.
