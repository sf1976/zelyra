# Zelyra 1.8.0 — Independent Proof Verification, Proof-Carrying Deployment & Explainable Decisions

The language compatibility line remains `0.1`. The following examples use
[the pricing decision project](../../examples/proof_decision/main.zyl). The
standalone checker can be built with `cargo build --locked -p zelyra-proof`.
Release archives carry the checker, the example sources,
and their reference proof within the existing Linux and Windows assets.

## Open proof and independent verification

```sh
zelyra certify examples/proof_decision/main.zyl
zelyra-proof-check zelyra-proof.json examples/proof_decision
```

The default output is a new `zelyra-proof.json` in the current directory.
Use `--output <path>` to write a different new file. Compilation or a failing
verifier rule blocks generation. The checker uses Rust, Serde JSON, SHA-256
and Ed25519, with a dependency graph independent of the Zelyra compiler,
runtime and database drivers.

| Field | Meaning in schema `1` |
| --- | --- |
| `schema_version`, `language_version`, `compiler_version` | Schema, language line and compiler version that issued the report |
| `entry`, `files` | Entry and sorted, unique forward-slash paths with SHA-256 over the exact UTF-8 file bytes |
| `embedded_ui_sha256` | Hash reported by the compiler for the embedded UI module, or `null` |
| `snapshot_sha256` | SHA-256 over compact UTF-8 JSON `[entry, files, embedded_ui_sha256]`, with file object keys ordered `path`, `sha256` |
| `evidence_classes` | `PROVEN`, `ENFORCED`, `TESTED`, `ATTESTED`, `ASSUMED`, `UNVERIFIED` |
| `assumptions`, `boundaries` | The fixed v1 trust and system boundaries |
| `observations` | Compiler results sorted by `(subject, rule, index)`, with a typed `outcome` and its allowed `evidence` |

Pass the directory containing the effective `zelyra.toml` as the source root.
With no manifest, pass the entry's parent directory. The snapshot covers the
loaded source closure, effective manifest and lockfile where present, and
the source and manifest files used by package content locks. The checker
validates the schema and hashes and rejects duplicate fields, unknown enum
values, and paths that escape the source root or traverse symlinks. Use a
stable, locally controlled tree during generation and verification.

`PROVEN` applies to the checked UTF-8 snapshot and its hash binding under
the stated assumptions. The compiler's semantic results are observations:
`compiler_proven` is `ASSUMED` by the independent checker. Checks delegated
to AST preconditions, postconditions and loop invariants carry `ENFORCED`
within that execution scope. `unknown`, `timeout`, `undecidable`, `unproven`
and `failed` can only carry `UNVERIFIED`. A valid proof file can record
unverified properties. Tests and trusted signatures supply `TESTED` and
`ATTESTED` evidence separately when available. Compiler correctness,
source-closure completeness, the embedded library, runtime selection, live
database and authorization state, deployment key custody and legal compliance
remain outside the independent semantic check.

## Review project changes

```sh
zelyra diff-verify old/main.zyl new/main.zyl --fail-on-privilege-escalation
```

Use corresponding entry files from two checked-out revisions. The JSON report
covers declared function, hook, action and API capabilities, project grants,
classification and redaction, route authentication and permissions, tenant
and object boundaries, state-transition roles and four-eyes rules, explicit
contracts and verifier results. The checker normalizes rule tokens to ignore
whitespace and comments. Changed policy expressions or effective execution
configuration can require review when the checker cannot establish that they
preserve the boundary. The command exits with status 1 on review findings
in strict mode, and on invalid input in either mode. Its scope is the modeled
declarations and compiler observations. Application behavior and policy
equivalence still require review.

## Build and verify a signed deployment

```sh
openssl genpkey -algorithm ED25519 -outform DER -out deployment-key.pkcs8
trusted_public_key=$(openssl pkey -inform DER -in deployment-key.pkcs8 \
  -pubout -outform DER | tail -c 32 | od -An -v -tx1 | tr -d '[:space:]')
zelyra build examples/proof_decision/main.zyl --bundle \
  --output deployment --signing-key deployment-key.pkcs8
zelyra-proof-check --bundle deployment "$trusted_public_key"
zelyra run deployment/project/main.zyl
```

The bundle is a directory with a checked source project, `SHA256SUMS`,
`zelyra-proof.json`, an SPDX 2.3 application SBOM and
`deployment-attestation.json`. The signed manifest commits to every payload
file and the entry path. The checker uses a 32-byte Ed25519 public key in
lowercase hexadecimal. The example derives it from the signing key locally.
In a deployment pipeline, give the verifier the public key through a separate
trusted channel. Key material, `.env`, live databases, host-provisioned assets,
and the separately installed runtime are outside the payload. Provision these
under the deployment operator's control. The bundle reproduces byte for byte with the same source,
toolchain version and signing key. The checker rejects an unlisted file, an
invalid signature or a mismatch in the manifest, proof, SBOM or checksum.
Its signature confirms what the trusted signer approved. Runtime permissions,
external state and legal compliance require operational evidence.

## Explain a decision

```sh
zelyra explain examples/proof_decision/main.zyl --entry unit_price --entry-args '[12]'
```

The JSON document contains ordered rule outcomes and source locations for AST
contracts, branches, loop checks and match selection. Pass only public
arguments. It emits neither the input and return values nor program output
or runtime error text. Because even a branch result can reveal a classified
value, any `@secret`, `@pii` or `@redact` declaration in the composed
project suppresses execution and returns an empty trace. The traced run
has a 10,000-step limit, denies host capabilities and parallel execution,
and uses no live database. Use the source ID and location against the same
project revision.

## Execution backends and WebAssembly

AST stays the default. Bytecode v30, selected with `--backend bytecode`,
remains opt-in. Full parity with the AST interpreter and a measured benefit
across representative execution workloads remain open. The CLI startup and
compiler benchmark below provides no backend performance evidence.

`zelyra wasm run module.wasm add 12 3` explicitly runs a pure WebAssembly
extension. The v1 profile accepts a single export of a straight-line
`(i32...) -> i32` function. It supports local and stack operations, signed and
unsigned comparisons, integer add/subtract/multiply and bitwise operations.
The parser rejects imports, memory, tables, other sections and instructions
outside the profile. Limits cover bytes, arguments, locals, operand stack
and instructions. The guest receives only the supplied integers and has no
host capability grants. [WebAssembly binary format](https://webassembly.github.io/spec/core/binary/modules.html)

```wat
(module
  (func (export "add") (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add))
```

Compile the example to `module.wasm` with `wat2wasm` before using the CLI.

## CLI performance

Reproduce with `python3 scripts/benchmark_release_cli.py <1.7.0-binary> <1.8.0-binary>`.
The threshold is +20% median latency on each invoice tutorial workload.

The benchmark compared the published Linux `v1.7.0` binary with the Linux
release candidate from `186f05ce` (Rust 1.98.1). Both binaries matched
their SHA-256 sidecars and ran on one pinned AMD EPYC-Milan CPU under Linux
6.12.117. The script alternated execution order, using three warm-up pairs
and 21 measured pairs per workload. [Candidate build](https://github.com/sf1976/zelyra/actions/runs/46145180688).

| `check` | 9.90 ms | 9.58 ms | −3.3% | +20% |
| `reflect --format=json` | 11.12 ms | 10.74 ms | −3.5% | +20% |
