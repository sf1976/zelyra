# Zelyra 1.3.5

## Declarative table state machines (`states`)

Tables can now declare first-class lifecycle state machines directly inside a
`table` definition:

```zyl
table sales_orders {
    id: Id primary auto
    status: String(20) default "draft"

    states status {
        draft -> confirmed, cancelled
        confirmed -> invoiced, cancelled
        invoiced -> paid
        paid -> final
        cancelled -> final
    }
}
```

From that single declaration, Zelyra derives:

- **Schema & default validation:** rejects undeclared targets, duplicate rules,
  non-`String` columns, defaults outside the state set, and states exceeding
  `String(N)` bounds.
- **Static SQL literal checks:** catches invalid state string literals in
  `INSERT`, `UPDATE`, and upsert assignments at compile time with Levenshtein
  typo hints.
- **Graph verification (`zelyra verify`):** statically proves reachability from
  the initial state, absence of non-final dead ends, and reachability of at
  least one `final` state (catching unreachable states and trapped cycles).
- **UI & runtime enforcement:** Create forms offer declared states with the
  initial state pre-selected; Edit forms render only the current state plus
  legal next states; API and form writes reject unknown states or illegal
  transitions under the `SELECT ... FOR UPDATE` row lock with HTTP 422.
- **Tooling & docs:** `zelyra reflect --format=json` exports `state_machines`
  per table, `zelyra doc --openapi` emits `enum` constraints, and
  `zelyra doc <file.zyl> --states` exports Mermaid `stateDiagram-v2` diagrams.

## Control-flow decision transactions (`transaction { ... }`)

`transaction { ... }` is no longer limited to linear sequences of bare SQL
statements. Inside a `transaction` block, Zelyra now supports `let`,
reassignment, `if`, `match`, `for`, `while`, `loop`, `sql_decode`, helper
function calls, `mail_queue`, and early `return` on one pinned database
connection across both the AST and MIR runtimes.

- Returning `Err(...)` or raising a runtime error rolls back the entire
  transaction automatically.
- Normal completion or returning a non-`Err` value commits the transaction.
- Simple bare-SQL transactions keep their fast single-batch execution path for
  compatibility with existing tests and Bytecode v30.

## Schema-checked SQL upserts, row locks, pluralization, and typo hints

- `query_tables` and the SQL validator now handle `ON DUPLICATE KEY UPDATE`,
  `ON CONFLICT (...) DO UPDATE SET`, `VALUES(col)`, `EXCLUDED.col`, and
  row-locking clauses (`FOR UPDATE [NOWAIT | SKIP LOCKED]`,
  `FOR NO KEY UPDATE`) without misreading keywords as table names, while
  validating upsert columns against the declared schema and keeping
  computed-column upsert protection fail-closed.
- `table_for_type` handles English `-s`/`-x`/`-z`/`-ch`/`-sh` plurals
  (`Address` -> `addresses`, `OrderStatus` -> `order_statuses`,
  `TaxBatch` -> `tax_batches`) and vowel+`y` (`ApiKey` -> `api_keys`).
- Unknown table names, `SELECT` columns, and upsert columns now report
  deterministic `(did you mean ...?)` suggestions.

## Typed `form` `execute` blocks & strict-architecture canonical starters

- Standalone `form` actions now support compiler-checked `uses` and
  `execute { ... }` blocks with form fields, action fields, route parameters,
  and `session` in scope, running inside a decision transaction.
- Typed `crud` action `execute` / `guard` blocks also receive any declared
  action `field` inputs alongside `row` and `session`.
- `zelyra new <dir> --layout standard --strict` writes
  `strict_architecture = true` to `zelyra.toml`. Canonical MariaDB starters lift
  direct-SQL write actions into `domain/actions.zyl` and call them through typed
  `execute` blocks so every `--layout standard` template passes
  `strict_architecture = true` out of the box.
- `strict_architecture = true` now accepts `tests/*.zyl` modules and the
  built-in `zelyra/ui.zyl` module, and MIR/Bytecode/runtime diagnostics report
  imported module file paths accurately via `diagnostic_with_span`.

## Release limits

- AST remains the default runtime backend. MIR supports control-flow decision
  transactions; the experimental Bytecode backend remains opt-in and fails
  closed (`E-MIR-UNSUPPORTED-001`) for control-flow decision transactions.
- Static SQL state-machine validation checks literal state values written in
  SQL; dynamic SQL parameters remain enforced at runtime by form/CRUD/API
  boundaries and database constraints.
- Action `guard` clauses remain supported on CRUD actions only; standalone
  `form` actions continue to reject `guard` with `E-FORM-002`.
- No new third-party dependencies or telemetry were added.
