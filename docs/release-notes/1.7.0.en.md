# Zelyra 1.7.0 — Information Flow Control, Tenant SQL & Verified Authorization v1

## Static Information Flow Control (`@pii`, `@secret`, `@redact`, `E-PRIVACY-001`)

Starting with `1.7.0`, table columns, record fields, and function parameters can declare explicit sensitivity annotations:

```zyl
type TenantId = Id

table customers scoped by tenant_id: TenantId {
    id: Id primary auto
    tenant_id: TenantId required
    email: String(255) required @pii @redact
    api_key: String(128) required @secret
}

struct CustomerDto {
    id: Id
    email: String @pii @redact
}

fn main() {
    assert_eq(redact("customer@example.test"), "[REDACTED]")
}
```

- **Compile-time `E-PRIVACY-001`:** The candidate analyzes `@pii` and `@secret` across bindings, `record_with`, record literals, loops, helper calls, and SQL projections. Function and loop summaries are iterated to convergence. The security review checks coverage of the modeled flows.
- **Forbidden sinks fail closed:** Unredacted leakage into `print(...)`, `Err(...)`, `http_*` requests, or `@pii`/`@secret` exposure on unauthenticated public `api`/`page` endpoints is rejected at compile time.
- **Explicit redaction (`redact(...)`):** `redact(val)` returns `"[REDACTED]"` consistently across AST, MIR, and Bytecode and clears `@pii` taint, while passing `@secret` values into `redact(...)` remains forbidden (`E-PRIVACY-001`).

## Compiler-Derived GDPR Catalog (`zelyra privacy`)

- `zelyra privacy map <file.zyl> [--format human|json|md]` reports all `@pii`/`@secret`/`@redact` columns, foreign-key links, and external sinks.
- `zelyra privacy export-plan <file.zyl> [--format human|json]` derives a deterministic GDPR Art. 15 / 20 data export plan.
- `zelyra privacy erase-plan <file.zyl> [--format human|json]` uses resolved foreign keys to order children before parents, preserves ledger rows, and flags dependent rows and delete guards for review. Cycles produce `E-PRIVACY-002` and an `UNVERIFIED` report with no steps. Execution and live constraints require operator review.

## Expanded Fail-Closed Tenant SQL Algebra

- Beyond multi-table `INNER`/`LEFT JOIN` queries, tenant SQL verification now supports **non-recursive `WITH` CTEs**, `GROUP BY` / `HAVING`, and tenant-safe single-table `UPDATE`, `DELETE`, and multi-row batch `INSERT` statements in functions.
- Continues to fail closed on `WITH RECURSIVE`, nested subqueries, `UNION`/`INTERSECT`/`EXCEPT`, `OR` predicates, `UPDATE` statements mutating `tenant_id`, and missing or mismatched nominal `TenantId` parameters.

## Resource-Scoped Capabilities (`Database`, `Network`, `FileSystem`)

- Capabilities can now be scoped to explicit resources:
  - `Database(read: [customers])`, `Database(write: [invoices])`
  - `Network(allow: ["api.datev.de"])`
  - `FileSystem(scope: "exports/")`
- Compile-time checks cover capability subsumption and literal scopes (`E-CAP-001`). Runtime checks cover dynamic URL hosts, resolved file-system paths, and SQL table access.
- `Email(templates: ["invoice"])` declares a template scope. Existing mail primitives lack a template identifier and require the broader `Email` capability. Template-bound sending remains open.

## Verified Authorization v1 & Six Evidence Classes

- `zelyra verify <file.zyl> --json` now includes `"evidence_class"` and adds `privacy` and `authorization` checks. In projects with authentication, tenant scopes, or ledgers, API handlers that declare database write capability require `requires auth` for every HTTP method. The report also counts the declared role and four-eyes transitions. The full role, object, and tenant authorization matrix remains under review.
- API handlers that execute tenant-scoped SQL need a verified tenant from an authenticated table validation route (`validates` with a tenant-scoped table). The AST runtime compares each checked SQL tenant parameter with that identity before database access, including SQL in helper functions. Calls without a verified identity or with a different tenant fail closed.
- `zelyra reflect --format=json` exports `privacy`/`redact` metadata on columns and fields along with a top-level `authorization` summary.

## Honest Scope Notes & Assumptions (`ASSUMED`)

- Static information flow, tenant SQL isolation, and scoped capability checks carry `PROVEN` or `ENFORCED` evidence strictly within the documented language and compiler scope.
- Legal GDPR compliance, real-world role assignment correctness, external identity providers, network perimeter security, and operational backup/retention schedules remain explicitly marked as **`ASSUMED`**.
- The tenant SQL test runs the same CTE, aggregate, batch insert, update, and delete on MariaDB and PostgreSQL using isolated fixtures for two tenants.
- AST remains the default execution path; MIR and Bytecode v30 remain opt-in.

## Upgrading from 1.6.0

Run `zelyra check <entry.zyl>` and `zelyra verify <entry.zyl> --json` with the
candidate binary before upgrading an application. The language compatibility line
remains `0.1`. Existing functions named `redact` keep their behavior on AST, MIR,
and Bytecode.

Consumers of `verify` JSON can read the new `evidence_class` field. `reflect`
keeps schema version `1` and adds field metadata and an `authorization` object.
Review and test any application changes that introduce classification annotations
or resource scopes before deploying them.

The Linux rehearsal installed v1.6.0 in an isolated prefix, replaced its
executable with the verified candidate, checked and verified the invoice
tutorial, then restored v1.6.0 and checked the tutorial again.

## CLI performance

On 28 November 2026, `zelyra check` and `zelyra reflect --format=json` ran against
the same invoice tutorial using the verified Linux `v1.6.0` release binary and
an optimized Linux build from `4dddcdda` (Rust 1.100.0). On one pinned AMD
EPYC-Milan vCPU under Linux 6.12.117, each workload alternated the binary order,
used three warm-up pairs, and recorded 21 timed pairs including CLI startup.
The tolerance was a maximum median increase of 20% per workload.

| Workload | 1.6.0 median | 1.7.0 candidate median | Change |
| --- | ---: | ---: | ---: |
| `check` | 8.42 ms | 8.95 ms | +6.4% |
| `reflect` | 10.15 ms | 10.45 ms | +2.9% |

A second run measured 8.86 → 9.33 ms for `check` (+5.3%) and
9.68 → 9.98 ms for `reflect` (+3.1%). Both runs stayed within tolerance.

Reproduce with `python3 scripts/benchmark_release_cli.py <baseline-binary> <candidate-binary>`.
These measurements cover compiler and reflection latency on this workload.
