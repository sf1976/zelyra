# Zelyra 1.2.17

## Sichere optionale und Mandanten-Relationen

Eine optionale Tabellenrelation wie `customer: Customer?` erzeugt nun eine
nullable `customer_id`-Spalte und einen echten Fremdschlüssel. Sind Quell- und
Zieltabelle mit demselben Tenant-Identitätstyp scoped, erzwingt ein
zusammengesetzter Fremdschlüssel die Zuordnung innerhalb desselben Mandanten:

```sql
FOREIGN KEY (tenant_id, customer_id)
REFERENCES customers (tenant_id, id)
ON DELETE RESTRICT
```

Der Planer ergänzt auf der Zieltabelle den eindeutigen Schlüssel
`(tenant_id, id)`, sofern er noch fehlt. Die Prüfung bestehender Daten
berücksichtigt beide Schlüsselspalten. Unterschiedliche Tenant-Identitätstypen
werden abgewiesen. `on_delete set_null` ist für scoped Relationen nicht
zulässig, weil es auch den erforderlichen Tenant-Schlüssel nullen würde.

## Spaltennamen und Dezimalwerte

`type` und `version` sind bereits kontextbezogen als Feldnamen erlaubt;
`order`, `group` und `status` sind normale Bezeichner. Für abweichende
SQL-Spaltennamen bleibt `storage_name "type"` die unterstützte Zelyra-Syntax.
Es wird keine zusätzliche `@column`- oder `r#`-Grammatik eingeführt.

`Decimal(precision, scale)` war bereits implementiert. Ganzzahlige
Standardwerte werden jetzt entsprechend der festgelegten Skala dargestellt:
`Decimal(12, 2) default 0` wird zu `DEFAULT 0.00`. `Money` bleibt
rückwärtskompatibel `DECIMAL(19,4)`; eine Reduzierung auf `(12,2)` hätte
bestehende Wertebereiche verkleinert. `Decimal(scale)` bleibt mangels
festgelegter Präzisionsregel unimplementiert.

## Prüfungen

Die Änderung enthält Unit- und Parser-Regressionstests sowie ein
MariaDB-E2E-Skript, das einen gültigen tenant-lokalen Verweis akzeptiert und
einen mandantenübergreifenden SQL-Insert am echten Fremdschlüssel scheitern
lässt. Der E2E-Nachweis gilt nur dann als bestanden, wenn das Skript mit einer
entbehrlichen lokalen MariaDB-Testdatenbank ausgeführt wurde.
