# Zelyra 1.3.0

## Canonical project layout and database starters

`zelyra new --layout standard` now generates compiler-checked MariaDB project
templates for minimal projects, CRUD, authentication, and a business starter.
Schema and web routes live in `schema/tables.zyl` and `routes/web.zyl`; imports
remain explicit and checkable. The profile is opt-in, so existing projects do
not need to migrate.

The standard business starter passed a protected MariaDB CRUD/API end-to-end
flow. This is a verified project starter, not a complete ERP. Templates that
keep SQL in routes are not claimed to conform to `strict_architecture`.

## Architecture checks and migration preview

`strict_architecture` follows statically resolved database calls from API and
form/CRUD routes to the `domain/` boundary. Write SQL and SQL whose effects
cannot be safely classified receive source-mapped diagnostics. Direct imports
from `routes/` into `domain/` are rejected. Statically known function values
are followed through local variables and typed callback parameters; unresolved
indirect database calls fail closed. Dynamic flows outside this analysis remain
explicitly unverified.

`zelyra migrate-layout --check` now reports deterministic findings per
declaration with file, source location, rule, reason, and candidate
destination. It is read-only and does not move files.

## Compiler-aware Zelyra Studio

With explicit selection, Studio suggests suitable CRUD and form blocks for
recognized tables. Form fields come from editable column metadata; keys,
generated columns, incomplete project maps, and name collisions do not produce
guessed code. Expression-hole suggestions use known compiler-inferred local
types and omit unknown types. SQL completion, imported module/record
suggestions, function signatures, and parameter help use the local project
analysis. Suggestions change source only after selection.

## Installation, Markdown, and diagnostics

Source installers persist the Cargo binary path. During interactive MariaDB
project setup, Zelyra can install Compose v2 using supported package managers;
non-interactive and browser-based setup never runs system package installs.

The pure `markdown_toc(source, label)` builtin creates escaped table-of-
contents links with the same heading IDs as the bounded Markdown renderer.
Layout and architecture diagnostics include source locations; selected
differential tests compare spans across AST, MIR, and Bytecode.

## Release limits

- The canonical layout is opt-in; `plugins/` does not get an automatic or
  unsecured loader.
- Layout migration provides a preview, not a file-moving mode.
- AST remains the default. MIR and Bytecode are experimental, opt-in, and fail
  closed for unsupported constructs. Full backend parity is not claimed; a
  possible default-backend change is a separate 1.5.0 gate.
- The business project is a starter, not a completed mini-ERP. The password
  generator/customer area and Mini-ERP Benchmark 01 follow as 1.3.x hardening
  work.
- Architecture analysis covers statically resolved cases; unresolved dynamic
  control flows are not considered verified.
