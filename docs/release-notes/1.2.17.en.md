# Zelyra 1.2.17

## Safe optional and tenant relations

An optional table relation such as `customer: Customer?` now creates a
nullable `customer_id` column and a real foreign key. When source and target
tables are scoped by the same tenant identity type, a composite foreign key
enforces that the relation stays within one tenant:

```sql
FOREIGN KEY (tenant_id, customer_id)
REFERENCES customers (tenant_id, id)
ON DELETE RESTRICT
```

The planner adds the unique `(tenant_id, id)` target key when needed. Existing
data preflight checks both key columns. Incompatible tenant identity types are
rejected. `on_delete set_null` is not allowed for scoped relations because it
would also null the required tenant key.

## Column names and decimal values

`type` and `version` are already accepted contextually as field names;
`order`, `group`, and `status` are ordinary identifiers. Use the existing
Zelyra syntax `storage_name "type"` to choose a different physical SQL column
name. No additional `@column` or `r#` grammar is introduced.

`Decimal(precision, scale)` was already implemented. Integer defaults now use
the declared scale: `Decimal(12, 2) default 0` becomes `DEFAULT 0.00`. `Money`
remains backward compatible at `DECIMAL(19,4)`; reducing it to `(12,2)` would
shrink existing value ranges. `Decimal(scale)` remains unsupported until a
precision rule is defined.

## Verification

The change includes unit and parser regression tests and a MariaDB E2E script
that accepts a same-tenant relation and makes a cross-tenant SQL insert fail
through the actual foreign key. The E2E evidence counts as passed only after
the script runs against a disposable local MariaDB test database.
