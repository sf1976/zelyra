# Zelyra 1.3.6

## Ergonomic `?` error propagation across AST, MIR, Bytecode, and transactions

Zelyra now supports the postfix `?` operator on `Result<T, E>` and `Option<T>`:

```zyl
fn confirm_order(order_id: Id) -> Result<Int, String> uses Database(read, write) {
    transaction {
        order = load_order(order_id)?
        ensure_stock(order.article_id, order.quantity)?
        reserve_stock(order.article_id, order.quantity)?
        sql { UPDATE sales_orders SET status = 'confirmed' WHERE id = :order_id }
        return Ok(order.id)
    }
}
```

- Type-checked against the enclosing function's `Result` error type (or `Option`
  return type); rejected inside lambdas, contracts, or mismatched return types.
- Runs natively across **AST, MIR, and Bytecode v30** (no bytecode wire-format
  breakage; operand stack height is cleaned up automatically on early return in
  compound expressions such as `Some(a? + b?)`).
- Inside `transaction { ... }`, a `Result::Err` propagated by `?` triggers an
  immediate early return and **automatically rolls back** the database
  transaction across AST and MIR.

## Guarded table state machine transitions (`states ... when`)

Declarative `states` blocks inside `table` definitions now support business
preconditions on individual transitions as well as multiple rules per source
state:

```zyl
table sales_orders {
    id: Id primary auto
    total_amount: Decimal(12, 2) required
    status: String(24) default "draft"

    states status {
        draft -> confirmed when total_amount > decimal("0") : "Order total must be positive."
        draft -> cancelled
        confirmed -> paid
        paid -> final
        cancelled -> final
    }
}
```

- Every `when` guard expression is statically checked to return `Bool` and to be
  pure (zero capabilities / zero side effects).
- Under the `SELECT ... FOR UPDATE` row lock, state changes evaluate the guard
  against the candidate row values and reject violations with HTTP 422 and the
  declared message, rolling back the transaction.
- `zelyra verify` proves graph reachability and reports guarded transitions
  honestly as runtime-enforced edges; `zelyra reflect --format=json` exports
  `"guarded": true/false`; `zelyra doc --states` labels guarded edges in
  Mermaid `stateDiagram-v2`.

## Compiler-verified multi-table tenant-scoped `SELECT` queries

Functions may now run read-only `SELECT` queries joining multiple `tenant_scope`
tables (including `LEFT JOIN` exclusion workflows such as campaign recipients +
unsubscriptions) when the compiler can structurally prove tenant isolation:

- Every referenced `tenant_scope` table occurrence must be constrained by a
  top-level conjunctive equality predicate (`<alias>.<tenant_col> = :<param>`
  in `WHERE` or `INNER JOIN ... ON`; specifically in `LEFT JOIN ... ON` for
  outer-joined tables).
- All tenant-scoped tables in the query must bind the **same** function
  parameter with the **exact nominal `tenant_type`** (e.g. `TenantId`, never raw
  `Int`).
- Re-verified at runtime in AST and MIR, including checking that the bound
  tenant parameter is a non-null integer value.
- Any write, subquery, CTE (`WITH`), set operation (`UNION`/`INTERSECT`/
  `EXCEPT`), `RIGHT`/`FULL`/`CROSS` join, top-level `OR`/`NOT`, non-equality
  operator (`!=`, `>=`, etc.), quoted or schema-qualified table, membership
  table, or recipient-scoped table continues to fail closed (`E-TENANT-003` /
  `E-CRUD-008`).

## Internal modularization

Extracted `cli/src/canonical_templates.rs`, `cli/src/tenant_boundary.rs`, and
`web/src/state_guards.rs` from `cli/src/main.rs` and `web/src/lib.rs` with zero
behavioral changes to keep the codebase maintainable ahead of `1.4.0`.

## Release limits

- AST remains the default runtime backend. `?` runs identically across AST, MIR,
  and Bytecode v30; verified multi-table tenant-scoped `SELECT` queries are
  supported in CLI/AST/MIR, while experimental Bytecode v30 continues to fail
  closed on custom SQL touching tenant-scoped tables.
- Multi-table tenant SQL verification covers read-only `SELECT` queries with
  `INNER JOIN` and `LEFT [OUTER] JOIN`; subqueries, CTEs, set operations, and
  custom SQL writes on tenant-scoped tables remain intentionally rejected.
- Structured Factur-X XML outbox attachments remain a separate roadmap item.
- Zero new third-party dependencies and zero telemetry were added.
