# Zelyra 0.4.0 release notes

**Status:** stable release published 2026-10-10 · **Tag:** `v0.4.0` · **Maturity:**
experimental; not approved for production use. The independent human onboarding
study was explicitly deferred to the mandatory 0.5.0 gate. No study or
acceptance result is claimed for 0.4.0.

## Highlights

- Experimental project-relative imports and deterministic module linking now
  compose the supported functions, types, records, database declarations,
  tables, views, components, pages, forms, CRUD, API, and authentication
  declarations. `context`, `impact`, `module plan`, and `module bundle` expose
  documented parts of that graph. The static dependency manifest can remain
  incomplete; module bundles are not a general deployment-closure guarantee.
- MariaDB runtime access has bounded pooling, connection and statement limits,
  and configurable certificate-verified TLS. The HTTP server has a 30-second
  exchange deadline, reserved liveness route, and a 64-connection worker cap.
  CPU-bound handlers remain synchronous; automatic request retries are not
  performed.
- Database plans expose stable fingerprints, data preflights, explicit review
  requirements, migration history, and supported manual reverse plans. Backups
  remain operator-managed. A crash during active MariaDB DDL can leave an
  ambiguous partial state.
- Account features add single-use password recovery with hashed tokens and an
  encrypted durable mail outbox, session listing/revocation, request IDs, API
  metadata, and bounded per-process quotas. Mail delivery is at least once;
  quotas do not coordinate across processes.
- Linux and Windows x86_64 release artifacts include SPDX SBOMs and GitHub
  attestations. The tested database compatibility claim is MariaDB 10.11.19,
  11.4.13, 11.8.9, and 12.3.3 in the Linux CI matrix; Windows TLS handshakes
  are not separately claimed.

## Upgrade and support boundaries

Before applying schema changes, inspect `zelyra db plan --format=json`, review
the plan and preflights, and verify an independent backup. Reverse DDL needs a
fresh reviewed plan and can remove data written after the forward migration.
Do not infer full PostgreSQL/MySQL runtime parity, complete module extraction,
distributed abuse protection, production readiness, or an external security
audit from this release.

Final stable artifact, installation, update, rollback, checksum, and attestation
evidence is recorded in the
[release verification record](../release-readiness/0.4.0-candidate-verification.md).
