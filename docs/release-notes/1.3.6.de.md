# Zelyra 1.3.6

## Ergonomische `?`-Fehlerpropagierung über AST, MIR, Bytecode und Transaktionen

Zelyra unterstützt jetzt den Postfix-Operator `?` auf `Result<T, E>` und
`Option<T>`:

```zyl
fn confirm_order(order_id: Id) -> Result<Int, String> uses Database(read, write) {
    transaction {
        order = load_order(order_id)?
        ensure_stock(order.article_id, order.quantity)?
        reserve_stock(order.article_id, order.quantity)?
        sql { UPDATE sales_orders SET status = 'confirmed' WHERE id = :order_id }
        return Ok(order.id)
    }
}
```

- Statisch typgeprüft gegen den `Result`-Fehlertyp (oder `Option`-Rückgabetyp)
  der umgebenden Funktion; abgewiesen in Lambdas, Contracts oder bei
  abweichendem Rückgabetyp.
- Läuft nativ über **AST, MIR und Bytecode v30** (kein Bruch des
  Bytecode-Formats; der Operanden-Stack wird bei verschachtelten Ausdrücken wie
  `Some(a? + b?)` bei frühem Return automatisch bereinigt).
- Innerhalb von `transaction { ... }` löst ein über `?` propagiertes
  `Result::Err` einen sofortigen frühen Return aus und **rollt die
  Datenbanktransaktion in AST und MIR automatisch zurück**.

## Bewachte Zustandsübergänge in Tabellen-Zustandsmaschinen (`states ... when`)

Deklarative `states`-Blöcke innerhalb von `table`-Deklarationen unterstützen nun
fachliche Vorbedingungen auf einzelnen Übergängen sowie mehrere Zeilen je
Quellzustand:

```zyl
table sales_orders {
    id: Id primary auto
    total_amount: Decimal(12, 2) required
    status: String(24) default "draft"

    states status {
        draft -> confirmed when total_amount > decimal("0") : "Auftragssumme muss positiv sein."
        draft -> cancelled
        confirmed -> paid
        paid -> final
        cancelled -> final
    }
}
```

- Jeder `when`-Ausdruck wird statisch auf `Bool` und Reinheit (keine
  Capabilities, keine Nebenwirkungen) geprüft.
- Unter der `SELECT ... FOR UPDATE`-Zeilensperre prüfen Zustandswechsel den
  Guard gegen die Zielzeile und lehnen Verstöße mit HTTP 422 und der
  deklarierten Meldung unter Rollback ab.
- `zelyra verify` beweist die Graph-Erreichbarkeit und weist bewachte Übergänge
  ehrlich als zur Laufzeit geprüfte Kanten aus; `zelyra reflect --format=json`
  exportiert `"guarded": true/false`; `zelyra doc --states` beschriftet
  bewachte Kanten in Mermaid `stateDiagram-v2`.

## Compilergeprüfte mandantengefilterte Mehrtabellen-`SELECT`-Abfragen

Funktionen können jetzt schreibgeschützte `SELECT`-Abfragen über mehrere
`tenant_scope`-Tabellen (inkl. `LEFT JOIN`-Ausschlussabfragen wie
Kampagnenempfänger + Abmeldungen) ausführen, sobald der Compiler die
Mandantenisolation strukturell nachweisen kann:

- Jede referenzierte `tenant_scope`-Tabelle muss durch eine konjunktive
  Gleichheitsbedingung auf oberster Ebene eingeschränkt sein
  (`<alias>.<tenant_col> = :<param>` in `WHERE` oder `INNER JOIN ... ON`; bei
  `LEFT JOIN`-Tabellen zwingend in deren eigener `ON`-Klausel).
- Alle mandantengeschützten Tabellen in der Abfrage müssen an **denselben**
  Funktionsparameter mit exakt dem **nominalen `tenant_type`** gebunden sein
  (z. B. `TenantId`, niemals rohes `Int`).
- Zur Laufzeit in AST und MIR erneut geprüft, inklusive Prüfung auf einen
  nicht-null Ganzzahlwert des gebundenen Mandantenparameters.
- Schreibabfragen, Subqueries, CTEs (`WITH`), Mengenoperationen
  (`UNION`/`INTERSECT`/`EXCEPT`), `RIGHT`/`FULL`/`CROSS`-Joins, `OR`/`NOT`
  auf oberster Ebene, Nicht-Gleichheitsoperatoren (`!=`, `>=` usw.), quotierte
  oder schemaqualifizierte Tabellen sowie Membership- und Recipient-Tabellen
  scheitern weiterhin geschlossen (`E-TENANT-003` / `E-CRUD-008`).

## Interne Modularisierung

`cli/src/canonical_templates.rs`, `cli/src/tenant_boundary.rs` und
`web/src/state_guards.rs` wurden ohne Verhaltensänderung aus `cli/src/main.rs`
und `web/src/lib.rs` herausgelöst, um die Codebasis für `1.4.0` aufgeräumt zu
halten.

## Grenzen dieser Version

- AST bleibt das Standard-Backend. `?` läuft identisch in AST, MIR und
  Bytecode v30; verifizierte mandantengefilterte Mehrtabellen-`SELECT`-Abfragen
  werden in CLI/AST/MIR unterstützt, während experimentelles Bytecode v30 bei
  benutzerdefiniertem SQL auf Mandantentabellen weiterhin geschlossen abweist.
- Die Mehrtabellen-Mandantenprüfung deckt schreibgeschützte `SELECT`-Abfragen
  mit `INNER JOIN` und `LEFT [OUTER] JOIN` ab; Subqueries, CTEs,
  Mengenoperationen und Schreib-SQL auf Mandantentabellen bleiben bewusst
  gesperrt.
- Strukturierte Factur-X-XML-Anhänge in der Outbox bleiben ein eigener
  Roadmap-Punkt.
- Es wurden keine neuen Drittanbieter-Abhängigkeiten und keine Telemetrie
  hinzugefügt.
