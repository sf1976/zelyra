# Zelyra 1.5.0 — Living Business Processes (`states` v2, `four_eyes` & `workflow`)

## Erweiterte Zustandsmaschinen (`states` v2) & natives Vier-Augen-Prinzip (`four_eyes`)

Deklarative `states`-Blöcke unterstützen ab `1.5.0` Rollenanforderungen und das native Vier-Augen-Prinzip direkt an einzelnen Zustandsübergängen – vollständig kombinierbar mit `when`-Guards:

```zyl
table purchase_orders {
    id: Id primary auto
    created_by: Id required
    total_amount: Decimal(12, 2) required
    status: String(24) default "draft"

    states status {
        draft -> submitted
        submitted -> approved requires role("approver"), four_eyes(created_by) when total_amount > decimal("0") : "Amount must be positive."
        submitted -> rejected requires role("approver")
        approved -> final
        rejected -> final
    }
}
```

- **Statische Schemaprüfung:** Der Compiler prüft, dass die in `four_eyes(<spalte>)` genannte Ersteller-Spalte existiert, nicht die Zustandsspalte selbst ist und einen Identitätstyp (`Id`, `Uuid`, `Int`, `UInt` oder `String`) besitzt.
- **Fail-Closed-Laufzeitdurchsetzung unter `SELECT ... FOR UPDATE`:** Bei jedem CRUD-Zustandswechsel prüft die Web-Laufzeit die erforderlichen Rollen und vergleicht die verifizierte Sitzungs-Identität gegen die Ersteller-Spalte. Selbstfreigaben, fehlende Rollen, unauthentifizierte Zugriffe und fehlende Ersteller-Werte werden zuverlässig unter Rollback abgewiesen.

## Deklarative Workflows (`workflow`), Timer-Regeln & Sagas

Neue Top-Level-`workflow`-Blöcke binden Zeitregeln (`after`), Eintritts-Hooks (`on enter`) und Kompensations-Hooks (`compensate`) direkt an eine typisierte `states`-Spalte:

```zyl
workflow PurchaseApproval on purchase_orders.status {
    after 72h in submitted -> escalate_order
    on enter approved {
        notify_approved()
    }
    compensate on rejected {
        release_budget()
    }
}
```

- **Statische Typ- & Capability-Prüfung (`E-WORKFLOW-001`):** Ziel-Tabelle, `states`-Spalte, Zustände, erlaubte Timer-Übergänge, Handler und explizite `uses`-Capabilities der Hook-Blöcke werden vom Compiler geprüft.
- **Formale Prozess-Verifikation (`zelyra verify`):** `ContractKind::Workflow` erkennt Timer-Zyklen (z. B. `pending -> retrying -> pending`) statisch und weist sie als `FAILED` ab; zyklenfreie Workflows werden als `PROVEN` ausgewiesen und nennen die zur Laufzeit geprüften `four_eyes`- und Rollen-Übergänge transparent.

## Prozessdiagramme, Reflection & LSP

- **`zelyra doc <datei.zyl> --workflows`** (und erweitertes `--states`): erzeugt deterministische Mermaid-`stateDiagram-v2`-Diagramme inklusive `[role: ...]`, `[four-eyes: <spalte>]`, `[guarded]`, `[after <dauer>]` und Hook-Notizen.
- **`zelyra reflect --format=json`:** exportiert `required_roles` und `four_eyes_column` je Zustandsübergang sowie das sortierte Top-Level-Feld `workflows`.
- **`zelyra lsp`:** zeigt `workflow`-Symbole im Outline, ergänzt `[role: ...]`/`[four-eyes: ...]` und gebundene Workflows im Tabellen-Hover und vervollständigt `workflow`, `four_eyes`, `after` und `compensate`.

## Ehrliche Einordnung

- Geprüfte Kind-Aggregat-Prädikate in `when`-Guards (`count(items) > 0`) und die automatische Hintergrund-Ausführung von `after`-Timern / `on enter`-Hooks über den residenten Scheduler-Worker bauen auf diesem typgeprüften Modell auf und werden nicht als bereits automatisch im Hintergrund laufend beansprucht.
- AST bleibt der Standard-Ausführungspfad; MIR und Bytecode v30 bleiben opt-in.
