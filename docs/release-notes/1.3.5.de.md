# Zelyra 1.3.5

## Deklarative Tabellen-Zustandsmaschinen (`states`)

Tabellen können nun erstklassige Lebenszyklus-Zustandsmaschinen direkt innerhalb
einer `table`-Deklaration beschreiben:

```zyl
table sales_orders {
    id: Id primary auto
    status: String(20) default "draft"

    states status {
        draft -> confirmed, cancelled
        confirmed -> invoiced, cancelled
        invoiced -> paid
        paid -> final
        cancelled -> final
    }
}
```

Aus dieser einen Deklaration leitet Zelyra automatisch ab:

- **Schema- und Default-Prüfung:** weist nicht deklarierte Zielzustände,
  doppelte Regeln, Nicht-`String`-Spalten, ungültige `default`-Werte und
  Zustände jenseits der `String(N)`-Länge ab.
- **Statische SQL-Literalprüfung:** erkennt ungültige Zustandsliterale in
  `INSERT`-, `UPDATE`- und Upsert-Anweisungen bereits zur Compile-Zeit samt
  Levenshtein-Tippfehlervorschlägen.
- **Graphverifikation (`zelyra verify`):** beweist statisch die Erreichbarkeit
  ab dem Startzustand, das Fehlen nicht-finaler Sackgassen sowie die
  Erreichbarkeit mindestens eines `final`-Zustands (erkennt unerreichbare
  Zustände und gefangene Zyklen).
- **UI- und Laufzeitdurchsetzung:** Create-Formulare bieten die deklarierten
  Zustände mit vorausgewähltem Startzustand an; Edit-Formulare zeigen nur den
  aktuellen Zustand sowie zulässige Folgezustände; API- und Formularschreibpfade
  weisen ungültige Zustände oder verbotene Übergänge unter der
  `SELECT ... FOR UPDATE`-Zeilensperre mit HTTP 422 ab.
- **Werkzeuge und Dokumentation:** `zelyra reflect --format=json` exportiert
  `state_machines` pro Tabelle, `zelyra doc --openapi` erzeugt
  `enum`-Einschränkungen, und `zelyra doc <file.zyl> --states` exportiert
  Mermaid-`stateDiagram-v2`-Diagramme.

## Entscheidungstransaktionen mit Kontrollfluss (`transaction { ... }`)

`transaction { ... }` ist nicht mehr auf lineare Folgen nackter SQL-Anweisungen
beschränkt. Innerhalb eines `transaction`-Blocks unterstützt Zelyra im AST- und
MIR-Laufzeitpfad nun `let`, Neuzuweisung, `if`, `match`, `for`, `while`, `loop`,
`sql_decode`, Hilfsfunktionsaufrufe, `mail_queue` und frühes `return` auf einer
gebundenen Datenbankverbindung.

- `return Err(...)` oder ein Laufzeitfehler rollt die gesamte Transaktion
  automatisch zurück.
- Normaler Abschluss oder ein Nicht-`Err`-Rückgabewert committet die
  Transaktion.
- Einfache SQL-Batch-Transaktionen behalten ihren schnellen Einzelbatch-Pfad für
  volle Kompatibilität mit bestehenden Tests und Bytecode v30.

## Schemageprüfte SQL-Upserts, Zeilensperren, Pluralisierung und Tippfehlerhinweise

- `query_tables` und der SQL-Validator verstehen nun `ON DUPLICATE KEY UPDATE`,
  `ON CONFLICT (...) DO UPDATE SET`, `VALUES(col)`, `EXCLUDED.col` sowie
  Zeilensperrklauseln (`FOR UPDATE [NOWAIT | SKIP LOCKED]`,
  `FOR NO KEY UPDATE`), ohne SQL-Schlüsselwörter als Tabellennamen zu deuten;
  Upsert-Spalten werden gegen das Schema geprüft, und der Schutz berechneter
  Spalten bleibt bei Upserts fail-closed.
- `table_for_type` unterstützt englische Pluralformen auf `-s`/`-x`/`-z`/`-ch`/
  `-sh` (`Address` -> `addresses`, `OrderStatus` -> `order_statuses`,
  `TaxBatch` -> `tax_batches`) sowie Vokal+`y` (`ApiKey` -> `api_keys`).
- Unbekannte Tabellen, `SELECT`-Spalten und Upsert-Spalten liefern nun
  deterministische `(did you mean ...?)`-Vorschläge.

## Typisierte `form`-`execute`-Blöcke und `strict_architecture`-fähige Standard-Starter

- Eigenständige `form`-Aktionen unterstützen nun compilergeprüfte `uses`- und
  `execute { ... }`-Blöcke mit Formularfeldern, Aktionsfeldern, Routenparametern
  und `session` im Scope und laufen innerhalb einer Entscheidungstransaktion.
- Typisierte `crud`-Aktionen (`execute` / `guard`) erhalten neben `row` und
  `session` nun ebenfalls alle deklarierten Aktionsfelder (`field ...`).
- `zelyra new <ordner> --layout standard --strict` aktiviert
  `strict_architecture = true` in `zelyra.toml`. Kanonische MariaDB-Vorlagen
  lagern direkte Schreib-SQL-Aktionen nach `domain/actions.zyl` aus und rufen
  sie über typisierte `execute`-Blöcke auf, sodass alle `--layout standard`-
  Vorlagen ab Werk `strict_architecture = true` erfüllen.
- `strict_architecture = true` akzeptiert nun `tests/*.zyl`-Module sowie das
  eingebaute Modul `zelyra/ui.zyl`; MIR-, Bytecode- und Laufzeitdiagnosen
  melden importierte Modulpfade über `diagnostic_with_span` präzise.

## Grenzen dieser Version

- AST bleibt der Standard-Laufzeitpfad. MIR unterstützt
  Entscheidungstransaktionen mit Kontrollfluss; das experimentelle
  Bytecode-Backend bleibt opt-in und weist Kontrollfluss-Transaktionen
  geschlossen mit `E-MIR-UNSUPPORTED-001` ab.
- Die statische SQL-Prüfung für Zustandsmaschinen prüft literale Zustandswerte
  im SQL; dynamische SQL-Parameter werden weiterhin zur Laufzeit an Formular-,
  CRUD- und API-Grenzen sowie durch Datenbankregeln durchgesetzt.
- Aktions-`guard`-Klauseln bleiben auf CRUD-Aktionen beschränkt; eigenständige
  `form`-Aktionen lehnen `guard` weiterhin mit `E-FORM-002` ab.
- Es wurden keine neuen Drittanbieter-Abhängigkeiten und keine Telemetrie
  hinzugefügt.
