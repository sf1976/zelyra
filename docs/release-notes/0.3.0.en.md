# Zelyra 0.3.0 release notes

**Status:** published 2026-10-03 · **Tag:** [`v0.3.0`](https://github.com/sf1976/zelyra/releases/tag/v0.3.0) · **Maturity:** experimental; not approved for production use.

The final artifacts and update path were verified. By explicit project-owner
decision, the independent human onboarding study was deferred to the mandatory
0.4.0 gate. This is not usability evidence; see the
[decision record](../release-readiness/0.3.0-human-gate-decision.en.md).

## Scope

Zelyra 0.3.0 is intended to improve the first-run path, generated web
applications, MariaDB/schema safety, machine-readable compiler interfaces, and
release evidence while keeping the product experimental. It is not a promise
of production readiness, universal database compatibility, or an external AI
service.

## Release highlights

- Generated CRUD, form, tableview, loading, confirmation, and error states use
  a consistent responsive design system. Named layouts, slots, project-local
  CSS tokens, and German/English catalogs remain within their documented
  boundaries.
- The source installer handles repeat installation, missing or unusable Cargo,
  isolated checks, and safe executable-only uninstall. `zelyra doctor` reports
  actionable Docker/Compose, permission, port, configuration, and database
  problems without exposing credentials.
- MariaDB schema planning is fail-closed for destructive and unsupported
  changes. Review-required changes, nullability preflights, idempotent setup,
  and the declared MariaDB compatibility matrix are covered by isolated tests.
- Generated acceptance applications cover CRUD, relations, search, filters,
  forms, authentication, permissions, and a customer/order tableview. The
  protected machine-management acceptance path covers anonymous denial, viewer
  access, create/edit denial, authorized CRUD, search, and deletion.
- `check --format=json`, `context`, source-only `impact`, deterministic
  formatting, and explicit `edit` previews provide documented machine-facing
  interfaces. They do not call an external AI provider or send source code to
  one.
- Linux and Windows x86_64 release packaging has metadata, checksum, archive
  safety, version, and repeatability checks. The final release workflow built
  both supported targets; installation and update were then smoke-tested for
  `v0.3.0` on Linux x86_64.

## Supported and tested scope

| Area | Evidence or boundary |
|---|---|
| Release binaries | Linux x86_64 and Windows x86_64 only |
| Source installation | User-local Bash/PowerShell installation; Rust is needed when no published binary is used |
| MariaDB runtime | Primary runtime reference; CI tests exact images 10.11.19, 11.4.13, 11.8.9, and 12.3.3 |
| SQLite | Local/database and schema-regression paths are tested; not full MariaDB feature parity |
| PostgreSQL | Schema inspection/safety paths are tested; not runtime parity |
| MySQL Server | Not part of the compatibility claim |
| macOS and other targets | Source installation only until native release artifacts exist |

The [database compatibility matrix](../database-compatibility.en.md) is the
authoritative boundary. It is not a certification, performance claim, or
production backup/upgrade guarantee.

## Known limitations and explicit non-goals

This release remains experimental and is not approved for production use. There
has been no independent external security audit, penetration test, or human
onboarding study for 0.3.0. The project owner explicitly deferred the human
study to the mandatory 0.4.0 acceptance gate; this is a release-scope decision,
not usability evidence; see the [decision record](../release-readiness/0.3.0-human-gate-decision.en.md).
The following are outside the automatic 0.3.0 promise:

- full PostgreSQL, MySQL Server, or SQL-Server runtime parity;
- MFA/WebAuthn, password reset, device/session management, and OIDC/OAuth2;
- multi-tenancy, background jobs, queues, production deployment hardening, and
  operational backup/restore guarantees;
- a visual drag-and-drop/theme editor, complete view-slot data binding, or
  general formal verification;
- compiler self-hosting, mandatory external AI integration, hidden telemetry,
  or benchmark/performance guarantees;
- automatic support for platforms without a published native artifact.

For schema changes, inspect `zelyra db plan` and the affected data before
`zelyra db apply`. Review-required changes need explicit approval; unsupported
changes remain rejected even when a destructive flag is supplied. Before a
production database change, create and verify an independent backup and test
the plan on a disposable copy.

## Installation and upgrade checklist

From a checkout, use the source installer:

~~~bash
./install.sh
zelyra --version
zelyra doctor main.zyl --env-file .env --json
~~~

Install and verify the stable release using its exact tag:

~~~bash
./install.sh --release v0.3.0
zelyra --version
zelyra update --check
~~~

Before upgrading an existing application, review the release notes and the
database plan, back up the database independently, and keep the previous
binary available for rollback. The installer replaces only the user-local
Zelyra executable; it does not migrate application data automatically.
