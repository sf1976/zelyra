# 0.9.9: PostgreSQL form decisions

Date: 2026-10-13. Unreleased development package. [Deutsch](0.9.9-postgres-form-decisions.de.md)

Form mutations on PostgreSQL now execute their protective guard decisions
within the same native transaction (`with_decision_transaction`) and on the same
borrowed connection. Tenant membership, resource and recipient authorizations,
row locking (`FOR UPDATE`), optimistic snapshot comparison (including native
NULL and literal text `\N`), business mutation statements, and unchained audit
logging reside within the same atomic block. Authorization errors, stale
snapshots, or audit insert failures prevent commit and fully roll back business
data.

## Technical details

1. **Native transaction adapter:** `web/src/lib.rs::execute_form_action` uses
   `with_decision_transaction` for PostgreSQL. Tenant verification, row locking
   (`FOR UPDATE`), snapshot comparison, statement execution, and audit logging
   operate over the same `DecisionTransaction` handle.
2. **PostgreSQL identifiers & syntax:** Columns and table names in dynamic CRUD
   and form queries are double-quoted via `quote_ident(..., is_postgres)`.
3. **Audit boundary:** Unchained audit logs write atomically with the mutation.
   Chained audit tables using MariaDB-specific `@zelyra_prev_hash`/`SHA2` are
   diagnostically rejected on PostgreSQL (`PostgreSQL does not support chained audit tables`).
4. **Header aliases:** `tenant_selector` accepts `X-Tenant-Id` in addition to
   `X-Zelyra-Tenant` as well as URL parameter `?tenant_id=`.

## Open gates

Chained PostgreSQL audit remains explicitly unsupported. Full PostgreSQL auth,
MFA, password reset parity, MySQL hard write bounds, and independent human
security reviews are not certified by this package. No new dependencies,
migrations, telemetry, or external AI services.
