# Zelyra 0.3.0 risk and acceptance register

**Status:** working register for the milestone, not a release approval.
**Baseline:** published experimental `0.2.0`; the repository currently still
reports `0.2.0` and has no `v0.3.0` tag.

This register records what is known from repository inspection, automated
checks, and the documented release process. There is no independent external
security audit and no documented novice-user study yet. The absence of a
reported issue or a green test is not evidence that arbitrary applications are
defect-free.

## Severity and decision rules

- **P0 / release blocker:** must be fixed or explicitly resolved with evidence
  before a 0.3.0 tag is created.
- **P1 / release risk:** must have a visible limitation, an ownerable test path,
  and a deliberate release decision; it may not be silently implied as
  supported.
- **P2 / deferred:** useful work outside the 0.3.0 promise; it belongs on the
  roadmap unless separately accepted with capacity and tests.

## Ranked register

| Priority | Risk or gap | Current evidence | 0.3.0 decision and acceptance path |
|---|---|---|---|
| P0 | Candidate artifacts, exact tag metadata, and published candidate install/update path are not yet proven for `0.3.0`. | Metadata, package, Linux smoke, and published `v0.2.0` smoke checks exist; the repository remains at `0.2.0`. | Block publication until the release workflow builds Linux/Windows artifacts, verifies checksums and versions, the candidate tag matches the workspace, and the published-candidate smoke test passes. |
| P0 | A release claim could exceed the tested security boundary. | Internal security review and protected CRUD/auth E2E exist; no external audit or penetration test exists. | Keep the release experimental; publish the residual risks below and do not claim production approval. |
| P1 | MariaDB support could be read as universal SQL/database support. | The exact four-version MariaDB matrix is green; SQLite regression and PostgreSQL schema-safety paths are separate. | Claim only the documented MariaDB matrix and limited SQLite/PostgreSQL scope; use `docs/database-compatibility.en.md` as the boundary. |
| P1 | TLS, proxy trust, process-local login throttling, and process-scoped CSRF state remain deployment risks. | `docs/security-review-0.2.0.md` documents the controls and residual risks; origin/host and cookie tests are green. | Require a trusted TLS proxy and explicit host configuration in deployment guidance; do not market the built-in server as production-hardened. |
| P1 | A new user may still encounter Docker or environment-specific onboarding friction. | Installer, doctor, clean-onboarding, generated-project, and Docker E2E paths are green. | Keep the documented troubleshooting path; an external novice study remains open and is not claimed as complete. |
| P1 | Native release coverage is limited to Linux/Windows x86_64. | Release workflow and published smoke test cover those targets; source installation covers other environments. | State unsupported native targets explicitly and retain the source-install fallback. |
| P2 | MFA/OIDC, multi-tenancy, jobs, full runtime parity, drag-and-drop editing, formal verification, and performance benchmarks are not delivered. | Roadmap and draft release notes list these as planned or out of scope. | Keep them deferred; none is a 0.3.0 blocker without a separate scope decision and acceptance test. |

## Acceptance map

Each included claim must point to evidence of the same scope:

- compiler and repository quality: `cargo fmt --check`, workspace check,
  Clippy, workspace tests, and the full CI run;
- database and generated applications: the MariaDB matrix, schema-safety suites,
  generated-project E2E, customer/order acceptance, and protected machine
  authorization E2E;
- release packaging: `scripts/check_release_metadata.py`,
  `scripts/test_package_release.py`, `scripts/verify_release_artifacts.py`,
  and the release workflow;
- installation and updates: `tests/installer-e2e.sh` and
  `tests/published-release-smoke.sh <published-tag>`;
- public claims and limitations: both draft release-note files, the database
  compatibility document, and the internal security review.

The final release checklist must replace baseline evidence with candidate-tag
evidence where the claim concerns published `0.3.0` assets. A source checkout
or a local package is not a substitute for that published-artifact test.

## Scope classification

**Included 0.3.0 goals:** safer first run, tested generated business and
machine-management paths, documented MariaDB/schema boundaries, stable local
machine interfaces, responsive generated views, and reproducible release
checks.

**Release blockers:** unresolved P0 items above, failing required CI/database/
security-boundary tests, mismatched version/tag metadata, unsafe or unchecked
artifacts, or a published candidate that fails installation/update smoke.

**Deferred roadmap:** all P2 items and any feature without a separate acceptance
condition. No date or public performance target is implied by this register.
