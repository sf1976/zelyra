# Zelyra 0.5.0 risk and evidence register

**Status:** active technical register; not release approval.
**Baseline:** published stable `v0.4.0`, commit
[`507c29e95084a59029d6b436bd69d9132c3a8937`](https://github.com/sf1976/zelyra/commit/507c29e95084a59029d6b436bd69d9132c3a8937).
**Candidate:** none. Human acceptance has not been performed and remains a
mandatory final gate.

This register maps the current 0.5.0 goal to repeatable evidence and limits.
Passing a test for one fixture does not prove arbitrary projects safe to
extract or deploy. Update this file when implementation or evidence changes;
keep it aligned with the [0.5.0 roadmap](../release-plans/0.5.0.en.md) and its
German counterpart.

## Ranked risks

| Priority | Risk or promise | Current evidence and limits | Gate before stable 0.5.0 |
|---|---|---|---|
| P0 | The known module graph may omit a dependency or runtime effect. | `module plan` is deterministic and reports recognized declarations, function capabilities, service contracts, and unresolved references. The module-import suite has 48 tests. `source_closure_complete`, `complete_deployment`, and `deployment_readiness.ready` remain false; implicit resource effects, assets, and dynamic dependencies are not fully modeled. | Prove closure completeness for the selected scope or remove the unsupported promise from scope. Keep negative fixtures for unknown effects and references. |
| P0 | An exported module may not build or run independently. | `tests/generated-project-docker-e2e.sh` passed on 2026-10-10 with the current 0.5.0 working tree. The fresh MariaDB app passed repeated setup; customer/order CRUD and reporting; anonymous denial; admin login and full workflow; viewer denial for create and reporting; invoice and inventory as separate Docker apps with writable CRUD and negative database-permission checks. Runtime and image compilers were pinned to published 0.4.0 commit `507c29e95084a59029d6b436bd69d9132c3a8937`. Both bundles still report incomplete static closure, so evidence is limited to these fixtures. | Repeat against the exact 0.5.0 candidate on a clean target. Cover both units, secrets, permissions, and startup without the original project. Do not generalize beyond these fixtures. |
| P0 | Database changes may be left in an ambiguous state by interruption or concurrent writes. | On 2026-10-10 at preparation source `3f3ed43`, the top-level `bash tests/schema-safety-e2e.sh` passed against SQLite and a fresh disposable MariaDB 11 container, including interrupted migrations, metadata-lock waits, reverse DDL, and backup/restore. Its `tests/mariadb-crash-recovery-e2e.sh` step stopped MariaDB after DDL commit but before journal progress, restarted it, detected the interrupted entry, applied a fresh plan, and verified the final schema. The generated Docker business workflow also held a concurrent transaction on the customer row while posting an older form; the post returned 409 and did not overwrite the committed concurrent value. These are bounded recovery and form-path tests, not production guarantees or application-wide concurrency proof. | Keep concurrent-write claims scoped to the tested row-locked form path and record operator decisions. Do not infer production recovery guarantees from bounded fixtures. |
| P0 | The frozen reference project and acceptance environment may not cover a complete business workflow. | `examples/customer_orders_modules/` is a checked multi-file slice with customer/order modules, explicit customer relation, reporting read grants, shared UI, dedicated database module, and explicit auth/permission contracts. The fresh Docker rehearsal passed on 2026-10-10: anonymous access returned 401; an admin completed customer CRUD, order creation, invalid-relation rejection (422), and reporting; a viewer with only `customers.view` could list customers but could neither create customers nor view reporting (403). A stale form returns 409 both after a prior update and when submitted during a concurrent transaction; the newer concurrent database value remains intact. Invoice and inventory exports ran as separate Docker apps with negative database-permission checks. Separate MariaDB schema-recovery, DDL/journal crash, and backup/restore rehearsals pass. Interrupted business-row recovery and a fully combined business-plus-recovery workflow remain untested. | Join backup/restore or migration recovery to the same business workflow; keep concurrency claims scoped to the tested form path. |
| P0 | Inferred module table ownership may be mistaken for database enforcement. | The compiler reports ownership and enforces recognized source-level access grants. `schema_ownership.enforced` remains false; MariaDB grants in the bounded Docker test are configured separately. | Keep compiler grants and actual database permissions distinct in docs and tests. Require least-privilege grants for each extracted app and test cross-module denial. |
| P1 | Password-reset email may be duplicated or stranded. | Contract version 1 declares required configuration, 30-second retry delay, at-least-once delivery, and possible duplicates. The encrypted outbox key is required and must remain stable across instances; losing it makes pending mail unreadable. SMTP credentials are not copied into bundles. | Preserve retry, restart, duplicate, enumeration, and key-handling tests. Human acceptance must confirm setup instructions are usable. |
| P1 | The release may be mistaken for an external security audit or production certification. | The internal security review and automated checks do not constitute an external audit or penetration test. Zelyra remains experimental; deployment and schema ownership limits are explicit. | Carry those limits into release notes and the public handbook. Make no unsupported audit or production-readiness claim. |
| P1 | Platform or artifact claims may exceed tested outputs. | Stable 0.4.0 Linux/Windows artifacts, checksums, SBOMs, attestations, install/update/rollback evidence are recorded in the [0.4.0 verification](0.4.0-candidate-verification.md). No 0.5.0 candidate artifacts exist. | Run candidate build, artifact, SBOM, provenance, install/update/rollback, and published-artifact smoke checks against one immutable 0.5.0 prerelease commit. |
| P1 | Independent onboarding may reveal blockers missed by automation. | The 0.4.0 study was deferred; it is not evidence of acceptance. The protocol and empty record are in [the study guide](0.5.0-onboarding-study.en.md) and [acceptance record](0.5.0-human-acceptance.en.md). | A non-developer must complete the study against the exact published 0.5.0 prerelease. Record the commit, date, redacted observations, blockers, and owner decision before the stable tag. |
| P2 | PostgreSQL/SQLite runtime parity, distributed limits, MFA/OIDC, background jobs, arbitrary module closure, and external audit could be inferred from adjacent features. | These are not established by the current 0.5.0 evidence. | Keep deferred unless a separate scope, implementation, risk review, and acceptance decision adds them. |

## Release rule

Do not publish stable `v0.5.0` while a P0 row lacks same-scope evidence or an
explicit scope decision. Publish a prerelease only after technical candidate
gates pass; keep it immutable during the human study. The human gate is never
waived by this register or by the 0.4.0 deferral.
