This is evidence for an unreleased technical work package on
`release/0.9.9-pre-release`, based on `8db093c`. It does not close the complete
0.9.9 release plan or establish production acceptance.

## Implemented behavior

- Password-reset quotas use an explicitly declared MariaDB table and persist
  across restarts and concurrent instances. HMAC fingerprints replace raw
  peer addresses. A transaction and advisory lock coordinate the 4,096-entry
  cap, request windows, and blocks; cleanup removes at most 100 old inactive
  entries per request. Database failures reject the operation and produce
  sanitized operator diagnostic `E-AUTH-043`.
- Schema validation requires compatible storage and its cleanup index.
  `E-AUTH-039`–`E-AUTH-042` identify configuration failures at the auth source.
  `context`, dependency analysis, table grants, bundle export, and table
  renaming include reset storage. Previously missing tenant-membership and
  MFA-storage dependency edges are now included too.
- A real SMTP E2E failure exposed generated index names exceeding MariaDB's
  identifier limit. Regression tests failed before the fix. Generated index,
  unique-index, and foreign-key names now use bounded deterministic names;
  creation, inspection comparison, and reviewed removal plans agree. Short
  names retain their spelling. Oversized declared table/storage-column names
  fail statically with `E-DB-001` and source positions.

## Compatibility and limits

Experimental password-reset projects must add `reset_rate_limits` and its
table, review their additive migration, and provide the required imports and
table grants. Ordinary login declarations retain their behavior. The new
optional `context` fields preserve schema version `1`.

Reset recovery remains limited to the documented MariaDB workflow. Instances
must share a writable database, quota settings, and delivery key. Proxy clients
share the TCP peer bucket; cleanup requires subsequent requests. Delivery is
still at least once. Independent security review remains open. Old PostgreSQL
objects whose long names were server-truncated may require reviewed adoption;
unrecognized objects are preserved or refused rather than silently dropped.
Final CI, platform coverage, and immutable-candidate release gates remain open.
