# 0.9.9: native calendar and UTC SQL boundaries

Unreleased work package on `fix/0.9.9-temporal-sql`, based on `c92ff2c`.
This closes native parameter/storage support for the listed temporal types.
Typed SQL result consumption remains a separate technical release gate.

## Reproduction and corrections

Regression tests ran before fixes. DATE/TIME parameters were incorrectly
classified as Timestamp. The old Timestamp mapping lacked milliseconds and
MariaDB/MySQL used TIMESTAMP with its narrower date range. Metadata checks
initially missed Time precision; PostgreSQL DATE metadata legitimately reports
precision 0 and must not be mistaken for fractional time precision.

The added `Timestamp default now` probe failed on real MySQL with
`ERROR 1067 ... Invalid default value for 'created'`. MariaDB showed schema
changes immediately after fresh creation. Both now use/recognize matching
CURRENT_TIMESTAMP(3) defaults, avoiding rejected creation and false drift.

- Native Date/Time/Timestamp bindings on MariaDB/MySQL and PostgreSQL; Gregorian
  bounds, whole-second clocks, exact milliseconds, NULLs and backend limits.
- Native PostgreSQL binary DATE/TIME/TIMESTAMPTZ reads; incompatible precision,
  non-finite values and timestamp without timezone fail with controlled errors.
- Timestamp storage: DATETIME(3) on MariaDB/MySQL, TIMESTAMPTZ(3) on PostgreSQL;
  whole-second PostgreSQL TIME(0). Schema inspection preserves time precision.
- Native connections start in UTC; PostgreSQL startup options are preserved
  with UTC appended. Date/Time/UTC millisecond storage checks are read-only.
- Forms, page parameters, SQL parameters and temporal list filters retain types.
  Missing/wrong storage blocks serve with E-DB-TEMPORAL at the declared column;
  the interpreter also checks before its first SQL operation. Auth/reset schema
  checks follow the new Timestamp declaration. No automatic migration approval.

## Compatibility and open work

Calendar years remain 0001–9999 in the language/PostgreSQL; MariaDB/MySQL native
Date/Timestamp storage supports the portable 1000–9999 range. DATETIME has no
timezone marker: external writers must honor UTC. Existing TIMESTAMP columns
need a backup and explicit reviewed migration, including the former connection
timezone. Existing URL precedence/secrets policies and migration approvals stay
in force. This adds no dependency, telemetry, service, or environment switch.

Raw SQL row text is retained; MariaDB/MySQL midnight values may be date-only,
while PostgreSQL timestamp text is canonical UTC with Z. Rows are not decoded
into typed variables for downstream calendar operations, and NULL versus
literal text needs separate closure. Full backend CRUD/auth/tenant parity,
local timezones/DST/leap seconds and general production approval are not
established by this package. 0.9.9 remains unfinished; IDE work follows technical
release blockers. See [rules](../dates.en.md) and [the release plan](../release-plans/0.9.9.en.md).

## CI follow-up: guarded password-reset delivery race

The first PR #68 run failed in the SMTP fixture at its assumption that both
concurrent replacement requests always produce emails. The guarded outbox
intentionally skips a token superseded before sending; successful HTTP requests
therefore do not imply three total captured emails. The fixture now captures
the first request before racing replacements, requires the current replacement
to finish, verifies its hash against the retained database token, and derives
the later cross-instance capture index from that observed baseline. Existing
stale-token, expiry, concurrent redemption, retry and session-revocation checks
remain. SQL/mailer/security implementation is unchanged.

Both the original fixture replay and the corrected SMTP/reset rehearsal passed
locally on isolated MariaDB 11.8.9 with the immutable artifact SHA above. The
failure was timing-dependent and was not reproduced locally. A fresh GitHub
run is required before integration. The original failure is recorded in
[the CI run](https://github.com/sf1976/zelyra/actions/runs/38324482653).

The fresh [CI run on `504a4a5`](https://github.com/sf1976/zelyra/actions/runs/38326463308)
passed the reset fixture, then exposed the generated-business readiness test's
old assumption that an unavailable database can still start a liveness endpoint.
Read-only temporal validation now deliberately requires metadata access before
listen. The fixture checks a controlled exit 1 with source-located
`E-DB-TEMPORAL` and no credential/address leak. The positive readiness, protected
CRUD/API/permissions, action errors, edit conflicts and session checks still run.
The complete generated-business rehearsal and isolated unavailable-startup
negative probe passed on MariaDB 11.8.9 using the same immutable artifact. No
runtime guard was bypassed; subsequent CI is required before integration.
