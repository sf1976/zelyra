# Zelyra 0.7.0 tenant context threat model

**Status:** reviewed as a narrowly scoped experimental 0.7 feature; not approved
for production. Independent security review remains a technical gate before
1.0.0.
**Scope:** a first, bounded tenant-aware database path, not a claim of complete
multi-tenancy.

This review is required before tenant identity, tenant-scoped queries, or tenant
authorization are added. The current web runtime authenticates sessions and
checks account permissions, then dispatches generated routes and handlers. The
project currently has one project-wide `DATABASE_URL`; the PostgreSQL runtime
slice in 0.6.0 does not provide tenant isolation. A route permission does not
by itself constrain rows returned or changed by SQL.

## Security objective

For a tenant-scoped operation, a principal may observe or change only records
belonging to a tenant for which the server has established membership and the
principal has the required permission. Missing, ambiguous, stale, or invalid
tenant context must deny access before returning tenant data or committing a
write. The tenant identifier is trusted only when derived and checked by the
server from authenticated identity and persisted membership.

## Assets and trust boundaries

| Asset | Boundary and consequence |
| --- | --- |
| Tenant-owned rows, related rows, and aggregates | A missing predicate or cross-tenant relation can disclose or corrupt another tenant's data. |
| Session identity and permissions | Request cookies and bearer tokens are untrusted until authenticated; account permission is not proof of tenant membership. |
| Tenant membership and selected tenant | Membership is server-side authorization state. A client-supplied tenant ID, header, route segment, or form value is only a selector and never an authorization grant. |
| SQL parameters and generated operations | Parameterization prevents injection but does not establish row ownership. Reads, writes, deletes, restore, joins, counts, and exports all need an isolation rule. |
| Caches, rendered pages, errors, and audit records | Tenant data can leak without a database read even when SQL is scoped. |
| Schema migrations and operator configuration | A partial backfill, nullable tenant key, or unconstrained relation can create a mixed-isolation deployment. |

The client, URL, request body, cookies before authentication, custom handler,
browser cache, and external identity provider are untrusted. The authenticated
session resolves a principal; the server's membership store and policy resolve
tenant access. Database enforcement is a separate boundary and must not be
inferred from compiler metadata.

## Threats and required controls

| Threat | Required control before release |
| --- | --- |
| Insecure direct object reference: substitute another tenant's ID in a path, form, API body, or relation | Bind tenant identity from authenticated server state. Scope the database operation itself and return the same not-found/denied behavior for cross-tenant identifiers. |
| Forged tenant selector in header, cookie, query, form, or route | Treat selectors as untrusted input; validate against active persisted membership on the server. Never let selector text populate an authorization context directly. |
| Missing or inconsistent tenant predicate in one operation | Centralize scoped execution for the bounded feature. Require tenant predicates on every read and mutation; fail closed if a query cannot be proven in scope. |
| Cross-tenant foreign-key or join relationship | Enforce same-tenant relations with composite keys/constraints or equivalent database checks. Validate relation targets within the same tenant in the same transaction. |
| Permission confused with membership | Require both ordinary permission and active tenant membership. Test each independently, including valid permission with no membership. |
| Membership changed between check and write | Resolve membership and perform the tenant-scoped mutation in one transaction or with an equivalent atomic policy check. |
| Custom SQL, raw handlers, views, reports, counts, or exports bypass the scoped path | Keep these paths unavailable for tenant data unless they use the same reviewed scoped executor. No transparent rewriting of arbitrary SQL is assumed. |
| Connection pool or request context leaks tenant identity across requests | Use explicit request-scoped values passed to query functions; do not use mutable process-global or thread-local tenant state. Reset any connection-local setting on every checkout/return if one is introduced. |
| Cache, error, log, or audit disclosure | Key tenant-specific cache entries by verified tenant and principal; avoid sensitive row values in errors/logs; bind audit tenant and actor to server-derived context. |
| Unsafe single-tenant to tenant-aware migration | Specify additive migration, deterministic backfill into an explicit default tenant, constraints, rollback limits, and interruption recovery before enabling tenant mode. Do not infer ownership from existing row IDs. |
| Denial of service through tenant selection or membership fan-out | Bound membership lookup and query work; reject malformed selectors and cap result sizes using existing runtime limits. |

## Design decisions for the first implementation

- The principal is the `user_id` from a validated, database-backed session.
  The existing static bearer-token mode has no user identity; tenant-scoped
  routes reject it rather than assigning a shared tenant principal.
- Membership is stored as `(user_id, tenant_id, active)` rows. An optional
  `X-Zelyra-Tenant` header or `tenant_id` URL query value is only an untrusted
  selector. If both are present they must agree; duplicate query selectors are
  rejected. Resolve the selection against the authenticated user's active
  membership on every request. If it is absent, select the tenant only when
  exactly one active membership exists; deny zero or multiple matches. Do not
  cache membership or tenant context. Generated CRUD links, form actions, and
  redirects preserve the URL selector; they do not provide a tenant switcher.
- Construct a request-local verified context only after membership succeeds.
  Pass it explicitly through generated CRUD dispatch. Never store tenant state
  in a global, thread-local, or pooled-connection variable.
- The first integrated slice uses the MariaDB reference runtime and one
  explicitly tenant-scoped generated CRUD table. List/detail reads and generated
  create/edit/delete/restore operations bind the verified tenant in their
  predicates. Mutations lock the active membership and scoped record in one
  transaction. Inserts supply the verified key; the key is hidden from forms
  and generated output. Membership-scoped responses use `private, no-store`.
- Tenant-owned relations, custom actions, raw SQL, TableViews, custom API
  handlers, and exports are rejected or remain unavailable for tenant-owned
  data in this slice. The compiler rejects forms and custom SQL in form
  actions, CRUD actions, page data, TableViews, and functions when they
  reference a tenant-owned or membership table outside its generated tenant
  CRUD route (`E-TENANT-003`). It also rejects unsupported SQL forms in
  tenant-enabled projects when table access cannot be checked. This avoids
  implying same-tenant relation safety before composite constraints and
  relation validation exist.
- Tenant mode is opt-in. Existing single-tenant projects do not change. A
  migration that turns it on for existing rows must stop unless an operator
  supplies an explicit ownership backfill and membership mapping; never assign
  a default tenant silently.

## Scope allowed for the first implementation

The initial increment supports one explicitly declared tenant-owned table and
its generated CRUD route family on MariaDB. It remains experimental until
database integration tests prove isolation across two tenants, including all
read and mutation paths, forged selectors, missing and revoked membership, and
permission checks. The feature remains opt-in and existing single-tenant
behavior is unchanged. This increment does not imply that all Zelyra SQL,
modules, generated CRUD, custom APIs, caches, or database backends are
tenant-safe.

## Maintainer security review and verification evidence

The maintainer review on 2026-10-10 at `b5b46ec` examined request dispatch,
authentication and membership resolution, selectors, generated read/write
queries, SQL access boundaries, error output, and reachable CRUD routes. It
found no release-blocking issue within the explicitly limited scope. A complete
independent security review was not performed; it remains required before
production approval and is scheduled for the 0.9.9/1.0.0 exit process.

- The database-backed session supplies the principal; account permission and
  active membership are checked separately. Missing, ambiguous, conflicting,
  or invalid selectors deny the request.
- Generated lists and details filter by tenant and membership. Create binds the
  tenant server-side; edit checks snapshot, membership, and record in a
  transaction. Delete and restore lock membership and the target record in the
  same transaction.
- Unsupported relationships and custom SQL access paths are rejected by the
  compiler. Tenant state is not stored globally or in pooled connections.
  Responses use `private, no-store`.
- E2E verifies row isolation, forged selectors, permissions, membership
  revocation, query errors, and a failing audit insert after update with an
  unchanged record and generic HTTP 500 response.

This review makes no claim about arbitrary SQL, relations, TableViews, exports,
other database backends, or full multi-tenancy.

The local MariaDB 11.4.13 E2E exercises two tenants, missing and forged tenant
selection, a user without the required CRUD permission, a permissioned user
without membership, list/detail isolation, create/edit/delete/restore, guessed
cross-tenant IDs and mutations, untrusted submitted tenant keys, selector
propagation through generated navigation, membership-query failure, and a
concurrent revocation during delete. A trigger also forces the audit insert to
fail after the row update; the test checks for HTTP 500 without database
details and verifies the row remains unchanged after rollback. A compiler regression test also proves
that an unscoped custom TableView of a tenant-owned table is rejected. The full
workspace tests, Clippy, handbook snippets, and release metadata checks pass
on the same working tree. Exact release commit
`3edad2121df488fa674ff76b053d73243469d1f3` passes branch CI
[#38086175488](https://github.com/sf1976/zelyra/actions/runs/38086175488) and
Linux/Windows package validation
[#38086175563](https://github.com/sf1976/zelyra/actions/runs/38086175563).
No tenant migration or backfill exists in 0.7; the runtime requires the
pre-existing tenant column and does not assign ownership to existing records.
The independent security review remains open.

## Evidence required before production approval

Before production approval, independent review must examine isolation tests,
missing and revoked memberships, missing permissions, query failures, session
and cache lifetimes, logs, and all reachable route families. Tenant relations
remain outside the 0.7.0 scope and must continue to be rejected by the compiler.
Run the database integration suite again against the 0.9.9 candidate.

This internal review is not independent human acceptance or an external
security audit. The first slice does not enable tenant behavior by default and
does not provide tenant-aware migrations or backfill. Production approval
remains deferred until the independent 0.9.9/1.0.0 exit gates pass.
