# Zelyra 0.9.0 local MFA threat model (draft)

Status: implementation review draft. This document is not an independent
security assessment and does not establish production readiness. MFA ships in
0.9 only as an explicitly configured preview.

## Assets

- TOTP seed and its encryption key.
- Password-only pending sessions and authenticated sessions.
- Recovery-code verifiers and their single-use state.
- MFA enrollment, disable, and recovery-code replacement actions.

## Threats and current controls

| Threat | Current control in the 0.9.0 branch | Evidence still required |
| --- | --- | --- |
| Database reader obtains TOTP seed | AES-256-GCM encryption with an operator-managed 32-byte key; authenticated associated data and random nonce | Independent review of key handling, nonce use, backup/restore and memory lifetime |
| Password theft alone grants access | Persistent sessions start with `mfa_verified = false`; guarded routes require it to be true | `tests/mariadb-mfa-e2e.sh` covers the login challenge and TOTP promotion; API/CRUD/session route coverage remains open |
| OTP replay or concurrent reuse | Factor row lock and stored accepted TOTP counter in the same MariaDB transaction as session promotion | Sequential and simultaneous reuse are exercised by `tests/mariadb-mfa-e2e.sh`; the supported MariaDB version matrix and independent review remain open |
| Recovery code replay | Argon2id verifier, locked unused row, and `used_at` update in the same transaction as session promotion | Sequential and simultaneous reuse are exercised by `tests/mariadb-mfa-e2e.sh`; migration/backup review remains open |
| Online guessing | Five failed MFA attempts set a 15-minute lock on the factor row | `tests/mariadb-mfa-e2e.sh` verifies the fifth-failure threshold, active rejection, stored 15-minute expiry, and valid recovery after an expired lock; cross-process behavior remains open |
| Cross-site settings changes | CSRF token plus same-origin validation; password and current TOTP required for disable/rotation | Browser-level CSRF and origin tests |
| Secret leakage in HTML caches or logs | Secret pages use `Cache-Control: no-store`; diagnostics omit codes and seeds | Proxy/browser cache review and log inspection |
| Key loss or operator lockout | No in-app key rotation or recovery flow exists; a database recovery runbook is documented | The integration test rehearses removal of factor and sessions and verifies the audit trail remains; independent review of key restoration remains open |

## Assumptions and limits

The application host and its environment are trusted. A compromised application
process can read the encryption key and plaintext seed during verification.
The current implementation supports MariaDB-backed sessions only. The MFA
screen copy is covered in both bundled languages by the unit suite and German
integration assertions. TOTP
authenticator interoperability, clock skew, operational key rotation, and
recovery after a lost authenticator require review before production release.
The current
default accepts the current 30-second TOTP step plus one step on either side.

## Release blockers

The protected page and API paths, sequential and concurrent TOTP and recovery
code reuse, fifth-failure lockout and expiry, and bilingual operator recovery
procedure now have integration coverage. The MariaDB version matrix is a 0.9.0
release gate. Schema migration and backup review, cross-process lockout
behavior, independent security review, and key restoration review are 1.0.0
production release gates. Human product acceptance remains reserved for 1.0.0.
