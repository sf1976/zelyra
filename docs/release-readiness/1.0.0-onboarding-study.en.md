# Zelyra 1.0.0 independent onboarding and acceptance study

**Status:** mandatory release gate; protocol not yet frozen and no study has
been conducted. Human studies deferred from 0.3.0, 0.4.0, and 0.5.0 belong to
this first major release.

Finalize this protocol after the 1.0.0 feature scope, supported platforms,
installation path, and shipped documentation are frozen. The tasks must cover
the actual promises of 1.0.0; do not reuse the 0.5.0 draft unchanged if the
product or handbook has changed. Run the study against an immutable, published
1.0.0 release candidate after all technical gates pass. A branch build, local
build, owner rehearsal, or automated test does not count as human acceptance.

## Participant and recording rules

- Recruit independent participants who did not develop Zelyra or write its
  handbook. Set and record the participant count before testing begins.
- Participation is voluntary. Do not retain participant names, credentials,
  private source code, screen recordings, or unnecessary personal information.
- Record the operating system, exact RC tag and commit, exact downloaded asset
  and checksum, task outcomes, interventions, redacted observations, blockers,
  and the project owner's explicit decision.
- Use disposable systems and databases. Do not expose participants to
  production credentials or data.
- The observer may intervene to prevent data loss, secret disclosure, or access
  to a non-disposable system. Record each intervention; it prevents an
  unassisted pass for the affected task.

## Study tasks

Before the protocol is frozen, derive realistic tasks from the final 1.0.0
scope. Include installation and first-run setup, the documented primary
development workflow, representative database/application tasks, recovery
from a documented failure, and the limits that operators must understand.
Participants receive only the public documentation shipped with the candidate
and the task sheet. The observer must not coach or supply commands.

Define pass criteria for each task before recruiting participants. Record
successes, failures, time only when useful, requests for help, incorrect
assumptions, and all safety interventions. A blocker must be fixed and the
technical release gates rerun; publish a corrected immutable candidate and
repeat affected tasks before stable `v1.0.0`.

The study evaluates the tested tasks and participants only. It does not prove
general usability, security, production readiness, or correctness of arbitrary
programs.
