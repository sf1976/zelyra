# Zelyra 0.3.0 onboarding study protocol

**Status:** protocol only; no human study has been claimed yet.

This protocol supplies the missing evidence for the 0.3.0 release-plan item
that requires a documented onboarding test with a person who does not develop
Zelyra. The currently selected test candidate is the published
[`v0.3.0-rc.2` release](https://github.com/sf1976/zelyra/releases/tag/v0.3.0-rc.2).
Until a different candidate is selected, use that exact release and record the
tag in the result. `v0.2.0` may be used only for a rehearsal and must be
labeled as such.

## Test setup

- Use a fresh Linux x86_64 user account or disposable VM with no Rust or Cargo
  installed. Record the distribution and version.
- Provide only the current [English getting-started guide](../getting-started.md)
  and the selected published release URL. Do not provide a private walkthrough.
- The participant must not be a Zelyra developer. The observer may answer only
  safety questions and must record every hint that was needed.
- Do not collect passwords, tokens, private source code, or other personal data.

## Participant task

Ask the participant to complete this task without prior Zelyra knowledge:

1. Install the selected release and make `zelyra --version` work in a new
   shell.
2. Create a minimal project with `zelyra new` in a temporary directory.
3. Run `zelyra check` and the smallest documented example successfully.
4. Run `zelyra doctor` and explain what the result means.
5. Find the documented next step for a MariaDB-backed project, but do not
   enter a real secret or modify a production database.

## Observation record

Record the release/tag, date, OS, elapsed time, each command that was run, the
first point of confusion, every observer hint, and every error message that
was not actionable from the guide. Redact personal data and secrets.

The test passes only if the participant reaches the first successful checked
project without hidden repository knowledge and can identify the safe next
step for MariaDB. A failed or partial test is still valuable evidence and must
remain visible with the associated blocker and proposed documentation fix.

## Result template

```text
Release/tag:
Date:
OS and version:
Participant role (no name):
Time to first successful `zelyra check`:
Commands needing explanation:
Unexpected blockers:
Guide changes proposed:
Pass / partial / fail:
Observer:
```

Attach the completed, redacted record to the release evidence before closing
the corresponding checkbox. This protocol is not itself evidence of a human
onboarding result.
