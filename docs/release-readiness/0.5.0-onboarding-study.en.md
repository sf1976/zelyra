# Zelyra 0.5.0 human onboarding acceptance protocol

**Status:** prepared, not conducted. This document is a test protocol, not a
result or release approval. Human acceptance was explicitly deferred for
0.4.0; the [deferral decision](0.4.0-human-acceptance.en.md) is not acceptance evidence and does not replace this mandatory 0.5.0 test.

## Goal and scope

A person who does not develop Zelyra and has not set up a Zelyra project should
follow the published documentation to understand a small multi-file
application. The test covers installation, the first project check, a clear
separation into business modules, shared database configuration, independent
export and startup of two application units, and writable CRUD in each unit.

The test evaluates the actual documentation and exact candidate. It does not
prove general usability, production readiness, security, or correctness of
arbitrary programs.

## Mandatory prerequisites

- Select a published 0.5.0 release candidate and record its tag, commit SHA,
  release URL, and SHA-256 of the downloaded artifact before testing. Do not
  test against a moving branch or an unverified local build.
- Build the task sheet only from the handbook and quick-start pages shipped
  with that exact candidate. Verify every command, syntax example, and
  limitation against its CLI first. Do not add CLI syntax guessed from this
  protocol.
- Use a fresh disposable VM or user account with a supported operating
  system. Record OS and version. Require Rust/Cargo only if the published
  installation path explicitly requires them.
- For database and Docker tasks, use only a disposable local MariaDB instance
  with no real data. Prepare credentials and ports safely in advance; the
  participant must not use production credentials.
- Recruit a participant who neither develops Zelyra nor helped write its
  handbook. Participation is voluntary. Do not retain their name,
  credentials, private source code, screen recording, or unnecessary personal
  information.

## Procedure

Give the participant only the candidate's public documentation, its download,
and the following business task. The observer must not explain Zelyra terms or
provide commands. The observer may intervene only to prevent data loss,
disclosure of a secret, or access to a non-disposable system; record every
intervention.

### Participant task

> Set up Zelyra and follow the handbook until you have a successfully checked
> application. Create two separate areas in it: invoicing and inventory. Both
> should use the documented shared database configuration. Then inspect which
> files and dependencies belong to each area. Export both areas separately,
> start them against the provided local test database, and exercise writable
> CRUD in each isolated application. Finally, explain which configuration can
> be set independently for each exported application and which limitations
> the documentation states.

Use the same task sheet for every participant. The observer records the
participant's own choices without steering them toward a prescribed
architecture or command.

### Observation and assistance

For each task, record start/end time, commands actually run, documentation
used, first uncertainty, errors, self-correction, and each required hint.
Statements such as “it is right here” or pointing to a particular menu item
count as assistance. Record safety interventions separately and do not allow
the risky action to proceed.

Do not record secrets or full environment variables. Before sharing the
report, remove names, personally identifying paths, hostnames, tokens,
passwords, and application data.

## Evaluation

Mark each task **independent**, **with hint**, **not completed**, or **stopped
for safety**. The study passes only if the participant, without technical
hints:

1. correctly installs the published compiler and verifies its version;
2. checks an application using the handbook and explains the role of the
   separate module files;
3. finds the shared database configuration and locates credentials in the
   intended runtime configuration;
4. understands a correct, bounded dependency preview for both modules;
5. builds and starts both required exports separately, verifies writable CRUD,
   and confirms the other module's files, routes, and data are absent;
6. accurately explains the limitations stated in the handbook.

A required feature absent from the release or failing during the task cannot
be marked as passed with observer assistance. Record every failure and do not
generalize a pass beyond the tasks and environment actually tested.

Store the redacted result as evidence for the exact candidate. Close the human
release gate only after all critical blockers are fixed and retested. The
existence of this protocol alone explicitly does not close that gate.
