# Zelyra 0.9.9: Security and Threat Review (Findings & Status)

**Status:** Preliminary review and technical baseline for version 0.9.9 (2026-10-13).
**CRITICAL NOTICE:** This document consolidates automated security regression tests and internal
developer auditing. It **DOES NOT** replace a required independent third-party security audit.
Such independent security audit has **not** been simulated or claimed as completed, and remains
a mandatory release gate before the final 1.0.0 release candidate.

## 1. Security Features and Protected Assets in 0.9.9

- **Local MFA (RFC 6238 TOTP):**
  - 160-bit secret encrypted with AES-256-GCM (`ZELYRA_MFA_ENCRYPTION_KEY`, 256-bit key).
  - 10 single-use recovery codes hashed server-side with Argon2id.
  - Session gating: Prior to factor verification, sessions have `mfa_verified = false`; guarded
    routes and APIs return HTTP 401.
  - Replay prevention: Used TOTP time steps and consumed recovery codes are invalidated atomically in the database.
  - Race condition mitigation: Concurrent requests presenting identical codes are serialized;
    exactly one succeeds, while parallel requests fail with 401.
  - Brute-force protection: 5 failed factor attempts lock the factor for 15 minutes (HTTP 429).
  - Disaster recovery: Manual removal of factor and sessions by the database operator preserves
    the immutable audit log (`auth_audit_log`).
- **Password Reset Quotas:**
  - Persistent rate limiting (`password_reset_limits`) survives application restarts.
  - Capacity shared across concurrent server instances.
  - Batch cleanup of expired records (up to 100 per request).
  - Zero credential exposure: Database stores only keyed cryptographic fingerprints.
- **CSRF Protection & Session Integrity:**
  - Strict CSRF token validation on all mutating HTTP routes (POST/PUT/DELETE).
  - Same-origin validation and secure cookie attributes (`SameSite=Lax`, `HttpOnly`, `Secure` under TLS/Proxy).
  - Session tokens stored as SHA-256 hashes in `auth_sessions`; plaintext tokens never leave the client.
- **Tenant and Recipient Isolation:**
  - Tenant-scoped queries and mutations enforce server-side active membership checks.
  - Recipient-scoped notifications (`recipient: user_id`) strictly hide entries from other users in
    the same tenant (returning 404 upon unauthorized access attempts).

## 2. Findings, Owners, and Decisions

| ID | Area | Finding / Risk | Owner | Decision in 0.9.9 | Status |
|---|---|---|---|---|---|
| SEC-001 | Auth / MFA | PostgreSQL does not currently support session auth or MFA backend (MariaDB-specific tables/codecs) | Core Team / DB | PostgreSQL auth remains disabled and explicitly documented for 0.9.9; targeted for modular adapters post-1.0 | Documented / Bounded |
| SEC-002 | Audit | Chained audit (`SET @`, `SHA2`) is not portable to PostgreSQL | Security / Web | PostgreSQL chained audit is rejected with clear diagnostic; unchained audit is permitted | Resolved / Rejected |
| SEC-003 | Mail | Outbox requires MariaDB or MySQL; PostgreSQL has no outbox worker driver | Core Team / Mail | `mail_queue` on PostgreSQL fails with an explicit error; documented honestly in support matrix | Documented / Bounded |
| SEC-004 | MFA Key | In-app key rotation missing for `ZELYRA_MFA_ENCRYPTION_KEY` | Ops / Security | Key rotation requires an operator re-encryption script; documented in operations handbook | Open Blocker for 1.0 |
| SEC-005 | Auditing | Independent security audit for 1.0.0 is still pending | Project Lead | All technical regressions pass cleanly for 0.9.9; external audit remains mandatory gate before 1.0.0 | Planned Release Gate for 1.0.0 |

## 3. Open Blockers for Version 1.0.0

1. **Independent Third-Party Security Review:** Comprehensive external evaluation of cryptography,
   randomness sources, session lifecycles, SQL generation, and tenant isolation.
2. **Operational Key Rotation Tooling:** Safe CLI command to re-encrypt stored MFA secrets during key change.
3. **Extended Platform Security Matrix:** Full backup and restore verification under concurrency.
