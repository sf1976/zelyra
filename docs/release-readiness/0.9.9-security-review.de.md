# Zelyra 0.9.9: Sicherheits- und Bedrohungsreview (Befunde & Status)

**Status:** Vorabprüfung und technischer Stand zur Version 0.9.9 (13.10.2026).
**WICHTIGER HINWEIS:** Dieses Dokument fasst automatisierte Sicherheitsprüfungen und interne
Entwickler-Audits zusammen. Es ersetzt **KEINE** geforderte unabhängige externe Sicherheitsprüfung.
Eine solche unabhängige Sicherheitsbewertung wurde **nicht** als durchgeführt erfunden und bleibt
ein obligatorisches Tor vor der finalen Freigabe von Version 1.0.0.

## 1. Schutzgüter und Sicherheitsfunktionen in 0.9.9

- **Lokale MFA (RFC 6238 TOTP):**
  - 160-Bit-Secret, verschlüsselt mit AES-256-GCM (`ZELYRA_MFA_ENCRYPTION_KEY`, 256-Bit-Schlüssel).
  - 10 Einmal-Wiederherstellungscodes, serverseitig mit Argon2id gehasht.
  - Sitzungssperre: Vor MFA-Bestätigung besitzen Sitzungen `mfa_verified = false`; geschützte
    Routen und APIs verweigern Zugriff mit HTTP 401.
  - Replay-Schutz: Verwendete TOTP-Zeitschritte und verbrauchte Recovery-Codes werden in
    derselben Transaktion ungültig gemacht.
  - Race-Condition-Härtung: Parallele Anfragen mit demselben Code werden atomar serialisiert;
    genau eine Anfrage gewinnt, die parallele wird mit 401 abgewiesen.
  - Brute-Force-Schutz: 5 Fehlversuche sperren den Faktor für 15 Minuten (HTTP 429).
  - Notfall-Runbook: Manuelles Entfernen von Faktor und Sitzungen durch den Datenbankadministrator
    erhält den lückenlosen Audit-Trail (`auth_audit_log`).
- **Passwort-Reset-Quoten:**
  - Persistente Ratenbegrenzung (`password_reset_limits`) überlebt Serverneustarts.
  - Geteilte Kapazität über parallele Instanzen.
  - Batch-Bereinigung abgelaufener Einträge (höchstens 100 pro Anfrage).
  - Keine Geheimnis-Offenlegung: In der Datenbank werden nur kryptografisch geschlüsselte Fingerabdrücke gespeichert.
- **CSRF-Schutz & Session-Sicherheit:**
  - Strenger CSRF-Token-Schutz auf allen mutierenden HTTP-Routen (POST/PUT/DELETE).
  - Same-Origin-Validierung und strikte Cookie-Attribute (`SameSite=Lax`, `HttpOnly`, `Secure` bei TLS/Proxy).
  - Session-Tokens werden als SHA-256-Hash in `auth_sessions` persistiert; Klartexttokens verlassen nie den Client.
- **Mandanten- und Empfänger-Isolation:**
  - Mandantengebundene Abfragen und Mutationen erzwingen serverseitige Mitgliedschaftsprüfungen.
  - Empfängergebundene Benachrichtigungen (`recipient: user_id`) schließen andere Benutzer desselben
    Mandanten strikt aus (404 bei Zugriffsversuchen).

## 2. Befunde, Verantwortliche und Entscheidungen

| ID | Bereich | Befund / Risiko | Verantwortlich | Entscheidung in 0.9.9 | Status |
|---|---|---|---|---|---|
| SEC-001 | Auth / MFA | PostgreSQL unterstützt derzeit kein Session-Auth- oder MFA-Backend (Codecs/Tabellen MariaDB-spezifisch) | Core Team / DB | PostgreSQL-Auth bleibt für 0.9.9 gesperrt und klar dokumentiert; Freigabe erst mit modularem Adapter post-1.0 | Dokumentiert / Begrenzt |
| SEC-002 | Audit | Chained Audit (`SET @`, `SHA2`) auf PostgreSQL nicht portabel | Security / Web | PostgreSQL-Chained-Audit wird mit klarer Fehlermeldung verweigert; nur unchained Audit ist zugelassen | Gelöst / Abgewiesen |
| SEC-003 | Mail | Outbox erfordert MariaDB oder MySQL; PostgreSQL hat keinen Outbox-Treiber | Core Team / Mail | `mail_queue` auf PostgreSQL bricht mit Fehlermeldung ab; ehrlich in Release-Plänen und Supportmatrix ausgewiesen | Dokumentiert / Begrenzt |
| SEC-004 | MFA-Schlüssel | Keine In-App-Schlüsselrotation für `ZELYRA_MFA_ENCRYPTION_KEY` | Ops / Security | Schlüsselrotation erfordert Re-Encryption-Skript; dokumentiert im Betreiberhandbuch | Offener Blocker für 1.0 |
| SEC-005 | Auditing | Unabhängige Sicherheitsreview für 1.0.0 steht noch aus | Projektleitung | Für 0.9.9 werden alle technischen Regressionen grün gehalten; externes Audit bleibt zwingendes Gate vor 1.0.0 | Geplantes Release-Gate für 1.0.0 |

## 3. Offene Blocker für Version 1.0.0

1. **Unabhängiges externes Sicherheitsreview:** Vollständige Überprüfung von Kryptografie,
   Zufallsquellen, Session-Lifecycle, SQL-Generierung und Mandantenisolation durch externe Prüfer.
2. **Operatives Schlüsselrotations-Tooling:** Bereitstellung eines sicheren CLI-Befehls zur
   Re-Verschlüsselung gespeicherter MFA-Geheimnisse bei Schlüsselwechsel.
3. **Erweiterte Plattform-Sicherheitsmatrix:** Echte Backup- und Restoreproben unter Last.
