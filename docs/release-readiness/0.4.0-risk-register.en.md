# Zelyra 0.4.0 risk and acceptance register

**Status:** working register, not release approval.
**Baseline:** final stable `v0.3.0` was published on 2026-10-03. The exact
commit, Linux/Windows x86_64 artifacts, checksums, workflow, limitations, and
Linux published-artifact smoke result are recorded in the [final release
verification](0.3.0-final-release-verification-2026-10-03.md). The deferred
human onboarding study was not performed; its explicit 0.3.0 risk decision is
not user-acceptance evidence.

This register gives the 0.4.0 plan a reviewable risk boundary. It records
risks before implementation and must be updated when evidence changes. No
green test, local rehearsal, or absence of a reported issue proves general
production readiness.

## 0.3.0 residual-risk carry-forward

| 0.3.0 residual risk | 0.4.0 disposition | Required evidence before final 0.4.0 |
|---|---|---|
| No independent human onboarding study was conducted. | The project owner explicitly defers this study to 0.5.0 for the 0.4.0 release decision. The waiver is not acceptance evidence. | Both-language owner decision records must be present for 0.4.0; a non-developer participant must complete the study against the exact published 0.5.0 candidate before `v0.5.0`. |
| Zelyra remains experimental; no independent external security audit or penetration test is claimed. | Carried forward; 0.4.0 claims stay bounded to reviewed and tested behavior. | Update the threat review and residual-risk decision; do not imply an external audit unless one is actually commissioned and completed. |
| Database and deployment support has explicit limits, including the tested MariaDB matrix and operational TLS/proxy responsibilities. | Carried forward; no universal SQL or production-hardening claim. | Preserve the compatibility matrix and add same-scope lifecycle, timeout, recovery, and deployment evidence for any expanded claim. |
| Native release artifacts are verified for Linux and Windows x86_64; other environments rely on source installation. | Carried forward until new targets pass native build and published-artifact smoke checks. | Verify each newly claimed target from its published artifact; retain the source-install limitation elsewhere. |
| MFA/OIDC, full database runtime parity, multi-tenancy, jobs, formal verification, visual editing, and performance guarantees were not included in 0.3.0. | Deferred by default; no feature is silently promoted into 0.4.0. | A separate scope, risk, implementation, and acceptance decision is required for any item added to scope. |

The source for this classification is the [0.3.0 risk register](0.3.0-risk-register.en.md),
the [human-gate decision](0.3.0-human-gate-decision.en.md), and the final
published-release verification linked above.

## Decision rules

- **P0 / release blocker:** must be fixed, explicitly reduced in scope, or
  supported by same-scope evidence before a final `v0.4.0` tag.
- **P1 / release risk:** needs a visible limitation, an ownerable test path,
  and a deliberate release decision; it must not be implied as supported.
- **P2 / deferred:** outside the 0.4.0 promise unless a separate scope and
  acceptance decision adds it.

## Initial ranked register

| Priority | Risk or gap | Evidence required | 0.4.0 decision and acceptance path |
|---|---|---|---|
| P0 | Multi-file projects could introduce nondeterministic builds, path escapes, cycles, or weakened visibility/effect checks. | Specification, valid and invalid fixtures, repeated build equality, project-root enforcement, and module-boundary capability tests. | The tested first slice remains experimental. Do not claim complete module extraction or deployment closure: unsupported references, partial diagnostic attribution, one project-wide database connection, and unenforced MariaDB schema ownership remain documented limits. |
| P0 | Pooling, retries, cancellation, or migrations could leave unknown transaction state or partial schema changes. | MariaDB matrix tests for timeout, interruption, retry, drift, supported reverse plans, populated tables, and repeated planning. | Keep operations bounded and fail-closed; MariaDB journals per-step progress and E2E proves recovery after interruption between steps and while DDL waits for a metadata lock. Supported reverse diffs are bound to fingerprints and require a fresh reviewed plan, explicit operator approval, and an independent verified backup. A crash during actual MariaDB DDL execution remains ambiguous; do not claim automatic or data-safe rollback. |
| P0 | A slow HTTP connection or synchronous handler could block other requests or exhaust server resources. | Socket tests for concurrent slow/fast requests and the fixed worker cap; verify request deadlines and overload behavior. | The listener handles up to 64 connections and drops excess; tests cover concurrency and the cap. A reserved, database-free liveness route confirms request dispatch; the HTTP operations guide defines application-owned readiness, the 30-second exchange deadline, and safe retry boundaries. The generated `mariadb-business` project has a bounded read-only readiness query, and its E2E covers reachable and unreachable MariaDB. Other application dependencies remain application-owned; there are no built-in dependency-readiness endpoints or automatic retries. MariaDB pool waits and statements now use the remaining exchange deadline, and timed-out statements are aborted server-side. CPU-bound and other blocking handler work remains synchronous and uncancellable. |
| P0 | Password recovery and session controls could leak account existence, tokens, or authorization state. | Expiry/replay/enumeration/CSRF tests, concurrent token-use rejection, secret-redacted logs, audit events, encrypted outbox recovery/backoff, session revocation, and generated-app acceptance. | The documented experimental MariaDB lifecycle is covered by unit, HTTP, and MariaDB/SMTP E2E tests, including two competing workers, retry timing, enumeration, expiry, replay, and restart recovery. Delivery is at least once; acknowledgement races can duplicate mail, and key loss strands pending messages. Keep the old key until the outbox is empty before rotation. Throttles are intentionally process-local, not distributed. The internal threat review records these boundaries; no external audit is claimed. Human onboarding is deferred to the mandatory 0.5.0 gate. |
| P1 | API versioning, correlation, and rate limits could break existing clients or be trusted beyond their persistence boundary. | Compatibility fixtures, structured diagnostics, correlation propagation, quota tests, and documented proxy/storage limits. | Request IDs, version/deprecation metadata, and bounded per-process quotas per TCP peer IP have compatibility and negative tests. Proxy headers are ignored. Restart and multiple instances do not share quota state; persistent or distributed limits are outside the release claim. |
| P1 | Granular effects and AI-native edits could silently expand authority or report guessed references. | Static/runtime grant tests, deterministic `impact`/`edit` output, stale-source rejection, and no-network checks. | Function-level SQL supports opt-in `Database(read)`/`Database(write)` grants with static and runtime enforcement, including typed API handlers. Broad database access remains necessary for framework-managed routes; `Email`, `Jobs`, schema-change effects, complete impact/edit coverage, and independent authoring evidence remain open. |
| P1 | Malformed source, SQL, templates, or HTTP input could trigger parser panics or unstable diagnostics. | Bounded deterministic mutation regressions plus repeatable coverage-guided runs across lexer/parser, SQL binder, template renderer, and HTTP request parser; retain crash inputs and add focused regressions. | CI runs 2,048 reproducible inputs per surface. Coverage-guided fuzzing found and fixed a parser stack overflow; the parser now rejects recursive input beyond 32 parser frames, and the failing corpus input is retained. Four 60-second local runs and the 15-second CI fuzz job passed on fixed commit `19e8778` in [run 37971762729](https://github.com/sf1976/zelyra/actions/runs/37971762729). Broader security review remains open. |
| P1 | Native release artifacts could be reproducible but not auditable or complete. | SBOM, dependency/license report, provenance, checksum, archive-safety, update/rollback, and supported-target checks. | CI runs pinned `cargo-deny` on Linux and Windows dependency graphs; SPDX-2.3 SBOMs are generated and hash-verified, and tagged builds are configured to attest archives and SBOMs. Candidate-specific published artifact, attestation, install/upgrade/rollback verification remains open. `NOASSERTION` licenses and duplicate-version warnings still need human review. |
| P1 | New operational workflows may remain difficult for users even when technical E2E tests pass. | A redacted human acceptance study using the exact published 0.5.0 candidate and a documented troubleshooting record. | The 0.4.0 study is explicitly deferred by the project owner and is not user-acceptance evidence. Complete the study and decision record as a mandatory 0.5.0 release gate. |
| P2 | Full PostgreSQL runtime parity, multi-tenancy, background jobs, MFA/OIDC, visual editing, and general formal verification remain large independent efforts. | Separate scope decisions and acceptance plans if later promoted. | Keep deferred; none becomes a 0.4.0 promise by implication. |

## Required evidence locations

- implementation and negative tests in the relevant workspace crates and
  `tests/` scripts;
- bilingual language/API/operations documentation and migration guidance;
- `docs/release-readiness/0.4.0-risk-register.en.md` and
  `docs/release-readiness/0.4.0-risikoregister.de.md` updates;
- bilingual owner decision records documenting the explicit 0.4.0 human-study deferral;
- a redacted human acceptance record for the exact 0.5.0 candidate before its final release;
- candidate artifact evidence, SBOM/provenance, checksums, and published
  upgrade/rollback smoke results.

## Release decision

The final gate must fail closed when a P0 item lacks same-scope evidence, a
published artifact differs from the verified candidate, a compatibility claim
exceeds its matrix, or the bilingual owner-approved human-study deferral record is missing. The register is
not permission to publish and does not replace the release plan.
