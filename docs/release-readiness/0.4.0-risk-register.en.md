# Zelyra 0.4.0 risk and acceptance register

**Status:** working register, not release approval.
**Baseline:** final stable `v0.3.0` was published on 2026-10-03. The exact
commit, Linux/Windows x86_64 artifacts, checksums, workflow, limitations, and
Linux published-artifact smoke result are recorded in the [final release
verification](0.3.0-final-release-verification-2026-10-03.md). The deferred
human onboarding study was not performed; its explicit 0.3.0 risk decision is
not user-acceptance evidence.

This register gives the 0.4.0 plan a reviewable risk boundary. It records
risks before implementation and must be updated when evidence changes. No
green test, local rehearsal, or absence of a reported issue proves general
production readiness.

## 0.3.0 residual-risk carry-forward

| 0.3.0 residual risk | 0.4.0 disposition | Required evidence before final 0.4.0 |
|---|---|---|
| No independent human onboarding study was conducted. | Carried forward as a mandatory release gate, not waived. | A new participant who does not develop Zelyra completes the [0.4.0 study protocol](0.4.0-onboarding-study.en.md) against the published candidate; record blockers and outcomes without secrets or unnecessary personal data. |
| Zelyra remains experimental; no independent external security audit or penetration test is claimed. | Carried forward; 0.4.0 claims stay bounded to reviewed and tested behavior. | Update the threat review and residual-risk decision; do not imply an external audit unless one is actually commissioned and completed. |
| Database and deployment support has explicit limits, including the tested MariaDB matrix and operational TLS/proxy responsibilities. | Carried forward; no universal SQL or production-hardening claim. | Preserve the compatibility matrix and add same-scope lifecycle, timeout, recovery, and deployment evidence for any expanded claim. |
| Native release artifacts are verified for Linux and Windows x86_64; other environments rely on source installation. | Carried forward until new targets pass native build and published-artifact smoke checks. | Verify each newly claimed target from its published artifact; retain the source-install limitation elsewhere. |
| MFA/OIDC, full database runtime parity, multi-tenancy, jobs, formal verification, visual editing, and performance guarantees were not included in 0.3.0. | Deferred by default; no feature is silently promoted into 0.4.0. | A separate scope, risk, implementation, and acceptance decision is required for any item added to scope. |

The source for this classification is the [0.3.0 risk register](0.3.0-risk-register.en.md),
the [human-gate decision](0.3.0-human-gate-decision.en.md), and the final
published-release verification linked above.

## Decision rules

- **P0 / release blocker:** must be fixed, explicitly reduced in scope, or
  supported by same-scope evidence before a final `v0.4.0` tag.
- **P1 / release risk:** needs a visible limitation, an ownerable test path,
  and a deliberate release decision; it must not be implied as supported.
- **P2 / deferred:** outside the 0.4.0 promise unless a separate scope and
  acceptance decision adds it.

## Initial ranked register

| Priority | Risk or gap | Evidence required | 0.4.0 decision and acceptance path |
|---|---|---|---|
| P0 | Multi-file projects could introduce nondeterministic builds, path escapes, cycles, or weakened visibility/effect checks. | Specification, valid and invalid fixtures, repeated build equality, project-root enforcement, and module-boundary capability tests. | Do not claim modules are stable until all graph, path, diagnostic, and effect-boundary tests pass. |
| P0 | Pooling, retries, cancellation, or migrations could leave unknown transaction state or partial schema changes. | MariaDB matrix tests for timeout, interruption, retry, drift, rollback, populated tables, and repeated planning. | Keep operations bounded and fail-closed; MariaDB journals per-step progress and E2E proves recovery after interruption between steps and while DDL waits for a metadata lock. A crash during actual DDL execution remains ambiguous; require operator approval and independent backup responsibility. |
| P0 | A slow HTTP connection or synchronous handler could block other requests or exhaust server resources. | Socket tests for concurrent slow/fast requests and the fixed worker cap; verify request deadlines and overload behavior. | The listener handles up to 64 connections and drops excess; tests cover concurrency and the cap. A reserved, database-free liveness route confirms request dispatch; the HTTP operations guide defines application-owned readiness, the 30-second exchange deadline, and safe retry boundaries. The generated `mariadb-business` project has a bounded read-only readiness query, and its E2E covers reachable and unreachable MariaDB. Other application dependencies remain application-owned; there are no built-in dependency-readiness endpoints or automatic retries. Synchronous handlers remain uncancellable. |
| P0 | Password recovery and session controls could leak account existence, tokens, or authorization state. | Expiry/replay/enumeration/CSRF tests, concurrent token-use rejection, secret-redacted logs, audit events, session revocation, and generated-app acceptance. | Experimental MariaDB recovery stores only token hashes, uses generic responses, audit and CSRF, applies process-local throttling, and revokes sessions; a two-instance loopback SMTP-sink E2E delays the first relay while another instance issues a replacement and confirms that the later email matches the stored token. A worker skips delivery when its token is no longer current. The same E2E covers concurrent redemption, where exactly one succeeds, and rejects a token whose expiry is set to `NOW()`. Another E2E forces SMTP connection refusal and verifies indistinguishable known/unknown-account responses and generic secret-free logs. Frozen-clock expiry equality, durable delivery recovery, persistent throttling, broader security review, and independent acceptance remain open. No final release claim until the full account lifecycle is reviewed and accepted. |
| P1 | API versioning, correlation, and rate limits could break existing clients or be trusted beyond their persistence boundary. | Compatibility fixtures, structured diagnostics, correlation propagation, quota tests, and documented proxy/storage limits. | Request IDs, version/deprecation metadata, and bounded process-local quotas per TCP peer IP are implemented. Proxy headers are ignored; restart/multi-instance behavior, reset limits, and full negative acceptance remain open. |
| P1 | Granular effects and AI-native edits could silently expand authority or report guessed references. | Static/runtime grant tests, deterministic `impact`/`edit` output, stale-source rejection, and no-network checks. | Effects are opt-in; unverified edges are omitted rather than presented as facts. |
| P1 | Malformed source, SQL, templates, or HTTP input could trigger parser panics or unstable diagnostics. | Bounded deterministic mutation regressions across lexer/parser, SQL binder, template renderer, and HTTP request parser; later add coverage-guided fuzzing and minimized crash cases. | CI now runs 2,048 reproducible inputs per surface with bounded size and mutation count, checks deterministic results, and fails on panics. Coverage-guided fuzzing and crash-corpus retention remain open. |
| P1 | Native release artifacts could be reproducible but not auditable or complete. | SBOM, dependency/license report, provenance, checksum, archive-safety, update/rollback, and supported-target checks. | The workflow generates and hash-verifies SPDX-2.3 SBOMs for Linux/Windows and is configured to attest tagged release archives with their SBOMs. A published-candidate attestation rehearsal, dependency/license audit, and complete artifact review remain open; `NOASSERTION` licenses are visible. |
| P1 | New operational workflows may remain difficult for users even when technical E2E tests pass. | A redacted human acceptance study using the published candidate and a documented troubleshooting record. | A technical rehearsal cannot close the human gate. |
| P2 | Full PostgreSQL runtime parity, multi-tenancy, background jobs, MFA/OIDC, visual editing, and general formal verification remain large independent efforts. | Separate scope decisions and acceptance plans if later promoted. | Keep deferred; none becomes a 0.4.0 promise by implication. |

## Required evidence locations

- implementation and negative tests in the relevant workspace crates and
  `tests/` scripts;
- bilingual language/API/operations documentation and migration guidance;
- `docs/release-readiness/0.4.0-risk-register.en.md` and
  `docs/release-readiness/0.4.0-risikoregister.de.md` updates;
- a redacted human acceptance record for the published 0.4.0 candidate;
- candidate artifact evidence, SBOM/provenance, checksums, and published
  upgrade/rollback smoke results.

## Release decision

The final gate must fail closed when a P0 item lacks same-scope evidence, a
published artifact differs from the verified candidate, a compatibility claim
exceeds its matrix, or the human acceptance record is missing. The register is
not permission to publish and does not replace the release plan.
