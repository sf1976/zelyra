# Zelyra 0.9.9: Mail and Notification System

**Status:** Implemented and verified (2026-10-13). Experimental 0.9.9 milestone.
No commitments for file attachments, named templates, or a generalized queue platform.
Independent security review and human product acceptance remain reserved for 1.0.0.

## 1. SMTP Contract and Transactional Outbox

- **Transactional Enqueueing:** `mail_queue(to, subject, text, html?)` is strictly allowed
  only inside a `transaction { ... }` block and is enqueued into the internal `zelyra_outbox`
  table within the same MariaDB/MySQL transaction as the business modification.
- **Safety and Type Checks:**
  - Arguments must be pure Strings without side effects.
  - Header injection protection: Newline characters (`\r`, `\n`) in recipient and subject are strictly rejected.
  - Payload size limits for outbox items are enforced prior to insertion.
  - The project network policy `[network].allowed_hosts` must explicitly permit the configured SMTP host.
- **TLS and Transport Behavior:**
  - Modes: `implicit_tls` (port 465, default), `starttls` (port 587), and `local_plaintext`
    (port 25, restricted to loopback `localhost`, `127.0.0.1`, `::1` without authentication).
  - Certificate validation: Configured private root CAs (`ZELYRA_SMTP_CA_CERT`) are respected.
    Untrusted CAs trigger immediate delivery abort and schedule retries; plaintext downgrade is impossible.
  - Timeouts: Bounded greeting and transport timeouts fail gracefully and schedule retries without crashing.
- **Delivery Semantics:**
  - At-least-once: The outbox worker (`zelyra outbox run`) retries on failure.
  - Duplicate window: Acknowledgment occurs after relay acceptance. The persistent outbox event ID
    is assigned as the RFC 5322 `Message-ID` (`<event_id>@zelyra.local`).
  - Real emails are structured as MIME `multipart/alternative` with plain text and optional HTML sections.

## 2. Tenant- and Recipient-Scoped Notification Center

- **Declaration in Zelyra:**
  ```zelyra
  crud Notification -> notifications {
      tenant: tenant_id
      recipient: user_id
      unread: read_at
      expires: expires_at
      requires auth
      soft_delete { column: archived_at }
  }
  ```
- **In-App Feed and Unread Count:**
  - Feed displays strictly active (non-expired, non-archived) notifications for the authenticated user
    in the active tenant.
  - `unread: read_at` dynamically calculates unread count (`read_at IS NULL`).
- **Recipient and Tenant Isolation:**
  - Lists, detail views, and counts filter strictly by `user_id = :authenticated_user_id` and
    `tenant_id = :active_tenant_id`.
  - IDOR attempts to access foreign notifications or foreign tenants return HTTP 404 (Not Found).
- **CSRF-Protected Read Receipts:**
  - POST `/notifications/{id}/read?tenant_id=...` validates the session CSRF token.
  - Atomically marks `read_at = CURRENT_TIMESTAMP` in a single transaction.
  - Records an audit log event (`notification.read`) in `auth_audit_log` when configured.
  - Foreign, expired, or archived notifications return 404. Invalid CSRF returns 403.
  - Upon success, unread count decrements and the action button disappears.
- **Compiler Safety Enforcement:**
  - `recipient` column cannot be exposed as CRUD field, list, search, or filter column.
  - Unscoped SQL queries and custom forms targeting recipient tables are rejected.
  - Tables may only relate through their recipient key.

## 3. Honest Boundaries

- **No File Attachments or Templates:** File attachments and named templates are explicitly
  unsupported and not claimed.
- **Backend Matrix:** The notification center and transactional outbox are verified on MariaDB/MySQL;
  PostgreSQL outbox support remains separate work post-1.0.
